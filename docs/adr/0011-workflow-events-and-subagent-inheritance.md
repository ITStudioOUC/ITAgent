# 0011. 工作流事件溯源与子 agent 双继承

## 状态

已采纳，2026-10-23。

## 决策

工作流是 JSON 配置，节点是子 agent。节点的完成状态由事件推导，不靠信号维持。

**节点结束写入一条完成记录（事务内），状态由记录推导。** 信号只作为低延迟优化存在，
丢了不影响正确性。这样崩溃恢复与重放是免费的，而不是另建一套机制。

**节点的写集与资源声明是配置的一部分**，包括文件、目录树、锁文件、端口、数据库，并支持
声明严格模式（见 0009）。工作流在载入与拉取第三方工作流时做静态检查：写集重叠、目录与
文件粗细不匹配、读写悬挂、环依赖、未声明的独占资源。

**工作流是"操作 agent 的程序"，必须与工具同权限级别对待。** 因此不给它任意表达式求值
能力，条件与参数传递限定在声明式文法和内置函数内。

**子 agent 有两种上下文继承方式，由主 agent 选择。**

- 简报模式：只注入压缩后的任务目标与简要上下文。便宜、抗污染，适合明确的小任务。
- 继承模式：直接继承主 agent 上下文，并在结尾追加主 agent 给出的简要指令。适合分头
  探索——因为前缀字节一致时供应商的前缀缓存会命中，实际成本比直觉低得多。

**子 agent 从父节点分叉，不追加到父的 head。** 子 agent 的结果只以摘要形式由父显式
追加合回，不做自动合并。派生深度与总预算有上限。

**工作流节点可声明独占资源**，这就是 w1mer 的"编译独占"落到设计里的位置。

## 理由

事件溯源而不是信号驱动，是因为信号在网络与进程边界上会丢、会重、会乱序，而"节点完成了
没有"是编排的核心状态。用记录推导状态，把可靠性建立在数据库事务上，这是已经有的事务
保证；信号只用来让界面更快地更新。这也让"重放一个工作流"变成读取事件序列，而不是
模拟一堆消息。

不给工作流表达式求值能力，是因为工作流来自第三方，它本质上是可执行程序。若允许任意
表达式，就等于在 server 里开了一个解释器沙箱，那需要另一套隔离机制与另一份攻击面。

两种继承方式都保留，是因为它们服务不同场景，而且成本差异在缓存命中后没有直觉上那么大。
简报模式省的是上下文长度，继承模式省的是"重新解释背景"的来回。分头探索时后者更快。

分叉不合并，是因为上下文合并需要语义级三方合并，那是另一个项目。显式追加把"合并"变成
一个有明确作者的动作，语义清晰且可审计。

## 后果

好的方面：崩溃可恢复；工作流可重放；冲突在启动前被发现；子 agent 成本可控。

代价：

- **事件表增长快**，因为节点状态变更也是事件。归档判据与 0002 一致。
- **静态检查只能覆盖声明过的写集**，模型临时写入仍需运行时兜底（见 0009）。
- **不做自动合并意味着父 agent 要花一轮整理子结果**，这是有意的成本。
- **继承模式会让子 agent 继承父的偏见**，分头探索时可能因此集体走错方向。简报模式是
  对冲手段，主 agent 需要自行选择。

需要重新审视的信号：如果父 agent 频繁需要"把两个子 agent 的结果融合"，说明缺少一个
显式的整合节点类型，届时应加一类内置节点而不是做自动合并。

## 被否决的替代方案

**节点完成靠信号驱动状态机。** 实现直观，延迟低。不选的理由是信号在进程边界上不可靠，
必须有重发与去重，而有了重发与去重之后，本质又回到了"记录推导状态"，只是多了一层缓存。

**允许工作流里写任意表达式（JS 或 Rhai 之类）。** 表达力强，第三方工作流可以做到很复杂。
不选的理由是它引入一个解释器沙箱，而工作流的信任级别与工具相同，等于把攻击面翻倍。

**子 agent 结果自动合并回父上下文。** 用起来最顺。不选的理由是需要语义级三方合并，
且合并冲突无法自动裁决；显式追加虽然多一轮，但没有不可预测的行为。

**只支持简报模式。** 最简单，成本最低。不选的理由是分头探索时子 agent 缺少隐性约束，
会走回头路（重新发现父已经排除的方案），而继承模式加前缀缓存的成本并没有想象中高。

**子 agent 追加到父 head（共享可变上下文）。** 省掉合并步骤。不选的理由是并发写同一
分支会让 head 的语义失效，且分支丢失是静默的。
