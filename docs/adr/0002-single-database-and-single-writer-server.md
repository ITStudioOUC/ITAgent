# 0002. 单数据库与 server 单写者

## 状态

已采纳，2026-10-23。

## 决策

全系统一个 SQLite 数据库文件，只由 server 进程打开。worker、执行器、工具都不持有
数据库连接，所有读写经 server 的 IPC 完成。

**workspace 是会话属性，不是请求参数。** server 从连接身份（同机取 peer 凭据）和握手
时的会话信息推导工作区，请求信封里不出现 workspace 字段。这条由接口形状保证：业务处理
函数的入参类型里根本没有这个字段。

**消息分两类。** 权威写（追加事件、比较并交换 head、获取与释放租约）的 ack 必须代表
已持久化，失败时阻塞重试，最终作为工具调用的失败上报。遥测（计时、界面进度）可以丢，
不参与正确性。队列在这里负责排序与批量，不负责提前答应；**队列可以异步，ack 不能异步**。

**server 内部是单写线程 + 有界队列 + 批量提交。** 读路径不做批量等待，写路径串行。
禁止长事务跨越 IO：不得出现"开事务 → 调模型 → 写回"或"开事务 → 执行工具 → 提交"。

**数据分成两类不同性质的东西。** 不可变的事件日志（append-only，按序号读取，可缓存、
可复制、可续传）与可变的权威状态（head、租约、工具目录版本、unit 状态）。两类不共用
缓存，因为失效策略根本不同。

**读路径合并成批量接口。** worker 要的是"从某个 head 出发按策略解析出的上下文"，不是
一棵树的逐节点拉取。接口形状是一次往返返回完整结果，避免调用次数随上下文深度增长。

## 理由

单库的直接理由是部署形态与未来迁移：一台 server 管多个工作区，一个库就是这台 server 的
自然单位；换成 Postgres 时只需要替换操作层实现。跨工作区统计（某工具的使用频次与失败
率，见工具检索的反馈信号）也只有共库才做得到。

把写集中到 server 有三个实际收益，其中第一个是真正的性能收益：

1. **批量提交。** 单写者可以把多个工作区的多条事件合并成一次持久化。SQLite 每次事务
   都有一次同步写入磁盘，高频工具调用下这是最贵的固定开销，而多个进程各自连库时无法跨进程
   合并。
2. **读缓存成立。** 事件 append-only 且不可变，写入后永不改变，因此可以安全缓存，未来
   也能做读副本而不需要一致性协议。
3. **凭据集中。** 模型 API 密钥、限流、成本账本都需要一个中央点。worker 与沙箱因此可以
   完全不出网，这是沙箱策略里最实惠的一条（见 0010）。

## 后果

好的方面：批量提交带来吞吐；单一备份单元；凭据不进沙箱；未来 Postgres 只需换操作层。

代价与对应的纪律：

- **作用域泄漏风险从"漏写 WHERE"变成"handler 误用参数"。** 只要 workspace 不从请求里
  读取，风险就降到零；因此这条被列为架构不变量。业务查询只能通过带作用域的入口访问，
  裸连接不对业务代码开放。
- **server 进入关键路径。** 每个工具调用前的租约获取、每次事件追加都要过一次本地
  socket。这是可接受的，但前提是读路径绝不等写路径。
- **失去了"搬目录即搬工作区"。** 补偿手段是导出与导入（元数据行 + 被引用的内容对象 +
  快照清单），它同时拿到复现能力。
- **写入串行化是纪律而非瓶颈。** 若把同步 IO 放进锁里，它会被放大成全局停顿。这条在
  实现时比在设计时更容易违反。

需要重新审视的信号：某工作区的事件表超过 200 MB，或单次上下文解析超过 20 毫秒。此时
先做归档（把旧事件段搬到内容寻址存储，库内只留索引），并保持范围读接口不变，所有调用
方零改动。

## 被否决的替代方案

**每工作区一个数据库，server 只存路由与注册表。** 这是本决策最有力的竞争方案，优点
很实在：多工作区并发时没有写竞争；搬移与备份工作区等于搬目录；server 挂掉后 worker
仍能完整工作；作用域隔离是物理的而非约定的。

不选的理由是它牺牲了三件事，而这三件事恰好是我们要的：跨工作区统计做不了；批量提交
跨不了进程（每个进程各自同步写入磁盘）；未来迁 Postgres 时要维护两套拓扑（一个全局库加
N 个工作区库，或者干脆放弃每工作区一库的形态，那时迁移成本比现在高得多）。

重新考虑的条件：如果最终形态变成"一台机器一个工作区"（比如桌面单机产品），每工作区
一库会重新占优，因为它的所有缺点都消失而优点全部保留。

**worker 只读打开数据库，写走 server。** 它省掉读路径的 IPC 往返，在 WAL 模式下技术上
可行。不选的理由不是性能而是复杂度守恒：它会留下两套读路径（一套走 server、一套走
本地），意味着两种 bug、两种权限模型、两种迁移约束，而只读连接仍然能看见其他工作区的
行，"进程碰不到库"这个易验证的性质也就没了。如果将来读路径真的成为瓶颈，正确解法是
在 worker 侧缓存解析结果并用序号失效，而不是开第二个连接。

**用消息中间件（Redis、NATS 等）做队列。** 不选的理由是它引入了第二个需要持久化的
组件，而这个队列承载的是权威写——那就等于有了两个真相来源。进程内队列加数据库事务
已经足够，且崩溃语义清楚。
