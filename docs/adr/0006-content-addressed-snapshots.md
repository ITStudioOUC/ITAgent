# 0006. 快照用内容寻址存储

## 状态

已采纳，2026-10-23。

## 决策

文件内容不进数据库。按内容哈希存到独立目录，文件名就是哈希（用 blake3，不用 sha256，
因为每次工具调用后都要算它，速度差一个量级）。数据库里只放元数据。

```
blobs/3f/3fab...c1        内容本身
blobs 表：hash, size, created_at
snapshots 表：id, workspace_id, seq, parent_id, kind, created_at
snapshot_entries 表：snapshot_id, path, kind, hash, mode
```

`kind` 取 `file`、`dir`、`tombstone`（当时被删除）三值。墓碑是必需项，原因见 0005。

**保留策略是基线加快照，不是纯滑动窗口。** 到达上限时，把最老的两个合并进基线
（squash），而不是丢弃最老的。这样"回到任务起点"永远可用，只是颗粒度变粗。

**允许显式重定基线，但它必须是独立动词、必须落库、且在没有人工确认时默认禁止。** 所谓
"自主模式"指 agent 在无人值守下连续推进的会话；该模式下重定基线一律拒绝，只有用户显式
发起的调用才允许。重定基线等于永久放弃之前的回滚点，不可逆。会话起点的基线是硬地板，
任何模式下都不能删除。

**回收用全局标记-清除加宽限期，不用引用计数。** 引用计数在崩溃、事务回滚、并发 squash
下容易失配，失配的后果是删掉仍在使用的对象，也就是数据损坏。因此从所有快照条目出发
标记，未标记的删除，并且不短于租约 TTL 的时间内不删（默认兜底 24 小时）——正在执行的
工具可能刚引用它而清单尚未提交。活跃租约表同时作为附加标记根，见 0018。

**大文件设阈值。** 超过 1 MiB 的文件只记录尺寸、修改时间与哈希，不存内容，回滚时警告
"此文件过大未纳入快照"。代码文件几乎不触发这条，因此不必引入分块切分。

**写入必须原子。** 先写临时文件、同步、再改名到最终路径。绝不出现"文件名已是哈希但
内容是半截"的状态，否则整个去重体系的正确性就没了。

## 理由

数据库只放元数据，是因为快照会频繁被合并与丢弃。如果内容存成行内大对象，squash 就是在
重写大量数据行，日志会快速膨胀，清理与备份都会变慢。换成内容寻址后，squash 只改清单行，
成本与文件大小无关。同一文件被十个快照引用时也只存一份。

这个选择还让"未来换 Postgres"变成只换元数据层：文件那块完全不受影响（Postgres 的大
对象是另一套机制，迁移时会是额外负担）。

基线加合并而不是纯滑动，是为了兑现"回到任务起点"这个承诺。纯滑动的语义是"早期状态
永久丢失"，这与长程任务的定位直接冲突。

标记-清除而不是引用计数，理由单一且明确：引用计数的失配是静默的数据损坏，而标记-清除
失配的后果只是"该删的没删"（占用空间）。在两种失败模式之间选择更安全的那种。

## 后果

好的方面：快照便宜到可以每次工具调用后做；跨工作区自动去重（同一仓库的多个工作树共享
大量相同内容）；合并成本与文件大小无关；迁移只涉及元数据。

代价：

- **删除变成全局操作。** 回收必须扫描全库引用，不能按工作区独立清理。宽限期让它变成
  低优先级的后台任务。
- **内容目录与数据库可能短暂不一致。** 崩溃可能留下无引用的对象，这是安全的（多占空间），
  而不是危险的（丢内容）。方向是刻意的。
- **超过阈值的文件不回滚。** 这是明确的已知缺口，必须在回滚输出里说出来。
- **重定基线是不可逆操作。** 因此它需要独立动词、默认禁止、硬地板，并且要落库留痕。

需要重新审视的信号：如果出现工作区里有大量接近阈值的文件（例如数据处理项目里的 CSV），
说明按整文件存储不再合适，届时应考虑分块或直接换文件系统快照，并新写一份记录。

## 被否决的替代方案

**内容存数据库大对象。** 单文件、单一备份单元、事务与元数据天然一致，实现也最简单。
不选的理由已在上文：squash 成本随文件大小增长，日志膨胀，迁移到 Postgres 时大对象是
另一套机制。

**git 影子仓库（独立 GIT_DIR）。** 优点很多：白拿差异、忽略规则、检出回滚、增量存储。
这是最有竞争力的替代方案。不选的理由有两条：一是它把回滚能力绑在 git 上，工作区本身
不是 git 仓库时（或处于特殊状态时）行为不可控；二是 agent 大量操作发生在未被版本控制
跟踪的文件上，而 git 对这类文件的内容寻址能力需要额外绕路。git 仍然作为差异展示的只读
工具使用，这是它最擅长的部分。

**文件系统快照（btrfs、zfs、APFS）。** 实现最省、语义最强（整树一致）。不选的理由是
跨平台不可用，Windows 没有对应物，而项目定位是跨平台。它作为可选加速器保留在沙箱的
保真度矩阵里，但不是基线机制。

**每小时或每轮定时快照。** 实现简单，但会在关键改动前后出现空档，而 agent 最需要回滚的
恰恰是"刚改坏的那一下"。按工具调用打点更贴合实际需求，成本也已经被内容寻址压到很低。

**引用计数。** 见上文。失败模式是损坏而非浪费，这个方向不能接受。
