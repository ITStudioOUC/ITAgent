# 0007. 受限 bash 文法与 heredoc

## 状态

已采纳，2026-10-23。

## 决策

工具调用不是 JSON 结构化参数，而是一条命令行。文法限制在第二档，手写词法与语法分析器。

**允许的构造。** 命令名加参数、管道 `|`、重定向 `>` `>>` `<`、heredoc `<<`。
不允许：命令替换 `$()`、反引号、`&&`、`;`、通配符、后台 `&`。

通配符没有例外。它会让单条命令的写入目标集合在执行前不可知，与"权限预检在任何执行之前
完成"以及"多路径原子获取"在结构上冲突。需要批量操作时用显式列出的路径，或使用工具自己的
参数（如 `--include`），它们的目标集合对执行器是可见的。

**heredoc 是通用能力，不是编辑工具的附属。** 它属于词法层，作用是"给命令提供标准输入"。
工具 manifest 里只需声明"接受标准输入"，工具本身不关心内容是从参数还是从标准输入来的。
因此编辑、打补丁、写入等工具共用同一个机制，目标路径在 heredoc 之前就已出现在参数里，
权限可以在内容到达之前就判定。

**heredoc 的接受形式。** 优先 `<<'EOF'`（引号形式，不做展开）；`<<"EOF"` 等价接受；
`<<EOF` 未加引号时，仅在内容不含展开字符时接受，否则拒绝并提示改用引号形式；`<<-EOF`
与 `<<<EOF` 明确拒绝并解释原因——后者在真实 bash 里是 herestring，语义完全不同，且会
静默写错内容，比报错危险。

`<<<` 的拒绝是本条里最值得强调的一处：判断依据是"模型对 bash 语法天然亲和"，而语法一旦
不符合 bash，就会在两条路径上产生静默分叉。

**版本一限制单命令加单个 heredoc，不允许与管道共存。** 覆盖率损失很小，换来的是"找内容
结尾"退化为纯粹的行扫描。

**全量收完再交由工具。** 绝不边收边交。正文完整收进临时文件后，以只读文件描述符交给工具；
目标文件的原子写入（临时文件加改名）是写入类工具的义务（见 0012），不是执行器的职责。
分隔符必须独占一行、大小写敏感、行尾不允许空格；正文按字节原样交付，不转换换行。

**分隔符由模型声明，且在解析后强制校验。** 声明的分隔符未出现即视为被截断，整条拒绝，
一个字节都不写。分隔符之后若有残留文本且无法解析为合法续接，整条拒绝——这条正是为了
捕获"脚本里嵌套了 heredoc、内层分隔符撞上外层导致提前截断"这种在纯扫描下不可检出的失败。

**重定向由执行器解释语法树后自己实现**，不把字符串交给真实 shell。否则 `cmd > file` 会在
命令失败前就把文件截断。管道的文件描述符同理，由执行器接管。

## 理由

第二档是正确的平衡点。仅允许参数会失去管道的表达力（读一段、过滤、再看），而放开到
全 shell（命令替换、通配、逻辑连接）会让权限模型失效：`$(curl ...)` 可以绕过一切声明，
通配符可以让路径检查与实际写入不一致。

手写解析器在这个受限文法下不难，而且它带来一个关键能力：**权限预检可以对整条管道的
所有节点在任何执行之前完成**。如果用字符串前缀匹配，就只能做粗略判断，而那种判断会被
路径穿越、符号链接、大小写差异绕过。

heredoc 在"命令是一个字符串"的前提下不是便利而是必需品：单引号里装不进单引号，双引号
里装不进双引号和 `$`，不加引号则管道与重定向会被当成语法。而一段真实代码里这些字符全都
有。结构化参数（单独的 stdin 字段）能绕开这个问题，但代价是命令不再是一条真命令——审计、
复现、工单粘贴都会失真，而这与本项目"命令可以直接在真实 shell 里执行"的定位冲突。

还有一个决定性因素：模型会自发写 heredoc。它被同类工具训练过，即便只提供结构化输入
字段，它仍会时不时输出 heredoc 形式。无论如何都得识别它，而识别已经是这件事的大部分
工作量。

## 后果

好的方面：命令可直接粘贴执行；权限可预检；截断与碰撞可检测；与沙箱内真实 bash 语义一致。

代价：

- **模型需要学一套受限文法。** 好处是它的错误是显式的（拒绝并解释），而不是静默地绕过
  权限。
- **命令的可发现性差。** 结构化参数是自描述的，命令行不是。因此需要懒加载的工具目录：
  提示里只放名称与一句话，按需展开详细用法。这会进入预算计算。
- **单命令无管道的限制**会让少数场景需要分步执行，多花一到两轮。
- **分隔符碰撞仍可能发生。** 模型选了一个常见词（`EOF`）而内容里恰好有它，只能整体拒绝。
  缓解办法是在工具描述里要求使用带前缀的罕见分隔符。

需要重新审视的信号：如果大量真实调用需要 `&&` 或命令替换，说明文法定得太紧，届时应
评估放开到第三档并配套真正的 shell 沙箱，而不是就地打补丁。

## 被否决的替代方案

**`<<<` herestring 写法。** 这是最初提出的形式，看起来更像 heredoc。不选的理由是它在
真实 bash 里语义完全不同（把字符串本身喂给标准输入），而且命令会成功执行，只是写入了
错误内容。静默错误比报错危险得多。

**结构化参数：独立的 stdin 字段。** 它更"干净"：少一个状态机，没有分隔符碰撞，工具目录
仍然是静态的。这是本决策最有力的竞争方案。不选的理由是命令不再可原样执行，与"bash 风格
工具与 bash 本身不冲突"的定位冲突；同时模型仍会自发写 heredoc，识别成本照样要付，只是
从"支持"变成"报错"。

**两个都支持（既有 stdin 字段也有 heredoc）。** 会导致同一份内容有时放字段、有时放内容体，
出现两条等价路径——这是最难写测试、最容易静默分叉的情况。二选一。

**把 heredoc 只实现在编辑工具里。** 省掉词法层的通用性。不选的理由是打补丁、写入、过滤
都需要它，各自实现一遍等于 N 份"怎么结束"的实现与 N 种 bug。

**放开到全 shell 并用沙箱兜底。** 表达能力最强。不选的理由是权限声明失去意义：一旦允许
命令替换，声明的写入范围与实际写入就无关了，只剩下沙箱这一道防线，而沙箱的保真度在三个
平台上并不等价。

**用现成的 shell 解析器 crate。** 省事，但它们实现的是完整 bash，包含我们明确禁止的构造，
事后过滤语法树比事前限制文法更容易漏。手写在受限文法下的规模是可控的。
