# 0005. 两层回滚正交

## 状态

已采纳，2026-10-23。

## 决策

系统里有两种回滚，名字接近但语义完全独立，互不触发、互不引用。

**文件回滚**移动工作区文件指针到某个文件快照。粒度是每次有改动的工具调用之后一次
快照，快照数量有硬上限，按工作区计算。

**上下文回退**移动上下文 head 指针到某个祖先节点。不改动工作区的任何内容。典型用法是
大粒度待办完成后回退到开启该待办的位置，注入摘要（见 0004）。

两者都是"移动一个指针"，只是指向的对象不同，因此共用同一套操作与审计记录。它们之间
唯一的联系是一条弱引用：帧里记的检查点编号可以是悬空的，解析时按漂移通知处理（见 0003
与 0018）。

**回滚保证的边界必须写死。** 只保证工作区内、工具 manifest 声明范围内、被工具修改过的
文件。范围外的一切（被忽略规则排除的构建产物、工作区外的写入、数据库迁移、后台进程、
网络副作用）不在保证范围内，回滚结束后输出"范围外可能残留"的清单。回滚时若检测到
范围内存在外部改动（判据见 0018：磁盘内容与目标快照记录的哈希不一致，且差异不由已记录的
工具调用产生），默认拒绝执行，除非显式要求强制。超过大小阈值的文件只报告、不删除也不覆盖
（见 0017）。

**文件回滚是一次对齐，不是一次写回。** 需要处理四种情况：快照里有而磁盘上没有则写回；
快照里有而内容不同则覆盖；快照里是墓碑（当时被删除）而磁盘上存在则删除；快照里没有
而磁盘上存在（快照之后新建）且位于范围内则删除。只做"写回"会留下大量后来新建的文件，
让 agent 误以为它们属于旧状态。

**快照在工具进程组被回收之后才打。** 后台进程（格式化器、监听器、测试运行器的子进程）
会在工具返回后继续写文件。在进程组被回收前打快照会得到半写状态，而它会被固化成"可回滚
的历史"。组的边界与回收责任见 0014。

## 理由

把两者分开是这套设计能同时服务两类需求的原因。文件回滚服务"试错"：agent 改坏了就退回去。
上下文回退服务"注意力管理"：待办做完了，过程中的试错细节不再需要占据预算，但文件要保留
成果。如果绑定成一个"回到过去"的复合操作，就无法表达"文件前进、上下文后退"这个最常用
的组合。

命名上刻意区分：文件叫回滚，上下文叫回退，压缩叫折叠。三者混用会让讨论与代码都失去精度。

边界写死的理由是可预期性。用户会按"回滚"这个词的最强含义去理解，而实际保证比那弱得多。
与其让每个人自己猜，不如明确说"只保证这些"，并把残留清单打印出来。这也是为什么 manifest
的写入范围同时是沙箱策略与回滚边界的依据——同一份声明，两个用途。

对齐而非写回，是因为快照只覆盖"被工具写过的路径"。这意味着快照是稀疏的，它对"当时
不存在"与"当时存在但没被记录"是同一个表示。墓碑解决了其中一半，另一半靠"快照之后新建
且在范围内"的推断。不做这个推断的后果是回滚不干净，而"不干净"在 agent 眼里就是"文件
状态不明"，比报错更糟。

## 后果

好的方面：两类需求各自最优；组合自由；回滚语义可预期；快照与沙箱共用一份声明。

代价：

- **快照数量有上限，因此早期状态终会不可达。** 缓解办法是基线加快照的合并策略（见
  0006），而不是无限增长。
- **回滚不覆盖构建产物与网络副作用。** 用户需要知道这一点，因此残留清单不是可选项。
- **稀疏快照的推断可能过头。** 如果某个文件在范围内、快照之后被创建，回滚会删除它。
  这在语义上正确（它不属于旧状态），但用户可能有意外情绪。因此回滚前的确认与事后清单
  都必须清楚。
- **`tombstone` 与"未记录"必须能区分**，否则对齐算法无法判断该删还是该留。这是实现时
  最容易漏的一列。

需要重新审视的信号：如果用户频繁要求"连构建产物也退回去"，说明需要引入整体快照（文件
系统快照或归档全树），那是另一个量级的成本，届时应新写一份记录而不是改这一份。

## 被否决的替代方案

**单一"回到过去"操作，同时回滚文件与上下文。** 直觉上更符合用户心智模型，实现也更省
（一个按钮）。不选的理由是它把最常用的组合（文件前进、上下文后退）变成了不可表达，
而那正是长程任务省上下文的主要手段。

**上下文回退时同步回滚文件，保证"记忆与现实一致"。** 语义最干净，永远不会出现漂移。
不选的理由是它摧毁了非线性开发：回到早期帧继续走另一条路时，你并不想丢掉那之后在文件
上取得的进展。漂移问题用漂移通知解决（见 0003 与 0018），代价是一行提示，而不是牺牲自由度。

**每次工具调用都做全树快照。** 语义最强，回滚最彻底，也不需要对齐推断。不选的理由是
成本：在中等仓库上每次调用扫全树并存储，会让工具调用的固定开销超过工具本身。按声明范围
加变动检测是可行的折中。

**用 git 提交作为快照。** 白拿差异展示、忽略规则与检出能力。不选的理由见 0006：它把回滚
机制绑在 git 上，且对未纳入版本控制的文件无效，而 agent 大量操作恰好发生在那类文件上。
git 仍然作为差异展示的只读工具使用，但不承担快照职责。

**回滚时自动 git stash 保护用户改动。** 看似安全，实际会产生"回滚之后 stash 列表里多了
一堆东西"的混乱，且 stash 与 agent 的改动难以区分。默认拒绝执行更简单可预期。
