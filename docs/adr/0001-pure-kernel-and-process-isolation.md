# 0001. 内核纯逻辑与进程隔离

## 状态

已采纳，2026-10-23。

## 决策

系统分成两类代码和三类进程，边界由编译器与操作系统共同保证。

**代码分两层。** `ita-kernel` 只放纯逻辑：消息树的结构与解析、命令文法的词法与语法
分析、租约与权限谓词、检查点与帧的类型。它不得依赖 `tokio`、`rusqlite`、`reqwest`、
`std::time` 或任何带 IO、时钟、随机数的 crate。其余能力（存储、协议、沙箱、执行器、
模型适配、工作流）都放在内核之外，通过显式传入的数据与内核交互。

**进程分三类。** server 持有数据库与模型凭据，是唯一权威；每个工作区一个 worker，
无状态、无数据库连接、无凭据；每个工作区一个执行器，负责权限预检、租约、沙箱委派与
进程组回收。工具二进制作为沙箱子进程运行，不直接接触上述任何一方。

**所有进程可丢弃。** worker 崩溃后从数据库重建，server 崩溃后 worker 降级为只读暂停
（见 0002），执行器崩溃后租约按 TTL 过期回收。任何一方都不持有不可重建的状态。

## 理由

内核纯逻辑不是为了代码整洁，而是为了四件具体的事：

1. 上下文回退与压缩是纯数据变换，只有做成纯函数才能在不调用模型的情况下单测，也才
   能在调试时逐字节复现某一轮看到的输入。
2. 权限谓词必须能被穷举测试。如果它读环境变量或文件系统，测试就只能覆盖碰巧跑到的
   路径，而权限判断的错误代价是数据被写到不该写的地方。
3. 多工作区并发时，进程隔离是唯一能同时做到环境变量隔离、崩溃隔离、重启隔离的手段。
   线程级隔离依赖每处代码都记得不共享状态，这种约定守不住。
4. 工具二进制来自第三方，运行在工作区里。如果主进程与工具在同一地址空间或同一信任
   域，工具能直接改写主进程的数据目录，沙箱就失去意义。

进程边界还有一个附带好处：本地进程拓扑已经定好（worker 与文件都在 server 所在机器，客户端
只负责显示），未来接远程时，worker 与
执行器本来就在远端，本地只作为客户端，不需要重新切分。

## 后果

好的方面：内核可以被快速穷举测试；工作区之间天然隔离；某一工作区崩溃不影响其他；
未来远程部署只是把进程换个位置。

代价有三处，都是已知且可接受的：

- 跨进程调用有固定开销，一次工具调用的路径变长。这条通过把读路径合并成批量接口来
  控制（见 0002），而不是靠缓存掩盖。
- 调试需要跨进程追踪，单步调试不再可能。因此事件日志必须是完整的（见 0002），
  它承担了调试入口的角色。
- 错误要在进程边界上翻译一次，错误类型的设计成本上升。

需要重新审视的信号：如果内核为了性能开始需要缓存、需要读取时钟、或者需要知道
"当前工作区路径"，说明职责划错了一层。正确做法是把那段逻辑上移到 server 或执行器，
而不是给内核开一个 IO 口子。

## 被否决的替代方案

**单进程单二进制、多线程共享状态。** 这是 claude-code 一类工具的常见形态，实现最快，
调试最方便。不选的理由是多工作区隔离无法保证：环境变量是进程级的，工具沙箱一旦能
写工作区外的路径就能污染其他工作区，任一工作区崩溃会带走全部会话。如果将来只做单
工作区单会话的产品形态，这个方案会重新变得合理，届时整个进程模型可以简化掉。

**每工作区一个独立数据库，server 只存路由。** 它保留了进程隔离，还额外获得"搬走
工作区等于搬目录"的能力。不选的理由见 0002。

**内核与外围同 crate、用 feature 开关约束。** 看起来省了一个 crate，实际上没有强制
力：feature 组合一多就没人验证纯逻辑变体是否还能编译，边界会在半年内消失。
