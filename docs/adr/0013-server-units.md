# 0013. server 内的 unit 监督

## 状态

已采纳，2026-10-23。

## 决策

server 内部由多个解耦的 unit 组成，有前置依赖关系，构成依赖拓扑。CLI 激活 server 时，
只要指定的必需 unit 都达到就绪状态即可正常显示页面，其余非必需 unit 在后台异步加载。

**unit 管进程生命周期，工作流管任务语义，两者不共享状态机。** 这条是硬边界：否则会出现
"节点租约被 unit 重启清掉"这类纠缠。

**依赖关系区分三种。** 硬依赖（失败则连带失败）、软依赖（失败只是降级）、仅排序
（不隐含依赖）。启动时静态校验无环。

**就绪不等于运行。** CLI 能显示页面需要的是"必要 unit 达到就绪"——数据库迁移完成、
IPC 套接字在监听、路由表载入完毕。进程活着只是运行。这个区分直接决定冷启动体感。

**崩溃处理保守。** 版本一不级联重启，只标记降级，并把能力集合的变化推送给已连接的
客户端。能力集合的推送与工具目录的追加通知是同一套机制。

**需要的最小拓扑**（用于验证设计）：

```
store  →  router  →  ipc        （必需）
lease  ↔  tools                  （租约仲裁与工具目录注册，必需）
model                            （首次调用模型时才需要）
telemetry                        （软依赖，缺了只是没有埋点）
```

这里的 `lease` 只做租约表维护与跨工作区资源仲裁，不是每工作区的执行器进程；工具执行在
独立的执行器进程里完成（见 0014）。

**资源清理与快照时机共用进程组设施。** unit 停止时对子进程组发信号并回收（见 0005）。

## 理由

这个设计解决的是冷启动体验：如果 CLI 必须等全部子系统就绪才能显示界面，用户会看到一个
没有反馈的等待。区分必需与非必需，让"打开就能用"成为默认。

依赖拓扑而不是简单启动序列，是因为 unit 之间的依赖并不全序：模型适配与工具注册互不依赖，
可以并行加载。

就绪与运行的区分，是因为"进程起来了"与"功能可用了"之间有实质差别：数据库进程活着但
迁移没跑完时，接受请求会失败。

不级联重启，是因为长程任务里重启会打断正在进行的工具调用与租约，而租约的 TTL 回收本来
就能处理崩溃。降级加能力推送让客户端知道缺什么，比自动恢复更可预测。

## 后果

好的方面：冷启动快；依赖关系显式；崩溃行为可预测；能力变化可推送。

代价：

- **两套监督语义（unit 与工作流节点）容易混淆**，必须靠文档与类型分开。
- **降级状态需要整条链路理解**：客户端要能展示"模型不可用"而不是报一个笼统的错误。
- **异步加载的非必需 unit 失败时用户可能不知道**，因此能力推送不能省。

需要重新审视的信号：如果必需 unit 集合不断膨胀（因为大家都想"先就绪"），说明就绪的定义
退化成了"启动完成"，届时应重新划分单元而不是继续加。

## 被否决的替代方案

**单进程顺序初始化，全部就绪后才接受请求。** 实现最简单，语义最清晰。不选的理由是冷启动
体感差，而且某些子系统（模型适配）在首次调用前根本不需要初始化。

**全套 systemd 语义（可选的 target、socket 激活、cgroup 资源控制等）。** 表达力强，
与用户直觉一致。不选的理由是这些语义大部分在单元进程内没有对应物，实现成本远高于收益。

**崩溃即级联重启整个 server。** 状态最干净。不选的理由是重启会打断正在进行的工具调用，
且长程任务的上下文重建成本很高。

**用独立进程做每个 unit（真正的多进程 supervisor）。** 隔离最强。不选的理由是这些 unit
共享数据库连接与内存缓存，跨进程会把 0002 的批量提交与读缓存优势抵消掉。注意这条只适用于
server 内部的 unit：每工作区的执行器是独立进程，因为它不共享这两样东西（见 0014）。
