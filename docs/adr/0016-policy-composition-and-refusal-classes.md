# 0016. 沙箱策略由工具清单与节点范围取交集

## 状态

已采纳，2026-10-24。澄清 0005、0009、0010 之间关于策略来源的缺口。

## 决策

**静态策略 = 工具清单范围 ∩ 节点权限范围。** 两个输入都在安装或配置阶段确定：

- 工具清单是**安装期上限**，由人工批准（0012）。
- 节点权限范围是**运行期收窄**，由工作流配置或会话默认给出。

任一方缺失时取另一方；两方都缺失时取空集（即该工具在此节点不可用）。交集规则意味着
节点只能收窄、不能扩权，这与"批准时看到的能力"保持一致。

**两类拒绝必须分开，因为它们对调用方的意义不同。**

| 类型 | 含义 | 是否重试 | 返回内容 |
|---|---|---|---|
| 策略拒绝 | 该路径或网络目标从来不在允许集合内 | 否，终态 | 被拒的目标、生效的策略来源（清单还是节点） |
| 租约拒绝 | 目标在允许集合内，但当前被别的调用占着 | 是 | 持有者标识、被改动的路径 |

策略拒绝由执行器把沙箱的拒绝翻译成统一事件，沙箱本身的错误码不泄漏到模型（否则模型会
针对具体机制写规避代码）。运行中才发现的违规（检查之后新建的符号链接、路径指向变化）一律
归入策略拒绝，不重试——重试只会重复同一个失败。

**执行器的检查与沙箱的强制是两个不同的东西，都要保留。** 执行器的检查给出好错误信息并
节省一次沙箱启动；沙箱是安全边界。两者用**同一份合成后的策略**，否则会出现"执行器放行、
沙箱拒绝"的静默不一致。

**降级模式取消。** 缺少必需维度时直接拒绝运行，并在包管理器与运行时的错误里写明缺哪一维。
不存在"仅策略检查、未强制"的模式，因此"安全边界在沙箱"这条不变量保持无例外。

## 理由

交集是唯一同时满足两个直觉的规则：授权只能收窄（安全），且节点能自我保护（最小权限）。
若以清单为准，只读节点拿到可写工具时仍是可写，节点声明的意图形同虚设；若以节点为准，
工具的实际能力与批准时看到的不一致，供应链信任链断裂。

两类拒绝分开，是因为它们的正确反应完全相反：策略拒绝重试永远不会成功，租约拒绝过一会儿
就好。混在一起会让 agent 对策略错误做无意义的指数退避，或对租约错误直接放弃。

取消降级模式，是因为"带条件的安全属性"在自动运行的场景里守不住：开关一旦存在就一定会被
打开，而打开后的损失是静默的。宁可让某些工具在某些平台不可安装——那是可见的失败，可以被
处理。

## 后果

好的方面：策略来源唯一确定；拒绝语义可区分；安全属性无例外；执行器与沙箱用同一份策略。

代价：

- **节点配置要写得比"直接跑工具"更细**，否则交集可能比预期窄（节点没声明某路径，即使工具
  允许也写不了）。这是刻意的，但会让初次配置有摩擦。
- **缺失维度直接拒绝运行，会降低跨平台可用性**。某些工具在 Linux 可用、在其它平台不可装。
- **交集计算的错误不直观**：用户看到"工具存在但不可用"时，需要能查到是哪一方收紧的。因此
  拒绝信息里必须带"生效的策略来源"，这不是可选项。
- **同一份策略两处解释**，实现时必须共用同一个函数，不能各写一份。

需要重新审视的信号：如果大量节点都要重复声明同一组路径，说明缺少节点级别的默认策略继承，
届时应加"项目默认范围"这一层，而不是放宽交集规则。

## 被否决的替代方案

**以工具清单为准，节点声明只用于调度。** 实现最省，语义简单。不选的理由是节点无法自我
保护，且"节点权限范围"这个概念失去意义。

**以节点范围为准，清单只作安装期参考。** 最灵活。不选的理由是工具的实际能力与批准时看到
的不一致，人工批准的信任基础消失。

**取并集。** 看起来"更宽松更好用"。不选的理由是它让节点可以扩权到清单之外，等于取消了
安装期批准。

**保留降级模式但要求每次运行人工批准。** 比一次性开关安全。不选的理由是频繁批准会让人形成
无脑同意的习惯，反而降低整体警觉性；而"这个工具在你这台机器上装不了"是一个清楚的、可处理
的状态。

**策略拒绝与租约拒绝使用同一错误类型，由调用方按字段判断。** 类型更少。不选的理由是调用方
（模型）最容易犯的错就是对不可重试的错误重试，类型分开是最强的提示。
