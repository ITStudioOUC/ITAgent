# 0017. 超阈值文件不在快照覆盖内

## 状态

已采纳，2026-10-24。解决 0005 的对齐规则与 0006 的超阈值规则之间的冲突。

## 决策

**超过大小阈值的文件属于"不在快照覆盖内"，不是"有条目但无内容"。**

在条目表里它们仍有一条记录（这样"当时存在"这个事实可查），但该记录携带一个明确的
"未存内容"标记与尺寸、修改时间。对齐算法对这类条目的处理：

| 磁盘现状 | 动作 |
|---|---|
| 不存在 | 不创建（无内容可写回），列入残留清单并标注尺寸 |
| 存在且哈希相同 | 什么也不做 |
| 存在且哈希不同 | **不覆盖**，列入残留清单并标注尺寸 |
| 快照之后新建、位于范围内 | **不删除**，列入残留清单并标注尺寸 |

即：**超阈值文件只报告，从不删除、从不覆盖。** 这与"回滚保证边界"的立场一致——保证不了的
东西就明确说出来，而不是靠删除制造"看起来回滚成功"的假象。

**残留清单是回滚结果的必要组成部分**，不是日志附加项。它至少包含：路径、尺寸、原因（超阈值、
范围外写入、后台进程遗留）。

**阈值默认 1 MiB，可配置。** 调整不影响语义（只影响哪些文件落入"仅报告"这一档）。

**"回滚即对齐"这条不变量加限定：** 对齐的语义是"范围内、有内容记录的文件与删除墓碑"，
不含因超过阈值未记录内容的文件。

## 理由

两个方向都有代价，比较的是失败模式：

删除超阈值文件是**不可逆的数据丢失**（内容没存，删了就无法恢复），而保留它只是"回滚不彻底"。
在两种失败之间，前者不可挽回。

反过来"遇到超阈值文件就拒绝整次回滚"也不行：一个 2 MiB 的日志文件就足以让回滚功能完全失效，
而超阈值文件在真实项目里并不罕见（日志、数据样本、生成物）。

"只报告"是唯一既不丢数据、又不让功能失效的选项。它把不确定性交还给用户：你知道这次回滚
没有覆盖这些文件，你可以自己决定删除还是保留。

保留一条记录（而非完全不记）是为了让"当时存在过什么"可查——否则回滚之后你无法判断某个
大文件是回滚前就有的、还是回滚后新建的。

## 后果

好的方面：不会静默删数据；回滚仍然可用；用户知道边界在哪；历史可查。

代价：

- **回滚可能留下大文件**，包括那些是在快照之后新建的。用户需要读残留清单才知道。
- **残留清单的质量直接影响体验**：只列路径不够，必须带尺寸与原因，否则用户无法判断分量。
- **阈值可配置意味着同一工作区在不同配置下回滚结果不同**，因此配置变更要记录。

需要重新审视的信号：如果实践中残留清单频繁出现同一批文件（比如一个稳定的日志文件），说明
该把它加入忽略清单，而不是把阈值调大。

## 被否决的替代方案

**按 0005 的原规则删除（范围内且快照之后新建就删）。** 语义一致：范围内一律对齐。不选的
理由是它会在无内容记录的情况下删除文件，而用户看到的是"回滚"不是"清理"，不可逆。

**遇到超阈值文件拒绝整次回滚。** 最安全。不选的理由是一个大文件就能让功能失效，而大文件在
真实项目里常见。

**把超阈值也存内容（去掉阈值）。** 语义最完整。不选的理由是它把快照成本与文件大小绑定，
一次大文件写入就会让快照从毫秒级变成秒级，而快照是每次工具调用后都要做的。

**对超阈值文件做分块存储。** 兼顾完整性与成本。不选的理由是它引入分块、去重与重组逻辑，
复杂度远超当前需求；代码文件几乎不触发阈值，等到真的遇到大量大文件时再考虑。
