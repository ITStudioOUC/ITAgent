# 0009. 单次调用租约与冲突检测分层

## 状态

已采纳，2026-10-23。

## 决策

写入权限的持有者是租约，粒度是**一次工具调用**，不做节点级租约。工作流层面的写冲突
靠启动前的静态检测提前拦截，两件事分层。

**租约的语义。** 校验权限通过并获得租约是同一个不可分割的动作（检查通过不等于占用成功）。
租约有 TTL 与心跳，因为跨进程的锁不能依赖"持有者退出即释放"——进程可能崩溃，崩溃后
必须能被回收。被拒时返回明确提示（谁改了、改了什么），由调用方决定重试或改写。

**多路径原子获取。** 管道或一条命令涉及多个写入目标时，排序后一次性全部获取，全成功或
全失败。这同时消灭了"拿到 A 再拿 B"的中间态，因此经典的循环等待死锁在结构上不可能发生。
嵌套调用（真实 bash 里再调用工具）继承外层租约，不允许在嵌套上下文里申请新路径。

**租约落库**，不只放在执行器内存里，因为崩溃回收与跨工作区全局资源（端口、构建缓存）
需要持久仲裁。

**租约只解决并发写，不解决陈旧写。** 写入时校验磁盘内容哈希是否等于调用者最后读到的
哈希；不相等则拒绝并返回"文件已更新 + 新的片段"。A 读了文件、租约已释放、B 改了、A 再写
——这个序列里没有任何并发，租约完全拦不住，而它是并行探索阶段最常见的失败模式。

**工作流节点的写集是声明，不是保证。** 节点里跑的是模型，它能在运行时写任何东西。因此
区分硬边界（节点的权限范围，进沙箱策略）与软预测（声明的写集，用于调度）。运行时发现
实际写入超出声明，记事件并告警，默认不阻塞；需要强隔离的节点显式声明严格模式，越界即拒。

**冲突检测在节点启动前做，且只在真正写入时才排队。** 两个节点都声明写同一文件时，允许
它们并发启动（读和分我可以并发），在第一次真正获取写租约时才等待。这样既避免写冲突，
又不牺牲并行度。

**写集要分资源类**，不能只比文件路径：文件、目录树（`target/` 这类）、锁文件、端口、
数据库。Rust 项目里两个节点都跑构建时会同时写产物目录与锁文件，按文件比对完全看不见，
而这是最常见的真实冲突。

**子节点继承父节点写集的交集**，否则声明再仔细也能被派生的子孙绕过。这与派生深度上限
是同一套机制。

**声明与实际要能事后比对。** 工具日志里已有实际写入的路径集合，可以自动算出偏差，并与
工具 manifest 的声明/观测双栏可视化共用同一套界面。

## 理由

选单次调用而不是节点级，是因为它简单且没有死锁：拿不到就立即返回，从不持有并等待。
节点级租约能减少写入被插入的次数，但代价是节点崩溃后工作区被锁到 TTL 到期，而且需要
心跳维持——这些成本换来的是"构建期间文件不被别人改"，而那个需求由静态检测在启动前就
满足了，不需要运行时的粗粒度锁。

分层的关键在于：**声明能预测大多数冲突，租约能兜住剩下的突发写入。** 只有前者会漏掉
模型临时决定的写入；只有后者会让并行的节点互相等待到不可预测。两者结合才是完整的。

资源类必须分类，因为"写同一个文件"是最容易发现的冲突，"都跑构建"是最常见却最隐蔽的。

## 后果

好的方面：无死锁；并行度高；冲突提示具体；声明可审计。

代价：

- **单次调用租约不保护跨调用的逻辑一致性。** 编辑、构建、再编辑之间可能被插入别人的改动。
  调用方需要接受这一点，或者把这类流程放进声明了独占资源的节点里。
- **静态检测依赖声明质量。** 声明写漏了就只能靠运行时告警发现，属于事后补救。
- **陈旧写校验要求调用方记录"最后读到的哈希"**，这要求读路径与写路径共享一套内容标识，
  否则校验无法进行。
- **严格模式会打断探索型节点。** 因此默认不开启，只给实现型节点用。

需要重新审视的信号：如果实测发现"单次调用租约导致构建结果与编辑不匹配"频繁发生（表现为
构建通过但代码是别人改过的版本），说明需要引入节点级独占，届时应新增一种资源类而不是把
租约粒度整体调粗。

## 被否决的替代方案

**节点级租约，整个节点期间独占工作区。** 这是 w1mer 的"单写者编译独占"的直接落地，语义
最干净。不选的理由是它会锁住不需要锁的时间：节点的大部分时间在推理而非写文件，而崩溃
后的锁死风险与心跳成本都要付。静态检测加单次租约覆盖了同样的目标。

**每次工具调用后重置 TTL 的节点级租约（混合方案）。** 复杂度最高，两套语义并存，且
"什么时候释放"变得依赖外部行为。不选。

**用文件系统锁（flock）替代租约。** 内核级、跨进程、进程退出自动释放，看起来更可靠。
不选的理由是跨平台差异大（Windows 的语义并不同），而且它无法表达"多路径原子获取"与
"拒绝时告诉你是谁占着"——后者需要额外的元数据表，等于又做了一遍租约。

**用数据库事务串行化所有写入。** 简单，但会把写事务与工具执行绑在一起，造成长事务，违反
0002 的纪律（事务绝不跨 IO）。

**启动时阻塞冲突节点，运行时不检测。** 实现最省。不选的理由是它依赖声明完全准确，而模型
会临时决定写别的文件；没有运行时的兜底，冲突就会以"文件被覆盖"的形式静默发生。
