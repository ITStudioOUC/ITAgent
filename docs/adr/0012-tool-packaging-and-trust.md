# 0012. 工具打包与信任链

## 状态

已采纳，2026-10-23。

## 决策

工具不是裸二进制，而是"清单 + 模板 + 二进制"的组合。清单参考 AUR 风格的声明式配置，
写入范围与网络意图写在清单里（见 0010）。

**模板是 ABI，不是可复制的示例代码。** 模板的职责只有三件：把参数与内容回传给执行器、
在执行器确认范围并授予租约后执行真正的二进制、把结果与退出码回传。清单里声明模板版本，
执行器同时支持当前版本与上一版本。模板必须极小、无依赖、可一眼审计完——它是整条信任链
的起点，不能有任何"顺便做点别的"的空间。

**首次安装需要人工批准，批准绑定"工具名 + 版本 + 内容哈希 + 平台"。** 升级时做权限差异
批准：只批新增的权限项，与移动平台的运行时权限同一思路，比每次全量重批可用得多。

**权限分析做双栏**：左栏是清单声明，右栏是沙箱实际触发过的访问与拒绝（来自试运行或历史
运行日志聚合）。差距既是风险，也是作者写错的地方。

**构建沙箱比运行沙箱更严。** 本地编译安装等于执行任意代码，这是整个工具系统里最危险的
环节。默认断网，只允许清单里声明的源；构建输入哈希进最终批准记录。否则运行期沙箱会被
安装期绕过。

**agent 无权自批准。** 提权请求必须由人来确认，这条是硬性规则而非默认行为。

**工具输出遵守固定契约**：标准输出给人看，`--json` 给编排器；截断策略明确；退出码语义
统一。写入类工具返回事实而非散文（路径、字节数、内容哈希、差异统计、快照编号），这些
正好喂给摘要的机器填事实部分。

## 理由

模板作为 ABI 而不是示例，是因为内核的回调协议必然要改。如果清单里贴的是一段需要重新
编译的源码，改一次协议就要重建全部已装工具，而它们是第三方代码，重建不一定成功。

首次批准绑定内容哈希而不是工具名，是因为工具名可以被同名替换。哈希让"批准过的东西"
与"将要运行的东西"是同一个对象。

双栏权限分析的理由：声明是作者的自我声明，不是事实。只展示声明的界面会给人一种"审阅过
了"的错觉，而那正是供应链攻击要利用的心理。

构建沙箱更严，是因为安装期是唯一"声明的权限还没生效"的时刻——代码还没装好，策略还没
绑定，而它正在以完整权限编译。

## 后果

好的方面：权限可读、可批、可审；升级不被全量重批打断；安装期风险被单独处理。

代价：

- **工具作者要写两份东西**（清单与模板），且模板版本要与执行器对齐。
- **双栏分析依赖试运行或历史数据**，新工具首次安装时右栏是空的，价值最低——而它恰恰是
  最需要审查的时刻。因此默认建议在批准前跑一次受限试运行。
- **构建期断网会让部分依赖无法解析**，需要 vendored 依赖或显式声明的源，工具作者体验
  变差。
- **哈希绑定意味着模板小改动也要重新批准。** 这是刻意的摩擦，但会拖慢迭代。

需要重新审视的信号：如果绝大多数工具都只声明最小权限（读工作区、无网络），说明双栏分析
与差异批准过重，可以简化成一次性批准加事后审计。

## 被否决的替代方案

**直接执行裸二进制，权限只写在清单里供人阅读。** 实现最省。不选的理由是没有地方插入
"校验并授予租约"这一步，权限就变成文档而非机制。

**模板可自由编写（每个工具自带一段接入代码）。** 灵活。不选的理由是它把回调协议复制到
每个工具里，协议一改就要全面重建，且每份接入代码都是新的攻击面。

**自动批准，信任包管理器来源。** 体验最好。不选的理由是本地编译安装的包不经过任何签名
流程，来源无法验证。

**只做声明栏的可视化。** 界面简洁。不选的理由是它把"声明"误当成"事实"，而这正是供应链
风险所在。

**每次升级全量重新批准。** 安全边界更强。不选的理由是频繁的小版本升级会让人形成"无脑
点同意"的习惯，反而降低整体安全性；权限差异批准让每次点击都有信息量。
