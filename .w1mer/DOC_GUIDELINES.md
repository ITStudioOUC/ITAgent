# ITAgent 开发文档写作规范

> 适用于 `.w1mer/` 下的全部文档与 `docs/adr/` 下的 ADR。目的：结论可读、可复核，
> 避免术语与数字堆成一团。代码注释规范见 `COMMENT_GUIDELINES.md`。

## 一、总则

| 原则 | 说明 |
|---|---|
| 先结论后数据 | 每条记录开头一到两句白话说明"做了什么、结果如何"，数字与表格放其后。只读开头也能判断要不要细看 |
| 写完整句子 | 用完整中文句陈述；禁止用 `/`、`+`、`→`、`｜` 把多个结论压成一行电报体 |
| 编号只作锚点 | 任务号、ADR 号、提交哈希用于交叉引用，正文用语义描述，不靠编号代替说明 |
| 缩写首现释义 | lease、CAS、WAL、landlock 等可保留原文，但首次出现写明含义；不自造私有简称 |
| 表格可用 | 对比与清单用表格没问题，但每格本身是完整表述 |

## 二、禁止项

| 禁止 | 替代 |
|---|---|
| 电报体：`14 头独占回归 13 修 0 新增` | `修复 13 个独占回归文件，未引入新失败` |
| 黑话链：`str 路径字节 pass 逐位不变` | `字符串路径的字节匹配结果完全一致` |
| 裸数字句：`七 crate 2879/1` | `七个 crate 共 2879 项测试，1 项既有失败` |
| 编号当主语：`05.1 解锁点` | `heredoc 状态机的阻塞点在于分隔符碰撞检测` |
| 全大写与斜杠堆叠：`IO/DB/VM 面` | 写成完整词，必要时首现加括注 |

## 三、结构建议

- 长文档分区：`## 结论` → `## 数据` → `## 风险与遗留`。
- 每条问题按 `现象 → 根因 → 处置` 顺序写，不把三段揉成一句。
- 引用代码位置统一 `文件:行号`；引用提交用七位短哈希并说明它做了什么，不只贴哈希。

## 四、ADR 格式（`docs/adr/NNNN-*.md`）

每份 ADR 固定五段，除"后果"可合并进"理由"外不可省略：

```markdown
# NNNN. <决策标题>

## 状态
提议 / 已采纳 / 已取代（被 NNNN 取代）/ 已废弃，附日期。

## 决策
一段话说清定了什么，随后列出该决定带来的具体约束与机制。

## 理由
为什么这样选。给出取舍依据，不只是好处。

## 后果
好的一面，以及**代价**。再写"什么信号出现时该重新审视"。

## 被否决的替代方案
- <方案>：<为何不选>；<什么条件下重新考虑>。
```

- "后果"里的代价段最容易被省略，也最有价值：它让未来遇到该代价的人知道这是预期内的，
  不是缺陷。
- 写"被否决"时不要写稻草人，要把对方最强的理由写出来再说明为何仍不选。
- 决策变化时新写一份，并在新旧两份的状态里互相指明；**已采纳的记录不再修改正文**。

## 五、ROADMAP 行模板

Task 列写做什么，一行完整句，写清目标与验收口径。Effect 列在完成时写"改了什么 +
结果如何 + 数据在哪"，完整数据放 `.w1mer/performance/` 或 `results/`，行内只留摘要。
Status 只取 `todo` `done` `reviewed` `issue`。

## 六、私有词汇黑名单

以下内部简称禁止出现在落盘产出（含 commit 信息）：

| 禁止 | 替代 |
|---|---|
| 转绿 / 转红 | N 个测试由失败变为通过 / 由通过变为失败 |
| 收口 | 收尾、完成剩余工作 |
| 残面 | 剩余工作 |
| 族（XX 族） | 同根因的一组测试 |
| 面（XX 面） | 一组相关的改动 |
| 锚点 / 锚核 | 对照基准 / 基线 |
| 关卡 / 解锁点 | 前置条件 / 阻塞点 |
| 逐位 | 完全一致（字节级说明"逐字节"） |
| 放行 | 允许通过 |
| 同形 | 同一模式 |
| 止血 | 临时控制影响范围 |
| 落盘 | 写入文件、归档 |

例外：`P0/P1/P2` 允许使用，但每篇文档首次出现时写明含义。

## 七、落盘前自查

1. 开头能否用一句人话概括？不能就重写。
2. 有没有把一串数字当句子？有就展开成完整句或移入表格。
3. 首次出现的缩写是否解释过？有没有自造简称？
4. 对照第六节黑名单扫一遍，命中即改。
