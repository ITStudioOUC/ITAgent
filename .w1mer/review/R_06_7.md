# Review R_06_7

Status: ok

## Conclusion

06.7 的提交把基线加增量 squash 与重定基线写成了计划第四节要求的样子：squash 是独立动词 `Store::squash_if_needed`，保留窗口作参数接收、存储层不硬编码 64，增量达到窗口时一个立即事务里读清单、折叠、先重挂子快照再删父、替换基线条目；重定基线是独立动词 `Store::rebaseline`，自主模式一律拒绝，留痕三列成组写入，基线行只更新不删除。计划第十三条验收全部写成了测试，实现与计划逐条吻合。正确性不靠改动代码自证：squash 与重定基线的立即性来自未改动的 `configure` 里 `set_transaction_behavior(Immediate)`，先重挂后删父的顺序来自未改动的 `0002_content.sql` 里 `parent_id` 的无动作自引用外键，留痕三列的成组与只对基线成立来自未改动的两条 CHECK 约束，超阈值条目原样保留来自未改动的 `0017` 语义。改动代码与这些未改动侧的契约没有冲突。

## 七项具体核对

1. **squash 是独立动词 `Store::squash_if_needed(scope, max_incrementals)`，不折进 06.6 的 `create_snapshot`。** `db.rs` 的 `squash_if_needed`（392 至 403 行）开一个立即事务，调用 `retention::needs_squash` 判定，达到窗口时调用 `squash::merge_in`，再提交。未改动的 `create_snapshot`（337 至 346 行）只调用 `snapshots::create_in`，不调用 squash。`snapshots::create_in`（`snapshots.rs`，未改动）只按链追加——分配 seq、链接父边、插入快照行与清单条目，不删任何快照行、不改写链。因此 06.6 的追加与 06.7 的链改写是两个独立动词，职责分离成立。
2. **保留窗口 64 作参数接收，存储层不硬编码。** `squash_if_needed` 的签名是 `(&mut self, scope, max_incrementals: usize)`，窗口是入参。`retention::needs_squash` 返回 `count as usize >= max_incrementals`，存储层没有 64 这个常量。ADR 0018 要求全部参数有配置入口、不允许以常量散落在调用点；配置结构尚未落地，存储层把窗口作参数接收、由调用方从配置读出后传入，是满足 ADR 的最简做法。测试显式传 64，不依赖存储层常量。
3. **达到窗口时最老两条并入基线，一个立即事务里读清单、折叠、先重挂后删父、替换基线条目。** `squash_if_needed` 开的事务来自 `conn_mut().transaction()`，其立即性由未改动的 `Store::configure` 里 `set_transaction_behavior(Immediate)` 提供，一开就是 `BEGIN IMMEDIATE`。`squash::merge_in` 读基线 B、最老两个增量 I1、I2（按 seq 升序）、I2 的子快照 I3（按 `parent_id` 查），折叠 B、I1、I2 的清单，然后重挂 I3 到 B，再删 I1、I2 的条目，再删 I1、I2 的行，最后替换基线条目。先重挂后删父的顺序由未改动的 `0002_content.sql` 的 `parent_id` 无动作自引用外键强制：若先删 I2 再重挂 I3，外键会拦住整笔（I3 仍指向被删的 I2）。该列注释（35 至 38 行）明确写了这条约定。
4. **折叠是左结合，墓碑删除不能丢，超阈值条目不被折叠覆盖。** `squash::fold` 从空 `BTreeMap<String, SnapshotEntry>` 开始，按链序（基线到目标）遍历每个清单：墓碑删掉该路径，文件与目录覆盖既有。左结合。折叠只覆盖路径、不改条目字段，因此超阈值条目（带 `hash`、`size`、`mtime`、`content_stored = 0`）折叠后原样保留，与未改动的 `0017` 的"超阈值文件只报告，从不删除、从不覆盖"一致。折叠结果只含 file 与 dir，不含墓碑，与 06.6 的条目形状校验对齐（写入路径的 Rust 类型让"墓碑带 content_stored"不可表示）。
5. **重定基线是独立动词 `Store::rebaseline(scope, RebaseRequest)`，自主模式被拒。** `db.rs` 的 `rebaseline`（417 至 426 行）开一个立即事务，调用 `retention::rebaseline_in`，再提交。`rebaseline_in` 第一步 `if req.mode == RebaseMode::Autonomous { return Err(StoreError::RebaseRejectedAutonomous); }`，自主模式一律拒绝。`RebaseMode` 是 `Autonomous` / `User` 枚举，避免布尔的"真值是自主还是用户"歧义。ADR 0006 要求重定基线是独立动词、没有人工确认时默认禁止，自主模式拒绝满足这条。
6. **留痕三列成组写入，基线行就地更新永不删除。** `rebaseline_in` 校验 `by`、`reason`、`confirmed_by` 三列任一为空则返回 `RebaseMissingConfirmation`，整笔回滚。写入时 `UPDATE snapshots SET rebased_by = ?1, rebase_reason = ?2, rebase_confirmed_by = ?3 WHERE id = ?4` 三列同进同出。基线行只更新不删除：`rebaseline_in` 删所有增量（及其条目），删基线条目再插折叠后的有效状态，再 UPDATE 基线行的留痕三列，基线行本身（id、seq、kind、parent_id）永不删除。成组与只对基线成立由未改动的 `0002_content.sql` 两条 CHECK 兜底（`rebase_trail_is_complete` 要求同进同出且非空串，`rebase_trail_only_on_baseline` 要求留痕只对基线成立），存储层写入前的显式校验是友好错误的第一道防线。
7. **十三条验收标准每条都写成测试且通过。** 计划第四节有十三条验收，`tests/squash.rs` 有八条（第 1 至 8 条：空操作、到顶合并、基线条目是折叠结果、有效条目不变、先重挂后删父、跨工作区拒绝、折叠不含墓碑、超阈值保留），`tests/retention.rs` 有五条（第 9 至 13 条：自主模式拒绝、留痕三列成组、缺确认被拒、基线只更新不删除、下一个快照是增量）。8 加 5 等于 13，与计划逐条对应。`squash.rs` 另有三条模块内单测守折叠算法（左结合覆盖加墓碑删除、超阈值保留、结果不含墓碑）。

## Findings

- `squash::merge_in` 的跨工作区校验复用了既有的 `StoreError::CrossWorkspace` 变体，但该变体的 `Display` 文案是"帧引用的会话或节点 {id} 属于另一工作区"，而这里传入的是快照 id，不是会话或节点。测试只按变体匹配（`matches!(err, StoreError::CrossWorkspace(_))`），所以通过，但人读错误信息会被误导。属外观瑕疵，不影响正确性，不阻塞。
- ROADMAP 的 06.7 行描述写"版本推进与文档定稿留待评审与探索者收尾后统一处理"，但已提交的 diff 里版本已从 0.1.38 推进到 0.1.39。版本推进本身符合 AGENTS 第 4 节（一个批次推进一位），ROADMAP 那一句只是略过时的描述，不构成返工。
- 除上述两点外，未发现会让测试通过但语义错的地方。计划风险表里"squash 折进 create_snapshot""保留窗口硬编码""先删父后重挂""重挂不校验跨工作区""折叠写成右结合或漏掉墓碑删除""超阈值条目被覆盖""自主模式不被拒""留痕三列不成组""重定基线删除基线行""重定基线后链不从基线重新开始"十处，实现都按计划的对策落地，且被对应测试钉住。

## 架构影响（供 CHANGES.md）

- `Store` 新增两个公开写动词：`squash_if_needed`（增量数达到保留窗口时把最老两个增量并入基线，窗口作参数接收）与 `rebaseline`（删所有增量、更新基线条目与留痕三列，自主模式拒绝）。快照链的"链改写"从 06.6 的"只按链追加"里分离出来，成为独立职责，与 06.5 把 `get` 收进本批、06.6 把读路径收进本批的裁决同型。
- 新增公开类型：`RebaseMode`（自主与用户发起的枚举）、`RebaseRequest`（留痕三列加发起模式）。新增错误变体：`RebaseRejectedAutonomous`、`RebaseMissingConfirmation`。`lib.rs` 声明 `retention`（公开，导出上述类型）与 `squash`（私有，只暴露 `pub(crate)` 的 `fold` 与 `merge_in`）两个模块。
- 保留窗口 64 从"存储层常量"变成"调用方从配置读出后传入的参数"，是 ADR 0018"全部参数走配置结构"在配置结构落地前的最小落地，配置结构落地后所有调用点跟着换。
- 留痕三列（`rebased_by`、`rebase_reason`、`rebase_confirmed_by`）从 06.2.1 定形的表结构 CHECK 变成有写入路径承接的动词：自主模式拒绝、三列成组写入、基线行只更新不删除，是 0006 的重定基线不可逆与"会话起点基线是硬地板"两条决策在存储层的落地。
