# 压缩提交计划审查

提交 `9195b7e`（加压缩提交计划与原子性前置校验）把压缩的最后一步做成纯函数计划：先校验折叠范围与事实层，再拼帧正文，本身不碰 IO 与数据库，0004 与 0018 第三节"先拿摘要、再一次短事务提交"的划分成立。问题在于计划与 head 令牌之间没有绑定，模块注释声称的第 3 步校验并不存在，四个错误变体里两个不可达；这些恰好是原子性唯一依赖的接缝，因此判 `issues`。

1. 令牌被剥成只含节点（`commit.rs:14` 至 `:20`、`:105`）。`HeadTokenLike` 只要 `node()`，与 `tree.rs:15` 至 `:18` 刚确立的"只带节点会放过回退后重用"直接相反，而这个 trait 也换不来解耦：`HeadToken` 就在同 crate 的 `context::tree`。真实风险在提交时——`CommitPlan` 只存 `parent: NodeId`（`:24` 至 `:37`），不存代次，server 端可以拿计划算出后重新读到的令牌做 CAS，两者节点相同、代次不同即通过，"基于旧 head 算出的覆盖段"就这样被写上树。应让计划携带完整令牌（或至少代次与会话），并让 CAS 比对的正是计划里那一个。
2. 注释声称的第 3 步不存在（`commit.rs:77`、`:103` 至 `:104`）。`FoldPlan` 没有父节点字段，`parent` 直接取 `head.node()`，"无法校验覆盖段止于该 head"的坦白是对的，但那样 `HeadMismatch`（`:48` 至 `:54`）永远构造不出来，是死代码，测试里也确实没有一条覆盖它。同一个洞里还有 `BadSummary`（`:43`）：入参已是解析通过的 `CompressOutput`，`plan` 无从复验，该变体同样不可达。要么删掉这两个变体，要么把校验做成真的——见下条。
3. "覆盖段止于 head"应由内核强制，而不是留给调用方。`Tree` 与祖先链都在内核里且是纯的，`plan` 完全可以接收 `history: &[Node]`（或 `&Tree`）并按 `fold` 反查：`covered` 必须是 `head` 祖先链的一段前缀、`covered` 与 `kept` 不重叠、`kept` 的起点确实是覆盖段之后。现在的签名让 `FoldPlan.kept` 完全没被使用（`:98` 至 `:118`），于是"同一件事以摘要与原文两种版本同时出现"（0004）与 `input.rs:112` 至 `:114` 明确留给提交阶段的检查都无人承接。
4. 两个"父"没有一致性检查。`parent` 来自计划时的令牌，提交时的令牌由调用方另给，类型上不约束二者同源；`CommitPlan::check(&HeadTokenLike)` 这类入口能把 `HeadMismatch` 变成可达并让调用方无法漏检，比在文档里写"必须用同一个令牌"（`:88` 至 `:89`）可靠。
5. 格式与 `resolve` 侧匹配，无需解析回读：`frame_text`（`resolve.rs:206` 至 `:212`）只是把 `summary` 原样嵌入并追加"覆盖 N 个节点"，散文已由 `format.rs:160` 去空白，拼接后不会产生歧义。两处小瑕疵：`Facts::render` 末尾带换行（`facts.rs:163` 至 `:165`），拼接后帧正文以空行收尾，追加说明前会多一个空行；事实段里的"覆盖轮数"（`facts.rs:163`）与 `frame_text` 的"覆盖 N 个节点"是两个不同口径的计数，却用同一个词，建议后者改称"节点数"。
6. 用例缺口（`commit.rs:120` 至 `:229`）。`事实层不完整时不出计划`（`:185` 至 `:192`）只用名字表达了"head 不变"，这在纯函数签名下已是能表达的极限，可以接受；但没有一条用例固定"先查折叠范围、再查事实层"的顺序（传空覆盖加坏事实应得到 `EmptyFold`），而 `:80` 至 `:82` 把顺序写成了契约；也没有一条用例让计划与令牌不一致，`HeadMismatch` 因此始终是零覆盖的死契约。
