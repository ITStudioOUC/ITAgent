# Review R_07_4

Status: ok

## Conclusion

07.4 的已提交工作满足验收口径：能力集是 unit 就绪状态的投影，`build_capability_set` 是纯函数把 `units` 表读出的 unit 状态投影成能力集（`ready` 进就绪列表，`degraded` 与 `failed` 进降级列表，两列表按标签排序），`CapabilityWatcher` 持 `Store` 句柄，`subscribe` 注册订阅者并立即推送完整能力集，`notify_change` 读表重建、版本号递增、向全部订阅者推送带版本号的完整能力集。十条验收全部写成测试并通过，全仓测试从 449 项增至 461 项（新增 12 项）。计划第八节的四处裁决逐条守住：能力集读 `units` 表不读内存状态，版本号是进程内计数器不落库（本批零新增迁移），推送走进程内 watch 通道不引入 tokio，工具目录追加不混进本批。结论 ok。

## Findings

### 验收口径核对：十条验收全过，461 项测试全绿

- 能力集是 unit 就绪状态的投影。`build_capability_set_projects_unit_states` 钉住：`store` 为 `ready` 进就绪列表，`model` 为 `degraded`、`telemetry` 为 `failed` 都进降级列表。投影对 `UnitState` 的三值域是全的——`ready` 进就绪，`degraded` 与 `failed` 进降级，无遗漏值。若投影丢弃 `failed`，该测试与七 unit 拓扑测试都会失败。
- 订阅者先收完整能力集。`subscribe_pushes_full_capability_set_at_version_zero` 钉住：订阅后第一条消息是完整能力集（`ready` 是 `[store]`、`degraded` 是 `[model]`、版本 0），不是增量。若首次推送只推变更，该测试失败。
- 降级后收带版本号的增量。`notify_change_pushes_version_incremented_set` 钉住：把 `model` 从 `degraded` 改成 `ready` 后调 `notify_change`，第二条消息版本号是 1，能力集反映新状态（就绪列表 `[model, store]`、降级列表空）。
- 版本号单调递增。`version_is_monotonically_increasing` 钉住：连续两次 `notify_change`，版本号从 0 增到 1 再增到 2，严格递增不回退不重复。若版本号不递增（每次都推版本 0），该测试失败。
- 就绪与降级区分。`ready_and_degraded_lists_are_disjoint` 钉住：`store` 在就绪列表、`model` 在降级列表，`store` 不在降级列表、`model` 不在就绪列表，两列表不相交。
- 失败 unit 计入降级。`failed_unit_counts_as_degraded` 钉住：`model` 为 `failed` 时进降级列表，不是丢弃。
- 能力集变更推送给已连接客户端。`all_subscribers_receive_the_push` 钉住：注册两个订阅者后调 `notify_change`，两个订阅者都收到推送（各两条消息）。若只推第一个订阅者，该测试失败。
- 推送与工具目录追加是同一套机制。`channel_carries_generic_capability_update` 钉住：通道消息是通用的 `CapabilityUpdate` 枚举，能力集变更是其中一种消息。07.4 只实现能力集，工具目录追加留到工具系统批次，但通道抽象让"同一套机制"成立。
- 七 unit 最小拓扑能力集。`seven_unit_minimal_topology_capability_set` 钉住：必需 unit（`store`、`router`、`ipc`、`lease`、`tools`）全部 `ready` 进就绪列表（按标签排序 `[ipc, lease, router, store, tools]`），`model` 为 `degraded`、`telemetry` 为 `failed` 都进降级列表。
- 能力集读 `units` 表。`capability_set_is_rebuilt_from_units_table` 钉住：直接改表（`store` 从 `ready` 改成 `degraded`）后调 `notify_change`，能力集跟表走（就绪列表 `[model]`、降级列表 `[store]`），不是读内存状态。若 watcher 缓存内存状态，该测试失败。
- 另两项补充测试：`empty_records_yield_empty_capability_set` 守住空记录得空能力集且版本号原样保留；`capability_set_output_is_sorted_by_label` 守住输出按标签排序、不随输入顺序变化。

### 四处裁决逐条守住

- 能力集读 `units` 表不读内存状态。`CapabilityWatcher::new` 与 `notify_change` 都调 `Store::read_all_unit_states` 读表重建，不读内存。`capability_set_is_rebuilt_from_units_table` 直接改表验证能力集跟表走，让"server 重启后恢复能力集"成立。
- 版本号是进程内计数器不落库。`CapabilitySet.version` 是 `u64` 进程内计数器，`notify_change` 用 `self.set.version + 1` 递增。本批零新增迁移，`Cargo.lock` 只有版本号推进（0.1.44 到 0.1.45），无新增 `[[package]]`。
- 推送走进程内 watch 通道不引入 tokio。`watch.rs` 无 `tokio`、无 `async`、无 socket、无网络，是同步进程内通知。`Subscriber` 是 `Box<dyn FnMut(&CapabilityUpdate)>`，无 `Send`/`Sync` 约束，纯单线程。
- 工具目录追加不混进本批。`CapabilityUpdate` 是单变体枚举（`CapabilitySet`），是通用的能力变更消息包装，工具目录追加以后在同一通道上加为第二种消息，机制相同。07.4 只实现能力集，不实现工具目录追加本身。

### 依赖、建表、纯净门核对

- 07.4 零新增依赖：`Cargo.lock` 只有版本号推进（0.1.44 到 0.1.45），无新增 `[[package]]`。`ita-server` 的 `Cargo.toml` 不动，`capability.rs` 与 `watch.rs` 只用 `std` 与既有 `ita_store` 的 `UnitState`、`Store`、`UnitId`。
- 不碰 `ita-store`：`units` 表与 `read_all_unit_states` 是 07.3 产出，07.4 只消费，不新增迁移、不改 store 操作。
- 能力集落 `ita-server` 的 `units` 模块，不进内核、不与 `ita-workflow` 混用。`CapabilitySet` 与 `CapabilityWatcher` 是独立类型，不复用工作流节点类型，守住 ADR 0013 的"两套监督语义靠文档与类型分开"。
- 内核纯净门与分层门通过：`ita-kernel` 无依赖，`ita-server` 的 `ita-*` 依赖边不变。版本推进 0.1.44 到 0.1.45 是批次计数器推进，落在 `batch-end` 前最后一次提交，符合 AGENTS.md 第 4 节。

### 架构影响注记

- 本批新增 `capability.rs` 与 `watch.rs` 两文件，`units` 模块契约扩大：从拓扑、状态机、探针、监督者、启动计划、启动门，加上能力集快照（`capability`）与能力变更推送（`watch`）。`mod.rs` 声明两模块并再导出 `CapabilitySet`、`build_capability_set`、`CapabilityUpdate`、`CapabilityWatcher`，模块头注释同步更新。
- `units` 表契约（07.3 产出）现在被能力集消费：表的三值域（`ready`/`degraded`/`failed`）是能力集快照的输入。store 契约未动，只是多了一个消费者。
- ADR 0013 的"能力集合的变化推送给已连接的客户端"与"能力集合的推送与工具目录的追加通知是同一套机制"现在落地为进程内 watch 通道；真实 socket 推送是 08.2 的事。ADR 0014 的"执行器是独立进程，不是 server 内的 unit"守住：能力集只投影 server 内部 unit（`store`、`router`、`ipc`、`lease`、`tools`、`model`、`telemetry`），不含执行器。
- 未动的契约：`topology.rs`、`state.rs`、`probe.rs`、`supervisor.rs`、`activation.rs`、`plan.rs` 六个文件 07.1 至 07.3 产出，07.4 只消费 `UnitId` 与 `Store::read_all_unit_states`，不修改。

### 非阻塞观察

- `subscribe` 的文档注释写"立即推送当前完整能力集（版本 0）"。构造时订阅版本确实是 0，但 `notify_change` 之后订阅，推送的能力集版本大于 0。这是计划自身的措辞，行为（推送当前完整能力集）正确，不是语义错误。属文档小疵，不阻塞。
- `build_capability_set` 用 `UnitId::new(...).expect(...)` 在非法标签时 panic。这与 store 的文档化不变量一致（unit 标识是校验过的标签），是对被破坏不变量的防御性断言，不是缺陷。若未来某路径写入未校验标签，能力集构建会响亮地 panic，可接受。

### 结论

state 置 `ok`。十条验收全过，461 项测试全绿，四处裁决逐条守住，依赖与纯净门保持。两处非阻塞观察不阻塞验收。
