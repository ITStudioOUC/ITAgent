## Findings

### 验收口径核对：十条验收全过，449 项测试全绿

- 计划与拓扑交叉校验：`StartupPlan::validate` 用 `topology.startup_order()` 取全部 unit，计划里的每个 unit 必须在拓扑里（幽灵 unit 被拒），必需集非空，必需集与非必需集不相交。六个测试覆盖合法计划、幽灵 unit、空必需集、两集相交、空计划、七 unit 最小拓扑计划。
- 启动门是纯函数：`activate(supervisor, plan) -> ActivationResult` 不写库、不转移状态，只判定。必需 unit 状态 `Ready` 计入就绪列表，`Starting`/`Failed` 计入未就绪列表，`NotStarted` 不计（被依赖阻塞，不是根因）；非必需 unit 状态 `Failed`/`NotStarted`/`Starting` 计入降级列表，`Ready` 不计。未就绪列表为空返回 `Ready`（带降级列表），否则返回 `NotReady`（带未就绪列表）。
- 就绪不等于运行：门只认 `Ready` 不认 `Starting`，`ready_is_not_running` 测试守住这条分界。
- unit 状态落库：`0003_units.sql` 建 `units` 表（`id TEXT PRIMARY KEY`、`state TEXT NOT NULL CHECK (state IN ('ready','degraded','failed'))`、`updated_at INTEGER NOT NULL`），只加不改，`CREATE TABLE IF NOT EXISTS`。`units.rs` 提供 `set_unit_state`（upsert）、`read_unit_state`（不存在返回 `None`）、`read_all_unit_states`（按标识排序）。七个测试覆盖写入读回、读不存在、覆盖写入、读全部排序、空库、字符串形式、非法状态被拒。
- 测试计数自洽：07.2 收尾 430 项，本批新增 19 项（plan 6、activation 6、units 7），合计 449 项，与 ROADMAP 记载一致。`migrate.rs` 的版本断言从 2 推进到 3，`first_migration_creates_tables_and_records_version`、`migrations_are_idempotent`、`newer_database_is_rejected` 三处测试同步更新，`repeated_sql_is_idempotent` 补 `MIGRATIONS[2]`。

### 偏差一：telemetry 改 `Failed` 终态防 `run_until_blocked` 无限循环

- 验收测试 10 原说 telemetry 返回 `NotReady`，但监督者 `step()` 按启动顺序遍历，第一个 `NotStarted`（全部依赖就绪）或 `Starting` 的 unit 被处理即返回。七 unit 最小拓扑的启动顺序是 `[model, store, router, ipc, telemetry, tools, lease]`（`seven_unit_minimal_topology_is_acyclic` 测试钉住），telemetry 在 tools 与 lease 之前。telemetry 保持 `Starting`（探针 `NotReady`）时，`step()` 每步先碰到 telemetry 重探针并返回，tools 与 lease 永远启动不了，`run_until_blocked` 永不终止。
- 实现者把 telemetry 改成 `Failed`（终态）而非 `NotReady`（`Starting`）。`Failed` 是终态，`next(Failed, Start)` 返回 `None`，监督者不重启、不重探针，`tools` 与 `lease` 能推进到就绪，`run_until_blocked` 终止。
- 验收测试 10 的语义仍然成立：断言是 `Ready` 且就绪列表是全部必需 unit、降级列表是 `[model, telemetry]`。telemetry 改 `Failed` 后，`activate` 对非必需 unit 的 `Failed` 状态计入降级列表，断言不变。`Failed` 是终态，依赖 telemetry 的 unit（本拓扑无）不会启动，但 telemetry 是孤立 unit，无依赖者，语义不受影响。
- 非必需 unit 的 `Starting` 计入降级由 `optional_not_ready_counts_as_degraded`（验收测试 4）单独覆盖，覆盖不丢失。实现者在测试注释里写明了改法理由，可复审。
- 此改法是绕开而非修复 `run_until_blocked` 无步数上限的既有问题，该既有问题不阻塞 07.3 验收，已单独汇报编排者。

### 偏差二：`NotStarted` 必需 unit 不计入未就绪

- 计划 2.2 说「所有非 `Ready` 的必需 unit 进未就绪列表」，但验收测试 1 说 `NotStarted` 必需 unit 不计（`router` 与 `ipc` 因依赖未就绪保持 `NotStarted`，不计入未就绪列表，它们是 `NotStarted` 不是 `Ready`）。实现者跟随验收测试 1。
- 裁决自洽：未就绪列表承载根因 unit（`Starting` 进程活着未就绪、`Failed` 终态失败），`NotStarted` 是被依赖阻塞的传递性 unit，不是根因。验收测试 1 的断言 `NotReady { not_ready: [store] }` 只列 `store`（`Starting` 根因），`router` 与 `ipc`（`NotStarted` 传递阻塞）不列，语义一致。
- 边界未守住：全部必需 unit 都是 `NotStarted` 时，`activate` 返回 `Ready` 加空 ready 列表。这个边界没有测试直接覆盖（验收测试 1 的 `store` 是 `Starting` 不是 `NotStarted`，所以未就绪列表非空）。该边界只在监督者从未被驱动时可达（全部 unit 未启动），server 会先驱动监督者再调 `activate`，属调用方责任而非门缺陷。风险等级低：不影响 07.3 验收，但语义上「全部 `NotStarted` 返回 `Ready` 加空 ready 列表」略反直觉，建议后续批次补一个测试守住这条边界或在门里显式处理。
