# 折叠范围审查

提交 43b0458 新增 `fold::plan`，按用户消息切轮、保留最近若干轮、覆盖段与保留段不重叠，主路径正确。但"一轮"在 crate 内存在两份互斥定义，`plan` 的步骤注释与实现相反，且历史头部不属于任何一轮的节点会被静默压进摘要，因此判 issues。

1. 「轮」有两份互斥定义（`compress/fold.rs:5`、`context/node.rs:161` 至 `:163`）。`fold` 以用户消息开启一轮，`Node::opens_turn()` 以助手消息开启一轮，后者自测还断言 `assert!(assistant.opens_turn())`（`node.rs:251` 至 `:253`）。用户消息这一侧对：以助手为界会让保留段从回答开始，而它对应的用户输入留在摘要里（`fold.rs:9` 至 `:11` 的理由成立）。`opens_turn()` 目前没有生产调用点，改它成本为零；建议改成用户消息并让 `plan` 调用它，而不是在 `fold.rs:77` 至 `:84` 再写一份 `matches!`，否则两者必然再次分叉。同时 `fold.rs:54` 的步骤 1 仍写"起点（助手消息）"，与同文件 `:5`、`:59` 相反，属旧定义残留，按注释复核会得出另一个结论。

2. 轮数恰好等于 `keep` 的处置是隐式的（`fold.rs:87` 至 `:97`、`:60` 至 `:61`）。判据不是"轮数必须大于保留数"，而是 `turn_starts.len() < keep` 再加"首个用户消息恰好落在下标 0"。以用户消息开头时返回 `NotEnoughTurns`，与注释一致；头部一旦有非轮节点，`keep_from > 0`，同样输入返回 `Ok` 且覆盖段只含那几个节点头。更麻烦的是调用方分不清"压完了"与"历史太短"：`found == keep` 该视为无需压缩，而 `Err` 在 0004 的流程里意味着可重试，会白跑一次压缩调用。建议参照 `trigger.rs:13` 至 `:40` 的三分支，把"没有可压的部分"拆成独立变体或返回 `Ok(None)`。

3. 不属于任何一轮的节点头会被压进摘要（`fold.rs:56`、`:99`）。`history[..keep_from]` 无条件覆盖起点之前的一切，其中可能包括 `FixedLayer` 与 `Todo`：0018 第三节要求固定层在压缩时点按当时状态重建，`node.rs:82` 至 `:84` 明说待办要原样保留而不能被摘要掉。这两类进了 `Frame.covers` 后，04.4 的 `resolve` 会让它们从 `recent` 与 `current` 段消失（`resolve.rs:226`），漂移说明与待办一并丢失。另外 `history` 是否允许含上一次压缩产生的 `Frame` 节点没有写明，覆盖旧帧与覆盖原文是两种语义；`kept` 也被定义为单一列表，而四段结构要求把它拆成最近轮次与当前待办两段。建议在 `plan` 里显式分类头部节点：固定层与待办跳过或拒绝，`Notice` 与 `Frame` 写清归属。若 05.6 直接把 `kept` 当作 `ResolveInput.recent`，待办就会被贴上最近轮次段标签——`resolve.rs:217` 至 `:219` 已说明段标签不能按节点类型推断，出现即说明本条已发生。

4. `found` 的饱和处理不影响判定，但有两处失真（`fold.rs:86`、`:73`）。超过 `u32::MAX` 需要四十亿个节点，物理上不可达，比较又走 `usize`，所以 `unwrap_or(u32::MAX)` 只引入一个测不到的哨兵值，字段改用 `usize` 即可去掉。真正的失真在 `keep == 0` 分支：那里硬写 `found: 0`，历史里明明有若干轮，诊断会误报成空历史。

5. 用例的辅助函数与两处断言有缺陷（`fold.rs:112` 至 `:117`、`:218` 至 `:227`、`:203` 至 `:213`）。末两位编码足以支撑四轮十二个节点，这是测试辅助函数的量级，不是设计问题。缺陷在别处：`工具节点不开启新轮` 的第二轮同时写了 `user(0)` 与 `assistant(0)`，两个节点 id 相同，真实树会以 `DuplicateNode` 拒绝（`tree.rs:174`），而该用例只断言长度所以照样通过；注释"第一轮的十一个节点里九个被覆盖"把整个历史的节点数当成了第一轮的节点数，第一轮实为九个。`保留段总是以用户消息开头` 断言的是实现自己切出的下标，属自证，抓不到"保留段从一条失去对应提问的助手回复开始"这个真实风险。
