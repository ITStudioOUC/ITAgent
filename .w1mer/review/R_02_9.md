## 逐项核对

1. **MSRV 改写等价**。`crates/ita-kernel/src/context/input.rs:124-128` 的嵌套与原来的 let-chain 短路一致：`frame.checkpoint` 为 `None` 时内层不执行，`checkpoint` 的借用只在内层 `if` 里使用；外层遍历 `self.frames` 与内层读取 `self.checkpoint_facts` 都是不可变借用，不存在作用域变化。`crates/ita-store/src/migrate.rs:139-143` 同理，`&Option<String>` 的 match ergonomics 让内层 `recorded` 绑定为 `&String`，与链式右操作数是同一个值。更关键的是两侧行为都被既有测试钉住：`input.rs:248-257` 同时断言"缺事实被拒"和"补上事实通过"；`migrate.rs:250-258` 断言哈希不一致被拒，`migrate.rs:221-232` 的重复迁移覆盖哈希一致的分支，`migrate.rs:260-272` 插入 NULL 哈希覆盖 `None` 分支。这三处测试本批一字未改，所以改写若把条件写反，测试阶段先红，不会等到 MSRV job。

2. **其它 1.88+ 语法与 API**。在 `crates/` 下检索 `&& let`、行首 `&&`、`while let` 以及 `is_none_or`、`pop_if`、`extract_if`、`split_once`、`take_if`、`trim_ascii`、`#![feature]` 均无命中；`crates/ita-kernel/src/command/ast.rs:145-149` 的行首 `&&` 是普通布尔续行，不是 let-chain。`cargo check --all-targets` 会编译 lib、bin、test、bench、example 与构建脚本，1.85 下任何更新的语法或 API 都会在那里失败（主 Agent 实跑退出 0）。唯一没被 `cargo check` 覆盖的是 doctest：当前 0 份，等第一份 doctest 出现时需要把 `cargo +1.85.0 test --doc` 补进 msrv 阶段，否则覆盖会静默缩小，见可选中 doctest 一条。

3. **`verify.sh` 的阶段契约**。`all` 等于 fmt 加 lint 加 test，msrv 单列，脚本头 `:1-12`、AGENTS 第 2 节、`STACK.md:8-9`、`README.md:102-103` 与详情文档 `:80` 的说法一致。未知阶段走 `:92-95` 的 `*)` 分支退出 2。失败传播成立：四个 stage 函数内部都是简单命令序列，`set -euo pipefail` 会让任一命令失败立刻退出，函数在 `case` 里作为简单命令调用，返回值不再被吞；`if ! version=$(...)` 与 `if ! command -v ...` 两处显式处理了预期失败。`cd "$(git rev-parse --show-toplevel)"` 在任何相对路径之前执行，`bash .w1mer/scripts/*.sh` 与各门的路径都相对仓库根，从子目录调用与 CI checkout 都成立。shellcheck 缺失时直接 `exit 1` 并打印安装命令，`SHELLCHECK` 可指向自定义二进制，单轨与"本地不得比 CI 松"的原则一致。

4. **`--metadata` 入口**。参数解析在 `check_layers.sh:27-40`，`cd` 在 `:53` 的 else 分支内，因此 `--metadata` 模式完全不依赖当前目录，符合详情文档 `:74` 的裁决。校验要求 `packages` 的 id 集合等于 `workspace_members`：真实的 `cargo metadata --no-deps` 只输出 workspace 成员，所以对真实路径不过严；传全量 metadata 会多出第三方包而被拒，对入口用途也不过松。正常路径只是把 `cd` 从脚本开头移到分支内，`cargo metadata` 的调用、`--locked` 与 stderr 原样诊断都保留（`:52-62`），行为没有变化。metadata 文件不存在退出 2，坏 JSON 由 `:69-73` 的 `except (OSError, JSONDecodeError)` 转成统一诊断；缺 `packages` 或 `id` 键是唯一没接住的输入，见可选第二条。

5. **门自测的约束力**。自测先用真实 `cargo metadata --no-deps` 生成基线并 `expect_pass baseline`（`:118`、`:154`），门整体坏成恒拒会先在这里红。十条失败样本覆盖普通、dev、build 的 `ita-*` 边，能力越权，改名依赖，反向 `ita-cli`，未登记二进制，未登记成员，陈旧成员，以及 `packages` 与 `workspace_members` 不一致；三条对照是基线加 dev、build 能力放行；一条错误路径是 metadata 文件不存在。断言匹配的是带 crate 名或固定短语的关键词，不是"任意非零退出"，所以门换错错误来源也会红。`rename` 样本构造正确：cargo metadata 的 `dependencies[].name` 是真实包名、`rename` 是别名，脚本按 `name` 判定，样本照此构造，删掉这条识别会被 `renamed_edge` 抓到。反证（`:182-191`）不是恒真：若 sed 没删掉那行，被改脚本仍会拒绝越权样本，测试报 FAIL；若门被改成恒绿，前面的失败样本与基线会先红。真实清单新增成员时，按流程登记允许表后基线仍通过，合成样本按包名查找也不受影响；未登记的新成员会让真实门与基线同时失败，这是预期行为，不是误报。

6. **CI 接线与假绿路径**。四个 job 与其安装项逐一对上：fmt 装 rustfmt 后跑 `verify.sh fmt`；lint 装 clippy，并在 runner 缺 shellcheck 时补装，然后跑 `verify.sh lint`；test 装 nextest 后跑 `verify.sh test`；msrv 装 1.85.0 后跑 `verify.sh msrv`。`dtolnay/rust-toolchain@1.85.0` 是按版本引用的合法用法，装的是 1.85.0 而不是 stable；即使 action 只把 1.85.0 设为默认工具链、仓库的 `rust-toolchain.toml`（`channel = "stable"`）在 rustup 解析时优先，`verify.sh msrv` 的两处 `+1.85.0` 与版本断言仍会把 job 钉在 1.85 上，不存在静默跑 stable 的假绿。`cargo doc` 用的是 rustc 组件里的 rustdoc 二进制，不依赖 `rust-doc` 文档组件，lint job 的 minimal profile 足够。`concurrency` 只在 PR 上取消（`:13`），main 推送保留完整记录；三处缓存的 `save-if` 都限定 main，PR 只读不写。未发现假绿路径：nextest 缺失时 `cargo nextest` 直接失败，clippy 缺失时 clippy 阶段失败，msrv 阶段有版本断言兜底。`actions/checkout@v4`、`Swatinem/rust-cache@v2`、`taiki-e/install-action@v2` 都是当前有效的引用。

7. **OxideJs 取舍**。与当前规模匹配：261 项测试约半秒、构建数秒，sccache、mold、测试分片与 ASan 的收益要等构建或测试进入分钟级才成立；`cargo deny` 需要外部 advisory 数据库，单独批次更合适。采纳的三项里，独立 MSRV job 价值最高，因为它把一个只写在清单里的声明变成了每次推送都验证的约束；只在 PR 上取消旧 run 与本仓按批推送的节奏相符；test job 内部先 build 再 nextest 已经共享编译产物，不需要 `needs`。没有发现该学却漏掉的低成本项；若要补，优先给 shellcheck 与 cargo-nextest 固定版本，以及补 doctest 的 MSRV 覆盖，两者都不需要新 job。

8. **文档一致性**。AGENTS 第 2 节、`STACK.md`、`verify.sh` 与详情文档 `:80` 的阶段清单一致；`--locked` 口径准确，build、clippy、doc、test 带锁，fmt 不带，`STACK.md:36-38` 写对了这一点。没有把"校验过"写成"验证过"的夸大：README 与 STACK 只陈述命令与 job 结构，实测数字只出现在详情与复审里，本复审也没有把主 Agent 的运行结果写成自己的实测。唯一的偏差是 HANDOFF 里调用脚本的 job 数量过时，见可选第一条。`Cargo.toml:20-22` 的注释说清了 1.85 是 edition 2024 的起点、let-chains 1.88 才稳定、msrv job 用 1.85.0 跑全目标检查，措辞准确。

9. **提交与版本**。两条提交信息都符合 AGENTS 第 3 节：类型 `docs` 与 `ci`，无 scope 前缀，无 `｜`，无 ROADMAP 或 ADR 编号，无提交哈希，无测试计数，主题写的是改了什么。`1365a86` 同时改了 CI、脚本、两处 Rust 源码与一处文档链接，但都服务于"让 MSRV 声明成立并把验证入口收拢"这一个目的，`ci` 类型成立；源码改写没有单独出现在主题里，第 3 节允许细节留在 `.w1mer/`。版本方面 `Cargo.toml:18` 仍是 `0.1.30`，本批是同史诗内的一个批次，收尾时应当用 `bump_version.sh batch` 推到 `0.1.31`，且必须是 `batch-end` 前的最后一次提交，见"批次收尾"。

- **`--metadata` 缺键只给 Python traceback（严重度：低）**。位置 `.w1mer/scripts/check_layers.sh:75-77`。`packages = meta["packages"]` 与 `package["id"]` 直接取键；文件不存在与坏 JSON 都有明确诊断（`:47-50`、`:69-73`），但 JSON 合法而缺少 `packages` 键、或某个包条目缺少 `id` 键时，Python 以 `KeyError` traceback 退出。退出码仍非零，不会造成假绿，只是诊断信息不符合入口约定。修法：用 `meta.get("packages")` 并校验它是列表、`package.get("id")` 校验存在，或顶层接住 `KeyError` 转成"分层门失败：…"；若补样本，详情文档 `:59` 的用例计数同步更新。
- `.github/workflows/ci.yml:41` 的 lint job 名称仍是"分层、纯净门与 clippy"，实际还包含门自测、shellcheck 与 rustdoc。只影响 CI 界面展示，改不改都不影响门禁，触碰该文件时可以顺手统一。
- `.w1mer/scripts/verify.sh:37-45` 的 shellcheck 可用性检查排在纯净门之后，而纯净门会跑 `cargo clippy -p ita-kernel` 编译内核。把这条检查挪到 lint 阶段最前面能让"缺工具"在编译前失败，行为正确，只是失败不够快。
- `.w1mer/scripts/check_layers_test.sh:145` 与 `:174` 用 `printf | grep -qF` 判定命中，`pipefail` 下若输出长到超过管道缓冲、`grep -q` 提前退出，写端会拿到 SIGPIPE 并被误判成"未命中"。现在的错误文案都远小于缓冲，不会触发；改成 `grep -qF -- "$needle" <<<"$output"` 更稳。
- `.w1mer/scripts/check_layers_test.sh:184` 的反证依赖 sed 精确命中 `"rusqlite": {"ita-store"},` 这一行。格式一变就删不掉规则，测试会以"删掉规则后仍然拒绝"的红脸报错，方向是安全的，但信息容易误导；用 Python 改常量更稳。
- 自测只覆盖 `--metadata` 路径，默认路径的回归由 `verify.sh lint` 先跑一次真实门兜住，单独运行 `check_layers_test.sh` 时没有覆盖。若要补，加一个不带参数的 `expect_pass` 即可，代价是每次多跑一次 `cargo metadata`。
- `verify.sh --help` 会被当成未知阶段退出 2。脚本头已经写了用法，不影响使用；若希望帮助以 0 退出，在 `case` 里单独处理一行即可。
- `verify.sh msrv` 只跑 `cargo check --all-targets`，不编译 doctest。当前 0 份 doctest，所以没有暴露；等第一份 doctest 落地时，msrv 阶段应补 `cargo +1.85.0 test --doc`，否则 MSRV 覆盖会静默缩小，而 CI 从外面看不出来。
