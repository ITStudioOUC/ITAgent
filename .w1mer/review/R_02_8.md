# 分层与能力归属门审查

Status: ok

## 结论

提交 `4c4f472` 把依赖方向、能力归属与单二进制形态变成了可执行门，脚本声明的三件事与它实际检查的内容一致；允许表与当前十一份清单逐项吻合，`ita-tools` 依赖 `ita-sandbox`、`ita-proto` 依赖 `ita-model` 两处裁决成立，也没有发现会阻塞后续史诗的过严边。需要修的是两类：脚本注释把 ROADMAP 编号当理由，违反注释规范；`cargo metadata` 失败时只报一句通用提示并丢弃 cargo 的原始诊断，还把"锁文件不一致"写成唯一原因。另有四处严重度低但真实存在的偏差，见问题三至问题六。门的设计与规模本身不需要重构。

## 逐项核对

1. **依赖方向**。`check_layers.sh:139-166` 遍历 `cargo metadata` 里每个成员的直接依赖；`dep_name in members` 的分支不区分种类，因此 `ita-worker` 注入 `ita-store` 的普通依赖与 dev 依赖都会失败，错误信息同时给出该 crate 允许的集合。允许集合只约束 `ita-*` 边，第三方 crate 不在此列，与头注释一致。当前十一份清单都是允许表的子集（`ita-store` 依赖 `ita-kernel`，`ita-server` 依赖 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow`，其余成员依赖为空），基线应通过。

2. **能力归属**。`check_layers.sh:159-166` 只对种类为普通的依赖生效，这与计划文档第 32 行的边界一致。`cargo metadata` 对普通依赖给 `kind: null`，代码用 `or "普通"` 归一后再比较，判断在当前 cargo 上成立；改名依赖（`package = "..."`）的 `name` 仍是真实包名，所以不能靠别名绕过。空的归属集合会静默跳过，见问题三。

3. **二进制形态**。`check_layers.sh:168-182` 用 `"bin" in target["kind"]` 收集产物，`src/bin/*.rs` 这类自动发现的目标同样会出现在 targets 里，不能靠新增文件绕过；集合双向比较，新增、改名、删除都会被指出。当前集合只有 `(ita-cli, ita)`，与 `crates/ita-cli/Cargo.toml:9-11` 一致，且 `ita-cli` 没有 `src/lib.rs`，所以任何 crate 都无法以库的形式依赖它，`:146-150` 那条特殊分支只是为了错误信息更清楚。

4. **成员与允许表双向一致**。`check_layers.sh:123-136` 做了成员差集、允许表键差集与能力归属人的成员校验，三处都能指出陈旧条目。当前 `Cargo.toml:3-15` 的十一个成员与允许表的十一个键完全对应。

5. **两处裁决**。两条边都不成环：`ita-sandbox` 只依赖内核，`ita-model` 只依赖内核，反方向也没有出现在表里。`ita-tools` 需要 `Sandbox` trait 来跑构建沙箱（ADR 0012 的安装期隔离），`ita-proto` 需要归一化消息类型来承载代理帧与流式转发（ADR 0008 的两层分工），都与目标职责相容。没有发现阻塞 06 至 16 的过严边：存储层的 CAS 与快照只用到未设限的第三方 crate；server 可以经由 `ita-tools` 拿到 `probe` 结果，不需要直接依赖沙箱；worker 的上下文与工具目录由 server 组装后按协议下发，不需要依赖 `ita-tools`。也没有发现会让不变量失守的过松边：`ita-proto` 依赖 `ita-model` 只是让协议层的使用方在构建面上多带一个纯类型 crate，模型层自身的依赖仍只允许内核，带不进数据库、网络或沙箱能力；`ita-cli` 允许全部十个库 crate 是组合根的定义；`ita-server` 允许 `ita-tools` 不越过单写者，server 本来就是唯一的写者。两处需要留意但不算缺陷：若将来改由 worker 自己渲染工具目录，就需要补一条 worker 到 tools 的边；若 `ita-cli` 要自己管理子进程组，可能需要 `nix`，用标准库的进程接口目前够用。

6. **实现质量**。`set -euo pipefail`、`mktemp` 加 `trap` 清理、错误聚合后统一退出 1 都是对的；没有引入新依赖（python3 已被其它脚本使用）。160 行 Python 内嵌在 bash 里仍是单文件、单次调用，拆成独立文件只会多一个文件，这部分无需改动。缺陷集中在问题二至问题四。

7. **CI 接线**。`ci.yml:52-57` 的顺序是分层门、纯净门、clippy，与 `STACK.md:27-29` 的描述一致；分层门最便宜且只读元数据，放在最前面能在编译前失败，合理。用 `bash` 显式调用不依赖可执行位。步骤名与 job 名互相印证，注释与三步的实际行为一致。

8. **文档一致性**。`STRUCTURE.md:40-52` 的十一行、`STACK.md:15-19` 的摘要与脚本里的允许表逐项一致，能力归属的摘要也与脚本不矛盾（`ulid` 未列入摘要，属于摘要取舍）。`STRUCTURE.md:9` 把 `Policy` 与 `Fidelity` 放在内核，与 `STACK.md:23-24` 的"跨平台可表达"一致。没有任何一处把门说成安全边界：脚本头 `:12-13`、`STRUCTURE.md:66-68`、`STACK.md:19` 与计划文档第 43 行都明确否认。`STRUCTURE.md` 的状态段没有提这道门，但下面"依赖边"一节已经写明，状态段其余陈述仍然准确，可以不改。

9. **提交与版本**。两条提交信息都符合 AGENTS 第 3 节：类型正确，中文单句，无 scope 前缀，无 ROADMAP 或 ADR 编号，无提交哈希，无测试计数。`Cargo.toml:18` 仍是 `0.1.29`，这是上一批的值，不是本批缺陷；本批必须在 `batch-end` 之前的最后一次提交里跑 `bump_version.sh batch` 推到 `0.1.30`，由脚本同步 `Cargo.lock`，且复审文档的提交要排在这一步之前，保证版本推进是最后一次提交。

## 问题

### 一、脚本注释把 ROADMAP 编号当理由（严重度：中）

位置：`.w1mer/scripts/check_layers.sh:24-25`、`:47-48`、`:53`。

现象：注释里出现"`12.7` 的模型代理帧与 `12.8` 的流式转发"、"`11.9` 的构建沙箱与 `11.14` 的 `Fidelity` 门"，以及"见 `.w1mer/detail/01_plan-02.md` 的 `02.8` 小节"。

后果：`COMMENT_GUIDELINES.md` 第一节与第七节明确禁止代码注释出现 ROADMAP 编号，唯一的例外是指向未完成工作的 `未实现：...，见 ROADMAP <编号>`。这三处都不是那种用法，而且编号会随 ROADMAP 重排而失效：脚本是长期存在的门，注释却指向会变的任务号。AGENTS 第 5 节把注释规范列为硬约束，这类偏差此前已单独返工过。

修法：改成语义描述，编号只留在计划文档里。第一处写"编码解码只能由协议层消费模型层的归一化类型，不能反过来"；第二处写"构建沙箱与保真度可用性门要直接使用 `Sandbox` trait"；第三处写"注入依赖会让锁文件过期，测完要还原清单与锁文件，步骤见本门对应的计划文档"。

### 二、元数据失败时丢弃 cargo 的原始诊断，并把原因写成唯一可能（严重度：中）

位置：`.w1mer/scripts/check_layers.sh:29-31`。

现象：命令把 stderr 重定向到 `/dev/null`，失败时只打印"cargo metadata 执行失败（清单与 Cargo.lock 不一致时也会走到这里）"。

后果：清单语法错误、工具链缺失、仓库不是 git 仓库、锁文件过期等完全不同的原因，在 CI 上都会显示成同一句话，而且括号里那句会把人引向锁文件。推送按 AGENTS 第 8 节五批一次，一次无法定位的 CI 失败代价很高。另外，`--no-deps` 不解析依赖，锁文件校验是否真的发生取决于 cargo 的实现，本批没有留下实测记录，把它写成既成事实不严谨；计划文档第 47 行的"注入测试前置步骤"因此可能是不必要的一步。

修法：把 stderr 接到第二个临时文件（同样用 `trap` 清理），失败时连同 cargo 原文一起打印；删掉括号里的断言，或改成"具体原因见上面的 cargo 诊断"。若确认 `--no-deps` 不校验锁文件，计划文档的注入步骤同步简化。

### 三、空的归属集合等于关闭规则（严重度：低）

位置：`.w1mer/scripts/check_layers.sh:161`。

现象：判断写成 `if owners and crate not in owners`。给某个能力登记空集合（含义是任何 crate 都不得使用）时，条件为假，规则静默失效。

后果：今天没有空集合条目，所以不影响现有行为；但"禁止某个 crate 出现在所有成员里"是这张表最自然的扩展方式，写下去却不生效，属于会骗过下一位维护者的漏洞。

修法：改为 `if owners is not None and crate not in owners`，错误信息里的归属列表为空时另外给一句"该能力不允许任何成员使用"。

### 四、能力判定复用了展示用的字符串（严重度：低）

位置：`.w1mer/scripts/check_layers.sh:144` 与 `:159`。

现象：先把 `kind` 归一成中文展示文字（`or "普通"`），再用 `kind == "普通"` 决定是否检查能力。

后果：控制流依赖展示字符串，将来有人为了文案把它改成 `"normal"` 或 `"普通依赖"`，能力检查会对所有普通依赖静默失效，而脚本仍然打印"分层门通过"。这类改动看起来只是改字，评审很难发现。

修法：先保留原始值 `raw_kind = dependency.get("kind")`，用 `raw_kind is None` 判定普通依赖，展示文字在拼错误信息时再生成。

### 五、沙箱能力的两处表述与实际边界不符（严重度：低）

位置：`.w1mer/detail/01_plan-02.md:37`、`.w1mer/scripts/check_layers.sh:53`、`:12-13`、`STRUCTURE.md:62-64`。

现象：`ita-tools` 依赖 `ita-sandbox` 的理由写成"要用 `Sandbox` trait 与 `Fidelity` 类型"，但 `STRUCTURE.md:9` 把 `Policy` 与 `Fidelity` 定义在内核，沙箱层只提供 `probe` 与 `apply`。另外，门的边界声明列出了 `std::net`、`tokio::net`、构建脚本、传递依赖与 `pub use`，没有提"被允许 `libc` 的 crate 可以用裸系统调用实现同等能力"：`ita-exec` 就在 `CAPABILITIES["libc"]` 里，完全可以在自己家里调 `landlock` 或 `seccomp` 的系统调用而不引入受限的 crate。

后果：第一条会让读者以为这条边是为了拿类型，将来若把 `Fidelity` 挪进沙箱层或反过来删边时判断失据；第二条使"沙箱原语只能在沙箱层"这句话比实际强，而门又自称边界诚实，两处放在一起容易被读成"执行器无法自己做强制"。

修法：理由改为"构建沙箱要直接使用 `Sandbox` trait"；边界声明补一句"允许 `libc` 的 crate 可以用裸系统调用绕过能力表，这道门只约束 crate 名"。

### 六、`STRUCTURE` 复制了整张允许表，而同一批的计划说不逐条复制（严重度：低）

位置：`.w1mer/codebase/STRUCTURE.md:40-52`、`.w1mer/detail/01_plan-02.md:50-51`。

现象：计划文档写"`STACK.md` 与 `STRUCTURE.md` 只做摘要并指向脚本，不逐条复制；脚本是唯一权威来源"，而 `STRUCTURE.md` 把十一行允许表完整抄了一遍。

后果：同一批的文档互相矛盾，后来者无法判断该以哪句为准；两份表若漂移，脚本会拦住代码，却不会拦住文档，`STRUCTURE.md` 会安静地过期。

修法：二选一。推荐保留完整表（它是人读契约，agent 从 `STRUCTURE` 读起），把计划文档那句改成"`STRUCTURE.md` 保留完整允许表，`STACK.md` 只做摘要，两者与脚本冲突时以脚本为准，并在同一批次修正文档"；若坚持只做摘要，则把 `STRUCTURE.md` 的表换成指向脚本的指针与几条后果。
