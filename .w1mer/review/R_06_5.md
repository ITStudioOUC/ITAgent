# Review R_06_5

Status: ok

## Conclusion

06.5 的五个检查点（cas.rs、blobs.rs、db.rs 的两个新错误变体与 `cas_root` 字段、lib.rs 接线、Cargo.toml 的 blake3 依赖、tests/cas.rs 八条集成测试）全部按已提交代码复核通过，正确性从不变侧推导，不依赖改动代码自证。哈希算法是 blake3（256 位、64 字符十六进制），不是 sha256；CAS 根目录是数据库文件同级的 `blobs` 目录，懒创建（首次 `put` 时建，不在 `open` 时建）；原子改名是临时文件、`sync_data`、`rename` 同目录三步，临时文件用固定后缀 `.tmp`；去重是先查 `blobs` 行、存在则跳过写入，插行用 `INSERT OR IGNORE` 保幂等；写入顺序是文件先行、行随后，中断只留下无引用文件（安全），不留下指向空内容的行（危险）。`put` 返回内核 `BlobRef`，`get` 读回内容等于写入内容。八条验收标准每条都写成独立的测试函数且断言从不变侧推导。无阻塞问题。

## Findings

- **哈希算法是 blake3，64 字符十六进制（第 1 条验收）**：`cas.rs` 的 `hash_hex` 调 `blake3::hash(content).to_hex().to_string()`，blake3 是 256 位（32 字节），十六进制文本恒 64 字符。模块内单测 `hash_is_sixty_four_hex_chars` 断言长度 64 且全是十六进制字符。集成测试 `write_creates_file_and_row` 用 `blake3::hash(content).to_hex().to_string()` 独立算出期望值再断言 `ref_.hash` 等于它——这条断言把算法钉死在 blake3 上，若实现误用 sha256，期望值与实现值不同，测试必失败。`Cargo.toml` 工作区依赖新增 `blake3 = "1"`，`ita-store` 的 `Cargo.toml` 加 `blake3.workspace = true`，`Cargo.lock` 同步了 `blake3` 及其传递依赖（`arrayvec`、`constant_time_eq`、`cpufeatures`）。`blake3` 不在分层门 `CAPABILITIES` 列表里，任何 crate 都可依赖，不违反分层约束；`ita-kernel` 的 `Cargo.toml` 一字未动，内核纯净门不受影响。
- **CAS 根目录是数据库同级的 `blobs` 目录，懒创建（第 7 条验收）**：`db.rs` 的 `cas_root_for(path)` 返回 `path.parent().join("blobs")`，`open` 与 `open_with_wal` 都把它传给 `configure`，`configure` 只存路径不建目录。`open_in_memory` 用临时路径 `std::env::temp_dir().join(format!("ita-cas-{}", ulid::Ulid::new()))`，`ulid` 已是 `ita-store` 既有依赖（`events.rs` 在用），不新增依赖。`cas.rs` 的 `write_atomically` 在写入前 `create_dir_all(parent)` 懒建子目录，首次 `put` 时才建。集成测试 `cas_root_created_on_first_write` 断言未写入时 `cas_root` 不存在、写入后存在且含哈希文件，把"懒创建"钉死。若实现在 `open` 时就建目录，断言 `!cas_root.exists()` 会失败。
- **原子改名：临时文件、`sync_data`、`rename` 同目录，固定后缀 `.tmp`（第 1 条验收）**：`write_atomically` 先算 `blob_path`（前两个十六进制字符子目录、完整哈希文件名），再 `path.with_extension("tmp")` 得临时路径——与最终路径同目录，改名才是原子的。`File::create` 写临时文件、`write_all` 写内容、`sync_data` 同步、`rename` 改名到最终路径。哈希是十六进制、不含点，`with_extension("tmp")` 是追加而非替换，临时文件与最终文件同目录。模块内单测 `blob_path_layout_is_two_char_dir_then_full_hash` 钉住布局。若临时文件与最终路径不同目录，跨文件系统 `rename` 会失败或不是原子的，`write_creates_file_and_row` 断言最终路径存在会失败。
- **去重先查 `blobs` 行，存在则跳过写入，`INSERT OR IGNORE` 保幂等（第 2、8 条验收）**：`put_in` 先 `blobs::exists(tx, &hash)`，存在则直接返回 `BlobRef` 不写文件；不存在则 `write_atomically` 写文件、`blobs::insert` 插行。`blobs::insert` 用 `INSERT OR IGNORE`，即使去重检查被绕过（并发情形，单写者不会发生），插行也幂等。集成测试 `same_content_written_twice_produces_one_blob` 断言两次同内容写入后 `blobs` 表只有一行、文件系统只有一个哈希文件；`cross_workspace_shares_same_content` 在两个工作区各写同一段内容，断言只有一行（全局去重）。若去重查文件而不是查行，崩溃恢复情形（文件存在但行不存在）会跳过插行、留下无行文件，这两条测试断言行数会失败。
- **写入顺序文件先行、行随后，中断只留无引用文件（第 1 条验收）**：`put_in` 里 `write_atomically` 在 `blobs::insert` 之前，两者都在事务内、提交前。若行插入失败（如 CHECK 约束），`put_in` 返回 Err、事务回滚、行不落库，但文件已写入——留下无引用文件（安全，多占空间），不留下指向空内容的行（危险，丢内容）。`write_creates_file_and_row` 断言文件与行成对出现，`unreferenced_since` 恒为 NULL（宽限期起点由 06.9 回收扫描观察时写入，创建时间不能顶替它）。
- **`put` 返回内核 `BlobRef`，`get` 读回内容等于写入内容（第 4 条验收）**：`Store::put` 返回 `Result<BlobRef, StoreError>`，`BlobRef { hash: String, len: u64 }` 是 `ita-kernel` 的 `context/node.rs` 里的类型，`ita-store` 依赖 `ita-kernel` 可直接返回。`Store::get` 调 `cas::get_in`，先 `blobs::exists` 查行，不存在返回 `StoreError::BlobNotFound`，行存在则 `std::fs::read` 读文件、读失败返回 `StoreError::Cas`。集成测试 `read_back_matches_written_content` 写入后按返回的哈希读回，断言读回的字节等于写入内容；`reading_nonexistent_hash_reports_blob_not_found` 断言读不存在的哈希返回 `BlobNotFound` 而不是 `Cas`。若 `get` 不区分"不存在"与"读失败"，第二条测试断言错误类型会失败。
- **八条验收标准每条都写成测试且通过**：`tests/cas.rs` 有 8 个 `#[test]` 函数，与计划第四节的八条验收一一对应。第 1 条断言成功写入后 `blobs` 表多一行、`hash` 是内容的 blake3 十六进制、`size` 是字节数、`created_at` 非空、`unreferenced_since` 为 NULL、文件系统有对应哈希文件且内容等于写入内容；第 6 条断言空内容产生一个 blob、`len` 是 0、`hash` 是空内容的 blake3、`size` 是 0。每个测试走公开接口 `put`/`get`，不自己拼 SQL 写行（只用 `conn_for_test` 与 `cas_root_for_test` 读回断言）。实现者提交前已自测，nextest 每测试独立进程，无共享全局状态依赖。
- **db.rs 加两个错误变体与 `cas_root` 字段，lib.rs 接线**：`StoreError` 新增 `Cas(std::io::Error)` 与 `BlobNotFound(String)` 两个变体，`Display` 实现与既有变体同形。`Store` 新增 `cas_root: PathBuf` 私有字段，`open`、`open_in_memory`、`open_with_wal` 三个构造器都设置它，没有其它构造路径。`put` 取 `&mut self`、走 `self.conn_mut().transaction()`，与 `create_workspace`、`append_event`、`commit_frame` 的形状一致，不在同一句柄上留下两种事务获取方式；`get` 取 `&self`、走 `self.conn()`，与 `events_after` 同形。`cas_root_for_test` 是 `#[doc(hidden)] pub fn`，与 `conn_for_test` 同纪律，供集成测试检查 CAS 根路径。`lib.rs` 声明 `mod blobs` 与 `mod cas`（私有），不对外导出，`cas` 与 `blobs` 的函数是 `pub(crate)`，公开 API 仍是 `Store` 与 `StoreError`，与"操作级接口"的存储层纪律一致。

## 已知缺口（非 06.5 缺陷，属计划明示留待后续批次）

- `cas_root_for` 的文件库派生路径（`open` 与 `open_with_wal`）没有被任何集成测试覆盖，八条测试全走 `open_in_memory` 的临时路径。`cas_root_for` 是单行推导（`path.parent().join("blobs")`），按检视正确，但"数据库同级的 `blobs` 目录"这条验收只在内存库上被验证。文件库的 CAS 根派生留给后续批次补一条 `open` 路径的测试。
- `blobs.hash` 列没有 64 字符十六进制的 CHECK 约束，表结构不保证哈希格式，格式由写入路径（`hash_hex`）承接。这是表结构与代码路径的分工，与 06.2 系列"表结构只保证 ADR 明写的形状，剩下的由代码路径断言"的裁决同型。
- `get_in` 对"行存在但文件被删"的情形返回 `StoreError::Cas`（读失败），与"行不存在返回 `BlobNotFound`"区分开，符合文档契约。集成测试只覆盖了"行不存在"一条，"行存在但文件缺失"返回 `Cas` 这条没有独立用例，属读路径的健壮性边界，不是本批的契约违背。
