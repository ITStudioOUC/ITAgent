# 事实层审查

提交 `99926f3`（加压缩事实层与必填校验）新增了一个纯函数事实层，结构校验与渲染都不碰 IO 与时钟，内核纯净门不受影响；但"有改动就必须有失败记录"这条拒绝规则会把合法批次挡在门外，0004 要求的事实项还缺实际耗时，失败记录本身反而不校验空串。因此判 `issues`。

1. 拒绝规则过强（`facts.rs:91` 至 `:93`、`facts.rs:39` 至 `:46`）。只改一行注释、首次编译即通过、或纯文档批次都会因 `changed_files` 非空而拿不到帧；而 0004 的代价段写明压缩发生在上下文最满时，此时拒帧换来的是重试窗口最窄的连续失败。要守的性质是"失败小节由机器填且不能被删"，不是"这段时间真发生过失败"。建议 `render` 无条件输出该小节（无失败时写"系统核对后无失败记录"），把"收集环节是否漏了"交给收集方自证，而不是让文件数与失败数互为前提。
2. "不可修改"是给模型的祈使句（`facts.rs:111`）。模型本来就无法改写机器生成的段落，这句反而容易让它在散文里复述约束或为事实辩护，白占预算；改成陈述句"以下内容由系统从事件表与检查点直接生成"更稳。
3. 事实项缺两处（`facts.rs:22` 至 `:34`）。0004 第 20 行还要求"报错摘要、实际耗时"：报错摘要现由 `Failure.outcome` 兼任，没有独立字段尚可接受；实际耗时在 `Facts` 里完全没有，按"参数可调、时钟在核外"的约束应由调用方以毫秒入参，内核不读时钟。缺这一项，"事实层完整"的验收并不成立。
4. 元组靠位置记字段（`facts.rs:24` 至 `:25`、`facts.rs:117` 至 `:119`）。增删行写反不会编译报错，只有渲染文本断言能发现；同模块 `recent.rs` 已用命名结构。改为 `struct ChangedFile { path, added, removed }`。
5. 失败记录不校验空白（`facts.rs:94` 至 `:98` 只查 `rejected`）。`attempt` 或 `outcome` 为空白时渲染出"` → `"，等价于把失败抹掉，正是事实层要防的事。应复用同一条空白检查并报出对应条目。
6. 用例缺口（`facts.rs:164` 至 `:236`）。没有"只有失败没有改动"这一组合；没有多条已否决方案中只有一条缺理由（未固定报哪一条，也未固定是否继续收集）；`validate` 三条规则的优先级未固定（轮数为零同时有改动时返回哪个错）；`facts.rs:232` 与 `facts.rs:222` 重复断言同一句"不可修改"。
7. 待闭合：验收里的"机器事实不被散文覆盖"目前只在类型上成立（`format.rs:7` 至 `:9` 的解析产物只有散文），事实段与散文拼进同一帧由后续的提交计划决定，本批没有可执行的证据。
