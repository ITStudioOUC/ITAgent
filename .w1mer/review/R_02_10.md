# 文档对齐审查

Status: ok

## 结论

本批的方向正确。`README.md` 去掉了硬编码版本号与“下一步进入内核”，四个位于内核之外的 crate 在模块头里写清了各自不做什么，`05_plan-06.md` 的 06.3 至 06.8 验收列补上了表结构无法承接、只能由写入路径保证的约定。按可读到的文件内容，改动只涉及文档与 `//!` 注释，没有触碰代码、表结构与测试。

但初审时 `README.md` 的现状段不完整：它漏掉了 `ita-proto`、`ita-server` 与 `ita-worker` 三个空壳 crate，把尚未开工的事件与快照写入写成“仍在推进”，又把只有纯逻辑完成的语义压缩写成“已经完成”。06.8 当时新加的“缺失内容时整次拒绝”与本仓已经记录的处置相反，且没有新的裁决记录；`05_plan-06.md` 的说明段当时还把 06.3 的表级不可变性称为“已裁决”，而仓库里找不到这条裁决。其中 06.8 与 `05_plan-06.md` 说明段这两处会让下一批的探索者看到互相矛盾的依据，因此初审判为 issues；`1e5bd6b` 已逐条处置，二次复审结论为 ok，见文末。

## 问题

### 1. README 的现状边界漏了三个空壳 crate，另有两处进度表述不准确（严重度：中）

- 位置：`README.md:9-13`。
- 现象：`README.md:9-10` 说“十一个 crate 与单二进制 `ita` 的角色分发已经落地”，这句话可以读成十一个 crate 都已实现；`:12` 的未开工清单只列了执行器、沙箱、工具安装、模型适配与工作流，漏掉了 `ita-proto`、`ita-server` 与 `ita-worker`。这三个 crate 目前都还是空壳：`crates/ita-proto/src/lib.rs` 与 `crates/ita-server/src/lib.rs` 除了文档注释与 lint 属性没有代码，`crates/ita-worker/src/lib.rs:23` 的 `run()` 是空函数。`:12` 又把“事件与快照写入”写成“仍在推进”，而 `crates/ita-store/src/` 只有 `lib.rs`、`db.rs`、`scope.rs` 与 `migrate.rs`，没有事件、内容寻址存储或快照模块，`HANDOFF.md:15` 也写明 `06.3` 起未开工。`:11` 的“语义压缩已经完成”只对内核里的六个压缩模块成立，模型适配与 server 的提交路径都还没开工，`:12` 自己也说模型适配尚未开工，`:13` 说当前没有端到端的工具调用路径。
- 后果：现状段是新读者判断“能跑什么、不能跑什么”的唯一入口。漏掉三个 crate 会让人去找不存在的协议层、server 与 worker 实现；“仍在推进”与“已经完成”会把未开工和纯逻辑完成读成可运行。
- 修法：把 `:9-10` 改成“十一个 crate 的骨架与单二进制 `ita` 的角色分发已经落地”；把 `:12` 的未开工清单补全为“协议、沙箱、执行器、工具、模型、工作流以及 server 与 worker 仍是空壳”，或者直接说“除内核、存储前段与 ita-cli 的角色分发外，其余 crate 仍是空壳”；把“事件与快照写入仍在推进”改成“事件与快照写入尚未开工”；把“语义压缩已经完成”改成“语义压缩的纯逻辑已经完成”。

### 2. 06.8 的“整次拒绝”与已记录的处置相反（严重度：中）

- 位置：`.w1mer/detail/05_plan-06.md:21`；对照 `.w1mer/detail/CHANGES.md:241-242` 与 `.w1mer/review/R_06_2.md:66`、`:78`。
- 现象：`05_plan-06.md:21` 写“写回前核对有内容条目的 blobs，缺失内容时整次拒绝并列出路径”；`CHANGES.md:241-242` 写“06.8 回滚前对每个有内容记录的条目核对并把缺失写进残留清单”，`R_06_2.md:66` 的理由是“缺失内容写进残留清单而不是让写回中途失败”。两种做法对同一个故障给出不同结果：前者让整次回滚失败，后者让回滚继续并把缺失路径交给残留清单。
- 后果：06.8 的探索者会同时读到两条相反的验收要求。若按“整次拒绝”实现，一个缺失的 blob 就会让整次回滚不可用；ADR 0017 已经以“一个 2 MiB 的日志文件不应让回滚功能完全失效”为由否决了“遇到超阈值文件拒绝整次回滚”，这里至少需要说明为什么缺失内容要采取相反的取舍。若按 `CHANGES.md` 实现，新的验收行就不成立。
- 修法：请主 Agent 先裁定一种行为并留下记录。若保留“整次拒绝”，在 `CHANGES.md` 补一条裁决，写明为什么部分回滚不可接受、路径列在错误信息还是残留清单里，并在同一条记录里注明 `R_06_2.md:78` 的建议已被改判；若保留 `CHANGES.md` 的处置，把 06.8 改成“缺失内容写进残留清单并跳过该条目，其余范围内文件照常对齐”。不要让 fixer 在没有裁决的情况下自行二选一。

### 3. 06.8 的残留清单漏了尺寸（严重度：低）

- 位置：`.w1mer/detail/05_plan-06.md:21` 与 `.w1mer/detail/01_plan-02.md:90`。
- 现象：两处都写“范围外不碰并在残留清单写明路径与原因”，而 `docs/adr/0017-oversized-files-outside-snapshot-coverage.md:24-25` 要求残留清单“至少包含：路径、尺寸、原因（超阈值、范围外写入、后台进程遗留）”。
- 后果：范围外写入的残留可能只带路径与原因，用户无法判断它有多大，ADR 0017 给的最低信息量没有达到。06.6 的超阈值条目已经要求带尺寸，范围外条目没有理由更少。
- 修法：把两处改成“写明路径、尺寸与原因”。

### 4. “已裁决”缺少可追溯记录（严重度：低）

- 位置：`.w1mer/detail/05_plan-06.md:28`。
- 现象：这句话把“事件表的不可变性在表结构层没有约束”称为“已裁决的已知缺口”，并要求后续批次不要再重开。仓库里能支撑这条说法的只有 02.10 计划自己的断言与 06.3 执行计划第九节的倾向：`.w1mer/detail/21_批次_06_3_事件追加_seq_分配与预览截断的执行计划.md:283` 仍写“需要一次明确裁决”，`.w1mer/HANDOFF.md:37-39` 也仍把“表级不可变性是否单开批次”列为四处待裁决之一。
- 后果：下一批的探索者无法知道这条裁决由谁在何时基于什么理由做出；“不要再重开”会让一个仍然开放的讨论提前关闭。`snapshot_entries.hash` 不设外键那一半没有问题，`CHANGES.md:229-242` 与 `R_06_2.md` 已经记录了理由和承接者。
- 修法：把 06.3 的决定写进可查的记录，例如在 `detail/21` 第九节或 `CHANGES.md` 补一句“06.3 决定不补触发器，理由是迁移只允许加表加列，触发器和表级不可变性属于另一类约束，由只提供追加接口的代码路径守住”，并删掉 `HANDOFF.md` 里的待裁决项；或者把“已裁决”改成“本史诗内决定不补，理由见……”。

### 5. 可选措辞（不阻塞本批）

- **tools 模块头的 shim 方向（低）**。`crates/ita-tools/src/lib.rs:4-5` 写“运行期执行由执行器经 shim 交给沙箱”。ADR 0014 第 26 至 28 行给出的父进程链是“执行器、沙箱监督进程、模板、工具二进制”，shim（沙箱内回调执行器的中间程序）是沙箱内的嵌套命令回调执行器的通道，不在执行器进入沙箱的路径上。建议改成“运行期执行由执行器交给沙箱监督进程；沙箱内的嵌套调用经 shim 回调执行器”。
- **README 的版本指针（低）**。`README.md:13-14` 写“进度与版本以 ROADMAP 为准”，但 `ROADMAP.md` 没有单一的当前版本字段，版本的事实来源是 `Cargo.toml:18`，`ROADMAP.md` 的 effect 只是每个任务的记录。建议改成“进度以 ROADMAP 为准，版本以 `Cargo.toml` 为准”，这样也与 02.10 计划里“版本号在 Cargo.toml 与 ROADMAP 的 effect 里已经有两处”的说法一致。
- **06.4 的“seq 都不变”（低）**。`05_plan-06.md:17` 写“帧行、head 与 seq 都不变”，读者可能把它理解成事件行的 seq 不变，而 02.10 的验收要求是冲突提交不消耗 `workspace_seq` 计数器。建议写成“冲突不消耗 seq，`workspace_seq` 的计数器保持原值”，这样用例才知道要断言哪一列。
- **06.3 与 06.4 的节点归属（低）**。`05_plan-06.md:16-17` 只约束“会话属于同一工作区”。`events.node_id` 与帧引用的节点同样可能跨工作区；`detail/21` 第九节在讨论外键时把 `session_id` 与 `node_id` 并列。建议在验收里写明节点也必须在同一工作区，或者明确节点归属留到 06.4，避免探索者只实现一半。

## 逐项核对

1. **README 的现状描述**。版本号、任务号与测试数都已去掉；`ita` 的占位行为与实现一致：`crates/ita-cli/src/main.rs:26-32` 对 master、worker、tool-host 三个角色都打印“角色 X 尚未实现”并返回成功，未知角色在 `:21-24` 退出 2，`--version` 在 `:16-19` 打印清单版本。问题集中在现状段的边界，见问题 1。

2. **四个模块头**。`ita-model` 声明不发起网络请求、不持有凭据、不写数据库，连接与鉴权在 server 的模型代理；`ita-proto` 声明不建立连接、不做路由、不持有会话状态，信封里没有 workspace 字段；`ita-workflow` 声明不执行节点、不碰存储，完成记录由 server 在事务内追加；这三处与 ADR 0001、0002、0008、0010、0011 与 0014 一致。`ita-tools` 的 IO 边界“不发起网络请求、不持有凭据、不执行已安装的二进制、安装期构建在沙箱内”与 ADR 0012 一致，只有 shim 的方向可以更准确，见可选第一条。这四条也与 `STRUCTURE.md:40-52` 的允许表一致：`ita-model` 只依赖内核，`ita-proto` 只依赖内核与 `ita-model`，`ita-tools` 只依赖内核、协议与沙箱，`ita-workflow` 只依赖内核；HTTP 与 TLS 只允许出现在 server。四个模块头都没有把“内核之外”写成“可以任意 IO”，也没有把合法能力说没。

3. **06 验收列**。06.3 补上了 `workspace_seq` 计数器与会话归属；06.4 补上了冲突不消耗 seq 与会话归属；06.5 补上了先写内容再插入 `blobs` 行的顺序；06.6 补上了 `content_stored = 1` 的条目必须在 `blobs` 里且不加外键、目录行写 `mode` 与 `mtime`、文件行写 `mode`、超阈值条目带修改时间；06.7 补上了重挂父边时父子快照属于同一工作区；06.8 补上了范围外不碰、残留清单与缺失内容。06.6 的三支 CHECK 在 `crates/ita-store/migrations/0002_content.sql:101-109`，`workspace_seq` 在 `0001_core.sql:70-73`，06.7 的 64 条增量与 06.9 的宽限期都能在 ADR 0018 的参数表里找到依据。06.8 的两处问题见问题 2 与问题 3；其余条目没有与 ADR 0006、0017 或 0018 冲突，也没有把“建议”写成“必须”。

4. **05_plan 的说明段**。`snapshot_entries.hash` 不设外键的理由与 ADR 0017 一致：超阈值条目按内容算出哈希但正文不进内容存储，加外键会把正常条目判成悬空；`CHANGES.md:229-242` 与 `R_06_2.md` 也记录了这条裁决。事件表不可变性的“已裁决”缺少记录，见问题 4。

5. **文档规范**。`README.md`、`05_plan-06.md` 与四个模块头都没有命中 `DOC_GUIDELINES.md` 第六节的私有词汇；新增段落是完整中文句，没有用 `/`、`+`、`→` 把结论压成电报体；“验收要求”比原来的旧说法清楚，后者是内部行话。`README.md` 不是 `DOC_GUIDELINES.md` 的强制范围，但新状态段里首次出现的 MSRV（最低支持的 Rust 版本）可以补一句中文释义，这是可选的可读性改进。

6. **该动而未动的文档**。`STRUCTURE.md:24-28` 的 Status 仍然成立：它写 `06.1` 至 `06.2` 已完成、`06.3` 起的事件与快照写入仍开放，与问题 1 建议的 README 说法一致；其中“The remaining crates are shells”对 `ita-cli` 略宽，因为它的角色分发已经实现，这一句可以在关闭 `06.2.3` 或开始 `06.3` 时一并收窄，不需要在本批改动。`06.2.3` 是测试改名的子批次，不影响这段的行为描述。`HANDOFF.md:8-15` 的版本 `0.1.31`、测试数 261 与最新功能提交 `d27bc42` 已经落后于本批，其中“06.3 起未开工”仍然成立；它不在 02.10 的文件边界内，建议主 Agent 在收尾时按 02.9 的做法补一次交接文档更新。`codebase/INDEX.md` 仍为空是 02.10 计划明确写的边界，模块文档留给后续 `w1mer sync` 生成，不属于本批。

7. **提交与批次边界**。`af5469c` 的标题是 `docs: 对齐 README、模块边界与存储验收要求`，`ddc8812` 的标题是 `docs: 登记文档对齐子任务`；两条都符合 AGENTS 第 3 节：类型为 `docs`，没有 scope 前缀，没有 `｜`，没有 ROADMAP 或 ADR 编号，没有提交哈希，没有测试计数。四个 `lib.rs` 的可读内容只有模块头注释与 lint 属性，没有行为代码；README 与 05_plan 是文档。`Cargo.toml:18` 仍是 `0.1.32`，本批是同史诗内的一个批次，收尾时用一次 `bump_version.sh batch` 推到 `0.1.33`，并让它成为 `batch-end` 前的最后一次提交。

## 架构影响

本批移动的是文档契约，不是代码契约。README 的现状段把“已实现”和“仍是空壳”分开；四个模块头把内核之外的 crate 各自的 IO、网络、存储与执行边界写成可读的约束；06.3 至 06.8 的验收列把表结构承接不了的责任明确交给写入路径，包括 seq 计数器、会话的同工作区校验、内容寻址存储的写入顺序、`content_stored = 1` 的 blob 断言、目录与文件的 `mode` 与 `mtime`、合并最老两条增量时的重挂范围、回滚残留清单与缺失内容处理。这些都不改变现有代码、表结构、迁移或依赖，只把后续批次的实现约束前移。

06.8 的“缺失内容时整次拒绝”如果被采纳，会改变未来回滚的失败模式：从“报告缺失并继续对齐其余文件”变成“整次回滚失败”。这一点需要在裁决记录里写清，不能只留在验收列。二次复审确认该方案最终未被采纳，06.8 已改为把缺失路径写进残留清单。按本次只读约束，我没有修改 `.w1mer/detail/CHANGES.md`；主 Agent 可以在收尾时把这一段并入 `CHANGES.md`。
