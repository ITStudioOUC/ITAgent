# Review R_06_3

Status: ok

## Conclusion

06.3 的四个检查点（events.rs、seq.rs、preview.rs、EventId、db.rs 的 conn_mut 与两个新方法、14 条集成测试）全部按已提交代码复核通过，正确性从不变侧推导，不依赖改动代码自证。seq 从 `workspace_seq` 计数器读改写而非 `MAX(seq)+1`，第 3 条预置计数器 100 的断言能把两者分开；预览截断按"头加尾"总预算判截断、按字节切回退字符边界，全中文正文用例守住多字节不切开；事件追加在 CAS/归属校验之后、失败回滚不消耗计数器，第 12、14 条从可观察的计数器值兜住；EventId 放内核复用 `id_type!` 宏、存储层用 `ulid` crate 生成，内核零依赖不引入时钟或随机；`conn_mut` 是 `pub(crate)` 且取 `&mut self`，与 `create_workspace` 形状一致。14 条验收每条都写成独立的测试函数，且都通过。无阻塞问题。

## Findings

- **seq 取自计数器而非表内最大值（第 3 条）**：`seq.rs` 的 `allocate` 在事务内读出 `next_seq`、写回 `next_seq + 1`、返回读出的值。第 3 条测试先把计数器预置成 100（此时表内最大 seq 是 3），追加一条得到 100；若实现用 `MAX(seq)+1` 会得到 4，断言 `appended.seq == 100` 会失败。不变侧的 `workspace_seq` 表由 `create_workspace` 与工作区行同事务写入（默认 1），`configure` 已设 `BEGIN IMMEDIATE`，读与写在同一事务内原子，分配与插入不会分叉。`CONVENTIONS.md` 禁用 `RETURNING`，`seq.rs` 用先 `SELECT` 再 `UPDATE` 的两步写法，没有用 `UPDATE ... RETURNING` 一步写法，守住了换 Postgres/MySQL 的门。
- **预览截断：头 4096 尾 1024、按字节切回退字符边界、判据是头加尾总预算（第 7 条全中文正文）**：`preview.rs` 的 `truncate` 在 `body.len() <= limit.total()`（5120）时整段进头、尾为空；超过才切，头取前 4096 字节、尾取后 1024 字节，各自回退到字符边界。全中文正文（每字 3 字节、共 9000 字节）用例：4096 不是 3 的倍数，首段退到 4095；尾段从 7977 字节起（第一个字符边界），共 1023 字节。第 7 条断言 `head.len() == 4095`、`tail.len() == 1023` 且两段与原文的头尾一致，能把"按字节切没回退"的实现暴露出来。边界两侧（5120 不截断、5121 截断）由第 8 条守住。默认值 4096/1024 只出现在 `PreviewLimit::defaults()` 一处，与 ADR 0018 第九节参数表第 116 行"事件正文预览 头 4 KiB + 尾 1 KiB"一致，没有以常量散落在调用点。
- **事件追加排在 CAS/归属校验之后，失败回滚不消耗计数器（第 14 条）**：`append_in` 先校验会话与节点归属（事务内 `SELECT EXISTS`），通过后才 `allocate` 分配 seq、再插入。校验失败在分配之前返回，计数器不消耗；插入失败（主键冲突）时事务回滚，`workspace_seq` 的写回一并回滚。第 12 条先占住 seq 1 那一行再追加，断言返回错误且 `next_seq` 与调用前相等；第 14 条引用 B 工作区的会话与节点被拒、计数器不变，不引用任何会话与节点的追加通过。三处失败点（开事务之前、插入那一步、校验那一步）合起来覆盖整个写入路径。
- **EventId 放内核复用 id_type! 校验，存储层用 ulid crate 生成**：`ids.rs` 用既有的 `id_type!` 宏加 `EventId`，与其余四个 id 共用同一套校验（26 字符、Crockford base32、首位 0 到 7），`context/mod.rs` 重新导出。内核零依赖（`Cargo.toml` 的 `[dependencies]` 为空），宏只加一个纯结构体类型，不引入时钟或随机，内核纯净门不破坏。`events.rs` 用 `ulid::Ulid::new().to_string()` 生成 id，`ulid` 已是 `ita-store` 的声明依赖（`ulid.workspace = true`，根 `Cargo.toml` 注释写明"ULID 需要时间戳，内核不碰时间，所以放在存储层"），不需要新增依赖。存储层没有另写一份 26 字符校验，避免了真正的重复。
- **conn_mut 是 pub(crate)，与 create_workspace 的 &mut self 形状一致**：`db.rs` 加 `pub(crate) fn conn_mut(&mut self) -> &mut Connection`，写方法取 `&mut self`，与 `create_workspace` 现有的形状一致，不在同一句柄上留下两种事务获取方式。`pub(crate)` 保证业务代码（其他 crate）拿不到连接，"作用域是业务查询唯一入口"这条约束不破。`append_event` 在 `self.conn_mut().transaction()` 里调用 `events::append_in`，`events_after` 走 `self.conn()` 只读。`conn()` 上原先的 `#[allow(dead_code)]` 已移除，因为 `events_after` 与既有测试现在正式用到它。
- **14 条断言每条都写成测试且通过**：`tests/events.rs` 有 14 个 `#[test]` 函数，与计划第四节的 14 条验收一一对应（前 4 条与第 10 至 13 条测 seq 与 id，第 5 至 9 条测预览截断，第 14 条测会话与节点归属）。每个测试走公开接口（`append_event`、`events_after`、`scope`），不自己拼 SQL 读事件行（只用 `conn_for_test` 读计数器与占位制造失败）。实现者提交前已自测，nextest 每测试独立进程，无共享全局状态依赖。

## 已知缺口（非 06.3 缺陷，属计划明示留待后续批次）

- 事件表"不可变"目前只是代码纪律，表结构层面无 `BEFORE UPDATE`/`BEFORE DELETE` 触发器；`events.id` 无唯一索引。两者都是后补得起的（`CREATE TRIGGER` 与 `CREATE UNIQUE INDEX` 是新增对象，不撞"迁移只加表加列"），计划第九节已裁决本批不做。
- `events.session_id` 与 `node_id` 无法在既有表上加外键（`ALTER TABLE ADD COLUMN` 只能给新列带 `REFERENCES`，给既有列补外键的唯一出路是重建表，撞 `DROP TABLE` 禁令），因此跨工作区错配只能由写入路径的 `SELECT EXISTS` 断言，本批已落。
