# 存储打开与迁移审查

提交 ef8a928（加存储打开、工作区作用域与迁移运行器）立起了存储句柄、作用域类型与内嵌迁移运行器，形状与 0002 的"单库、单写者、作用域由连接推导"一致；问题集中在"纪律只写在注释里、没有门承接"这一类：工作区注册不是原子操作，迁移脚本的内容漂移无法发现，`BEGIN IMMEDIATE` 与 WAL 两条宣称的机制都没有真正落地。判 `issues`，第 1、2 条建议在 06.2、06.3 开始写表数据之前修掉。

1. 工作区行与 `workspace_seq` 行分两条语句写（`db.rs:113` 至 `:123`），中间崩溃会留下一个有工作区、没有计数器的库；更糟的是这条路径不可修复——重跑时第一条 `INSERT OR IGNORE` 影响零行，直接返回 `WorkspaceExists`（`db.rs:117` 至 `:119`），计数器行再也补不上，06.3 的 seq 分配会拿到 `QueryReturnedNoRows`。两条插入应放进同一事务，并且 `create_workspace` 取 `&mut self`（或用 `unchecked_transaction` 并说明理由），因为现在的 `&self`（`db.rs:107`）在类型上就开不了事务。另外用 `INSERT OR IGNORE` 的行数判断"已存在"会把任何被 IGNORE 的约束违例都报成 `WorkspaceExists`，`INSERT ... ON CONFLICT(id) DO NOTHING` 能表达得更准确。
2. "只加不改"没有任何检查。迁移内容变了而版本号没变时，已经迁移过的库在 `migrate.rs:104` 至 `:108` 判定 `pending` 为空、直接返回成功，改过的 SQL 根本不执行；新库却按新内容建表，同一个版本号对应两套表结构，而 `VersionGap`（`migrate.rs:97` 至 `:102`）只查空洞、不查内容。修法是在 `schema_version` 里存每份脚本的哈希（加一列，本身是合法的只加迁移）并在启动时比对，不一致就拒绝启动；再加一条测试扫描 `MIGRATIONS` 的 SQL，断言不含 `DROP`、`DELETE`、`ALTER TABLE ... DROP`、`VACUUM`、`PRAGMA`。
3. 注释说"跑了旧版本二进制"会被版本校验抓住（`migrate.rs:80` 至 `:81`），实际不会：旧二进制看到 `applied = [1,2,3]`、自己的 `MIGRATIONS` 只到 2 时，`pending` 为空、返回 `Ok(3)`，用旧代码读写新表结构。应显式比较 `current` 与 `MIGRATIONS` 的最大版本，前者更大就报错。
4. `busy_timeout` 是设了（`db.rs:93`），但没有任何一处用 `BEGIN IMMEDIATE`：唯一的 `conn.transaction()`（`migrate.rs:110`）是默认的 DEFERRED。WAL 下先读后写的事务可能拿到 `SQLITE_BUSY_SNAPSHOT`，它不是"重试这条语句"能解决的，必须整笔重来，5 秒忙等对它也不生效。`db.rs:7` 至 `:8` 声称这条纪律"在这里落地"是不成立的。最省事的修法是在 `configure` 里 `conn.set_transaction_behavior(TransactionBehavior::Immediate)`，让后续所有 `conn.transaction()` 自动是立即事务，注释就从约定变成构造。
5. WAL 失败被静默吞掉（`db.rs:91`）。文件库在共享内存不可用的文件系统上会退回 rollback journal，正确性不变但"读不被写阻塞"这个前提悄悄消失，而这正是后面单写者加批量提交假设的基础；而且 `pragma_update` 走 `execute_batch`，连成功时返回的实际模式也不检查，写了 `WAL` 不等于拿到了 `wal`。应改用 `pragma_update_and_check` 并断言结果为 `wal`，只在 `open_in_memory` 路径跳过（内存库无所谓 journal 模式，不必靠失败来兜）。
6. 作用域目前只证明"工作区存在"，不证明"来自连接"。`Store::scope`（`db.rs:135`）接受任意来源的 `WorkspaceId`，而 `WorkspaceId::parse` 是公开的，因此 0002 说的"handler 误用参数"风险原样保留；`scope.rs:6` 至 `:7` 声称"Store 的查询方法都要求传一个作用域"，但本批次没有任何一个这样的方法，类型层面的"漏带工作区不可表达"还是空头承诺。同时 `create_workspace`（`db.rs:107`）与 `workspace_count`（`db.rs:154`）是不带作用域的公开入口，后者是跨工作区读，容易被后续模块照抄成业务查询。`WorkspaceScope::workspace()`（`scope.rs:39` 至 `:41`）把 id 原样交回，也给了绕过类型的口子。这些要等 06.3、06.4 首个带作用域的操作方法落地时一并定形，本期至少要改写 `scope.rs:6` 的措辞，别把计划写成既成事实。
7. 表结构挡不住跨工作区错配。`nodes.workspace_id` 与 `nodes.session_id` 各自有外键（`0001_core.sql:30` 至 `:31`），但没有约束"这个会话属于同一个工作区"，一条 A 工作区的节点指向 B 工作区的会话可以写进去；`events.session_id`、`events.node_id`（`0001_core.sql:51` 至 `:52`）连外键都没有，事件可以引用不存在或跨工作区的对象，而事件是按 `(workspace_id, seq)` 读的，污染会直接出现在作用域内。要堵住得给 `sessions` 加 `UNIQUE(workspace_id, id)` 并用复合外键 `(workspace_id, session_id)`，这条属于 06.2 的 schema 定稿范围，本期先记下形状。另外 `events.id` 只有 `TEXT` 没有 `UNIQUE`，同一事件的 ULID 可以在两个工作区各存一份。
8. 两处小瑕疵：`now_millis` 在时钟异常时返回 0（`db.rs:189`），会写出 `created_at = 0` 的行，与"1970 年"不可区分，宁可返回错误；`busy_timeout` 的 5 秒是散落在调用点的常量（`db.rs:93`），与 0018 第九节"参数统一走配置结构"冲突。
9. 用例层面，`迁移是幂等的`（`migrate.rs:187` 至 `:192`）只证明"同样的 SQL 跑两遍不炸"，恰好掩盖了第 2 条的情形，改名成"脚本可重复执行"更诚实；缺一条"文件库的 journal_mode 确实是 wal"和一条"工作区注册后计数器行一定存在"的断言。

## 处置记录

| 问题 | 处置 |
|---|---|
| 工作区行与计数器行分两条语句写，中断后计数器永远补不上 | 改为同一事务；`create_workspace` 取 `&mut self`（类型上就要求可开事务）；`INSERT ... ON CONFLICT(id) DO NOTHING` 表达"已存在"比 `OR IGNORE` 准确 |
| 迁移脚本内容漂移无法发现 | `schema_version` 加 `script_hash` 列（加列本身是合法迁移），启动时比对，不一致报 `ScriptChanged`；补用例 |
| 旧二进制读写新表结构不会被拦住 | 比较库版本与程序支持的最高版本，库更高则报 `DatabaseNewer`；补用例 |
| `BEGIN IMMEDIATE` 只在注释里 | `configure` 里 `set_transaction_behavior(Immediate)`，迁移事务随之变为立即事务 |
| WAL 失败被静默吞掉 | 新增 `open_with_wal`：读回实际模式并断言为 `wal`，否则报 `WalUnavailable`；内存库走另一条路径 |
| 作用域只证明工作区存在，不证明来自连接 | `scope.rs` 的模块注释改为"目标是每个业务查询都传作用域，本批次还没有这样的方法"，不再把计划写成既成事实 |
| `events`/`nodes` 缺跨工作区复合约束 | 留给 06.2 的 schema 定稿（需要 `UNIQUE(workspace_id, id)` 加复合外键），已记入审查文档 |
| `now_millis` 时钟异常返回 0 | 改为返回错误（`ClockBeforeEpoch` / `ClockOverflow`） |
| 用例只证明"脚本跑两遍不炸" | 改名"脚本可重复执行"，另补"脚本不含破坏性语句"的扫描用例 |
