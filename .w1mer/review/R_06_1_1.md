# 迁移脚本指纹稳定化审查

## 结论

判 `ok`。提交 `5b83fa9` 把 `script_hash` 从标准库的 `DefaultHasher` 换成自带的 FNV-1a 64，并在值前加 `fnv1a64:` 前缀，实现与计划文档的算法裁决逐条对得上：两个常量（偏移基数 `0xcbf29ce484222325`、质数 `0x100000001b3`）的值正确，更新顺序是"先异或后回绕乘法"，按 `as_bytes()` 逐字节迭代，`wrapping_mul` 保证 debug 与 release 同值，全程不经过 `Hash`/`Hasher`，因此旧实现里由 `str::hash` 写入的 `0xff` 终止符与额外混入的长度都不复存在。四条新用例中的三条各自钉住一种独立的错法（更新顺序写反、按字符码点而非 UTF-8 字节迭代、算法被换回标准库），`run()` 的三条检测与新前缀不冲突，全仓只有 `migrate.rs` 一处读写该列，没有引入依赖、表结构或事务变化。没有阻塞问题，只有两处措辞与用例区分力的非阻塞观察。

## 逐项核对

### 1. FNV-1a 实现

常量与循环（`migrate.rs:183` 至 `:199`）逐项核对：偏移基数等于规范的 14695981039346656037，质数等于 1099511628211（`0x0000_0100_0000_01b3` 的十六进制位数为 16 位，等价于 `0x100000001b3`）；`hash ^= u64::from(byte)` 只污染低 8 位，符合 FNV-1a 对单字节的定义；`hash = hash.wrapping_mul(...)` 是回绕乘法，不依赖构建模式。

`script_hash`（`migrate.rs:201` 至 `:208`）只做 `format!("fnv1a64:{:016x}", ...)`，没有 `Hash`/`Hasher` 参与。这一点由已知向量严格钉住：只要多写入一个终止符字节、多混一次长度或漏掉一次乘法，结果都不可能是给定值，因此"终止符或长度前缀混入"这条风险已被用例排除，而不只是靠读代码判断。

算法的跨版本稳定性成立的原因是它不依赖任何 std 实现，只依赖写死的常量与本文件的循环，源码不变则值不变。

### 2. 四条新用例是否钉住行为

我按三种典型错法复算了替代值，用来判断每条用例的区分力：

| 错法 | 空串 | `"a"` | `"foobar"` | `"迁移"` | 会被哪条抓住 |
|---|---|---|---|---|---|
| 正确实现 | `cbf29ce484222325` | `af63dc4c8601ec8c` | `85944171f73967e8` | `b07037ac985004f6` | — |
| 先乘后异或（FNV-1） | 不变 | `af63bd4c8601b7be` | `340d8765a4dda9c2` | 变 | `script_hash_matches_known_vectors` |
| 按字符码点迭代 | 不变 | 不变 | 不变 | `dc48cd094294da95` | 只有 `script_hash_uses_utf8_bytes` |
| 换回标准库哈希器 | 变（且无前缀） | 变 | 变 | 变 | 四条全部 |

由此得出两点：`migrate.rs:311` 至 `:315` 的公开向量覆盖了常量、更新顺序与多轮进位；`migrate.rs:331` 至 `:334` 那条不是重复，因为 ASCII 输入在"字节 vs 字符"两种实现下结果相同，多字节输入是唯一能分辨迭代单位的输入。

`script_hash_is_stable_for_same_input`（`migrate.rs:318` 至 `:322`）区分力最弱：纯函数以同一实参调用两次必然相等，它只能挡住重新引入随机种子（`RandomState`），挡不住确定性的 `DefaultHasher` 回归——后者由向量用例负责。这是可接受的冗余守卫，不算凑数，也不必改。

已有 7 条用例没有被误改：`git show 5b83fa9` 的差异只在文件头部（`script_hash` 的实现与注释）与 `mod tests` 末尾，`migrate.rs` 现有 11 个 `#[test]`，正好是 7 加 4；其中 `重复执行不重复建表也不报错` 是"写入时算一次、下次打开再算一次"这条往返的唯一覆盖，期望值一字未动，指纹改算法后它仍能证明新库自洽。`已执行脚本内容变化时拒绝启动` 写入的 `'deadbeef'` 不带前缀，与新值必然不等，断言依旧锐利。

用例命名与说明符合 `COMMENT_GUIDELINES` 第六节（英文 snake_case 加一行中文 `///`）。同文件其余中文测试名属 `detail/20` 排队中的英文化重构，不在本批范围，本批新用例不构成口径分裂。

### 3. `run()` 的三条检测与新前缀

`run()`（`migrate.rs:107` 至 `:181`）的顺序是版本连续、脚本未改、库不高于程序：`VersionGap` 在读取哈希之前就返回，与指纹无关；脚本比较对 `script_hash` 为 `NULL` 的行跳过，对当前二进制里不存在的版本 `continue`，因此真实的高版本库即便写入了带前缀的哈希，也只会落到 `DatabaseNewer`，不会被误报成 `ScriptChanged`——现有用例 `数据库版本高于程序支持时拒绝启动` 用 `NULL` 覆盖了这条路径，两条路径共用同一个 `continue` 分支，无需另补。

全仓读写点核对：`script_hash` 只出现在 `migrate.rs` 的建表语句、查询、比较、插入与测试里；`db.rs:197` 的 `schema_version()` 只读 `MAX(version)`，`tests/schema.rs` 完全不碰该列，没有任何第二处需要同步。

### 4. 兼容代价

旧开发库必然失败，这不是概率问题：新值一定带 `fnv1a64:` 前缀，旧值一定不带，所以第一条已执行版本就不相等，报 `ScriptChanged { version: 1 }`。计划文档第 45 至 47 行把现状（会报错）、处置（仓库未发布，删库重建）与后续约束（发布后不得再用这种破坏性切换）三段都写明了，如实。实现侧也一致：比较是精确相等，没有"接受两种格式"的过渡分支，因此不存在"看起来兼容其实半兼容"的状态。

一处可以更精确，但不影响本批：计划写的"引入指纹版本列"只提供标识，不恢复可校验性——旧算法是标准库哈希器，跨版本本就不可复现，过渡期只能盲接受旧行（标为旧版、跳过比较），不能重新算出旧值来比对。将来真要做双格式过渡时，靠的是"跳过比较"而不是"多一列"。这句话是否补半句由计划维护者定，代码侧没有对应待办。

### 5. 文档注释

旧说法已删净：`script_hash` 上方不再出现"长度与字节数一起参与"和"用标准库的哈希器"，全仓 `DefaultHasher` 只剩计划文档里描述现状的那一句；新注释明确写了"标准库的默认哈希器不保证跨 Rust 版本稳定"、"前缀用于未来换算法时识别旧值"、"不承担防篡改"，与 FNV 非密码学强度的定位一致。`MigrateError::ScriptChanged` 的说明没有随之改动，仍然是"有人改了已发布的迁移文件"，这在改后依然成立（旧格式库只是过渡现象，且已被计划文档承接）。

一处措辞不精确，见问题 1。

### 6. 依赖、表结构与事务

差异只有 `crates/ita-store/src/migrate.rs` 一个文件（49 增 7 删），`Cargo.toml`、`Cargo.lock` 都未改，`ita-store` 的依赖表仍是 `ita-kernel`、`rusqlite`、`ulid` 三项。`schema_version` 的建表语句未变，`script_hash` 仍是可空 `TEXT`，新值 24 字符（8 字符前缀加 16 位十六进制）没有长度约束冲突，索引与主键不受影响。迁移事务块（`migrate.rs:160` 至 `:178`）未动，两条迁移 SQL 未动。提交信息 `fix: 迁移脚本指纹改用跨版本稳定的 FNV-1a` 合规：类型正确、中文完整句、无 scope 前缀、无内部编号、无提交哈希与测试计数。

### 7. 是否补"只跑到 v1 的库升级到当前版本"的用例

判断是不补。理由有三条：本批验收边界明写只覆盖指纹算法与稳定性用例，而该路径落在迁移执行器的 `pending` 计算上，与本次改动没有耦合；按现码推演它是通的（`applied = [(1, h)]` 时 `current = applied.len() = 1`，`pending` 只含版本 2，在同一个立即事务里补上），没有新的证据说明它坏了；为了一个与本改动无关的分支临时加用例，会让本批的差异同时承载两个目的。这条留给存储层用例整理的批次统一处理更合适。
