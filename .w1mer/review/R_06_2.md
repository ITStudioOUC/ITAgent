# 初始表结构审查

提交 48d41d2（加内容寻址与快照的初始表结构）建起四张表，主键、唯一索引与工作区外键的基本面成立，用例也从"表存在"走到了"约束真的在拦"。撤下 ok 的理由只有一条：整份迁移没有一个 CHECK，"只在某种取值下才成立"的规则全留在注释里；而 SQLite 不支持追加约束、迁移扫描器又禁 DROP TABLE（`migrate.rs:278`），补约束只能在 0002 做，晚一批就得重建表。

1. 非法组合是默认路径：`kind` 无取值域（`0002_content.sql:39`），`content_stored` 带 `DEFAULT 1`（`:44`），写墓碑时省略该列即得"tombstone 且 content_stored=1"。0017 的三种归宿（有内容、超阈值、墓碑）在语义上能表达，但没有一条 CHECK 固定"file 且 content_stored=0 时 hash 与 size 必填""tombstone 与 dir 的 hash 为空"。更贴合 0017 第九行的做法是把"未存内容"并进 kind 扩为四值，让非法组合不可表达。
2. 重定基线的留痕没进表：`rebased_by` 与 `rebase_reason` 是裸可空列（`:22` 至 `:24`），注释承诺的"是否经过人工确认"没有对应列，0006 的"会话起点基线是硬地板"也无标记位，至少要有 CHECK 限定只有 baseline 可非空。
3. 读集语义自洽：无记录靠行不存在表达，"无记录按未知处理、允许写入"（0018 第四节）不需要一行带空哈希，`last_hash` 非空（`:57`）没有问题。缺口在索引——按会话回收要全表扫，因为 `session_id` 上没有索引。
4. `blobs` 不带引用计数列，与 0006 一致；但文件头注释（`:4`）写的"引用计数所需的元数据"直接违反该决策，属陈述错误。宽限期起点缺字段：`created_at`（`:11`）是创建时间，不是"变为无引用"的时刻，而宽限期正是为"刚被引用、清单尚未提交"这个窗口服务的，06.9 前需补 `unreferenced_since` 或扫描运行表。
5. 快照条目不带 workspace_id，跨工作区查询必须 join `snapshots`（`:36` 至 `:46`）。这与 0006 自绘的形状一致，可接受，但 `0001_core.sql:4` 的"一切业务表都带 workspace_id"因此不再成立，应写明这处例外。
6. "只加不改"满足：0002 全是 CREATE，单列 CHECK 或加列日后尚可 `ALTER TABLE ADD COLUMN`，这一步不在扫描器黑名单里；跨列 CHECK（第 1、2 条要的那种）SQLite 加不了，重建表又撞 DROP TABLE 禁令，因此这两条只能本批次定形。计划里拆核心表与内容表两份文件，实际核心表已在 0001 建完，合并成一份是对的。
7. squash 会删两个最老的增量，而 `parent_id` 是无动作自引用外键（`:20`），子快照存在时删父会被外键拦住；要么给 `ON DELETE SET NULL`，要么在 squash 事务里显式重挂父边，现在没写。该列也没索引，按父查子与窗口查询都要全表扫。
8. 用例只有主键与 `snapshots.workspace_id` 外键（`schema.rs:41` 至 `:112`）：`snapshot_entries.snapshot_id`、`read_set` 两个外键、kind 取值域、墓碑与内容标记互斥、重定基线与 kind 的关系都没测；用例名"两张内容表都存在"（`:24`）实际遍历四张表。

### 独立验证了什么、怎么验证的

reviewer 是只读角色，shell 只放行 git 与 w1mer，因此无法真的执行 `sqlite3`。改为读本仓实际编译进去的那一份引擎源码：`Cargo.lock:190` 锁 `libsqlite3-sys 0.30.1`，其随包 `sqlite3/sqlite3.c:462` 声明 `SQLITE_VERSION "3.46.0"`。引擎行为加上手算真值表，是可复核的替代，但比实跑弱一档，这一点如实记在这里。

- **CHECK 求值为 NULL 时算通过，这条说法成立。** `sqlite3GenerateConstraintChecks` 对每条 CHECK 复制表达式后调用 `sqlite3ExprIfTrue(pParse, pCopy, allOk, SQLITE_JUMPIFNULL)`（`sqlite3.c:134951`），而 `sqlite3ExprIfTrue` 的约定是"结果为 NULL 时按 `SQLITE_JUMPIFNULL` 跳转"（`:114640` 至 `:114647`，掩码定义在 `:18323`）。这里跳转目标就是 `allOk`，即通过。所以只写 `content_stored IN (0, 1)` 而不写 `IS NOT NULL` 确实会放过漏写的列；fixer 的判断不是猜测。
- **条目形态 CHECK 的接受矩阵**（手算，24 种组合）。`file` 只有在 `hash`、`size` 都非空且 `content_stored` 取 0 或 1 时通过，其余全部拒绝，包括 `content_stored` 为 NULL 与为 2 两种。`dir` 与 `tombstone` 只有在 `hash` 与 `content_stored` 皆空时通过。**`size`、`mode`、`mtime` 三列在这两个分支里完全没被引用**，所以"dir 带 size""墓碑带 size"能写进库；`file` 分支也没有 `size >= 0`，负尺寸同样能进。
- **三列成组 CHECK 等价于同进同出。** `IS NULL` 恒返回 0 或 1，永不为 NULL，所以 `(a IS NULL) = (b IS NULL)` 不会退化成 NULL。三列全空得 `1=1 AND 1=1` 为真，三列全给得 `0=0 AND 0=0` 为真，其余组合必有一项为假。因此"三列全空通过"成立，且两两组合与三列一起判断等价。用例只覆盖了三类非空组合，`rebase_confirmed_by` 单独非空这一种没测，但表达式本身也拦得住。
- **`content_stored` 去掉默认值改可空的三分法自洽。** `file` 显式 0（超阈值）或 1（已存）、`dir` 与墓碑留空（不适用），与 0017 的三种归宿（有内容、超阈值、墓碑）加上"目录不涉及内容"对齐；0017 第 9 行至第 12 行要求的"未存内容标记 + 尺寸 + 修改时间"正好落在 `content_stored = 0` 这一支。显式传 NULL 不会被默认值补上（`sqlite3ColumnDefault` 只在读出行时回填，写入值就是 NULL，`sqlite3.c:153325` 至 `:153342`），所以"不写该列即被拒"这条用例真的牵着约束。
- **`parent_id` 保留 NO ACTION 的取舍成立，但"整笔失败"有边界。** SQLite 的 `NO ACTION` 在语句结束时才检查（`RESTRICT` 才是立即检查），因此"父与子写在同一条 DELETE 里"会通过，只有"父被删、子还在"才失败。真正的 squash 形状是后者（删两个最老增量时，它们的子增量还在），所以"忘记重挂就整笔失败"在这条路径上成立。前提是 `PRAGMA foreign_keys=ON`（`db.rs:101`），任何绕过 `Store::configure` 建连接的地方都会让它静默失效——目前没有这样的路径，但这条保证是连接级的，不是库级的。
- **"跨列约束不能后补"仍然成立。** `sqlite3AlterFinishAddColumn`（`sqlite3.c:116450` 起）把新列定义文本拼进 `CREATE TABLE`，显式拒绝 `PRIMARY KEY` 与 `UNIQUE`（`:116487` 至 `:116498`）；既有列上没有任何追加约束的通道。所以本批是 0002 最后一个方便定形的窗口。
- **没有调用点需要跟着改。** 全仓检索 `content_stored`、`rebased_by`、`unreferenced_since`，除两份迁移与 `tests/schema.rs` 外零引用；`Store` 的公开面没变，`db.rs` 的既有用例（含"外键约束已开启"）不受影响。
- **文档改动核对。** `AGENTS.md` §8、`ROADMAP.md` 的 Task granularity 段、十七份 `detail/*_plan-*.md` 的开头句已经一致，全仓再没有"不超过八个文件""400 行"的残留（只剩 `detail/20` 里描述这次改动的引文）。新判据仍可操作："一个验收行为、单次可验证、不混入无关改动"三句都能在一次复审里对着 diff 判断，只是去掉了唯一的量化预警，拆分触发点从"超过八个文件"变成"做不完或验收口径说不清"。

### 复审发现的问题

9. **条目形态 CHECK 漏了 `size`，与本批自己的处置记录冲突（中）。** `0002_content.sql:76` 至 `:80` 的第二支只写了 `hash IS NULL AND content_stored IS NULL`，而处置记录第 1 行与 `CHANGES.md` 都写成"`dir` 与墓碑必须三者皆空"。谁会注意到：没有人。用例 `tombstone_and_content_are_mutually_exclusive`（`schema.rs:205` 至 `:232`）只测了 hash 与 content_stored 两种越界，没有一条让目录或墓碑带 size。触发路径是默认实现而不是疏忽：06.6 写条目时若对每个路径统一取一次 `lstat` 并整行填充，目录与墓碑自然带上 size，而 CHECK 默许。后果是残留清单与会话对比里出现"墓碑却有 64 字节"这类不自洽的行，且这类行无法靠后来的迁移补约束（跨列 CHECK 加不上）。建议把第二支补成 `AND size IS NULL`，第一支补 `size >= 0`（负尺寸会污染 0017 要求的"标注尺寸"）。
10. **`entry_kind_is_limited_to_file_dir_and_tombstone` 证明不了取值域（低至中）。** `kind = 'symlink'` 同时违反形态 CHECK（两个分支的 kind 条件都不成立，整式为假），所以把单列 `CHECK (kind IN ('file','dir','tombstone'))` 整行删掉，这条用例仍然通过。事实上形态 CHECK 已经蕴含了取值域，单列 CHECK 是冗余的第二道锁。谁会注意到：没有，用例的断言消息却说"未知的条目类型应当被拒"。建议把用例说明改成"取值域由形态 CHECK 兜住，单列 CHECK 是冗余保险"，或补一条只让单列 CHECK 生效的用例（现在的表结构下构造不出来，所以说明改文案更实际）。
11. **"确认者为空即没有人工确认"与实现不一致（低）。** `0002_content.sql:37` 至 `:38` 的注释用"为空"表述，实现只认 NULL；`rebase_confirmed_by = ''` 与另外两列非空一起写入会通过，被当成有确认。谁会注意到：没有，用例只用 NULL 与完整字符串。建议注释改成"为 NULL 才算没有人工确认，写入方不得用空串代替"，或让 06.7 的写库路径拒绝空串。

13. **本批提交的两份文档对 `snapshot_entries.hash` 外键给出相反结论（低至中）。** `detail/20` 的 3.3 节（`:262` 至 `:266`）把它写成"硬窗口内的最后一次机会"并明确建议补，`CHANGES.md`（`:228` 至 `:230`）记录该方案已被否决。下一批 06.2.2 的探索者会读 `detail/20`，很可能照着补上去，然后撞上超阈值条目（见下节）。建议在 `detail/20` 那一段就地加一句"已裁决不补，理由见 CHANGES"，与"已采纳的 ADR 不再修改正文"同理，让两份文档不再打架。同一节 `:256` 至 `:258` 还有一处自相矛盾：说"列级 CHECK 只引用自身列"，紧接着给出的 SQL 却引用 `created_at`；结论（可后补）不受影响，但判据写错会让后人误判哪些约束不能后补。

### 关于 `snapshot_entries.hash` 外键的独立意见

fixer 的理由成立。0006 第 34 行与 0017 第 9 行至第 12 行都写明超过阈值的文件"只记录尺寸、修改时间与哈希，不存内容"，CAS 写入发生在阈值判定之后，所以这类哈希不会在 `blobs` 里有行；表里也没有任何"未存内容"标志可以让外键条件化。SQLite 没有部分外键，`content_stored = 1 时才检查`这种条件外键表达不出来，所以加 `REFERENCES blobs(hash)` 会把 0017 规定的正常条目判成悬空引用，属误伤。

结论：不补外键是对的，但这条缺口要有明确的承接者，而现在 `CHANGES.md` 只写了"被否掉"，没写"由谁在何时检查"。我的建议是把检查放到代码侧：06.6 写入时断言 `content_stored = 1` 的条目其 hash 必在 `blobs` 里（一条 `SELECT EXISTS` 就够），06.8 回滚前对每个有内容记录的条目同样核对，缺失内容写进残留清单而不是让写回中途失败。没有外键时这条坏数据的表现形式是"GC 从条目出发标记不到任何对象，回滚时才在写回那一步炸"，所以越早断言越省事。若要表级兜底，只剩两条路——给 `blobs` 补"仅元数据"的行，或加触发器——前者会让 GC 的标记根语义变糊，后者引入隐藏行为，都不如代码断言。

## 二次复审处置（批次 06.2.1.1）

1. **条目形态 CHECK 漏 `size`、`mode`、`mtime`（问题 9）。** 约束从两支拆成三支：`file` 支

### 独立验证了什么、怎么验证的

本轮 shell 仍只允许 git 与 w1mer，`sqlite3` 可执行文件在机器上（`/usr/bin/sqlite3`）但调用被

（`Cargo.lock:190` 锁 `libsqlite3-sys 0.30.1`，其随包 `sqlite3/sqlite3.c:462` 声明
`SQLITE_VERSION "3.46.0"`），二是手算真值表。用例本身能跑，但那是实现者的自测，本轮没有独立

### 一、墓碑带 size 这条坏数据确实写不进去了

三支的判定列如下，逐列核对过：`file` 要求 `hash`、`size` 非空且 `size >= 0`、`content_stored`
非空且取 0 或 1；`dir` 要求 `hash`、`size`、`content_stored` 三者皆空；`tombstone` 要求
`hash`、`size`、`mode`、`mtime`、`content_stored` 五者皆空。墓碑带 `size = 64` 的求值过程是：
`kind = 'tombstone'` 让第一支与第二支的 kind 条件都为假，整支因此为假；第三支要求
`size IS NULL`，实际非空，同样为假；三支相或为假，约束拒绝。这条与主 Agent 的实跑结果一致。

上一轮的问题是第二支完全没有引用 `size`，所以目录与墓碑都能带尺寸；现在两支各自出现 `size`，
而且墓碑支把它与 `mode`、`mtime` 一并纳入。就"堵住这类行"这个验收口径而言，改动是到位的。

### 二、CHECK 求值为 NULL 的绕过路径：本表达式里不存在

引擎行为先复核一遍：`sqlite3GenerateConstraintChecks` 对每条 CHECK 复制表达式后调用
`sqlite3ExprIfTrue(pParse, pCopy, allOk, SQLITE_JUMPIFNULL)`（`sqlite3.c:134951`），而
`sqlite3ExprIfTrue` 的约定是结果为 NULL 时按 `SQLITE_JUMPIFNULL` 跳到目标（`:114640` 至
`:114647`，掩码定义在 `:18323`），跳转目标就是通过。所以"求值为 NULL 会被判通过"这条前提成立。

要出问题，必须让整条表达式能求值成 NULL。逐层看：三支开头都是 `kind = '<字面量>'`，而 `kind`
是 `NOT NULL`，因此三支的 kind 比较各有确定真值，并且恰好一支为真、两支为假。支内其余子条件
全部是 `IS NULL` 或 `IS NOT NULL`，恒返回 0 或 1，永不为 NULL。唯一的比较式 `size >= 0` 前面
紧贴着 `size IS NOT NULL`，而 SQLite 的 AND 是三值逻辑（`sqlite3.c:95650` 至 `:95665` 的
`and_logic` 表），假与 NULL 相与得假而不是 NULL，所以 `size` 为空时这一支一样是确定的假。
于是整式在 `kind` 取任何值、其余列取任何值（含 NULL）时都落在 0 或 1 上，不会退化成 NULL。

一条已接受的边界，不是漏洞：`size` 列是 INTEGER 亲和性，但亲和性只做转换、不做类型限制。
`0.5` 这类不能无损转成整数的实数原样以 REAL 存下，`'abc'` 这类非数字文本以 TEXT 存下，两者
都不等于负值，所以 `size >= 0` 拦不住它们。比较跨存储类别时按类别顺序比（数值小于文本，
`sqlite3MemCompare` 在 `sqlite3.c:89404` 至 `:89443` 先把数字一侧判小），所以 `'abc' >= 0`
求值为真，同样通过。实际风险可以忽略——06.6 的尺寸来自 `lstat`，永远是整数——所以不为它加
`typeof(size) = 'integer'` 这类额外判断，但要知道这道约束保证的是"非负"，不是"非负整数"。

每列是否都被显式判定，逐列列一下：`file` 支判定 `hash`、`size`、`content_stored`；`dir` 支判定
`hash`、`size`、`content_stored`；`tombstone` 支判定 `hash`、`size`、`mode`、`mtime`、
`content_stored`。`mode` 只在墓碑支出现，这是下一节讨论的设计选择，不是漏写；`path` 与
`snapshot_id` 由 `NOT NULL`、主键与外键负责，不在形态约束的职责内。

还有一条连接级的旁路，与约束表达式无关：SQLite 有 `PRAGMA ignore_check_constraints`
（`sqlite3.c:138429` 的 pragma 名表），打开后全部 CHECK 静默失效。它默认关闭，本仓也没有任何
一处设置它（`db.rs:101` 只设 `foreign_keys`，`db.rs:123` 只读 `journal_mode`），因此当前不构成
风险；但和"外键只在连接上生效"一样，这条保证是连接级的。将来若有第二条建连路径（例如诊断工具
直连库文件），它同样要记得这是一个可以关掉的开关。

### 三、dir 保留 mode 与 mtime：这个划分自洽，我同意

三条理由，其中第一条是决定性的。

区分的职责不落在这两列上。`file` 与 `dir` 的分界是 `hash`、`size`、`content_stored` 三列的
"全有"与"全无"，这两组取值互补，任何一行只可能落进一支，所以文件行与目录行在 CHECK 上不会
混淆；`mode` 与 `mtime` 在 `file` 支里同样不判空，它们既不参与区分，也不影响取值域的完整性。
所以"目录与文件在 CHECK 上区分不足"这个担心不成立：需要区分的那三列已经全都判了。

`size` 与 `mode`、`mtime` 不是同一类量。`size` 在本表里被 0017 用作"标注尺寸"，语义是文件正文
长度，目录的 `st_size` 是文件系统块尺寸，与回滚无关，写进来会让残留清单失去意义；`mode` 与
`mtime` 则确实是目录自身的事实，0006 把条目定义为"记录当时这个路径是什么"，回滚要恢复目录权限
时这两列是唯一来源。

时间窗口不可逆。本仓的跨列 CHECK 只能在建表时定形（`sqlite3AlterFinishAddColumn` 只接受新列的
column-def，`sqlite3.c:116450` 至 `:116499`；迁移扫描器又禁 `DROP TABLE`），本批若判空，等于把
目录的这两个事实永久排除在表外。"允许而不要求"是这里唯一保守的方向。

需要写清的两条边界，它们不是回退理由，而是承接关系的说明：其一，允许不等于要求，目录行的
`mode` 与 `mtime` 都可以为空，所以"目录权限一定可恢复"不是表结构保证的，要由 06.6 写入时填；
其二，`file` 支没有要求 `mtime` 非空，而 0017 对超阈值文件要求"尺寸与修改时间"，这条同样只能
落在 06.6 的写入路径上。两处都应写进 06.6 的验收。

第二条留一个需裁决的口子：若希望"超阈值条目一定带修改时间"由表结构保证而不是写入纪律，本批
已经是最后的窗口（`ALTER TABLE` 之后加不上）。要精确表达得写成
`(content_stored = 1 OR mtime IS NOT NULL)`，光加 `mtime IS NOT NULL` 会连带要求已存内容的
普通文件也带修改时间，超出 0017 的范围。我的意见是不补：0017 第 12 行只对超阈值那一档提要求，
把它压进一个三支相或的表达式里，代价是这张表最需要一眼读懂的约束多一层括号，收益只是省掉
06.6 的一条写入纪律。落差改为写进 06.6 的验收。

### 四、重定基线三列的空串判断：堵住了空串，没有误伤合法用法

逐列看：`rebased_by`、`rebase_reason`、`rebase_confirmed_by` 各加一条
"为空或非空串"。前面的 `IS NULL` 守卫保证 `<> ''` 只在列非空时求值，而 `'abc' <> ''` 恒为
真或假，不会退化成 NULL，所以三条新子句不会把整条约束变成可被 NULL 绕过的形状。合法用法上，
任何非空字符串都通过：中文原因、英文用户名、带空格的人名都不受影响；唯一被拒的是空串本身，
而空串在任何口径下都不携带"谁"或"为什么"。

"删掉会有人注意到"这一点可以构造出来：三列都非空时前两个相等式都成立，此时只有新子句为假才会
拒绝，因此用例里"空串的确认者""空串的发起人""空串的原因"三条各自唯一地牵着新子句，删掉新子句

这种病态输入与"用空白填充"混为一谈，收益不足，不作为问题记录。

### 二、三值逻辑：整式为 NULL 的路径不存在，且与合取顺序无关

前提先复核一遍：CHECK 表达式求值为 NULL 时算通过。引擎的做法是对每条 CHECK 复制表达式后调用
`sqlite3ExprIfTrue(pParse, pCopy, allOk, SQLITE_JUMPIFNULL)`（`sqlite3.c:134951`），而
`sqlite3ExprIfTrue` 的约定是"求值为 NULL 时按 `SQLITE_JUMPIFNULL` 跳到目标"（`:114645` 至
`:114647`），跳转目标 `allOk` 就是通过。所以"退化成 NULL 等于绕过"这个前提成立。

`content_stored` 为空时的求值链如下，逐步写出：

1. `content_stored IN (0, 1)` 在 `content_stored` 为 NULL 时求值为 NULL，这一步 fixer 没有
   否认，它只是被同一支前面的 `content_stored IS NOT NULL` 接住。
2. `(content_stored = 1 OR mtime IS NOT NULL)` 的值为：`mtime` 非空时是 `NULL OR TRUE`，即真；
   `mtime` 为空时是 `NULL OR FALSE`，即 NULL。
3. 两个值再与同一支前面的 `content_stored IS NOT NULL` 相合。该子句恒返回 0 或 1，在标记为空时
   是假，而 `and_logic[] = { 0, 0, 0, 0, 1, 2, 0, 2, 2 }`（`sqlite3.c:95653`）显示假与 NULL 相
   与得假。于是整支落在确定的假上，约束拒绝。

更值得说明的是：这个结论不依赖合取顺序。SQLite 的 `AND` 是二元左结合，实际求值顺序会把
`content_stored IS NOT NULL` 放在 `IN` 与新项之前，这是 fixer 的理由所依赖的一点；但即便有人
把新项挪到最前面，`NULL AND FALSE` 在真值表里同样是假（`and_logic` 的索引 `2*3+0` 得 0），
结论不变。代码生成层也自洽：`TK_AND` 走 `sqlite3ExprIfFalse(pLeft, d2, jumpIfNull^SQLITE_JUMPIFNULL)`
（`:114675` 至 `:114677`），左端为假时直接跳过右端并且不跳向 `allOk`，不会因为右端是 NULL 而
误判通过。

再看三支相或。只要有一支为 NULL 且没有一支为真，整条 CHECK 就会退化成 NULL 而被判通过，所以
必须每支都永不为 NULL：`file` 支如上；`dir` 与 `tombstone` 支的每个子条件都是 `IS NULL`，
恒返回 0 或 1，而开头 `kind = '<字面量>'` 与 `kind` 的 `NOT NULL` 一起保证比较有确定真值。
三支都落在 0 或 1 上，相或也就落在 0 或 1 上。结论：新项没有开洞。

### 独立验证的方式与边界

本轮 shell 只允许 `git` 与 `w1mer`，`sqlite3`、`python3` 的调用被权限拒绝，所以没有实跑数据库，也没有独立复跑用例。改用两条可复核的路径：一是按引擎源码核三值逻辑（`Cargo.lock:190` 锁 `libsqlite3-sys 0.30.1`，其随包 `sqlite3/sqlite3.c:462` 声明 `SQLITE_VERSION "3.46.0"`；`and_logic[]` 在 `:95653`、`or_logic[]` 在 `:95656`、CHECK 走 `sqlite3ExprIfTrue(..., allOk, SQLITE_JUMPIFNULL)` 在 `:134951`、NULL 按 `SQLITE_JUMPIFNULL` 跳转的约定在 `:114645` 至 `:114647`），二是按这两张真值表把 `entry_shape_matches_kind` 转写成求值模型，穷举 960 种列值组合逐格算。主 Agent 已实跑过的三条（未存内容缺修改时间被拒、补上可插、已存内容缺修改时间可插）作为交叉证据，但那是实现者侧的结果，不是本轮独立取得。这一点比实跑弱一档，如实记在这里。

### 一、最终形态的自洽性：任何能写进去的行都有确定真值，三支互斥覆盖

穷举的六个取值域是 `kind` 五种（含 `symlink` 与空）、`hash` 两种、`mode` 三种、`size` 四种、`mtime` 两种、`content_stored` 四种，共 960 种组合。结果是接受 25 种（`file` 18、`dir` 6、`tombstone` 1），求值为 NULL 的 24 种全部落在 `kind` 为空的行上。把 `kind` 为空的那一档剔掉再算一遍，768 种组合里求值为 NULL 的是 0 种——这是本轮最强的一条结论，它说明在库里可能出现的每一行上，约束都给得出确定答案。

这条结论的意义要说清：只有整条 `CHECK` 求值为 NULL 才会被当成通过，而 `kind` 是 `NOT NULL`，所以那 24 种组合根本写不进库。凡是能写进去的行，`CHECK` 要么真要么假，没有第三条路。而 `kind` 非空时三支的 `kind = '<字面量>'` 恰好一支为真、两支为假，假的那两支由 "假与任何值相与得假" 收掉，因此整式落在 0 或 1 上——这一层不依赖每一支内部是否全员 `IS NULL`，比五次复审的证明更强一点，也说明新增的 `(content_stored = 1 OR mtime IS NOT NULL)` 即便内部求值为 NULL 也翻不了盘。

三支互斥这一点按列核对过：文件行要求 `hash`、`size`、`content_stored` 三列全有，目录行要求这三列全无，墓碑行要求 `hash`、`size`、`mode`、`mtime`、`content_stored` 五列全无，因此任何一行最多落进一支，不存在"两支同时为真"让非法行通过检查的路径。逐项边界也逐个算过：标记 0 且 `mtime` 空为假、补上 `mtime` 为真、标记 1 且 `mtime` 空为真、`size = -1` 为假、目录带 `size` 为假、目录带 `0o755` 与 `mtime` 为真、全空墓碑为真、墓碑带 `size` 为假、`symlink` 为假、`kind` 为空为 NULL。与五次复审的手算一致。

### 二、最终 CHECK 组合是否留下语义荒谬的行

就这套组合的**设计**而言，没有。判定逐支核对：`file` 支要求 `hash`、`size`、`content_stored` 三列全有且 `size` 非负、标记取 0 或 1，并要求标记为 0 时 `mtime` 非空；`dir` 支要求同样这三列全空、`mode` 与 `mtime` 可空；`tombstone` 支要求五列全空。这三支的判空集合两两不相容，任何一行最多落进一支，因此不存在"某一支放宽后把另一支的行放进来"的路径——`mtime` 这一项只加在 `file` 支内部，`dir` 与 `tombstone` 的判空集合一个字都没动。

语义上三种承诺各自内部一致、互相不重叠：`file` 承诺哈希、尺寸、内容标记齐全，正文未存的再额外承诺修改时间，与 0017"未存内容标记与尺寸、修改时间"逐项对齐；`dir` 承诺"当时是个目录"，因此不许有哈希与正文尺寸，而允许 `mode` 与 `mtime`——目录确实拥有这两项事实，回滚恢复目录权限时是唯一来源；`tombstone` 承诺"当时这里没有东西"，因此五列全空。

有一层要说清，否则"没有荒谬行"会被读得过宽：这套组合管的是**哪些列必须成组出现**，它管不到**某一列的取值是否有意义**。后者依赖各列自己的判断，而这几列自初始迁移起只做了 `IS NULL` 与极少数数值下界，没有空串判断与类型判断。这些宽松之处都是本批之前就存在的，不属于本批判据，按角色约定只在给主 Agent 的报告里说明，不进本文件的审查条目，也不影响 `ok`。

### 三、`mtime` 与 `mode` 在三支里的归属不是拼凑出来的

`mode` 只在 `tombstone` 支被判空、在 `file` 与 `dir` 两支都自由，这个不对称不是遗漏：`file` 与 `dir` 的区别由 `hash`、`size`、`content_stored` 三列承担，`mode` 不参与区分；而墓碑必须"什么都没有"，所以它连 `mode` 一起判空。同理 `mtime` 在 `file` 支只对标记 0 有要求（正文未存时要靠它判断磁盘上的文件动过没有），在 `dir` 支完全自由，在墓碑支必须为空。三支各自对这两列的要求都能从 0006 的"条目记录当时这个路径是什么"与 0017 的"超阈值只报告"推出来，没有一条是为凑齐而加的。
