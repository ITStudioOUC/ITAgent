# Review R_06_6

Status: ok

## Conclusion

06.6 的提交把快照清单的创建与读取写成了计划第四节要求的样子：seq 用表内最大值加一在立即事务内分配，父边由存储层自动链接，快照 id 复用内核的 `CheckpointId`，content_stored = 1 的条目在事务内用 `SELECT EXISTS` 断言 blobs 存在而不加外键，条目形状是三种 kind 的枚举让非法形状不可表示，读路径把快照元信息与清单都收进本批。计划第十三条验收全部写成了测试，实现与计划逐条吻合。正确性不靠改动代码自证：seq 的原子性来自未改动的 `configure` 里 `set_transaction_behavior(Immediate)`，条目形状来自未改动的 `0002_content.sql` 形态 CHECK，id 的合法性来自未改动的 `id_type!` 宏校验，blobs 断言来自未改动的 `blobs::exists`。改动代码与这些未改动侧的契约没有冲突。

## 七项具体核对

1. **快照 seq 用 `COALESCE(MAX(seq), 0) + 1` 在立即事务内分配，无计数器表无迁移。** `snapshots.rs` 的 `create_in` 在事务内执行 `SELECT COALESCE(MAX(seq), 0) + 1 FROM snapshots WHERE workspace_id = ?1`。事务的立即性来自 `Store::configure`（未改动）里 `conn.set_transaction_behavior(Immediate)`，因此 `conn_mut().transaction()` 一开就是 `BEGIN IMMEDIATE`，读到的最大值在写回前不会被别人改。`snapshots` 表没有计数器表，本批也没有新增迁移文件，seq 分配不依赖任何计数器。
2. **父边由存储层自动链接。** `create_in` 取该工作区 `seq` 最大的快照作父，没有则父为空、`kind` 取 `baseline`，否则取 `incremental`。首个快照是基线、其余是增量这条不变量由存储层保证，调用方只给清单不给链结构。
3. **快照 id 复用内核 `CheckpointId`，不新造 `SnapshotId`。** `create_in` 用 `CheckpointId::parse(ulid::Ulid::new().to_string())` 生成 id。ULID 产出 26 字符 Crockford base32、首位落在 0 到 7，与 `id_type!` 宏的校验完全相容。`ids.rs` 未被改动，没有新增类型。
4. **content_stored = 1 的条目其 hash 必在 blobs 里，事务内 `SELECT EXISTS` 断言，不加外键。** `entries.rs` 的 `insert_in` 在 `content_stored` 为真时调用 `blobs::exists(tx, hash)`，不存在则返回 `MissingBlob` 错误，整笔回滚。`snapshot_entries.hash` 列没有外键，超阈值条目（content_stored = 0）带哈希却没有 blob，加外键会把正常条目判成悬空，因此断言放在写入路径而不是表结构层。
5. **条目形状是三种类 Rust 枚举，非法形状不可表示。** `SnapshotEntry` 是 `File` / `Dir` / `Tombstone` 三变体：墓碑没有 `content_stored`、`mode`、`mtime` 字段，目录没有 `hash`、`size`，只有文件带内容标记。文件条目 `content_stored = 0` 却缺 `mtime` 这一唯一无法在类型层面不可表示的形状，由写入路径以 `InvalidEntryShape` 校验错误拒绝，而不是落进表结构的 CHECK 兜底。
6. **读路径属于本批，跨工作区校验靠 join `snapshots.workspace_id`。** `Store::snapshot` 与 `Store::snapshot_entries` 是公开只读方法。`snapshot_entries` 表不带工作区列，两个读路径都先 `SELECT EXISTS(... FROM snapshots WHERE id = ?1 AND workspace_id = ?2)` 校验归属，不等则返回 `UnknownSnapshot`。
7. **每条验收标准都写成测试且通过。** 计划第四节有十三条验收，`tests/snapshots.rs` 有十三个 `#[test]`，与计划逐条对应。主 Agent 的提示词写"十四条"，是计数差一，不是实现缺陷——计划与测试文件都是十三条，实现与计划一致。

## Findings

- `entries.rs` 的 `row_to_entry` 对未知 kind 返回 `rusqlite::Error::InvalidParameterName`。这个变体本意是命名参数错误，用在数据校验上是误用。实际不可达：`kind` 列被 `0002_content.sql` 的 CHECK 约束在 `('file', 'dir', 'tombstone')`，不会有第四种值落库。属外观瑕疵，不影响正确性，不阻塞。
- 除上述一点外，未发现会让测试通过但语义错的地方。风险表里"用计数器分配 seq""父边恒为空""kind 恒为 incremental""blobs 断言在提交之后做""超阈值缺 mtime 不被拒""跨工作区读不校验"六处，实现都按计划的对策落地，且被对应测试钉住。

## 架构影响（供 CHANGES.md）

- `Store` 新增三个公开方法：`create_snapshot`（写）、`snapshot` 与 `snapshot_entries`（读）。快照链的 seq 与父边从"调用方给的结构"变成"存储层不变量"，首个快照是基线、其余是增量的契约移到存储层。
- 新增公开类型：`SnapshotEntry`（三 kind 枚举）、`CreatedSnapshot`、`SnapshotInfo`。新增错误变体：`MissingBlob`、`UnknownSnapshot`、`InvalidEntryShape`。
- 读路径（快照元信息 + 清单）成为 06.7 squash 与 06.8 回滚对齐的公共依赖，与 06.5 把 `get` 收进本批同型。
