# Review R_03_4

Status: issues

## 结论

装配主体正确：`&input[token.offset + 2..]` 的切片安全且基准正确，`<<` 之后的分隔符不会混进参数，`ita edit a.rs <<'X'` 的 args 恰好是 `["edit","a.rs"]`。问题集中在结构错误的类型、重定向目标的空值校验与两个上限参数的形状，因此判为有问题。

## 发现

1. 两个 heredoc 的错误类型落错，`ConflictingHereDoc` 分支不可达（`crates/ita-kernel/src/command/parse.rs:85-95`）。`heredoc = Some(..)` 之后立刻 `break`，循环再也看不到第二个 `HereDocStart`，:85 与 :55 两处 `heredoc.is_some()` 都是死代码；实际拦截来自 `heredoc.rs:142-149`，报的是 `TrailingText` 并提示"不要在正文之后追加说明"，与真实原因无关。
2. `<` 与 `<<` 的拒绝不对称。`< in <<'X'` 报 `ConflictingHereDoc`（parse.rs:88-90），`<<'X' ... < in` 报 `TrailingText`，同一条规则两种错误类型。
3. 重定向目标允许空串（parse.rs:73-82）。`> ""` 装配出 target 为空的 `Redirect`，`write_paths()` 返回 `[""]`；资源键层若按 `root.join(target)` 归一，空串拼出的正是工作区根目录。另 `ast.rs:27-29` 声称解析器会去掉多余与末尾斜杠，parse.rs 未做任何归一，这条契约目前与实现相反。
4. `MAX_TOKENS` 挡不住内存放大（parse.rs:34-40、126-130）。`scan` 返回的 `Vec<Token>` 里每个词已各持一份 `String`，上限在分配完成之后才执行；注释"词法层已经限制了输入规模"不成立，lex.rs 没有长度门。
5. 两个上限的形状互相矛盾（parse.rs:29、122、130）。`max_body` 是裸 `usize`，`MAX_TOKENS` 是硬编码常量；0018 第九节要求参数走配置结构，且 `MAX_TOKENS` 不在参数表里。`parse_with_defaults` 公开再导出（mod.rs:20），生产代码误用它没有任何摩擦，"生产路径应从配置取值"只是注释。
6. 错误偏移有两套基准（parse.rs:19-21）。`MissingTarget` 与 `ConflictingHereDoc` 用输入绝对偏移，`scan_heredoc` 系列相对 `<<` 之后那段；`parse` 已是唯一入口却未写基准，`error.rs:17` 的"字节偏移"会被读成输入绝对偏移。
7. 测试缺口：缺"参数含 `=`"、"命令名带引号"、"`> \"\"`"、`MAX_TOKENS` 边界四类；`> >` 与三种 heredoc 结构拒绝已覆盖（parse.rs:181-184、196-215）。

## 未决

本批次新增的分隔符行尾检查把回车当空白接受（`heredoc.rs:144`），而终止行的回车不参与匹配（`heredoc.rs:69`），两条规则不一致。两条路径最终都报 `UnterminatedHereDoc`，与真实 bash 一致，因此影响只在诊断信息上，不构成错误放行。

## 处置记录

| 问题 | 处置 |
|---|---|
| `ConflictingHereDoc` 分支不可达，两个 heredoc 实际报残留文本 | 结构约束前移到装配之前：先数 `<<` 与 `<` 记号再装配，两条规则共用同一种错误 |
| `>` 与 `<<` 的拒绝不对称 | 同上，两者都由前移后的检查处理 |
| 重定向目标允许空串 | 空串按缺少目标拒绝，偏移指向那个空串 |
| `MAX_TOKENS` 在词法之后才检查，挡不住内存放大；且以常量硬编码 | 新增 `parse_with_limits` 让上限可配置；注释写明它限制的是装配工作量而不是输入字节数 |
| 缺用例 | 补等号参数、带引号的命令名、空目标、上限边界、同行两个 heredoc 五例 |

另一处实现事实：`ast.rs` 曾声称"去多余斜杠"，实际没有做；该注释在 03.1 已改为"只去多余
斜杠由解析器负责、符号链接归一属于租约层"，此处补记解析器当前不做任何路径归一。
