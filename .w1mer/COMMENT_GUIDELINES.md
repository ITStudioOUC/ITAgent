# ITAgent 注释规范

> 本项目所有代码注释遵循本规范。规范变更先改本文件，再改代码。
> 开发文档写作规范见 `.w1mer/DOC_GUIDELINES.md`。

## 一、总则

| 原则 | 说明 |
|---|---|
| 写语义，不写历史 | 注释解释"代码做什么、为什么这么做"，不记录"哪个任务或讨论修的" |
| 禁止内部编号 | 注释里不出现 ROADMAP 编号（`05.1`）、ADR 编号（`ADR-0003`）、提交哈希。根因归档在 `.w1mer/`，代码里用语言描述问题本身 |
| 语言统一中文 | 注释与说明文字用中文，术语保留英文（lease、landlock、CAS、heredoc 等），句子用中文；标识符（含测试函数名）用英文 snake_case，见第六节 |
| 宁缺毋滥 | 只写代码无法自明处。不写 `// i += 1` 这类废话 |

## 二、函数与接口注释（`///`）

按四段结构书写，无内容的小节省略：

```rust
/// <一句话：做什么>。
///
/// <算法思路 / 为何这样设计，1-3 句>。
///
/// # 步骤
/// 1. <第 1 步做什么>
/// 2. <第 2 步做什么>
///
/// # 边界与前提
/// - <参数约束 / 前置条件 / 特殊值处理>
///
/// # 副作用
/// - <修改了哪些状态 / 可观察影响>
///
/// # 注意事项
/// - <调用时机 / 性能代价 / 与其它模块的隐含契约>
```

规则：

- `# 步骤` 只给多步骤的复杂函数；单步函数一句话描述即可，不堆小节。
- `# 边界与前提` 必须覆盖空输入、边界值、非法参数的处理方式。
- `# 副作用` 必须标注对外部状态的修改：写盘、发事件、获取或释放租约、修改 head。
- `# 注意事项` 写调用时机、性能代价、并发约束。跨进程的契约尤其要写明。

本节的四段结构适用于实现代码的注释；测试函数只写一行说明，命名规则见第六节。

## 三、实现内部注释（`//`）

分步骤书写，步骤之间空一行，不写序号（改动步骤时无需重排）：

```rust
fn acquire(scope: &Scope, paths: &[PathId]) -> Result<Lease> {
    // 排序去重：固定顺序是原子获取多路径的前提，避免两个请求以相反顺序互等。
    let ordered = sort_and_dedup(paths);

    // 一次性尝试全部路径，任何一个被占立即整体失败并释放已拿到的部分。
    let lease = scope.try_acquire_all(&ordered)?;

    // 记录归属，供后续"文件已更新"通知反查读集。
    scope.record_holder(&lease)?;
    Ok(lease)
}
```

规则：

- 每个独立逻辑步骤前放一行，写这一段的意图，不写代码字面意思。
- 循环与分支内部只在关键判断处加注释；显然的代码不加。
- 长函数允许 `// ── 大段标题 ──` 做二级分区。

## 四、模块头注释（`//!`）

```rust
//! <模块职责一句话>。
//!
//! <关键不变量 / 与其他模块的契约，要点式列出>。
```

模块级不变量放这里，不散落在函数里。例如"本模块不做权限判定，只做文法解析"。

## 五、`unsafe` 与安全相关

每个 `unsafe` 块前必须有 `# Safety` 注释，写明调用者必须保证的前提，而不是复述代码。

```rust
// SAFETY: fd 由本函数刚创建且未移交他人，进程内无并发关闭路径。
unsafe { libc::dup2(fd, 1) };
```

沙箱、权限检查、文件路径规范化三处的注释必须写明"这是快速失败还是安全边界"——
混淆两者是本项目最容易埋下的漏洞。

## 六、测试函数命名与说明

测试函数名用英文 snake_case，标识符里不留中文；函数上方紧跟一行 `///` 中文说明。名字说清
"什么条件下、期望什么结果"，说明说清"这个用例守的是什么行为、为什么值得守"。两者分工
不同，不互相复述名字字面意思。

```rust
/// 未加引号的分隔符在正文含 `$` 时被拒：真实 shell 会展开变量。
#[test]
fn unquoted_delimiter_with_dollar_is_rejected() {
```

命名判据是"条件加期望结果"：前半段写前提，后半段点明期望。结果词用 `_is_rejected`、
`_is_accepted`、`_is_noop`、`_conflicts`、`_does_not_*`、`_reports_*` 这类可观察的说法；
`_test`、`_works`、`_ok`、`_correct` 不携带信息，一律不用。

好坏对照：

| 判据 | 好例 | 坏例 | 坏例的问题 |
|---|---|---|---|
| 条件写在名字里 | `unquoted_delimiter_with_dollar_is_rejected` | `dollar_is_rejected` | 少了"未加引号"这个前提，同模块里"有引号时含 `$` 反而被接受"的用例就与它无法区分 |
| 期望结果具体 | `terminator_with_trailing_space_does_not_match` | `bad_terminator_is_rejected` | 终止行带空格与带回车是两条不同用例，都写"被拒"就分不清守的是哪一条 |
| 保留原判据细节 | `unreachable_and_changed_reports_unknown_direction` | `unreachable_and_changed_is_rejected` | 这条守的是"无法判断新旧所以不给方向"，写成"被拒"等于把判据换成了另一条规则 |
| 标识符纯英文 | `heredoc_body_is_captured_into_command` | `heredoc_正文被收进命令` | 中文与英文用下划线拼在一起，标识符里仍留着中文 |

规则：

- 中文名里的区分细节必须保留：`不报方向` 写成 `reports_unknown_direction`，`按第一个闭合
  处理` 写成 `splits_at_first_close`，`而不是覆盖` 写成 `not_overwritten`，`只解释四个`
  写成 `only_interprets_four`。丢掉这些词，等于丢掉这条用例存在的理由。
- 混合名（中文夹着下划线拼接的英文术语）与纯中文用下划线分段的名字都要改成纯英文，
  中文部分承载的语义（哪个动作被拒、为什么被拒）必须落进英文名或说明行，不能只剩一个
  笼统的"被拒"。
- `///` 写行为与代价，已有的 `//` 行内注释写实现机制，两者不重复。名字本身已足够自明的
  用例同样要写这一行，它是原中文语义的唯一载体。
- 断言消息、表驱动用例里的 `name` 字段是给人看的诊断数据，不是标识符，仍然用中文。

## 七、禁止项

| 禁止 | 替代 |
|---|---|
| `// B003：...`、`// 05.1 ...`、`// ADR-0002 ...` | 语义描述 |
| `// hack / workaround / temp / 临时补丁` | 语义描述；确有简化时用 `// ponytail:` 标注已知上限 |
| `// TODO` 无主 | `// 未实现：<缺什么能力>，见 ROADMAP <编号>`（ROADMAP 编号允许出现在这一种情况：指向未完成工作） |
| 中英混杂、无标点的流水注释 | 完整中文句 |
| 与代码重复的注释 | 删除 |
