# 批次 07.3 必需与非必需启动门与降级的执行计划

拆分依据给 07.3 的验收是"必需未就绪时激活返回未就绪，非必需失败只标记降级"。核对基线 bb02c19 的已提交代码、07.1 的执行计划（detail 28）、07.2 的执行计划（detail 29）、ADR 0013 与 0014 之后，结论是：**验收口径成立且不需要改，但它依赖的六件事必须写进计划，否则实现者会在细节上做对状态、做错语义。** 六件事分别是：启动门与计划是纯逻辑，落在 `ita-server` 的 `units` 模块，建在 07.1 的 `UnitId`/`Topology` 与 07.2 的 `UnitState`/`Supervisor` 之上（ADR 0013 明确"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，unit 类型不得与工作流节点类型混用）；启动计划声明哪些 unit 是必需（激活门）、哪些是非必需（降级），必需集非空，计划与拓扑交叉校验；启动门是纯函数，必需 unit 全部就绪才返回就绪，任一必需 unit 未就绪（未启动、启动中、失败）都返回未就绪，非必需 unit 失败只标记降级不阻塞激活；就绪不等于运行由 `Ready` 与 `Starting` 的区分承载，门只认 `Ready` 不认 `Starting`；unit 状态落库与 `units` 表建表归 07.3（07.2 计划 detail 29 第 2.6 条明确裁决），激活门需要持久化降级状态供 07.4 的能力集快照消费；07.3 不引入 tokio、不碰异步执行，真实 unit 的异步加载留到后续批次。文件规划 `crates/ita-server/src/units/{activation,plan}.rs` 与现状吻合，但 07.2 计划把 `units` 表建表与 unit 状态落库归 07.3，因此本批还需新增迁移文件与 `ita-store` 的 unit 状态操作，文件规划不完整。

## 结论

1. 07.3 的原始拆分成立。基线 bb02c19 的 `ita-server` 只有 `lib.rs` 与 `units` 模块（`mod.rs`、`topology.rs`），07.2 在其上加 `state.rs`、`probe.rs`、`supervisor.rs`，07.3 在其上加 `activation.rs` 与 `plan.rs`。需要改写的是"怎么做"，不是"做什么"。
2. **启动门与计划是纯逻辑，落在 `ita-server`，不进内核。** ADR 0013 的硬边界是"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，代价段点名"两套监督语义（unit 与工作流节点）容易混淆，必须靠文档与类型分开"。因此 unit 类型必须独立于 `ita-workflow` 的节点类型，而内核的职责域是"上下文树的解析、命令文法的分析、租约与权限的策略判定"（`lib.rs` 文档注释），unit 启动门不在其中。07.1 已把 `UnitId`/`DepKind`/`Topology` 落在 `ita-server`，07.2 已把 `UnitState`/`UnitEvent`/`Supervisor` 落在同一模块，07.3 沿用同一模块，维持不改。
3. **启动计划声明必需与非必需。** 计划是 `StartupPlan` 类型，两个集合：`required`（必需 unit，激活门等待它们全部就绪）与 `optional`（非必需 unit，后台异步加载，失败只标记降级）。必需集非空（至少一个 unit 是必需，否则 CLI 永远激活不了）。计划与拓扑交叉校验：计划里的每个 unit 必须在拓扑里，必需集与非必需集不相交。计划是静态声明，在启动前建好，不动态建行。
4. **启动门是纯函数，必需 unit 全部就绪才返回就绪。** 门是 `activate(supervisor, plan) -> ActivationResult` 纯函数：对每个必需 unit，状态是 `Ready` 才计入就绪列表，否则计入未就绪列表；对每个非必需 unit，状态是 `Failed`/`NotStarted`/`Starting` 才计入降级列表，`Ready` 不计。未就绪列表为空则返回 `Ready`（带降级列表），否则返回 `NotReady`（带未就绪列表）。门不改变状态，只判定。
5. **就绪不等于运行由 `Ready` 与 `Starting` 的区分承载。** 门只认 `Ready`，不认 `Starting`。一个必需 unit 进程活着（`Starting`）但探针未通过，门返回未就绪。这是 ADR 0013 的核心语义，也是冷启动体感的关键。非必需 unit 的 `Starting` 状态计入降级（还在启动中，功能未可用），不是未就绪。
6. **unit 状态落库与 `units` 表建表归 07.3。** 07.2 计划（detail 29）第 2.6 条明确裁决："unit 状态落库与 `units` 表建表归 07.3，因为激活门需要持久化状态（server 重启后恢复 unit 状态）"。基线的两份迁移文件（`0001_core.sql`、`0002_content.sql`）都没有 `units` 表，07.2 不新增迁移。07.3 新增 `0003_units.sql` 迁移（只加不改），建 `units` 表存 unit 状态（`ready`/`degraded`/`failed`），并在 `ita-store` 加 unit 状态读写操作。`units` 表是 07.4 能力集快照的基础：能力集由 unit 状态推导（哪些就绪、哪些降级），07.4 读 `units` 表建能力集。
7. **07.3 不引入 tokio、不碰异步执行。** 基线的 `ita-server/Cargo.toml` 只有 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow` 四个依赖，没有 tokio、没有 async。07.3 是纯数据类型与纯函数加一次迁移，零新增依赖。真实 unit 的异步加载（非必需 unit 在后台启动）留到后续批次，07.3 的门是同步判定。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、07.2 的执行计划（detail 29）产出的类型、以及基线 bb02c19 的 `ita-server` 现状。

## 二、启动门与计划的实际形状

### 2.1 启动计划声明必需与非必需

`StartupPlan` 是两个集合：`required: BTreeSet<UnitId>`（必需 unit，激活门等待它们全部就绪）与 `optional: BTreeSet<UnitId>`（非必需 unit，后台异步加载，失败只标记降级）。计划是静态声明，在启动前建好，不动态建行。

计划与拓扑交叉校验：计划里的每个 unit 必须在拓扑里（`topology.units` 包含），必需集非空，必需集与非必需集不相交。校验失败返回显式错误，不静默继续。

ADR 0013 最小拓扑的实例化：`store → router → ipc`（必需）、`lease requires tools`（必需，`↔` 落单方向）、`model` 孤立（非必需，首次调用模型时才需要）、`telemetry` 孤立（非必需，软依赖）。因此计划是 `required = {store, router, ipc, lease, tools}`、`optional = {model, telemetry}`。

### 2.2 启动门是纯函数，必需 unit 全部就绪才返回就绪

`activate(supervisor: &Supervisor, plan: &StartupPlan) -> ActivationResult` 是纯函数：对每个必需 unit，状态是 `Ready` 才计入就绪列表，否则计入未就绪列表；对每个非必需 unit，状态是 `Failed`/`NotStarted`/`Starting` 才计入降级列表，`Ready` 不计。未就绪列表为空则返回 `ActivationResult::Ready { ready, degraded }`，否则返回 `ActivationResult::NotReady { not_ready }`。门不改变状态，只判定。

`ActivationResult` 是两变体：`Ready { ready: Vec<UnitId>, degraded: Vec<UnitId> }`（激活成功，带就绪的必需 unit 与降级的非必需 unit 列表）与 `NotReady { not_ready: Vec<UnitId> }`（激活未就绪，带未就绪的必需 unit 列表）。

### 2.3 就绪不等于运行由 `Ready` 与 `Starting` 的区分承载

门只认 `Ready`，不认 `Starting`。一个必需 unit 进程活着（`Starting`）但探针未通过，门返回未就绪。这是 ADR 0013 的核心语义。非必需 unit 的 `Starting` 状态计入降级（还在启动中，功能未可用），不是未就绪。`Failed` 的必需 unit 计入未就绪（不再重启，ADR 0013"版本一不级联重启"），`Failed` 的非必需 unit 计入降级。

### 2.4 降级标记是持久化写，不是门的一部分

门是纯判定，不写库。降级标记是门之后的独立步骤：server 拿到 `ActivationResult::Ready { degraded }` 后，把降级列表里的每个 unit 状态写成 `degraded` 落库（`units` 表）。这是 `ita-store` 的 unit 状态操作，不是 `ita-server` 的门逻辑。门与落库分离，让"判定"与"持久化"各归各位。

### 2.5 `units` 表是 07.4 能力集快照的基础

`units` 表存 unit 状态（`ready`/`degraded`/`failed`），07.4 读它建能力集快照。表结构是 `id TEXT PRIMARY KEY`、`state TEXT NOT NULL`、`updated_at INTEGER NOT NULL`。`state` 是字符串不是枚举，取值域是 `ready`/`degraded`/`failed`。`updated_at` 是 epoch 毫秒，记录状态最后更新的时间。

### 2.6 unit 状态落库与 `units` 表建表归 07.3

07.2 的状态机在内存里（纯逻辑），不建表、不新增迁移。07.3 新增 `0003_units.sql` 迁移（只加不改，`CREATE TABLE IF NOT EXISTS units`），并在 `ita-store` 加 unit 状态读写操作。`ita-store` 的 `units.rs` 是 `pub(crate)` 函数，吃 `&Connection` 或 `&Transaction`，返回 `Result<..., StoreError>`，与 `heads.rs`、`events.rs` 同型。`Store` 结构加 `set_unit_state`、`read_unit_state`、`read_all_unit_states` 三个公开方法，与 `append_event`、`events_after` 同型。

## 三、ADR 对启动门与降级的硬要求

与 07.3 相关的决策分布在 ADR 0013、0014 与 ROADMAP 07 行，逐条对照如下。

| 要求 | 出处 | 07.3 怎么落地 |
|---|---|---|
| CLI 激活 server 时，只要指定的必需 unit 都达到就绪状态即可正常显示页面，其余非必需 unit 在后台异步加载 | 0013 决策段 | `StartupPlan` 声明必需与非必需，`activate` 门只等必需 unit 就绪，非必需 unit 失败只标记降级 |
| 就绪不等于运行 | 0013 决策段 | 门只认 `Ready` 不认 `Starting`，`Starting` 的必需 unit 计入未就绪 |
| 崩溃处理保守，版本一不级联重启，只标记降级 | 0013 决策段 | `Failed` 的必需 unit 计入未就绪（不再重启），`Failed` 的非必需 unit 计入降级 |
| 能力集合的变化推送给已连接的客户端 | 0013 决策段 | 07.3 落库降级状态，07.4 读 `units` 表建能力集快照并推送 |
| 依赖关系区分三种：硬依赖、软依赖、仅排序 | 0013 决策段 | 07.3 消费 07.1 的 `DepKind`，计划不消费种类（种类只影响 07.2 的失败传播） |
| unit 管进程生命周期，工作流管任务语义，两者不共享状态机 | 0013 决策段 | unit 启动门落 `ita-server`，不进内核、不与 `ita-workflow` 混用 |
| 两套监督语义靠文档与类型分开 | 0013 后果段 | `StartupPlan`/`ActivationResult` 独立类型，不与工作流节点类型复用 |
| 执行器是独立进程，不是 server 内的 unit | 0014 决策段 | 07.3 的 unit 是 server 内部子系统，不含执行器；`lease` 只做租约表维护与跨工作区资源仲裁 |
| 必需与非必需启动门与降级 | ROADMAP 07 行 | `activation.rs`/`plan.rs` 两文件 |
| 必需未就绪时激活返回未就绪，非必需失败只标记降级 | ROADMAP 07 行验收 | 门返回 `NotReady`（必需未就绪）或 `Ready`（带降级列表），非必需失败不阻塞 |

三处需要特别说清的核实结果。

**第一，`ita-server` 基线只有 `mod.rs` 与 `topology.rs`，`units` 模块由 07.1 建。** 基线 bb02c19 的 `crates/ita-server/src/units/` 只有 `mod.rs`（`UnitId`、`DepKind`）与 `topology.rs`（`Topology`、`find_cycle`、`startup_order`、`CycleError`），07.2 加 `state.rs`、`probe.rs`、`supervisor.rs`，07.3 在其上加 `activation.rs` 与 `plan.rs`。07.3 不修改 07.1 的 `topology.rs`，只消费它的 `Topology` 与 `startup_order`。

**第二，`units` 表建表与 unit 状态落库归 07.3。** 07.2 计划（detail 29）第 2.6 条明确裁决："unit 状态落库与 `units` 表建表归 07.3，因为激活门需要持久化状态（server 重启后恢复 unit 状态）"。基线的两份迁移文件（`0001_core.sql`、`0002_content.sql`）都没有 `units` 表，07.2 不新增迁移。07.3 新增 `0003_units.sql` 迁移（只加不改），并在 `ita-store` 加 unit 状态读写操作。

**第三，`lease` 不是执行器。** ADR 0014 明确"执行器是每个工作区一个独立进程，不是 server 内部的一个 unit"，0013 最小拓扑里的 `executor` 更名为**租约仲裁**，职责收窄为维护租约表与仲裁跨工作区资源。因此 07.3 的 unit 集合里 `lease` 是租约仲裁，不是执行器，测试里不得把执行器当成 unit 实例化。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **必需未就绪时激活返回未就绪。** 建 `store → router → ipc`（`router requires store`、`ipc requires router`），计划是 `required = {store, router, ipc}`，假探针对 `store` 返回 `NotReady`（`store` 保持 `Starting`），驱动监督者到阻塞，调 `activate`，断言返回 `NotReady` 且未就绪列表是 `[store]`（`router` 与 `ipc` 因依赖未就绪保持 `NotStarted`，不计入未就绪列表，它们是 `NotStarted` 不是 `Ready`）。守的是"必需未就绪时激活返回未就绪"。
2. **全部必需就绪时激活成功。** 建同一拓扑，所有探针返回 `Ready`，驱动监督者到完成，调 `activate`，断言返回 `Ready` 且就绪列表是 `[store, router, ipc]`（拓扑序），降级列表为空。守的是"全部必需就绪时激活成功"。
3. **非必需失败只标记降级，不阻塞激活。** 建 `store → router`（必需）与 `model`（非必需，孤立），假探针对 `store` 返回 `Ready`、对 `model` 返回 `Failed`，驱动监督者，调 `activate`，断言返回 `Ready` 且就绪列表是 `[store]`、降级列表是 `[model]`（`model` 失败不阻塞激活）。守的是"非必需失败只标记降级"。
4. **非必需未就绪计入降级。** 建 `store`（必需）与 `telemetry`（非必需，孤立），假探针对 `store` 返回 `Ready`、对 `telemetry` 返回 `NotReady`（`telemetry` 保持 `Starting`），驱动监督者，调 `activate`，断言返回 `Ready` 且降级列表是 `[telemetry]`（非必需 unit 的 `Starting` 计入降级，不是未就绪）。守的是"非必需 unit 的 `Starting` 计入降级"。
5. **就绪不等于运行。** 建 `store`（必需），假探针对 `store` 返回 `NotReady`（`store` 保持 `Starting`，进程活着但未就绪），驱动监督者，调 `activate`，断言返回 `NotReady` 且未就绪列表是 `[store]`（`Starting` 的必需 unit 计入未就绪，不是就绪）。守的是"就绪不等于运行"。
6. **计划与拓扑交叉校验。** 建 `store → router` 拓扑，计划里含拓扑里没有的 unit（如 `ghost`），断言计划校验失败（显式错误，不静默继续）。守的是"计划与拓扑交叉校验"。
7. **必需集非空。** 建拓扑，计划里必需集为空，断言计划校验失败。守的是"必需集非空"。
8. **必需集与非必需集不相交。** 建 `store → router` 拓扑，计划里 `store` 同时在必需集与非必需集，断言计划校验失败。守的是"必需集与非必需集不相交"。
9. **unit 状态落库。** 建 `units` 表（迁移），调 `set_unit_state` 写 `store` 为 `degraded`，调 `read_unit_state` 读回，断言状态是 `degraded`。守的是"unit 状态落库"。
10. **七 unit 最小拓扑激活与降级。** 按 ADR 0013 最小拓扑实例化：`store → router → ipc`（必需）、`lease requires tools`（必需）、`model` 孤立（非必需）、`telemetry` 孤立（非必需），假探针对必需 unit 返回 `Ready`、对 `model` 返回 `Failed`、对 `telemetry` 返回 `NotReady`，驱动监督者，调 `activate`，断言返回 `Ready` 且就绪列表是全部必需 unit、降级列表是 `[model, telemetry]`。守的是"ADR 0013 最小拓扑的激活与降级"。

第 1、5 条守的是"必需未就绪时激活返回未就绪"与"就绪不等于运行"。第 2 条守的是"全部必需就绪时激活成功"。第 3、4、10 条守的是"非必需失败只标记降级"。第 6、7、8 条守的是"计划与拓扑交叉校验"。第 9 条守的是"unit 状态落库"。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 门把 `Starting` 当 `Ready`（把"进程活着"当就绪） | 正常路径通过，未就绪时才暴露 | 第四节第 5 条：断言 `NotReady` 的必需 unit 返回未就绪 |
| 非必需 unit 失败阻塞激活（把降级当未就绪） | 正常路径通过，非必需 unit 失败时才暴露 | 第四节第 3、4 条：断言非必需 unit 失败只标记降级，不阻塞激活 |
| 门改变状态（在门里写库或转移状态） | 正常路径通过，门是纯函数才暴露 | 门是纯函数，不写库、不转移状态；降级标记是门之后的独立步骤 |
| 计划与拓扑不交叉校验（计划里的 unit 不在拓扑里） | 正常路径通过，计划含幽灵 unit 时才暴露 | 第四节第 6 条：断言计划校验失败 |
| 必需集为空（CLI 永远激活不了） | 正常路径通过，必需集为空时才暴露 | 第四节第 7 条：断言计划校验失败 |
| 必需集与非必需集相交（一个 unit 既是必需又是非必需） | 正常路径通过，相交时才暴露 | 第四节第 8 条：断言计划校验失败 |
| `units` 表用枚举而不是字符串 | 编译通过，但"只加不改"的纪律被破坏 | `state` 是字符串，取值域是 `ready`/`degraded`/`failed` |
| unit 状态落库落 `ita-server` 而不是 `ita-store` | 编译通过，但"唯一数据库写者"被破坏 | unit 状态操作落 `ita-store`，`ita-server` 只消费 |
| 启动门落内核而不是 `ita-server` | 编译通过，但"两套监督语义靠类型分开"失效 | 启动门落 `ita-server` 的 `units` 模块，不进内核、不与 `ita-workflow` 混用 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：`units` 表建表与 unit 状态落库归 07.3，不是 07.2。07.2 计划（detail 29）第 2.6 条明确裁决。若把 `units` 表建表混进 07.2，会让"这一批只有一个目的"失效，且 07.2 的纯逻辑会被 IO 污染。这条职责分离是"这一批只有一个目的"的前提，不靠调用方记得"`units` 表归 07.3"。

## 八、已裁决的分歧点

一处分歧点由 Explorer 直接定形（`units` 表建表与 unit 状态落库归 07.3，沿用 07.2 计划 detail 29 第 2.6 条的裁决），其余三处（启动门的返回形状、计划的校验范围、降级标记的时机）也由 Explorer 直接定形，理由充分。

| 分歧 | 两种做法 | 定形 |
|---|---|---|
| 启动门的返回形状 | 甲：`ActivationResult` 两变体（`Ready` 带降级列表、`NotReady` 带未就绪列表）。乙：`Result<(), Vec<UnitId>>`（成功带降级列表、失败带未就绪列表） | **直接定形选甲。** 理由见第二节第 2.2 条。`ActivationResult` 是显式枚举，两种结果各有名字，不靠 `Result` 的 `Ok`/`Err` 语义承载"激活成功但降级"这种非错误结果 |
| 计划的校验范围 | 甲：计划与拓扑交叉校验（计划里的 unit 必须在拓扑里、必需集非空、两集不相交）。乙：只校验必需集非空 | **直接定形选甲。** 理由见第二节第 2.1 条。计划含幽灵 unit 会在门里静默通过（拓扑里没有这个 unit，门查不到它的状态），交叉校验让"计划里的 unit 必须在拓扑里"成为不变量 |
| 降级标记的时机 | 甲：门之后的独立步骤（server 拿到 `Ready` 结果后写库）。乙：门里写库 | **直接定形选甲。** 理由见第二节第 2.4 条。门是纯判定，不写库；降级标记是持久化写，与判定分离，让"判定"与"持久化"各归各位 |
| `units` 表建表与 unit 状态落库 | 甲：归 07.3。乙：归 07.2 | **直接定形选甲。** 理由见第二节第 2.6 条。07.2 计划（detail 29）第 2.6 条已裁决，07.3 沿用 |

## 九、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 07.3：能力集快照与变更推送（07.4）；真实 unit 实现（`store`、`router`、`ipc` 等，后续批次）；真实的每 unit 就绪探针实现（检查迁移、套接字、路由表，留到真实 unit 存在时）；非必需 unit 的异步加载（后台启动，后续批次）；执行器进程（0014，独立进程，不是 unit）；工作流节点类型（`ita-workflow`，与 unit 类型分开）；事件日志与模型代理（08.x）；本地 socket 与连接级工作区绑定（08.2）；group commit（08.4）；异步执行（07.3 是同步纯逻辑加一次迁移）。

## 十、Explorer 核对与补强（基线 bb02c19）

本节的核对对象是批次基线 bb02c19 的已提交代码，不是实现者的工作树。结论是：十条验收对基线全部成立，启动门与计划的口径都没有被证伪，需要改写的只是"怎么做"与一处文件规划的不完整。下面逐条记录核对结果与四处补强。

### 10.1 `ita-server` 现状核对：`units` 模块只有 `mod.rs` 与 `topology.rs`

基线 bb02c19 的 `crates/ita-server/src/units/` 只有 `mod.rs`（`UnitId`、`DepKind`）与 `topology.rs`（`Topology`、`find_cycle`、`startup_order`、`CycleError`），07.2 加 `state.rs`、`probe.rs`、`supervisor.rs`，07.3 在其上加 `activation.rs` 与 `plan.rs`。07.3 不修改 07.1 的 `topology.rs`，只消费它的 `Topology` 与 `startup_order`。

### 10.2 迁移文件核对：没有 `units` 表

`0001_core.sql` 建 `workspaces`、`sessions`、`nodes`、`events`、`workspace_seq`；`0002_content.sql` 建 `blobs`、`snapshots`、`snapshot_entries`、`read_set`。没有 `units` 表，也没有 unit 状态列。07.2 不新增迁移，07.3 新增 `0003_units.sql`。

### 10.3 07.2 产出类型核对：`UnitState`/`Supervisor`/`ReadinessProbe`

07.2 的执行计划（detail 29）产出 `UnitState`（六变体）、`UnitEvent`（六变体）、纯转移函数 `next`、`ProbeResult`（三变体）、`ReadinessProbe` trait、`Supervisor`（`step`/`run_until_blocked`/`shutdown`/查询方法）。07.3 的 `activate` 消费 `Supervisor` 的 `state` 查询方法，不重新实现状态机。07.3 的 `StartupPlan`/`ActivationResult` 与 07.2 的 `UnitState`/`Supervisor` 是同一 `units` 模块下的不同类型，互不混用。

### 10.4 四处补强

**第一，`units` 表建表与 unit 状态落库归 07.3。** 07.2 计划（detail 29）第 2.6 条明确裁决。07.3 新增 `0003_units.sql` 迁移（只加不改），并在 `ita-store` 加 unit 状态读写操作。这条裁决避免了 07.2 混入 IO 与建表，保持"这一批只有一个目的"。

**第二，启动门是纯函数，不写库、不转移状态。** 门是 `activate(supervisor, plan) -> ActivationResult` 纯函数，只判定不改变。降级标记是门之后的独立步骤（server 拿到 `Ready` 结果后写库），与判定分离。这保证了"门是纯判定"是可测试的（第四节第 3、4 条），且"非必需失败只标记降级"不依赖单一实现点。

**第三，就绪不等于运行由 `Ready` 与 `Starting` 的区分承载。** 门只认 `Ready`，不认 `Starting`。一个必需 unit 进程活着（`Starting`）但探针未通过，门返回未就绪。这是 ADR 0013 的核心语义。非必需 unit 的 `Starting` 状态计入降级（还在启动中，功能未可用），不是未就绪。

**第四，计划与拓扑交叉校验。** 计划里的每个 unit 必须在拓扑里，必需集非空，必需集与非必需集不相交。校验失败返回显式错误，不静默继续。这条让"计划里的 unit 必须在拓扑里"成为不变量，不靠调用方记得"计划与拓扑一致"。
