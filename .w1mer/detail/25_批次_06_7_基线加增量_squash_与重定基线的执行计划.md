# 批次 06.7 基线加增量 squash 与重定基线的执行计划

拆分依据给 06.7 的验收是"增量达 64 条时最老两条并入基线且有效条目不变，合并事务先重挂子快照再删父，重挂时父子快照属于同一工作区；自主模式重定被拒且留痕三列成组写入"。核对基线 7bd41c0 的已提交代码与 06.6 的计划（detail/24）之后，结论是：**验收口径成立且不需要改，但它依赖的五件事必须写进计划，否则实现者会在细节上做对数值、做错语义。** 五件事分别是：squash 是独立动词而不是折进 06.6 的 `create_snapshot`（06.6 明确不碰链改写，只按链追加）；保留窗口 64 是参数而不是散落常量（ADR 0018 要求配置入口）；合并事务里先重挂子快照再删父是无动作外键的硬约束（忘记重挂整笔失败）；重定基线是独立动词、自主模式一律拒绝、留痕三列成组写入；squash 折叠出的基线条目只含 file 与 dir，不含墓碑。文件规划 `squash.rs` 与 `retention.rs` 与现状吻合，另需在 `db.rs` 加错误变体与两个公开动词、在 `lib.rs` 声明模块。

## 结论

1. 06.7 的原始拆分成立。表结构（`snapshots` 与 `snapshot_entries` 的 CHECK、`parent_id` 的无动作自引用外键、重定基线留痕三列）与 ADR 0005、0006、0017、0018 都没有把这项工作推到别的批次，也没有出现让验收口径失效的变更。需要改写的是"怎么做"，不是"做什么"。
2. **squash 是独立动词，不是折进 `create_snapshot`。** 06.6 的计划明确"06.7 的重定基线是独立动词，会改写链，本批不碰链改写，只负责按链追加"。因此 06.6 的 `create_snapshot` 不调用 squash，06.7 提供独立的 `Store::squash_if_needed`，由 server（后续批次）在创建快照之后调用。这条与 06.5 把 `get` 收进本批、06.6 把读路径收进本批的裁决同型：链改写是独立职责，不混进追加。
3. **保留窗口 64 是参数，不是散落常量。** ADR 0018 要求"全部参数都要有配置入口""不允许以常量形式散落在调用点"。配置结构尚未落地（属于后续批次），因此 06.7 的 `squash_if_needed` 把保留窗口作为参数接收，由调用方（server）从配置结构读出后传入。存储层不硬编码 64。
4. **合并事务先重挂子快照再删父，是无动作外键的硬约束。** `parent_id` 是自引用外键，刻意不加级联也不置空（06.2.1 的裁决）。squash 删最老两个增量时，它们的子增量还在，若先删父后重挂，外键会拦住整笔。因此事务内顺序是：先把子快照重挂到基线，再删父快照。这条约定写进 0002 的列注释，并由"子快照存在时删父被拒"的用例把行为固定下来。
5. **重定基线是独立动词，自主模式一律拒绝，留痕三列成组写入。** 重定基线等于永久放弃之前的回滚点，不可逆。会话起点的基线是硬地板，任何模式下都不能删除（基线行只更新不删除）。自主模式（agent 无人值守连续推进）下重定基线一律拒绝，只有用户显式发起的调用才允许。留痕三列（`rebased_by`、`rebase_reason`、`rebase_confirmed_by`）由 CHECK 约束成组同进同出，且只对基线成立。
6. **squash 折叠出的基线条目只含 file 与 dir，不含墓碑。** 折叠是按路径覆盖、墓碑删除的左结合操作。折叠 B、I1、I2 后，被墓碑删除的路径不在结果里，因此新基线条目只有 file 与 dir。这条与 06.6 的条目形状校验对齐：写入路径的 Rust 类型让"墓碑带 content_stored"不可表示，折叠结果天然不含墓碑。
7. 06.7 不追加事件、不写回收、不做回滚对齐、不算事件 seq、不写 `events` 或 `nodes` 行、不新增迁移。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、迁移文件的实际内容、以及 06.6 之后剩下的代码。

| 拆分里的说法 | 现状 | 判断 |

## 二、squash 与重定基线的实际形状

### 2.1 squash 是独立动词，保留窗口是参数

`Store::squash_if_needed(&mut self, scope, max_incrementals: usize)` 是公开动词。它数该工作区的增量快照数，达到 `max_incrementals` 时把最老两个增量并入基线，否则是空操作。保留窗口 64 是参数，不是散落常量：ADR 0018 要求"全部参数都要有配置入口""不允许以常量形式散落在调用点"，配置结构尚未落地（属于后续批次），因此存储层把窗口作为参数接收，由调用方（server）从配置结构读出后传入。

`max_incrementals` 的语义是"允许的最大增量数"。基线加 64 个增量意味着增量数达到 64 时触发 squash。触发条件是增量数 `>= max_incrementals`，合并最老两个后增量数减二。server 在每次创建快照后调用它，因此触发时增量数恰好是 64，合并后是 62，窗口在 62 到 64 之间振荡。

squash 不折进 `create_snapshot` 的理由有三条。第一，06.6 的计划明确"本批不碰链改写，只负责按链追加"，链改写是 06.7 的职责。第二，链结构是存储层的不变量，squash 改写链（删最老两个增量、重挂子边、更新基线条目），与 06.6 的追加是不同职责，混进 `create_snapshot` 会让"这一批只有一个目的"失效。第三，server 可能在创建快照与 squash 之间做别的（比如打日志），squash 作为独立动词让 server 显式控制时机。

### 2.2 合并事务：先重挂子快照再删父

squash 的合并事务在立即事务内执行，顺序是：

1. 读基线 B、最老两个增量 I1、I2，以及 I2 的子快照 I3（按 `parent_id` 查）。
2. 折叠 B、I1、I2 的清单，得到新基线条目（只含 file 与 dir，不含墓碑）。
3. 重挂子快照：`UPDATE snapshots SET parent_id = B.id WHERE id = I3.id`。
4. 删 I1、I2 的条目：`DELETE FROM snapshot_entries WHERE snapshot_id IN (I1, I2)`。
5. 删 I1、I2 的行：`DELETE FROM snapshots WHERE id IN (I1, I2)`。
6. 替换基线条目：删 B 的旧条目，插折叠后的新条目。
7. 提交。

顺序的硬约束在第 3 步与第 5 步之间：`parent_id` 是无动作自引用外键，若先删 I2 再重挂 I3，外键会拦住整笔（I3 仍指向被删的 I2）。因此必须先重挂 I3 到 B，再删 I1、I2。这条约定写进 0002 的列注释，并由"子快照存在时删父被拒"的用例把行为固定下来。

重挂前的跨工作区校验：I3 与 B 的 `workspace_id` 必须相等（都等于作用域的工作区），不等则返回错误。这条是防御性校验——在正确构造的链里它们永远相等，但存储层不靠"链一定正确"假设，而是显式校验。

### 2.3 折叠算法：按路径覆盖，墓碑删除

折叠是左结合的覆盖加墓碑删除操作。从一个空映射开始，按链序（基线到目标）遍历每个快照的清单，对每条条目：

- 墓碑：从映射删掉该路径。
- file 或 dir：把该路径设为该条目（覆盖既有）。

结果是有效状态。折叠满足结合律：`fold(fold(B, I1, I2), I3, ..., I64) == fold(B, I1, I2, I3, ..., I64)`。因此 squash 前后最新快照的有效条目相等，这是"有效条目不变"不变量的数学基础。

折叠出的新基线条目只含 file 与 dir，不含墓碑：被墓碑删除的路径不在结果里。这条与 06.6 的条目形状校验对齐——写入路径的 Rust 类型让"墓碑带 content_stored"不可表示，折叠结果天然不含墓碑，写入时不会触发形状校验的墓碑支。

`content_stored = 0` 的超阈值条目在折叠中保留原样：折叠只覆盖路径，不改条目的字段，因此超阈值条目（带 `hash`、`size`、`mtime`、`content_stored = 0`）折叠后仍是超阈值条目。这条与 0017 的"超阈值文件只报告，从不删除、从不覆盖"一致。

### 2.4 重定基线：独立动词，自主模式拒绝，留痕三列成组

`Store::rebaseline(&mut self, scope, req: RebaseRequest)` 是公开动词。`RebaseRequest` 携带 `by`、`reason`、`confirmed_by`（留痕三列）与 `mode`（自主或用户发起）。

动词的逻辑：

- 自主模式（`mode` 是自主）：返回 `RebaseRejectedAutonomous`，整笔回滚，不留痕。
- 留痕三列任一为空：返回 `RebaseMissingConfirmation`，整笔回滚。CHECK 约束要求三列成组同进同出且非空串，存储层在写入前显式校验，不靠 CHECK 兜底。
- 用户发起且三列非空：应用重定基线。删所有增量快照（及其条目），更新基线行的条目为最新快照的有效条目，写入留痕三列。基线行只更新不删除（会话起点的基线是硬地板）。

重定基线等于永久放弃之前的回滚点，不可逆。它把"任务起点"移动到当前状态：基线条目变成当前状态，所有增量被放弃。下一个快照是增量，父边是基线。

留痕三列由 CHECK 约束成组同进同出（`rebase_trail_is_complete`）且只对基线成立（`rebase_trail_only_on_baseline`）。存储层在写入前显式校验三列非空，不靠 CHECK 兜底——CHECK 是表结构层的兜底，写入路径的校验是友好错误的第一道防线。

## 三、ADR 对快照保留的硬要求

与 06.7 相关的决策分布在四份 ADR 里，逐条对照如下。

| 要求 | 出处 | 06.7 怎么落地 |
|---|---|---|
| 保留策略是基线加快照，不是纯滑动窗口：到达上限时把最老的两个合并进基线（squash），而不是丢弃最老的 | 0006 决策段 | squash 合并最老两个增量进基线，不丢弃，"回到任务起点"永远可用 |
| 允许显式重定基线，但必须是独立动词、必须落库、且在没有人工确认时默认禁止 | 0006 决策段 | `rebaseline` 是独立动词，自主模式拒绝，留痕三列落库 |
| 重定基线等于永久放弃之前的回滚点，不可逆；会话起点的基线是硬地板，任何模式下都不能删除 | 0006 决策段 | 重定基线删所有增量、更新基线条目，基线行只更新不删除 |
| 回收用全局标记-清除加宽限期，不用引用计数 | 0006 决策段 | 06.7 不写回收，squash 删的条目对应的 blob 由 06.9 的标记-清除回收 |
| 快照保留是基线加 64 个增量，到顶时最老两个合并进基线，不丢弃 | 0018 参数表 | 保留窗口 64 是参数，由调用方从配置结构读出后传入 |
| 全部参数都要有配置入口，不允许以常量形式散落在调用点 | 0018 第九节 | 保留窗口是 `squash_if_needed` 的参数，存储层不硬编码 64 |
| 超过大小阈值的文件只记录尺寸、修改时间与哈希，不存内容，回滚时警告 | 0006 与 0017 决策段 | 折叠保留 `content_stored = 0` 的条目原样，超阈值文件只报告不覆盖 |
| 回滚即对齐：范围内、有内容记录的文件与删除墓碑，不含因超过阈值未记录内容的文件 | 0017 决策段 | 06.7 把折叠做对，06.8 的对齐算法据此区分"写回"与"只报告" |

三处需要特别说清的核实结果。

**第一，`parent_id` 是无动作自引用外键，squash 必须先重挂再删父。** `0002_content.sql` 的注释明确"合并必须在同一事务里先把子快照重挂到基线、再删父快照。留成无动作外键，忘记重挂会让整笔事务失败"。06.2.1 的裁决保留了无动作外键，不加 `ON DELETE SET NULL`：置空会让谱系静默断掉，且空父边与"顶层快照"不可区分。因此 squash 事务内先重挂 I3 到 B，再删 I1、I2。

**第二，留痕三列由 CHECK 约束成组同进同出且只对基线成立。** `0002_content.sql` 的 `rebase_trail_is_complete` 约束要求三列同进同出且非空串，`rebase_trail_only_on_baseline` 约束要求留痕只对基线成立。存储层在写入前显式校验三列非空，不靠 CHECK 兜底。squash 不写留痕三列（它们是重定基线的职责），因此 squash 后基线的留痕三列仍为 NULL。

**第三，折叠满足结合律，是"有效条目不变"不变量的数学基础。** 折叠是左结合的覆盖加墓碑删除操作，`fold(fold(B, I1, I2), I3, ..., I64) == fold(B, I1, I2, I3, ..., I64)`。因此 squash 前后最新快照的有效条目相等。这条不需要额外证明，是折叠定义的直接推论，但测试仍要显式断言，因为"测试通过但语义错"的风险在于实现者写错折叠顺序（比如右结合或漏掉墓碑删除）。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **增量数未达保留窗口时 squash 是空操作。** 创建基线加 63 个增量，调用 `squash_if_needed(scope, 64)`，断言快照行数不变、基线条目不变、无错误。守的是"未达到窗口不合并"。
2. **增量数达到保留窗口时最老两条并入基线。** 创建基线加 64 个增量，调用 `squash_if_needed(scope, 64)`，断言快照行数减二（64 个增量变 62 个）、最老两个增量的行被删、基线行仍在。守的是"到顶时合并最老两个"。
3. **合并后基线条目是折叠 B、I1、I2 的结果。** 创建基线加 64 个增量，每条增量的清单各不相同，调用 squash 后读出基线条目，断言每条等于折叠 B、I1、I2 的结果（按路径覆盖、墓碑删除）。守的是"折叠算法正确"。
4. **合并后最新快照的有效条目不变。** 创建基线加 64 个增量，先折叠整条链得到合并前最新快照的有效条目，调用 squash 后再折叠新链（基线加 62 个增量）得到合并后的有效条目，断言两者逐条相等。守的是"有效条目不变"不变量，这是本条验收的核心。
5. **合并事务先重挂子快照再删父。** 创建基线加 64 个增量，调用 squash 后断言 I3 的 `parent_id` 是基线的 id（不是被删的 I2 的 id）、I1 与 I2 的行被删、I3 的行仍在。守的是"先重挂后删父"的顺序。
6. **重挂时父子快照属于同一工作区。** 构造 I3 与基线属于不同工作区的坏链（用测试专用连接直接改 `workspace_id`），调用 squash，断言返回跨工作区错误、整笔回滚、I3 的 `parent_id` 不变。守的是"重挂时父子快照属于同一工作区"。
7. **折叠结果不含墓碑。** 创建基线加 64 个增量，其中 I1 或 I2 对某路径写墓碑，调用 squash 后断言新基线条目里没有该路径的墓碑条目（该路径被删除）。守的是"折叠出的基线条目只含 file 与 dir，不含墓碑"。
8. **超阈值条目在折叠中保留原样。** 创建基线加 64 个增量，其中某增量对某路径写 `content_stored = 0` 的超阈值条目（带 `hash`、`size`、`mtime`），调用 squash 后断言新基线条目里该路径仍是 `content_stored = 0` 且 `hash`、`size`、`mtime` 不变。守的是"超阈值文件只报告，从不删除、从不覆盖"。
9. **自主模式重定基线被拒。** 创建基线加若干增量，调用 `rebaseline(scope, RebaseRequest { mode: 自主, ... })`，断言返回 `RebaseRejectedAutonomous`、快照链不变、留痕三列仍为 NULL。守的是"自主模式重定被拒"。
10. **留痕三列成组写入。** 创建基线加若干增量，调用 `rebaseline(scope, RebaseRequest { mode: 用户, by, reason, confirmed_by })`，断言基线行的 `rebased_by`、`rebase_reason`、`rebase_confirmed_by` 三列全部等于传入值、所有增量行被删、基线条目变成最新快照的有效条目。守的是"留痕三列成组写入"。
11. **留痕三列任一为空时重定基线被拒。** 调用 `rebaseline` 但 `confirmed_by` 为空串，断言返回 `RebaseMissingConfirmation`、整笔回滚、留痕三列仍为 NULL。守的是"没有人工确认时默认禁止"。
12. **重定基线后基线行只更新不删除。** 调用 `rebaseline` 后断言基线行的 `id` 与 `seq` 不变（仍是首个快照的 id 与 seq 1）、`kind` 仍是 `baseline`、`parent_id` 仍是 NULL、条目与留痕三列被更新。守的是"会话起点的基线是硬地板，任何模式下都不能删除"。
13. **重定基线后下一个快照是增量。** 调用 `rebaseline` 后创建新快照，断言新快照的 `kind` 是 `incremental`、`parent_id` 是基线的 id、`seq` 是 2（基线 seq 1 加一）。守的是"重定基线后链从基线重新开始"。

第 1、2 条合起来守的是触发条件。第 3、4、7、8 条合起来守的是折叠算法与"有效条目不变"不变量。第 5、6 条守的是重挂顺序与跨工作区校验。第 9、10、11、12、13 条守的是重定基线的自主模式拒绝、留痕三列成组、基线只更新不删除、链重新开始。

## 八、已裁决的分歧点

三处分歧点已由主 Agent 裁决，全部采纳 Explorer 的建议（均选甲）：保留窗口 64 作为参数接收、存储层不硬编码（ADR 0018 禁止散落常量，配置结构落地前由调用方从配置读出后传入）；squash 是独立动词、`create_snapshot` 不调用它（06.6 只沿链追加，链改写是 06.7 的职责，混进会让"这一批只有一个目的"失效）；重定基线的 mode 用 `RebaseMode` 枚举（自主与用户发起各有名字，避免布尔的"真值是自主还是用户"歧义）。裁决理由见下表"建议"列。

| 分歧 | 两种做法 | 建议（已裁决采纳） |
|---|---|---|
| 保留窗口 64 的读取方式 | 甲：`squash_if_needed` 把窗口作为参数接收，存储层不硬编码。乙：存储层硬编码 64 为常量，后续批次再改配置结构 | **建议选甲。** 理由见第二节。ADR 0018 要求"全部参数都要有配置入口""不允许以常量形式散落在调用点"，配置结构尚未落地，存储层把窗口作为参数接收，由调用方从配置结构读出后传入，是满足 ADR 的最简做法。硬编码 64 会在配置结构落地时返工所有调用点 |
| squash 是独立动词还是折进 `create_snapshot` | 甲：squash 是独立动词，`create_snapshot` 不调用它。乙：squash 折进 `create_snapshot`，创建快照后自动合并 | **建议选甲。** 理由见第二节。06.6 的计划明确"本批不碰链改写，只负责按链追加"，链改写是 06.7 的职责。混进 `create_snapshot` 会让"这一批只有一个目的"失效，且 server 可能在创建快照与 squash 之间做别的 |
| 重定基线的 mode 表示 | 甲：`RebaseMode` 枚举（自主或用户发起）。乙：布尔 `autonomous: bool` | **建议选甲。** 理由见第二节。枚举让"自主模式"与"用户发起"各有名字，避免布尔的"真值是自主还是用户"歧义。与 06.6 的 kind 词表问题同型，不发明完整枚举，留给后续批次统一补 |

## 十、Explorer 核对与补强（基线 7bd41c0）

本节的核对对象是批次基线 7bd41c0 的已提交代码，不是实现者的工作树。结论是：十三条验收对基线全部成立，表结构、折叠算法与留痕三列的口径都没有被证伪，需要改写的只是"怎么做"与三处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 表结构核对：全部成立

`0002_content.sql` 的 `snapshots` 与 `snapshot_entries` 表与计划第二节所写逐列一致。`snapshots` 的主键是 `id`，`workspace_id` 有外键，`seq` 与 `workspace_id` 组成唯一索引，`parent_id` 是无动作自引用外键，`kind` 有取值域 CHECK，重定基线留痕三列有 `rebase_trail_is_complete` 与 `rebase_trail_only_on_baseline` 两条 CHECK。`snapshot_entries` 的主键是 `(snapshot_id, path)`，`kind` 有取值域 CHECK，形态 CHECK 已定形（06.2.1.1 补强），`content_stored` 不给默认值。`snapshots_by_parent` 索引已建，重挂与窗口查询按父查子不用全表扫。

### 10.2 句柄形状核对：`conn_mut` 已就位

`Store` 把 `Connection` 私有持有，`conn()` 与 `conn_mut()` 都是 `pub(crate)`，由 06.3 提供。`conn_mut` 取 `&mut self`，与 `create_workspace` 的形状一致。`configure` 已经设了 `set_transaction_behavior(Immediate)`，所以 `conn_mut` 拿到的事务一开就是 `BEGIN IMMEDIATE`，"重挂与删父在同一事务内"这条硬约束由现有配置直接提供，不需要额外动作。

### 10.3 06.6 读路径核对：squash 与重定基线的公共依赖

06.6 的计划（detail/24）提供 `Store::snapshot_entries`（读清单，按路径排序）与 `Store::snapshot`（读快照元信息）。squash 读 B、I1、I2 的清单合并，重定基线读最新快照的清单更新基线，两条都依赖 06.6 的读路径。06.6 的读路径是 06.7 与 06.8 的公共依赖，与 06.5 把 `get` 收进本批的裁决同型。

### 10.4 四处补强

**第一，`snapshots_by_parent` 索引已建，重挂与窗口查询按父查子不用全表扫。** `0002_content.sql` 的 `CREATE INDEX IF NOT EXISTS snapshots_by_parent ON snapshots(parent_id)` 已定形。squash 按 `parent_id` 查 I2 的子快照 I3，窗口查询沿父边走，索引让这两条路径不用全表扫。

**第二，留痕三列的 CHECK 已定形，存储层在写入前显式校验不靠 CHECK 兜底。** `rebase_trail_is_complete` 约束要求三列同进同出且非空串，`rebase_trail_only_on_baseline` 约束要求留痕只对基线成立。存储层在写入前显式校验三列非空，返回 `RebaseMissingConfirmation`，CHECK 是表结构层的兜底，写入路径的校验是友好错误的第一道防线。

**第三，折叠算法是纯 SQL 操作，无文件系统访问，可在模块内单测。** 折叠读清单、按路径覆盖、墓碑删除，不碰 CAS 目录，不读写文件。`squash.rs` 的折叠与 `retention.rs` 的留痕三列校验都是纯 SQL 操作，可在模块内单测，不需要集成测试的临时目录。

**第四，squash 与重定基线都改写链，而 06.6 的 `create_snapshot` 只按链追加。** 这条职责分离是"这一批只有一个目的"的前提。06.6 的 `create_snapshot` 自动链接父边、推导 kind，但不删快照行、不改写链。06.7 的 squash 与重定基线改写链（删最老两个增量、重挂子边、更新基线条目），是独立职责，不混进 `create_snapshot`。

### 10.5 一处与 ROADMAP 的计数差异

ROADMAP 的 06.7 行写"基线加增量 squash 与重定基线"，拆分依据的验收口径写"增量达 64 条时最老两条并入基线且有效条目不变，合并事务先重挂子快照再删父，重挂时父子快照属于同一工作区；自主模式重定被拒且留痕三列成组写入"。两处对验收口径的描述一致，没有计数差异。这里只作记录，不改 ROADMAP 表格行。
