# 批次 07.1 拓扑类型与依赖无环校验的执行计划

拆分依据给 07.1 的验收是"有环声明返回环路径，合法拓扑得到稳定启动顺序"。核对基线 96dd1b4 的已提交代码与 ADR 0013、0014 与 ROADMAP 07 行之后，结论是：**验收口径成立且不需要改，但它依赖的六件事必须写进计划，否则实现者会在细节上做对数值、做错语义。** 六件事分别是：拓扑类型与无环校验是纯逻辑，落在 `ita-server` 而不是内核（ADR 0013 明确"两套监督语义靠文档与类型分开"，unit 类型不得与工作流节点类型混用）；依赖有三种且方向语义一致（`Requires`/`Wants`/`After` 都产生"被依赖者先启动"的边，种类只影响 07.2 的失败传播，不影响 07.1 的图结构）；无环校验对三种边的并集做判定，任何环都是致命的并返回环路径（ADR 0013 最小拓扑里 `lease ↔ tools` 的双向记号必须落成单方向边，否则它自己就是环）；稳定启动顺序是词典序最小的拓扑序（Kahn 加最小堆），同输入必同输出；unit 标识是标签名义类型而不是 ULID（unit 是固定命名的子系统，不是动态建行的实体）；07.1 不新增依赖、不建表、不碰 tokio。文件规划 `crates/ita-server/src/units/{mod,topology}.rs` 与现状吻合，另需在 `lib.rs` 声明 `units` 模块。

## 结论

1. 07.1 的原始拆分成立。基线 96dd1b4 的 `ita-server` 只有 `lib.rs` 一个空壳，`units` 模块不存在，需要从零建；两份迁移文件（`0001_core.sql`、`0002_content.sql`）都没有 `units` 表，本批不建表、不新增迁移。需要改写的是"怎么做"，不是"做什么"。
2. **拓扑类型与无环校验是纯逻辑，落在 `ita-server`，不进内核。** ADR 0013 明确"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，代价段点名"两套监督语义（unit 与工作流节点）容易混淆，必须靠文档与类型分开"。因此 unit 类型必须独立于 `ita-workflow` 的节点类型，而内核的职责域是"上下文树的解析、命令文法的分析、租约与权限的策略判定"（`lib.rs` 文档注释），unit 拓扑不在其中。拆分依据的文件规划 `crates/ita-server/src/units/{mod,topology}.rs` 与 STRUCTURE 的"ita-server：units/supervisor、router、DB+queue owner"一致，维持不改。
3. **依赖有三种，方向语义一致。** ROADMAP 07 行定名 `Requires`/`Wants`/`After`，对应 ADR 0013 的硬依赖（失败则连带失败）、软依赖（失败只是降级）、仅排序（不隐含依赖）。三种边在 07.1 的图结构里方向完全相同：`X` 依赖 `Y`（无论哪种种类）都产生 `Y → X` 的边，即被依赖者先启动。种类只记录在边上，供 07.2 的失败传播（`Requires` 传播失败、`Wants` 降级）与 07.3 的必需门消费，07.1 不消费种类。
4. **无环校验对三种边的并集判定，任何环都致命。** ADR 0013 只说"启动时静态校验无环"，没有区分环里边的种类。验收口径"有环声明返回环路径"是单数的：任何环都返回环路径。因此图是三种边的并集，DFS 三色标记，撞灰节点即提取环。被否决的替代是"按种类分环"（`Wants` 环、`After` 环不致命），它更复杂且没有动机：软依赖的语义在失败处理（07.2），不在启动排序，一个互相 `Wants` 的 unit 对谁也不触发谁启动，是退化形状，直接拒绝更简单。
5. **`lease ↔ tools` 的双向记号必须落成单方向边。** ADR 0013 最小拓扑写 `lease ↔ tools（租约仲裁与工具目录注册，必需）`。若按字面建成互相 `Requires`，它自己就是一个环，拓扑被自己的无环校验拒绝，矛盾。因此 `↔` 是"两者耦合"的记号，不是字面环：落成单方向边（`lease` 依赖 `tools`），`tools` 先启动。测试里按这个方向实例化，并在注释里写明这条裁决。
6. **稳定启动顺序是词典序最小的拓扑序。** Kahn 算法加按 unit 标签排序的最小堆：同输入必同输出，且输出是所有合法拓扑序里词典序最小的那一个，是规范形。"稳定"的判据是确定性，最小堆给的是最规范的确定性，07.2 的状态机与 07.3 的激活门可以按这个顺序推进而不必自己再排序。
7. **unit 标识是标签名义类型，不是 ULID。** CONVENTIONS 的"ID 用 ULID"适用于入库的实体（节点、会话、工作区、检查点、事件），而 unit 是固定命名的子系统（`store`、`router`、`ipc`、`lease`、`tools`、`model`、`telemetry`），拓扑在启动时静态声明，不动态建行。`UnitId` 是校验过的标签名义类型：小写字母数字加连字符，非空，首尾不连字符，与 systemd unit 命名同型。内核的 `id_type!` 宏是 crate 私有的，`ita-server` 不能复用，在 `units/mod.rs` 里自己定义。
8. **07.1 不新增依赖、不建表、不碰 tokio。** 基线的 `ita-server/Cargo.toml` 只有 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow` 四个依赖，没有 tokio、没有 async。07.1 是纯数据类型与纯函数，零新增依赖。分层门允许 `ita-server` 依赖 `ita-kernel`、`ita-store`、`ita-proto`、`ita-model`、`ita-workflow`、`ita-tools`，本批一个都不加。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、两份迁移文件的实际内容、以及基线 96dd1b4 的 `ita-server` 现状。

| 拆分里的说法 | 现状 | 判断 |
|---|---|---|
| 验收"有环声明返回环路径" | 基线无任何环检测代码，`units` 模块不存在 | 成立，本批从零建 |
| 验收"合法拓扑得到稳定启动顺序" | 基线无任何拓扑排序代码 | 成立，本批从零建 |
| 文件 `crates/ita-server/src/units/{mod,topology}.rs` | 两个文件都不存在，`lib.rs` 只有文档注释 | 成立，另需 `lib.rs` 声明 `units` 模块 |
| 依赖"02" | 02 骨架已完成，`ita-server` 空壳就位 | 成立，无新增前置 |
| 无环校验是"启动时静态校验" | ADR 0013 定形，无动态环的语义 | 成立，纯函数，无 IO |
| 三种依赖 `Requires`/`Wants`/`After` | ROADMAP 07 行定名，ADR 0013 给语义 | 成立，种类只记录不消费 |

被证伪的是拆分之外的一件事：拆分没有提到 ADR 0013 最小拓扑里 `lease ↔ tools` 的双向记号怎么落成边。若按字面建成互相 `Requires`，它自己就是环，拓扑被自己的无环校验拒绝。因此 `↔` 必须落成单方向边（`lease` 依赖 `tools`），这是本批唯一需要裁决的建模决定，见第二节第 2.4 条与第八节。

## 二、拓扑类型与无环校验的实际形状

### 2.1 类型落在 `ita-server`，不进内核

`UnitId`、`DepKind`、`Topology` 三个类型都在 `crates/ita-server/src/units/` 下。理由见结论第 2 条：ADR 0013 的硬边界是 unit 类型与工作流节点类型分开，内核的职责域不含 unit 拓扑。`ita-server` 的 crate 文档注释说"本 crate 位于内核之外，可以持有 IO、时钟或网络句柄；但这些副作用必须收在本层"，纯逻辑模块放进来不违反这条：副作用收在本层，纯数据类型与纯函数是本层的合法组成。

### 2.2 三种依赖方向语义一致，种类只记录不消费

`DepKind` 是三个变体：`Requires`（硬依赖，失败则连带失败）、`Wants`（软依赖，失败只是降级）、`After`（仅排序，不隐含依赖）。三种边在图结构里方向完全相同：`add_requires(dependent, target)`、`add_wants(dependent, target)`、`add_after(dependent, target)` 都产生 `target → dependent` 的边，即被依赖者 `target` 先启动。种类记录在边上，供 07.2 的失败传播与 07.3 的必需门消费，07.1 不消费种类。

方向语义的定形是刻意的：三种依赖在启动排序上都是"被依赖者先启动"，差别只在失败时怎么处理（`Requires` 连带失败、`Wants` 降级、`After` 无关）。把三种边折成同向边，让 07.1 的图结构与种类解耦，07.2 再按种类叠失败语义。

### 2.3 无环校验对三种边的并集判定，任何环都致命

`Topology::find_cycle(&self) -> Option<Vec<UnitId>>` 用 DFS 三色标记（白/灰/黑）在三种边的并集图上找环。撞灰节点即提取环路径：从栈顶回溯到灰节点，再补回起点，形成闭合环（首元素等于尾元素）。环路径是 `Vec<UnitId>`，例如 `[A, B, C, A]`，调用方直接看见环怎么走完一圈。

`startup_order(&self) -> Result<Vec<UnitId>, CycleError>` 先调 `find_cycle`，有环则返回 `CycleError`（带环路径），无环则做 Kahn 拓扑排序。验收口径"有环声明返回环路径"由 `startup_order` 的 `Err` 分支直接满足，测试断言 `Err` 里的环路径。

### 2.4 `lease ↔ tools` 落成单方向边

ADR 0013 最小拓扑的 `lease ↔ tools（租约仲裁与工具目录注册，必需）` 按字面建成互相 `Requires` 会自己成环。因此 `↔` 落成单方向边：`lease` 依赖 `tools`，`tools` 先启动。理由：租约仲裁需要工具目录注册完成才能仲裁跨工作区资源，工具目录注册不依赖租约仲裁。测试里按这个方向实例化，并在 `mod.rs` 的文档注释里写明这条裁决，防止后来人把它读成双向环。

### 2.5 稳定启动顺序是词典序最小的拓扑序

`startup_order` 用 Kahn 算法加按 `UnitId` 标签排序的最小堆：入度为零的 unit 全进堆，每次取标签最小的出堆、追加到顺序、松弛其后继。同输入必同输出，且输出是所有合法拓扑序里词典序最小的那一个。"稳定"的判据是确定性，最小堆给的是最规范的确定性。07.2 的状态机与 07.3 的激活门按这个顺序推进，不必自己再排序。

### 2.6 unit 标识是标签名义类型，不是 ULID

`UnitId` 是校验过的标签名义类型：小写字母数字加连字符，非空，首尾不连字符，不连续连字符。与 systemd unit 命名同型。内核的 `id_type!` 宏是 crate 私有的（`macro_rules!` 无 `#[macro_export]`），`ita-server` 不能复用，在 `units/mod.rs` 里自己定义 `UnitId` 与解析校验。`UnitId` 派生 `Debug`、`Clone`、`PartialEq`、`Eq`、`PartialOrd`、`Ord`、`Hash`，`Ord` 供最小堆排序，`Hash` 供边的集合去重。

## 三、ADR 对拓扑类型与无环校验的硬要求

与 07.1 相关的决策分布在 ADR 0013、0014 与 ROADMAP 07 行，逐条对照如下。

| 要求 | 出处 | 07.1 怎么落地 |
|---|---|---|
| 依赖关系区分三种：硬依赖、软依赖、仅排序 | 0013 决策段 | `DepKind` 三变体 `Requires`/`Wants`/`After`，中文文档注释 |
| 启动时静态校验无环 | 0013 决策段 | `find_cycle` 纯函数，DFS 三色标记，无 IO |
| 就绪不等于运行 | 0013 决策段 | 07.1 不涉就绪，只定拓扑与排序；就绪是 07.2 |
| unit 管进程生命周期，工作流管任务语义，两者不共享状态机 | 0013 决策段 | unit 类型落 `ita-server`，不进内核、不与 `ita-workflow` 混用 |
| 两套监督语义靠文档与类型分开 | 0013 后果段 | `UnitId`/`DepKind`/`Topology` 独立类型，不与工作流节点类型复用 |
| 执行器是独立进程，不是 server 内的 unit | 0014 决策段 | 07.1 的 unit 是 server 内部子系统，不含执行器；`lease` 只做租约表维护与跨工作区资源仲裁 |
| 依赖拓扑（`Requires`/`Wants`/`After`） | ROADMAP 07 行 | 三种依赖定名，与 systemd 词汇一致 |
| 版本一不级联重启，只标记降级 | 0013 决策段 | 07.1 不涉重启，失败传播是 07.2 |

三处需要特别说清的核实结果。

**第一，`ita-server` 基线是空壳，`units` 模块不存在。** 基线 96dd1b4 的 `crates/ita-server/src/` 只有 `lib.rs`（文档注释加两条 `deny`），`Cargo.toml` 只有四个依赖。07.1 从零建 `units` 模块，不修改任何既有代码，只在 `lib.rs` 加一行 `pub mod units;`。

**第二，两份迁移文件都没有 `units` 表。** `0001_core.sql` 建 `workspaces`、`sessions`、`nodes`、`events`、`workspace_seq`；`0002_content.sql` 建 `blobs`、`snapshots`、`snapshot_entries`、`read_set`。没有 `units` 表，也没有 unit 状态列。07.1 不建表、不新增迁移，unit 状态落库是 07.2 或 07.3 的事。

**第三，`lease` 不是执行器。** ADR 0014 明确"执行器是每个工作区一个独立进程，不是 server 内部的一个 unit"，0013 最小拓扑里的 `executor` 更名为**租约仲裁**，职责收窄为维护租约表与仲裁跨工作区资源。因此 07.1 的 unit 集合里 `lease` 是租约仲裁，不是执行器，测试里不得把执行器当成 unit 实例化。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **有环声明返回环路径。** 建 `A requires B`、`B requires C`、`C requires A`，调 `startup_order`，断言返回 `Err` 且环路径是 `[A, B, C, A]`（闭合，首等于尾）。守的是"有环声明返回环路径"。
2. **合法拓扑得到稳定启动顺序。** 建 `store → router → ipc`（`router requires store`、`ipc requires router`），调 `startup_order`，断言顺序是 `[store, router, ipc]`，且重复调用十次输出相同。守的是"合法拓扑得到稳定启动顺序"。
3. **自依赖是环。** 建 `A requires A`，调 `startup_order`，断言返回 `Err` 且环路径是 `[A, A]`。守的是"自环被检出"。
4. **孤立 unit 合法。** 建单个 unit 无边，调 `startup_order`，断言顺序是 `[unit]`。守的是"无边拓扑合法"。
5. **空拓扑合法。** 建空拓扑，调 `startup_order`，断言顺序是 `[]`。守的是"空拓扑合法"。
6. **三种边都参与无环判定。** 建 `A wants B`、`B after A`（无 `Requires`），调 `startup_order`，断言返回 `Err` 且环路径是 `[A, B, A]`。守的是"无环校验对三种边的并集判定，不是只对 `Requires`"。
7. **稳定顺序是词典序最小的拓扑序。** 建菱形：`A` 先于 `B`、`A` 先于 `C`、`B` 先于 `D`、`C` 先于 `D`（`B requires A`、`C requires A`、`D requires B`、`D requires C`），调 `startup_order`，断言顺序是 `[A, B, C, D]`（`B` 在 `C` 前，因为 `B` 标签小于 `C`）。守的是"稳定顺序是词典序最小的拓扑序"。
8. **重复边幂等。** 建 `A requires B`，再加一次 `A requires B`，调 `startup_order`，断言顺序是 `[B, A]` 且无环。守的是"重复边不重复计数"。
9. **同一对 unit 多种类边合法。** 建 `A requires B` 与 `A after B`（都是 `B → A`），调 `startup_order`，断言顺序是 `[B, A]` 且无环。守的是"同一对 unit 不同种类的边不冲突"。
10. **七 unit 最小拓扑无环。** 按 ADR 0013 最小拓扑实例化：`store → router → ipc`（`router requires store`、`ipc requires router`）、`lease requires tools`（`↔` 落单方向）、`model` 孤立、`telemetry` 孤立，调 `startup_order`，断言返回 `Ok` 且顺序合法（`store` 在 `router` 前、`router` 在 `ipc` 前、`tools` 在 `lease` 前）。守的是"ADR 0013 最小拓扑是合法 DAG"。

第 1、3、6 条守的是环检测（并集判定、自环、非 `Requires` 环）。第 2、7 条守的是稳定顺序（确定性、词典序最小）。第 4、5 条守的是退化形状合法。第 8、9 条守的是边的集合语义。第 10 条守的是 ADR 0013 最小拓扑的实例化。

## 六、实现顺序与每步验证

分两次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的先做"排，`UnitId` 与 `DepKind` 是最便宜的类型定形，`Topology` 的环检测与拓扑排序是核心算法。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `units/mod.rs`（`UnitId`、`DepKind`）与 `lib.rs` 声明模块 | `cargo nextest run -p ita-server -E 'test~unit_id'`，`UnitId` 的解析校验与 `Ord`/`Hash` 派生 |
| 二 | 写 `units/topology.rs`（`Topology`、`find_cycle`、`startup_order`、`CycleError`）与内联测试 | `cargo nextest run -p ita-server`，此时 `topology.rs` 的测试覆盖第四节全部十条验收 |

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里入册，断言消息仍然用中文。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 无环校验只对 `Requires` 边判定，漏掉 `Wants` 与 `After` 环 | 正常路径通过，`Wants`/`After` 环不被检出才暴露 | 第四节第 6 条：建非 `Requires` 环，断言被检出 |
| `lease ↔ tools` 按字面建成互相 `Requires`，自己成环 | 单条测试通过，最小拓扑实例化时才暴露矛盾 | 第四节第 10 条：按单方向实例化，断言无环 |
| 稳定顺序不是词典序最小，只是某个确定序 | 同输入同输出通过，但顺序不是规范形 | 第四节第 7 条：菱形断言 `B` 在 `C` 前 |
| `UnitId` 用裸 `String` 而不是名义类型 | 编译通过，但"把 unit 标签当别的东西传"这类错误不在编译期拦住 | `UnitId` 是名义类型，`add_requires` 只吃 `UnitId` |
| 重复边重复计数，环路径重复 | 正常路径通过，重复边才暴露 | 第四节第 8 条：加两次同边，断言顺序不变 |
| 环路径不闭合（首不等于尾） | 正常路径通过，读环路径时看不出环怎么走完一圈 | 第四节第 1 条：断言首元素等于尾元素 |
| `UnitId` 用 ULID 而不是标签 | 编译通过，但 unit 是固定命名子系统，ULID 语义错 | `UnitId` 是标签名义类型，解析校验小写字母数字加连字符 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：unit 类型落 `ita-server` 而不是内核。ADR 0013 的硬边界是 unit 类型与工作流节点类型分开，内核的职责域不含 unit 拓扑。若把 `UnitId`/`Topology` 放进内核，会让"两套监督语义靠类型分开"失效，且内核的 `lib.rs` 文档注释（"上下文树的解析、命令文法的分析、租约与权限的策略判定"）会被违背。这条职责分离是"这一批只有一个目的"的前提，不靠调用方记得"unit 类型不进内核"。

## 八、已裁决的分歧点

一处分歧点已由主 Agent 裁决（采纳 Explorer 建议选甲：无环校验是三种边的并集判定，任何环都致命——验收口径"有环声明返回环路径"是单数的，软依赖语义在失败处理不在启动排序，互相 `Wants` 是退化形状直接拒绝更简单，乙更复杂且没有动机）；其余三处（`lease ↔ tools` 落单方向边、`UnitId` 用标签名义类型、稳定顺序用 Kahn 加最小堆）由 Explorer 直接定形，理由充分。

| 分歧 | 两种做法 | 建议（无环校验范围已裁决采纳，其余三处已定形） |
|---|---|---|
| 无环校验的范围 | 甲：三种边的并集判定，任何环都致命。乙：按种类分环，`Wants` 环与 `After` 环不致命，只 `Requires` 环致命 | **建议选甲。** 理由见第二节第 2.3 条。验收口径"有环声明返回环路径"是单数的，任何环都返回环路径；软依赖的语义在失败处理（07.2），不在启动排序，互相 `Wants` 的 unit 对谁也不触发谁启动，是退化形状，直接拒绝更简单。乙更复杂且没有动机 |
| `lease ↔ tools` 的建模 | 甲：落单方向边（`lease` 依赖 `tools`）。乙：按字面建成互相 `Requires` | **建议选甲。** 理由见第二节第 2.4 条。乙会让最小拓扑自己成环，被自己的无环校验拒绝，矛盾 |
| `UnitId` 的类型 | 甲：标签名义类型。乙：ULID | **直接定形选甲。** 理由见结论第 7 条。unit 是固定命名子系统，不是动态建行实体，ULID 语义错 |
| 稳定顺序的算法 | 甲：Kahn 加最小堆，词典序最小。乙：DFS 后序逆，某个确定序 | **直接定形选甲。** 理由见第二节第 2.5 条。最小堆给的是最规范的确定性，07.2 与 07.3 按这个顺序推进不必自己再排序 |

## 九、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 07.1：状态机、就绪探针与停止顺序（07.2）；必需与非必需启动门与降级（07.3）；能力集快照与变更推送（07.4）；unit 状态落库与 `units` 表建表（07.2 或 07.3）；`Requires`/`Wants` 的失败传播语义（07.2）；就绪与运行的区分（07.2）；执行器进程（0014，独立进程，不是 unit）；工作流节点类型（`ita-workflow`，与 unit 类型分开）；事件日志与模型代理（08.x）；本地 socket 与连接级工作区绑定（08.2）；group commit（08.4）。

## 十、Explorer 核对与补强（基线 96dd1b4）

本节的核对对象是批次基线 96dd1b4 的已提交代码，不是实现者的工作树。结论是：十条验收对基线全部成立，类型规划、依赖种类与无环校验的口径都没有被证伪，需要改写的只是"怎么做"与一处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 `ita-server` 现状核对：空壳，`units` 模块不存在

基线 96dd1b4 的 `crates/ita-server/src/` 只有 `lib.rs`（文档注释加 `#![deny(unsafe_code)]` 与 `#![deny(missing_docs)]`），`Cargo.toml` 只有 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow` 四个依赖，没有 tokio、没有 async。07.1 从零建 `units` 模块，不修改任何既有代码，只在 `lib.rs` 加一行 `pub mod units;`。

### 10.2 迁移文件核对：没有 `units` 表

`0001_core.sql` 建 `workspaces`、`sessions`、`nodes`、`events`、`workspace_seq`；`0002_content.sql` 建 `blobs`、`snapshots`、`snapshot_entries`、`read_set`。没有 `units` 表，也没有 unit 状态列。07.1 不建表、不新增迁移，unit 状态落库是 07.2 或 07.3 的事。

### 10.3 内核 `id_type!` 宏核对：crate 私有，不能复用

`crates/ita-kernel/src/context/ids.rs` 的 `id_type!` 宏是 `macro_rules!` 无 `#[macro_export]`，crate 私有。`ita-server` 不能复用，`UnitId` 在 `units/mod.rs` 里自定义。内核的五种 id（`NodeId`、`SessionId`、`WorkspaceId`、`CheckpointId`、`EventId`）都是 ULID，`UnitId` 是标签名义类型，与它们不同型，不复用。

### 10.4 四处补强

**第一，unit 类型落 `ita-server` 而不是内核。** ADR 0013 的硬边界是 unit 类型与工作流节点类型分开，内核的职责域不含 unit 拓扑。若把 `UnitId`/`Topology` 放进内核，会让"两套监督语义靠类型分开"失效。这条职责分离是"这一批只有一个目的"的前提。

**第二，`lease ↔ tools` 落单方向边。** ADR 0013 最小拓扑的 `↔` 按字面建成互相 `Requires` 会自己成环。因此 `↔` 落成单方向边（`lease` 依赖 `tools`），测试里按这个方向实例化，并在 `mod.rs` 的文档注释里写明这条裁决。

**第三，无环校验对三种边的并集判定。** ADR 0013 只说"启动时静态校验无环"，没有区分环里边的种类。验收口径"有环声明返回环路径"是单数的：任何环都返回环路径。因此图是三种边的并集，`Wants` 环与 `After` 环同样致命。被否决的替代是"按种类分环"，它更复杂且没有动机。

**第四，稳定顺序是词典序最小的拓扑序。** Kahn 加最小堆给的是最规范的确定性，07.2 的状态机与 07.3 的激活门按这个顺序推进不必自己再排序。菱形断言 `B` 在 `C` 前，守的是"词典序最小"而不是"某个确定序"。
