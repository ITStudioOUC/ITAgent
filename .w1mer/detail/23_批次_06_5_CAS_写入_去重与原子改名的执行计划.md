# 批次 06.5 CAS 写入、去重与原子改名的执行计划

拆分依据给 06.5 的验收是"同内容两次写入只产生一个 blob；先写内容到最终哈希路径再插入 blobs 行，中断只留下无引用文件，不留下指向空内容的行"。核对基线 3088c70 的已提交代码之后，结论是：**验收口径成立且不需要改，但它依赖的四件事必须写进计划，否则实现者会在细节上做对数值、做错语义。** 四件事分别是：哈希算法是 blake3 不是 sha256（需要新增依赖）；CAS 根目录是数据库文件同级的 `blobs` 目录（Store 需要持有 CAS 根路径）；原子改名是"临时文件 → 同步 → 改名"（临时文件与最终路径同目录）；去重是"先查 blobs 行，存在则跳过写入"。文件规划 `cas.rs`、`blobs.rs` 与现状吻合，另需在 `db.rs` 加两个错误变体、在 `lib.rs` 声明模块、在 `Cargo.toml` 加 `blake3` 依赖。

## 结论

1. 06.5 的原始拆分成立。表结构（`blobs` 表）与 ADR 0006 都没有把这项工作推到别的批次，也没有出现让验收口径失效的变更。需要改写的是"怎么做"，不是"做什么"。
2. 哈希算法是 **blake3**，不是 sha256。ADR 0006 明确"用 blake3，不用 sha256，因为每次工具调用后都要算它，速度差一个量级"。`blake3` 目前不是工作区依赖，需要新增。
3. CAS 写入是 **"先写内容到最终哈希路径，再插入 blobs 行"**。临时文件与最终路径在同一目录，改名是原子的。中断只留下无引用文件（安全，多占空间），不留下指向空内容的行（危险，丢内容）。
4. 去重是 **"同内容两次写入只产生一个 blob"**。实现是"先查 blobs 行，存在则跳过写入"。由于单写者，没有并发竞争。
5. CAS 根目录是 **数据库文件同级的 `blobs` 目录**，懒创建（首次 `put` 时建目录，不在 `open` 时建）。`Store` 持有 CAS 根路径，`open` 从数据库路径派生，`open_in_memory` 用临时路径。
6. 06.5 不写快照清单、回滚对齐与回收（06.6 至 06.9），不算事件 seq，不写 `nodes` 或 `events` 行。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、迁移文件的实际内容、以及 06.3 之后剩下的代码。

| 拆分里的说法 | 现状 | 判断 |
|---|---|---|
| 验收"同内容两次写入只产生一个 blob" | `blobs` 表已建，`hash` 是主键 | 成立，去重是"先查行，存在则跳过" |
| 验收"先写内容到最终哈希路径再插入 blobs 行" | `blobs` 表只有元数据，正文在文件系统里 | 成立，文件写入与行插入是两步，顺序是文件先行 |
| 验收"中断只留下无引用文件，不留下指向空内容的行" | ADR 0006 明确"崩溃可能留下无引用的对象，这是安全的" | 成立，方向是刻意的 |
| 文件 `crates/ita-store/src/{cas,blobs}.rs` | 两个文件都还不存在，`lib.rs` 只声明了 `db`、`events`、`migrate`、`preview`、`scope`、`seq` | 成立，另需 `db.rs` 加错误变体、`lib.rs` 声明模块、`Cargo.toml` 加 `blake3` |
| 依赖"06.2" | 06.2 提供 `blobs` 表结构 | 成立，另需 06.3 的 `conn_mut` 与既有事务入口 |

被证伪的是拆分之外的一件事：拆分没有提到哈希算法与 CAS 根目录。`blobs` 表只有 `hash`、`size`、`created_at`、`unreferenced_since` 四列，没有任何一列能表达"内容在哪里"或"用什么算法算的哈希"。因此 06.5 必须自己定形哈希算法与 CAS 目录布局，这是本批唯一的跨 crate 设计决定，见第二节。

## 二、CAS 写入的实际形状

### 2.1 哈希算法：blake3，不是 sha256

ADR 0006 明确"用 blake3，不用 sha256，因为每次工具调用后都要算它，速度差一个量级"。`blake3` 目前不是工作区依赖，需要新增。`blake3` 不在分层门的 `CAPABILITIES` 列表里，因此任何 crate 都可以依赖它，不违反分层约束。

`blake3` 的哈希是 256 位（32 字节），十六进制文本是 64 字符。`BlobRef.hash` 是这 64 字符的十六进制文本。

### 2.2 CAS 目录布局：数据库文件同级的 `blobs` 目录，懒创建

ADR 0006 的布局是 `blobs/3f/3fab...c1`。目录是哈希的前两个十六进制字符，文件是完整哈希。CAS 根目录是数据库文件同级的 `blobs` 目录。

`Store` 持有 CAS 根路径（`cas_root: PathBuf`）。`open` 从数据库路径派生（`path.parent().join("blobs")`），`open_in_memory` 用临时路径（`std::env::temp_dir().join(format!("ita-cas-{}", ulid::Ulid::new()))`）。目录在首次 `put` 时懒创建（`create_dir_all` 子目录），不在 `open` 时建——不为不用 CAS 的库建空目录。

### 2.3 原子改名：临时文件 → 同步 → 改名

ADR 0006 明确"先写临时文件、同步、再改名到最终路径。绝不出现'文件名已是哈希但内容是半截'的状态"。实现是：

1. 在最终路径同目录创建临时文件（同文件系统，改名才是原子的）。
2. 把内容写入临时文件。
3. 同步临时文件（`sync_data`，即 fdatasync）。
4. 把临时文件改名到最终路径。Linux 的 `rename` 是原子的，会原子替换已存在的目标。

临时文件命名用固定后缀 `.tmp`（单写者没有并发竞争，崩溃后留下的 `.tmp` 文件是无引用对象，06.9 的回收会清掉）。

### 2.4 去重：先查 blobs 行，存在则跳过写入

"同内容两次写入只产生一个 blob"的实现是：先查 `blobs` 行是否存在，存在则直接返回哈希（不写文件），不存在则写文件并插入行。由于单写者，没有并发竞争。插行用 `INSERT OR IGNORE`，即使去重检查被绕过（并发情形，虽然单写者不会发生），插行也是幂等的。

### 2.5 写入顺序：文件先行，行随后

写入的顺序是刻意的：先写文件（原子改名），再插入 `blobs` 行。中断只留下无引用文件（安全，多占空间），不留下指向空内容的行（危险，丢内容）。ADR 0006 明确"崩溃可能留下无引用的对象，这是安全的（多占空间），而不是危险的（丢内容）。方向是刻意的"。

## 三、ADR 对 CAS 的硬要求

与 06.5 相关的决策分布在两份 ADR 里，逐条对照如下。

| 要求 | 出处 | 06.5 怎么落地 |
|---|---|---|
| 文件内容不进数据库，按内容哈希存到独立目录，文件名就是哈希 | 0006 决策段 | `blobs` 表只有元数据，正文在文件系统里；文件名是 blake3 哈希 |
| 用 blake3，不用 sha256，速度差一个量级 | 0006 决策段 | 新增 `blake3` 依赖，哈希算法固定为 blake3 |
| 写入必须原子：先写临时文件、同步、再改名到最终路径 | 0006 决策段 | 临时文件与最终路径同目录，`sync_data` 后 `rename` |
| 崩溃可能留下无引用的对象，这是安全的（多占空间），而不是危险的（丢内容） | 0006 后果段 | 文件先行、行随后，中断只留下无引用文件 |
| 回收用全局标记-清除加宽限期，不用引用计数 | 0006 决策段 | 06.5 不写回收，但 `unreferenced_since` 列已建，留给 06.9 |
| 大文件设阈值，超过 1 MiB 只记录尺寸、修改时间与哈希，不存内容 | 0006 决策段 | 06.5 不写阈值判定，那是 06.6 快照清单的工作 |
| 事件表每工作区超过 200 MB 时归档，库内只留索引 | 0002 第 62 行至第 63 行 | 06.5 不写归档，但 CAS 写入是归档的目标 |
| 完整请求与响应以内容寻址引用加预览的形式进事件表，引用必须能还原完整报文 | 0018 第六节 | 06.5 提供 `put` 与 `get`，让事件表的内容寻址引用能还原完整报文 |

三处需要特别说清的核实结果。

**第一，`blobs` 表是全局的，不带工作区列。** `0001_core.sql` 的注释明确"blobs 按内容哈希全局去重，跨工作区共享同一份，因此不带工作区列"。因此 CAS 写入不取 `WorkspaceScope`，`put` 与 `get` 都不带作用域参数。这是与 06.3 事件追加（必须带作用域）的关键区别。

**第二，`unreferenced_since` 列在 06.5 恒为 NULL。** 它是"宽限期起点"，由 06.9 的回收扫描观察"变为无引用"的时刻时写入。06.5 的 `put` 插入行时 `unreferenced_since` 为 NULL，表示"还没被观察过"。`created_at` 不能顶替它——宽限期服务的是"刚被引用、清单尚未提交"这个窗口，拿创建时间当起点会把刚写入的对象提前判死。`0002_content.sql` 的注释明确"创建时间不能顶替它"。

**第三，`BlobRef` 是内核的类型，不是存储层的。** `BlobRef { hash: String, len: u64 }` 在 `ita-kernel` 的 `context/node.rs`，`ita-store` 依赖 `ita-kernel`，可以直接返回它。`put` 返回 `BlobRef`，`hash` 是 blake3 十六进制，`len` 是内容字节数。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **写入后文件与行都存在。** 写入一段内容，断言 `blobs` 表里多了一行，`hash` 是内容的 blake3 十六进制，`size` 是内容字节数，`created_at` 非空，`unreferenced_since` 为 NULL；文件系统里 CAS 根目录下有对应的哈希文件，内容等于写入的内容。守的是"写入成功时文件与行成对出现"。
2. **同内容两次写入只产生一个 blob。** 写入同一段内容两次，断言 `blobs` 表里只有一行，文件系统里只有一个哈希文件。守的是"去重"。
3. **不同内容产生不同的 blob。** 写入两段不同的内容，断言 `blobs` 表里有两行，`hash` 不同，文件系统里有两个哈希文件。守的是"哈希区分内容"。
4. **读回内容与写入一致。** 写入一段内容，用返回的哈希读回，断言读回的字节等于写入的内容。守的是"内容寻址引用能还原完整报文"（0018 第六节）。
5. **读不存在的哈希返回错误。** 用一个不在 `blobs` 表里的哈希读，断言返回 `BlobNotFound` 错误。守的是"读路径能区分'不存在'与'读失败'"。
6. **空内容也产生一个 blob。** 写入空内容（0 字节），断言 `blobs` 表里有一行，`hash` 是空内容的 blake3 十六进制，`size` 是 0。守的是"空内容不是非法输入"。
7. **CAS 根目录在首次写入时创建。** 打开一个库，不写入任何内容，断言 CAS 根目录不存在；写入一段内容后，断言 CAS 根目录存在且包含哈希文件。守的是"懒创建，不为不用 CAS 的库建空目录"。
8. **跨工作区共享同一份内容。** 在两个工作区各写入同一段内容，断言 `blobs` 表里只有一行（全局去重），两个工作区的事件都引用同一个哈希。守的是"blobs 是全局的，不带工作区列"。

第 2 条与第 3 条合起来守的是同一件事：哈希是内容的函数，同内容同哈希、不同内容不同哈希。第 4 条守的是"引用能还原报文"，是 0018 第六节的落地。第 7 条守的是"懒创建"，避免为不用 CAS 的库建空目录。第 8 条守的是"全局去重"，是 `blobs` 表不带工作区列的落地。

## 六、实现顺序与每步验证

分三次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的先做"排，`blobs.rs` 的表操作不碰文件系统，最便宜也最容易把"行存在性"这条细节一次做对。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `blobs.rs` 的表操作与它的模块内单测，`db.rs` 加两个错误变体与 `cas_root` 字段 | `cargo nextest run -p ita-store -E 'test~blob'` |
| 二 | 写 `cas.rs` 的原子写入与哈希计算，`lib.rs` 接线，`Cargo.toml` 加 `blake3` | `cargo nextest run -p ita-store`，此时 `tests/cas.rs` 覆盖第四节第 1、2、3、4、6、7 条 |
| 三 | 补 `get` 路径与其余验收，跑完整三件套 | `cargo nextest run --workspace --locked`、`cargo build --workspace --locked`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo fmt --all --check`、`bash .w1mer/scripts/check_kernel_purity.sh` |

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里入册，断言消息仍然用中文。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 行先行、文件随后 | 正常路径的断言全部通过，崩溃时才会留下"指向空内容的行" | 第四节第 1 条断言文件与行成对出现；实现里文件写入在行插入之前，顺序由代码结构保证 |
| 用 sha256 而不是 blake3 | 同内容同哈希、不同内容不同哈希都成立，去重也通过 | 实现里哈希算法固定为 blake3，`Cargo.toml` 加 `blake3` 依赖；测试断言 `hash` 是 64 字符的十六进制（blake3 是 256 位，sha256 也是 256 位，但算法不同，哈希值不同） |
| 临时文件与最终路径不同目录 | 正常路径通过，跨文件系统 `rename` 会失败或不是原子的 | 实现里临时文件与最终路径同目录；测试断言 CAS 根目录的布局是 `blobs/<2字符>/<完整哈希>` |
| 去重查文件而不是查行 | 文件存在但行不存在（崩溃恢复情形）时，查文件会跳过插行，留下无行文件 | 第四节第 2 条与第 8 条：去重查 `blobs` 行，存在则跳过；行不存在则写文件并插行 |
| `unreferenced_since` 被写成 `created_at` | 正常路径通过，06.9 的宽限期判定会提前判死刚写入的对象 | 第四节第 1 条断言 `unreferenced_since` 为 NULL；实现里 `put` 插入行时 `unreferenced_since` 恒为 NULL |
| CAS 根目录在 `open` 时创建而不是懒创建 | 不用 CAS 的库也会建空目录，测试断言目录存在时通过 | 第四节第 7 条：打开库不写入时目录不存在，写入后目录存在 |
| `get` 路径不区分"不存在"与"读失败" | 读不存在的哈希返回 `Cas` 错误而不是 `BlobNotFound`，测试断言错误类型时通过 | 第四节第 5 条：读不存在的哈希返回 `BlobNotFound`，读失败返回 `Cas` |
| 空内容被当成非法输入拒绝 | 正常路径通过，空内容的写入被拒 | 第四节第 6 条：空内容产生一个 blob，`size` 是 0 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：`blobs` 表的 `hash` 是主键，`put` 用 `INSERT OR IGNORE` 插行。这意味着即使去重检查被绕过（并发情形，虽然单写者不会发生），插行也是幂等的。这条与 06.3 的"分配与插入同一事务"同型，是"写入路径的幂等性"。

## 八、已裁决的分歧点

四处分歧点已由主 Agent 裁决，全部采纳 Explorer 的建议（均选甲）：CAS 根目录是数据库文件同级的 `blobs` 目录（`Store` 自包含）；06.5 同时提供 `put` 与 `get`（`get` 是验证 `put` 与 0018 第六节的前提，也是 06.6 与 06.8 的公共依赖）；临时文件用固定后缀 `.tmp`（单写者无并发竞争）；06.5 只同步文件、不同步目录（目录同步是 durability 加强，留给后续批次）。裁决理由见下表"建议"列。

| 分歧 | 两种做法 | 建议（已裁决采纳） |
|---|---|---|
| CAS 根目录的位置 | 甲：数据库文件同级的 `blobs` 目录。乙：`Store::open` 多一个参数，CAS 根路径由调用方给出 | **选甲。** 理由见第二节。乙把 CAS 根路径的决策推给调用方，而调用方（server）目前还没有定形 CAS 根路径的约定；甲让 `Store` 自包含，`open` 从数据库路径派生，`open_in_memory` 用临时路径。导出导入（18.x）时整个目录树就是工作区数据，甲更自然 |
| `get` 路径是否属于 06.5 | 甲：06.5 提供 `put` 与 `get`。乙：06.5 只提供 `put`，`get` 留给 06.6 或 06.8 | **选甲。** 理由见第四节第 4 条。`get` 是验证 `put` 的前提（读回内容断言等于写入内容），也是 0018 第六节"引用必须能还原完整报文"的落地。06.6 与 06.8 都要读 blob，`get` 是它们的公共依赖。乙把 `get` 推迟会让 06.5 的验收无法自证 |
| 临时文件的命名 | 甲：固定后缀 `.tmp`。乙：唯一名（pid + 计数器） | **选甲。** 单写者没有并发竞争，固定后缀足够。崩溃后留下的 `.tmp` 文件是无引用对象，06.9 的回收会清掉。乙的唯一名是为并发准备的，单写者用不上 |
| 是否同步目录（rename 后的 durability） | 甲：06.5 只同步文件，不同步目录。乙：06.5 同时同步文件与目录 | **选甲。** 理由见第二节。同步文件保证"内容在改名前已持久"，同步目录保证"改名本身已持久"。06.5 的验收是"崩溃不留下指向空内容的行"，文件同步足够；目录同步是 durability 的加强，留给后续批次 |

## 九、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 06.5：快照清单、回滚对齐与回收（06.6 至 06.9）；事件 seq 分配与预览截断（06.3 已完成）；帧节点与 head 的比较并交换（06.4）；批量提交与 group commit（08.4）；事件读路径的缓存与续传（08.5）；大文件阈值判定（06.6）；回收的标记-清除与宽限期（06.9）；导出导入（18.x）。

## 十、Explorer 核对与补强（基线 3088c70）

本节的核对对象是批次基线 3088c70 的已提交代码，不是实现者的工作树。结论是：八条断言对基线全部成立，表结构、哈希算法与 CAS 目录布局的口径都没有被证伪，需要改写的只是"怎么做"与四处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 表结构核对：全部成立

`0002_content.sql` 的 `blobs` 表与计划第二节所写逐列一致。`blobs` 的主键是 `hash`，`size` 与 `created_at` 非空，`unreferenced_since` 可空且带 CHECK 约束（`unreferenced_since IS NULL OR unreferenced_since >= created_at`）。`blobs` 表不带工作区列，是全局的，跨工作区共享同一份。`0001_core.sql` 的注释明确"blobs 按内容哈希全局去重，跨工作区共享同一份，因此不带工作区列"。

### 10.2 句柄形状核对：`cas_root` 是必须补的缺口

`Store` 把 `Connection` 私有持有，只暴露 `conn()`（crate 内部，返回 `&Connection`）与 `conn_for_test()`。`Store` 目前不持有 CAS 根路径，因此 06.5 必须给 `Store` 加一个 `cas_root: PathBuf` 字段。`open` 从数据库路径派生（`path.parent().join("blobs")`），`open_in_memory` 用临时路径（`std::env::temp_dir().join(format!("ita-cas-{}", ulid::Ulid::new()))`）。`ulid` 已经是 `ita-store` 的声明依赖，临时路径名不需要新增依赖。目录在首次 `put` 时懒创建，不在 `open` 时建。

### 10.3 内核类型核对：`BlobRef` 是内核的类型

`BlobRef { hash: String, len: u64 }` 在 `ita-kernel` 的 `context/node.rs`，`ita-store` 依赖 `ita-kernel`，可以直接返回它。`put` 返回 `BlobRef`，`hash` 是 blake3 十六进制，`len` 是内容字节数。`BlobRef` 的 `hash` 是"内容的哈希，十六进制文本形式"，与 blake3 的 64 字符十六进制一致。

### 10.4 四处补强

**第一，`blake3` 不是工作区依赖，需要新增。** `Cargo.toml` 的工作区依赖只有 `rusqlite` 与 `ulid`，`Cargo.lock` 里没有 `blake3`。06.5 必须在工作区依赖加 `blake3 = "1"`，在 `ita-store` 的 `Cargo.toml` 加 `blake3.workspace = true`。`blake3` 不在分层门的 `CAPABILITIES` 列表里，因此任何 crate 都可以依赖它，不违反分层约束。

**第二，CAS 根目录的位置是 06.5 唯一的跨 crate 设计决定。** 拆分依据没有提到 CAS 根目录在哪里，`blobs` 表也没有"内容在哪里"的列。06.5 必须自己定形 CAS 根目录的位置，这是本批唯一的跨 crate 设计决定。建议选甲（数据库文件同级的 `blobs` 目录），理由见第八节。

**第三，`get` 路径属于 06.5，不是 06.6 或 06.8。** 拆分依据的验收只提到"写入、去重与原子改名"，没有提到读路径。但 `get` 是验证 `put` 的前提（读回内容断言等于写入内容），也是 0018 第六节"引用必须能还原完整报文"的落地。06.6 与 06.8 都要读 blob，`get` 是它们的公共依赖。建议选甲（06.5 提供 `put` 与 `get`），理由见第八节。

**第四，`unreferenced_since` 列在 06.5 恒为 NULL。** 它是"宽限期起点"，由 06.9 的回收扫描观察"变为无引用"的时刻时写入。06.5 的 `put` 插入行时 `unreferenced_since` 为 NULL，表示"还没被观察过"。`created_at` 不能顶替它——宽限期服务的是"刚被引用、清单尚未提交"这个窗口，拿创建时间当起点会把刚写入的对象提前判死。`0002_content.sql` 的注释明确"创建时间不能顶替它"。

### 10.5 一处与 ROADMAP 的计数差异

ROADMAP 的 06.5 行写"CAS 写入、去重与原子改名"，而 ADR 0006 的布局是 `blobs/3f/3fab...c1`。两处对 CAS 目录布局的描述一致，没有计数差异。这里只作记录，不改 ROADMAP 表格行。
