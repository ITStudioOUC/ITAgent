# 测试函数名英文化与初始表结构约束定形的执行计划

本批次做四件事：把全仓 250 个中文测试函数名改成英文 snake_case 并在每个函数上方补一行
中文说明；把这条命名规则写进注释规范；按用户要求去掉批次粒度里的行数指标；核实
`.w1mer/review/R_06_2.md` 前两条关于"跨列 CHECK 只能在建表时定形"的判断。核实结论是
**判断成立，但表述偏窄**：不能后补的不止跨列 CHECK，任何针对既有列的 CHECK、既有列的
默认值、既有外键的删除动作都改不了，因为 SQLite 的 `ALTER TABLE` 只有五种语句。

## 结论

1. 改名按三个内核提交加两个小 crate 提交推进，每个提交只覆盖一个模块组，共五次；规范文档
   独立成第一次提交，先立规矩再动代码。
2. 英文名的判据是"条件加期望结果，且不丢区分细节"；`///` 一行写这个用例守的行为与代价，
   已有的行内 `//` 讲机制，两者不重复。
3. 注释规范新增一节放在第七节，不动已有小节编号，只在第二节加一句指向。
4. `AGENTS.md` 第 8 节与 `ROADMAP.md` 的 Task granularity 段都要改；只改一处会让两处
   互相矛盾，下一批会照着旧口径拆任务。
5. 初始表结构里有五类约束属于**本批不写就永久丢失**：`snapshots.kind` 与
   `snapshot_entries.kind` 的取值域、`snapshot_entries` 的形态互斥 CHECK、重定基线留痕的
   两条 CHECK、`content_stored` 的默认值必须去掉、以及外键的删除动作。宽限期起点列与两个
   索引都可以后补，不属于硬窗口。

### 1.2 分批建议

一次改 250 个名字的提交无法复审： reviewer 只能用"数一数有没有少"这种机械方式检查，看不出
哪个名字译错了。按模块组切成五次提交，每次 60 至 80 个名字，单个提交内部的语义同源，复审
可以顺着一个模块的术语表读完。五个提交同属一个批次，按 `AGENTS.md` 第 4 节共用同一个版本号，
版本只在最后一次提交前推进一次。

建议的提交顺序与主题（主题里不写用例数量，遵守第 3 节）：

1. `docs: 规定测试函数名用英文并在上方写一行中文行为说明` —— 先改规范，再改代码，
   这是第 5 节"规范变更先改文件"的要求。同时改 `AGENTS.md` 第 8 节与 `ROADMAP.md`。
2. `test: 命令文法用例改为英文名并补行为说明`（80 个）。
3. `test: 上下文核心用例改为英文名并补行为说明`（80 个）。
4. `test: 语义压缩用例改为英文名并补行为说明`（62 个）。
5. `test: 存储与角色分发用例改为英文名并补行为说明`（28 个）。

拆法上有一个可选变体：把第 2 次再拆成 `command/lex` 加 `heredoc` 与 `ast`、`parse` 两半。
不建议这么做——词法与装配共用同一套术语（词、算符、分隔符、正文），拆开后复审要跨两个提交
对照同名词的译法，反而更难。同理，存储 19 个与命令行 9 个合成一次提交，因为两者都小，
单独提交只是增加批次开销。

### 1.3 命名风格样例

规则有三条，缺一条就会丢信息：

- 名字写"条件 + 期望结果"，结果用 `_rejected`、`_accepted`、`_is_noop`、`_conflicts`、
  `_does_not_*` 这类后缀明说，不用 `_test`、`_works`、`_ok` 这种没有信息量的结尾。
- 同一个模块内成对的用例必须能靠名字区分（例如 `_when_empty` 与 `_when_unquoted`）。
- 中文名里凡是"不报方向""按第一个闭合处理""而不是覆盖"这类**判据细节**，英文名里必须
  保留对应词，不能只留一个"被拒"。

代表性改名（前两条是用户点名的混合名，其余覆盖不同写法）：

| 原中文名 | 英文名 | 译法说明 |
|---|---|---|
| `不可达且已变化时不报方向` | `unreachable_and_changed_reports_unknown_direction` | 关键在"不报方向"：此时无法判断新旧，任何方向词都会误导模型。译成 `reports_no_change` 或 `rejects` 都丢了这条判据 |
| `散文里含闭合标记字符串时按第一个闭合处理` | `prose_containing_close_marker_splits_at_first_close` | "按第一个闭合处理"必须落成 `splits_at_first_close`；只写 `rejects_nested_marker` 会把实现细节译反——实际是切分后残留文本被拒，不是检测嵌套 |
| `heredoc_正文被收进命令` | `heredoc_body_is_captured_into_command` | 混合名，中文"正文被收进命令"是主语义，`heredoc` 是术语；英文名把术语放前面，动词短语完整保留"收进命令" |
| `双引号内只解释_bash_也解释的四个转义` | `double_quotes_interpret_only_the_four_bash_escapes` | "只解释那四个"是这条用例的全部价值，`only` 与 `four` 都不能省，省了就变成"双引号内解释转义"这种过宽的说法 |
| `回退到当前_head_是允许的空操作` | `rewind_to_current_head_is_allowed_noop` | 混合名；`rewind` 与 `restore` 在本仓是两个不同动词（前者动上下文指针，后者动工作区文件），不能互换 |
| `追加的父必须就是当前_head` | `append_parent_must_be_current_head` | 说的是"父必须等于当前 head"，不是"必须是祖先"，两者的拒绝错误类型不同 |
| `重复的节点_id_被拒而不是覆盖` | `duplicate_node_id_rejected_not_overwritten` | "而不是覆盖"是防回归的重点：早期实现会静默覆盖，名字里保留 `not_overwritten` 才能看出这是在守什么 |
| `乱序到达的旧记录不覆盖新记录` | `out_of_order_older_record_does_not_overwrite_newer` | 三个信息都要留：乱序、旧、不覆盖新 |
| `未加引号且正文含美元符号时拒绝` | `unquoted_delimiter_rejected_when_body_contains_dollar` | 条件两段（未加引号、含美元符）都要写出，否则与"未加引号且正文含反斜杠"那条无法区分 |
| `终止行带尾随空格时不匹配` | `terminator_with_trailing_space_does_not_match` | "不匹配"是这条用例守的行为，不能弱化成 `rejected`（拒绝发生在别处） |
| `失败记录缺一半被拒` | `failure_record_missing_either_half_is_rejected` | "缺一半"指尝试与结果两半缺一，`either_half` 把这一点说清 |
| `两个子会话从同一节点分叉后令牌不可互换` | `head_tokens_not_interchangeable_after_fork_from_same_node` | 三个条件缺一不可：两个子会话、同一节点分叉、令牌不可互换 |
| `零预留时越过上限也拒绝压缩` | `compression_refused_when_over_limit_even_with_zero_reserve` | "即使零预留也要拒"是防回归点（容易写成零预留就必然稀缺而放行） |
| `字节数是正文总长度且不与预算混用` | `byte_count_is_body_length_not_budget` | 后半句是历史缺陷的回归守卫，必须保留 `not_budget` |
| `失败矩阵逐条命中` | `failure_matrix_cases_each_hit_expected_error` | 集成测试的入口用例，名字要说明是表驱动逐条比对，而不是只跑一条 |

### 1.4 `///` 说明的写法

每个改名后的测试函数上方紧贴一行 `///`，写在 `#[test]` 之上，让说明读起来是这个用例的
标题：

```rust
/// 检查点不可达且磁盘已变化时不报方向：此时无法判断哪边更新，任何方向词都会误导模型。
#[test]
fn unreachable_and_changed_reports_unknown_direction() {
```

判据是"这个用例守的是什么行为"，不是复述名字。已经有一段行内 `//` 讲机制的用例
（例如 `compress/format.rs` 的闭合标记用例），`///` 只写行为与代价，行内 `//` 保留机制说明，
两者不互相抄。名字本身已足够自明的用例也要写，因为这一行同时是中文语义的唯一载体——中文名
去掉之后，如果不写 `///`，原意就只剩英文名这一层表达，等于永久丢失一层。

### 1.5 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 漏改或改重 | 编译期会抓到重名，但漏改不会报错，只是残留中文名 | 改前用 `grep -P '^\s*fn .*[\x{4e00}-\x{9fff}]'` 存一份清单，改后要求同一命令在 `crates/` 下零命中 |
| 用例数变化 | rename 时误删或误合并函数 | 改前改后各跑一次 `cargo nextest list --workspace`，比对用例总数与逐 crate 数量；这个数字只用于自查，不写进提交主题 |
| 译名丢信息 | 英文名比中文名宽泛，以后无法从名字看出防的是什么回归 | 按 1.3 的三条规则逐条自检；reviewer 抽查每个模块五个名字，要求能反译回中文 |
| 过滤表达式失效 | 文档或习惯里的 `-E 'test~中文正则'` 找不到用例 | 全仓检索确认没有把中文用例名写进脚本或 CI；已确认无此类引用，`AGENTS.md` 只写过滤语法不写具体名字 |
| 诊断消息被误改 | `tests/command_matrix.rs` 的 `Case.name` 是中文 | 那是给人看的诊断数据，不是标识符，保持中文；只改 `#[test]` 函数名 |
| lint 交互 | 内核 `#![deny(missing_docs)]` | 只约束公开条目，测试模块内是私有函数，加 `///` 不触发任何 lint，也不与 clippy 冲突 |

## 三、跨列 CHECK 的核实

### 3.1 结论

`R_06_2.md` 的第 1、2 条判断成立，但把范围说窄了。真实情况是：**SQLite 没有"给既有表或
既有列追加约束"的语句**，所以凡是需要约束既有列的规则，只要本批不写进 `CREATE TABLE`，
以后就只能重建表；而重建表的第一步是 `DROP TABLE`，迁移扫描器禁掉了它。

### 3.2 核实依据

SQLite 的 `ALTER TABLE` 只支持五种语句，语法产生式里没有 `ADD CONSTRAINT`：

- 内嵌源码 `libsqlite3-sys 0.30.1`（`Cargo.lock` 记录该版本，随包 SQLite 3.46.0）
  的语法表只有四条 `ALTER TABLE` 产生式：`RENAME TO`、`ADD COLUMN`、`DROP COLUMN`、
  `RENAME COLUMN`（`sqlite3.c` 第 174623 至 174627 行）。
- 同一份源码里 `sqlite3AlterFinishAddColumn`（第 116450 行起）把新列定义文本拼进
  `CREATE TABLE` 语句，它只接受一个 column-def，并且显式拒绝 `PRIMARY KEY` 与 `UNIQUE`
  （第 116491 至 116498 行）。也就是说，`ADD COLUMN` 能附带 CHECK，但只能附在**新列**上。
- 官方 `ALTER TABLE` 文档第 1 节把支持范围写成"重命名表、重命名列、加列、删列"，
  第 8 节给出的通用改表办法是 12 步流程，第 6 步就是 `DROP TABLE`。
- 本仓 `crates/ita-store/src/migrate.rs` 的用例（第 274 至 282 行）在迁移脚本里禁掉
  `DROP TABLE`、`DELETE FROM`、`VACUUM`、`PRAGMA` 四个词。12 步流程撞 `DROP TABLE`；
  官方文档里"改默认值、删约束"用的另一种 9 步流程要 `PRAGMA writable_schema`，撞
  `PRAGMA`。两条绕路都被堵死。
- `migrate.rs` 另有脚本指纹校验（第 134 至 143 行）：已执行过的版本若脚本内容变了，
  直接报 `ScriptChanged` 拒绝启动。因此 0002 只能在它还没跑进任何长期库之前定形；
  当前它只进过开发期的内存库与 `.ita/` 临时库，属于仍在同一史诗内的窗口。

### 3.3 本批不写就永久丢失的清单

| 约束 | 位置 | 为什么是硬窗口 | 建议写法 |
|---|---|---|---|
| `snapshots.kind` 取值域 | `0002_content.sql` `snapshots` | CHECK 挂在既有列上，`ADD COLUMN` 只能给新列加 CHECK | `kind TEXT NOT NULL CHECK (kind IN ('baseline','incremental'))` |
| 重定基线留痕三列同进同出 | 同上 | 跨三列的 CHECK，既有列无法追加 | `CHECK ((rebased_by IS NULL) = (rebase_reason IS NULL) AND (rebased_by IS NULL) = (rebase_confirmed_by IS NULL))` |
| 留痕只对基线成立 | 同上 | 跨列且引用 `kind` | `CHECK (rebased_by IS NULL OR kind = 'baseline')` |
| `snapshot_entries.kind` 取值域 | `snapshot_entries` | 同上 | `kind TEXT NOT NULL CHECK (kind IN ('file','dir','tombstone'))` |
| 条目形态与 `kind` 互斥 | 同上 | 跨多列（`kind`、`hash`、`size`、`mode`、`mtime`、`content_stored`），既有列上的约束无法追加 | 见 3.4 片段 |
| `content_stored` 的默认值必须去掉 | 同上 | 改既有列的 DEFAULT 没有 `ALTER` 语句，只能走 `PRAGMA writable_schema` 那条 9 步流程，被扫描器禁 | 列声明写成 `content_stored INTEGER,`，不给 DEFAULT |
| 外键的删除动作（`snapshots.parent_id` 自引用、`snapshot_entries.snapshot_id` 指向 `snapshots`、`read_set.session_id` 指向 `sessions`） | `snapshots`、`snapshot_entries`、`read_set` | 既有外键的 `ON DELETE` 子句同样没有 `ALTER` 语句 | 见 3.5 |

可以后补、不属于硬窗口的三项，本批顺手写进去只是省一次迁移，不写也不会永久丢失：

- `blobs.unreferenced_since`：它是新增列。修正一句判据：能后补的不只是"列级 CHECK"，
  新列的 CHECK 也可以引用同一张表的既有列——`ALTER TABLE ... ADD COLUMN` 会把新列定义
  连同 CHECK 一起拼进 `CREATE TABLE` 文本，而 CHECK 表达式里出现哪个列名不受限制。已在
  本仓随包的 3.46.0 上实跑确认：`ALTER TABLE blobs ADD COLUMN unreferenced_since INTEGER
  CHECK (unreferenced_since IS NULL OR unreferenced_since >= created_at)` 执行成功，且随后
  写入早于 `created_at` 的值被该 CHECK 拒绝。因此这条约束即便晚一批加也不丢。
  真正的判据是"约束是否挂在一个既有列上"：挂在新列上可以后补，挂在既有列上就不行。
- `snapshots(parent_id)` 与 `read_set(session_id)` 索引：`CREATE INDEX` 任何时候都能加。
- 各表的单一 `NOT NULL`：只要新增列带非空默认值就能后补，本批不涉及。

额外发现一条 review 没有点到、但同属硬窗口的决策：`snapshot_entries.hash` 目前没有指向
`blobs(hash)` 的外键。少了它，条目可以指向一个不存在的 blob，回收是从条目出发标记的，
悬空哈希会让"内容已不在库里的条目"看起来正常。补外键只能现在补，之后同样改不了。
`dir` 与墓碑的 `hash` 为 NULL，外键对 NULL 不校验，不影响这两类。建议写成
`hash TEXT REFERENCES blobs(hash)`，与形态 CHECK 一起定形。

> **已裁决：此建议不采纳，本项目不补该外键。** 理由是 0017 规定的超阈值条目只记录哈希而
> 正文不入内容存储，这些哈希在 `blobs` 里没有行；SQLite 又不支持部分外键，条件化的
> "仅当 `content_stored = 1` 时检查"表达不出来，加外键会把 0017 规定的正常条目误判成悬空
> 引用而拒绝。完整理由与被否决的替代方案见 `.w1mer/detail/CHANGES.md` 里批次 06.2.1 的
> 记录。缺口的承接者改为代码侧：写入时断言 `content_stored = 1` 的条目其哈希必在 `blobs`
> 里，回滚前对每个有内容记录的条目同样核对，缺失内容写进残留清单而不是让写回中途失败。
> 本节保留原文是为了留下当时的判断过程，实施时以上面这条裁决为准。

### 3.4 建议的 `snapshot_entries` 片段

```sql
CREATE TABLE IF NOT EXISTS snapshot_entries (
    snapshot_id     TEXT NOT NULL REFERENCES snapshots(id),
    path            TEXT NOT NULL,
    kind            TEXT NOT NULL CHECK (kind IN ('file', 'dir', 'tombstone')),
    hash            TEXT REFERENCES blobs(hash),
    mode            INTEGER,
    size            INTEGER,
    mtime           INTEGER,
    content_stored  INTEGER,
    PRIMARY KEY (snapshot_id, path),
    CONSTRAINT entry_shape_matches_kind CHECK (
        (kind = 'file' AND hash IS NOT NULL AND size IS NOT NULL
            AND content_stored IS NOT NULL AND content_stored IN (0, 1))
        OR (kind IN ('dir', 'tombstone') AND hash IS NULL AND content_stored IS NULL)
    )
);
```

每个分支都显式写 `IS NULL` 与 `IS NOT NULL`，因为 CHECK 求值为 NULL 时算通过，
只写 `content_stored IN (0, 1)` 会让漏写的标记静默过关。这条注意事项目前只写在注释里，
应改进建表语句。

> **这段片段已过时，以上面 3.3 节末尾的裁决和实际迁移文件为准。** 落地时的形态比这里更严：
> `file` 支补了 `size >= 0`，目录与墓碑拆成两支，目录只判 `hash`、`size`、`content_stored`
> 为空而保留 `mode` 与 `mtime`（目录确实有权限位与修改时间），墓碑六列全空；`hash` 没有
> `REFERENCES blobs(hash)`。为什么目录的 `mode` 与 `mtime` 不判空、为什么外键不补，理由分别
> 写在实际迁移的列注释与 3.3 节的裁决里。

### 3.5 外键动作的建议

三处外键动作现在是默认的 `NO ACTION`，也就是删除被引用行会被拦住。建议保持不变，
理由与 `snapshots.parent_id` 那段的现有注释一致：改成 `ON DELETE SET NULL` 会让"父边为空"
与"顶层快照"不可区分，谱系静默断掉；改成 `CASCADE` 则删一个快照会连带删掉条目，
而删除动作发生在 squash 事务里，级联删除会绕过"先重挂子快照再删父"的显式顺序。

保持 `NO ACTION` 的代价是删除方必须先处理引用：squash 删最老两个增量前要先
`DELETE FROM snapshot_entries WHERE snapshot_id IN (...)` 并重挂子快照；会话回收要先删
`read_set` 行再删 `sessions` 行。这两条是代码顺序要求，写进对应子任务的验收里，不靠表结构
兜底。若决定改用级联，必须在本批写进 `CREATE TABLE`，之后就改不了了。
