# 批次 07.2 状态机、就绪探针与停止顺序的执行计划

拆分依据给 07.2 的验收是"未就绪时后续依赖不启动，停止按逆序执行且失败不级联重启"。核对基线 72d33c3 的已提交代码、07.1 的执行计划（detail 28）、ADR 0013 与 0014 之后，结论是：**验收口径成立且不需要改，但它依赖的五件事必须写进计划，否则实现者会在细节上做对状态、做错语义。** 五件事分别是：状态机、就绪探针与监督者是纯逻辑，落在 `ita-server` 的 `units` 模块，建在 07.1 的 `UnitId`/`DepKind`/`Topology`/`startup_order` 之上（ADR 0013 明确"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，unit 状态机不得与工作流节点状态混用）；状态机是六个状态加一个纯转移函数，非法转移返回 `None` 而不是原地不动（ADR 0013"就绪不等于运行"由 `Starting` 与 `Ready` 的区分承载）；就绪探针是三值结果（就绪/未就绪/失败）加一个可注入的 trait，探针是"功能可用"的判定，不是"进程活着"的判定；监督者是同步的，按 07.1 的拓扑序推进启动、按逆拓扑序执行停止，失败的单位永不重启、其依赖者永不启动（ADR 0013"版本一不级联重启，只标记降级"）；07.2 不新增依赖、不建表、不碰 tokio，unit 状态落库是 07.3 的事。文件规划 `crates/ita-server/src/units/{supervisor,state,probe}.rs` 与现状吻合，另需在 07.1 建的 `units/mod.rs` 里声明这三个模块。

## 结论

1. 07.2 的原始拆分成立。基线 72d33c3 的 `ita-server` 只有 `lib.rs` 一个空壳，`units` 模块不存在，需要 07.1 先建 `units/mod.rs` 与 `units/topology.rs`，07.2 在其上加 `state.rs`、`probe.rs`、`supervisor.rs`。需要改写的是"怎么做"，不是"做什么"。
2. **状态机、探针与监督者是纯逻辑，落在 `ita-server`，不进内核。** ADR 0013 的硬边界是"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，代价段点名"两套监督语义（unit 与工作流节点）容易混淆，必须靠文档与类型分开"。因此 unit 状态机必须独立于 `ita-workflow` 的节点状态，而内核的职责域是"上下文树的解析、命令文法的分析、租约与权限的策略判定"（`lib.rs` 文档注释），unit 状态机不在其中。07.1 已把 `UnitId`/`DepKind`/`Topology` 落在 `ita-server`，07.2 沿用同一模块，维持不改。
3. **状态机是六个状态加一个纯转移函数。** 状态是未启动、启动中、就绪、失败、停止中、已停止。转移函数 `next(state, event) -> Option<UnitState>` 是纯函数，非法转移返回 `None` 而不是原地不动。"就绪不等于运行"由 `启动中`（进程活着但未就绪）与 `就绪`（探针通过、功能可用）的区分承载，这是 ADR 0013 的核心语义。
4. **就绪探针是三值结果加可注入 trait。** 探针结果是就绪、未就绪、失败三值。探针是"功能可用"的判定（数据库迁移完成、套接字在监听、路由表载入完毕），不是"进程活着"的判定。探针以 trait 形式注入监督者，07.2 定义抽象，真实的每 unit 探针实现（检查迁移、套接字、路由表）留到真实 unit 存在时再做。
5. **监督者是同步的，按拓扑序启动、按逆拓扑序停止。** 监督者消费 07.1 的 `Topology` 与 `startup_order`，按拓扑序推进启动，一个 unit 只有在全部依赖都就绪后才启动。停止按逆拓扑序执行，依赖者先于被依赖者停止。失败的单位永不重启，其依赖者永不启动（ADR 0013"版本一不级联重启，只标记降级"）。07.2 是纯逻辑，crate 无 tokio，监督者是同步的，真实 unit 的异步执行留到后续批次。
6. **07.2 不新增依赖、不建表、不碰 tokio。** 基线的 `ita-server/Cargo.toml` 只有 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow` 四个依赖，没有 tokio、没有 async。07.2 是纯数据类型与纯函数，零新增依赖。unit 状态落库与 `units` 表建表是 07.3 的事（激活门需要持久化状态），07.2 的状态机在内存里。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、07.1 的执行计划（detail 28）产出的类型、以及基线 72d33c3 的 `ita-server` 现状。

| 拆分里的说法 | 现状 | 判断 |
|---|---|---|
| 验收"未就绪时后续依赖不启动" | 基线无任何状态机或监督者代码，`units` 模块不存在 | 成立，本批在 07.1 之上从零建 |
| 验收"停止按逆序执行" | 基线无任何停止顺序代码 | 成立，本批从零建 |
| 验收"失败不级联重启" | 基线无任何重启抑制代码 | 成立，本批从零建 |
| 文件 `crates/ita-server/src/units/{supervisor,state,probe}.rs` | 三个文件都不存在，`units` 模块由 07.1 建 | 成立，07.2 加三个文件并在 `mod.rs` 声明 |
| 依赖"07.1" | 07.1 产出 `UnitId`/`DepKind`/`Topology`/`startup_order`（detail 28） | 成立，07.2 消费这些类型 |
| 状态机是纯逻辑 | ADR 0013 定形，无 IO | 成立，纯函数，无 IO |
| 就绪探针是"功能可用"判定 | ADR 0013"就绪不等于运行" | 成立，探针是抽象，真实实现留后 |

被证伪的是拆分之外的一件事：拆分没有提到 unit 状态落库与 `units` 表建表归哪一批。07.1 的计划（detail 28）把"unit 状态落库与 `units` 表建表"列为 07.1 不做的事，并标注是"07.2 或 07.3"。本批裁决：07.2 的状态机在内存里（纯逻辑），unit 状态落库与 `units` 表建表归 07.3（激活门需要持久化状态），见第二节第 2.6 条与第八节。

## 二、状态机、就绪探针与停止顺序的实际形状

### 2.1 状态机是六个状态加一个纯转移函数

`UnitState` 是六个变体：`NotStarted`（未启动）、`Starting`（启动中，进程活着但未就绪）、`Ready`（就绪，探针通过）、`Failed`（失败，探针失败，不再重启）、`Stopping`（停止中）、`Stopped`（已停止）。`UnitEvent` 是驱动转移的事件：`Start`、`ProbeReady`、`ProbeFailed`、`ProbeNotReady`、`Stop`、`Stopped`。转移函数 `next(state: UnitState, event: UnitEvent) -> Option<UnitState>` 是纯函数，非法转移返回 `None`。

合法的转移边是：未启动加 `Start` 到启动中；启动中加 `ProbeReady` 到就绪；启动中加 `ProbeFailed` 到失败；启动中加 `ProbeNotReady` 到启动中（原地重试）；就绪加 `Stop` 到停止中；停止中加 `Stopped` 到已停止。其余组合都返回 `None`。

"就绪不等于运行"由 `Starting` 与 `Ready` 的区分承载：`Starting` 是进程活着但未就绪（运行），`Ready` 是探针通过、功能可用（就绪）。这是 ADR 0013 的核心语义，也是冷启动体感的关键。

### 2.2 就绪探针是三值结果加可注入 trait

`ProbeResult` 是三个变体：`Ready`（就绪）、`NotReady`（未就绪，仍在启动）、`Failed`（失败）。`ReadinessProbe` 是 trait，唯一方法 `probe(&self, unit: &UnitId) -> ProbeResult`。监督者持有 `Box<dyn ReadinessProbe>`，在 unit 处于 `Starting` 时调用探针，按结果转移状态。

探针是"功能可用"的判定，不是"进程活着"的判定。ADR 0013 把就绪定义为"数据库迁移完成、IPC 套接字在监听、路由表载入完毕"，这些都是功能可用性的检查，不是进程存活检查。07.2 定义探针抽象，真实的每 unit 探针实现（检查迁移、套接字、路由表）留到真实 unit 存在时再做，07.2 的测试用假探针。

### 2.3 监督者按拓扑序启动，一个 unit 全部依赖就绪后才启动

`Supervisor` 持有 `topology: Topology`、`states: HashMap<UnitId, UnitState>`、`probe: Box<dyn ReadinessProbe>`。构造时所有 unit 初始化为 `NotStarted`。`step(&mut self) -> StepOutcome` 驱动一次监督者循环：按 `startup_order` 遍历，找到第一个 `NotStarted` 且全部依赖都 `Ready` 的 unit，把它转移到 `Starting`，调用探针，按探针结果转移（`Ready` 到就绪、`Failed` 到失败、`NotReady` 保持启动中）。`StepOutcome` 是 `Progressed(UnitId)`（有进展）或 `Blocked`（无进展）。`run_until_blocked` 反复调 `step` 直到 `Blocked`。

"未就绪时后续依赖不启动"的核心规则是：一个 unit 只有在全部依赖都 `Ready` 时才启动。如果依赖是 `Starting`（未就绪），依赖者不启动；如果依赖是 `Failed`，依赖者永不启动（保持 `NotStarted`）。这条规则 baked 进监督者：它只启动 `NotStarted` 且依赖全 `Ready` 的 unit。

### 2.4 失败不级联重启

`Failed` 的 unit 永不回到 `Starting`（不重启），其依赖者永不启动（保持 `NotStarted`）。这条规则有两层保障：状态机层面，`next(Failed, Start)` 返回 `None`（状态机本身拒绝重启失败 unit）；监督者层面，`Failed` unit 不是 `NotStarted`，不会被重新选中启动，其依赖者因依赖未 `Ready` 而永不启动。ADR 0013 的理由是"重启会打断正在进行的工具调用与租约，而租约的 TTL 回收本来就能处理崩溃。降级加能力推送让客户端知道缺什么，比自动恢复更可预测"。ADR 0014 补充：执行器崩溃时其租约按 TTL 过期，工作区恢复可写，server 的 unit 也不需要级联重启。

### 2.5 停止按逆拓扑序执行

`shutdown(&mut self) -> ShutdownResult` 按 `startup_order` 的逆序遍历，对每个 `Ready` 的 unit 执行 `Ready → Stopping → Stopped` 的转移。`Failed`、`NotStarted`、`Stopped` 的 unit 跳过（无可停止）。`ShutdownResult` 记录被停止的 unit 列表。逆序保证依赖者先于被依赖者停止：`ipc` 依赖 `router` 依赖 `store`，停止时 `ipc` 先停、`router` 次之、`store` 最后，保证一个 unit 停止时没有东西还依赖它。

### 2.6 unit 状态落库与 `units` 表建表归 07.3

07.2 的状态机在内存里（纯逻辑），不建表、不新增迁移。unit 状态落库与 `units` 表建表归 07.3，因为激活门需要持久化状态（server 重启后恢复 unit 状态）。基线的两份迁移文件（`0001_core.sql`、`0002_content.sql`）都没有 `units` 表，07.2 不新增迁移。

## 三、ADR 对状态机、就绪探针与停止顺序的硬要求

与 07.2 相关的决策分布在 ADR 0013、0014 与 ROADMAP 07 行，逐条对照如下。

| 要求 | 出处 | 07.2 怎么落地 |
|---|---|---|
| 就绪不等于运行 | 0013 决策段 | `Starting`（运行）与 `Ready`（就绪）区分，探针是就绪判定 |
| 崩溃处理保守，版本一不级联重启，只标记降级 | 0013 决策段 | `Failed` unit 永不重启，依赖者永不启动，状态机与监督者双层保障 |
| 依赖关系区分三种：硬依赖、软依赖、仅排序 | 0013 决策段 | 07.2 消费 07.1 的 `DepKind`，启动排序对三种边一致（被依赖者先启动） |
| unit 管进程生命周期，工作流管任务语义，两者不共享状态机 | 0013 决策段 | unit 状态机落 `ita-server`，不进内核、不与 `ita-workflow` 混用 |
| 两套监督语义靠文档与类型分开 | 0013 后果段 | `UnitState`/`UnitEvent`/`Supervisor` 独立类型，不与工作流节点状态复用 |
| 执行器是独立进程，不是 server 内的 unit | 0014 决策段 | 07.2 的 unit 是 server 内部子系统，不含执行器；`lease` 只做租约表维护与跨工作区资源仲裁 |
| 执行器崩溃时其租约按 TTL 过期 | 0014 决策段 | 07.2 不涉执行器进程，unit 的失败不级联重启与执行器的 TTL 回收是两条独立路径 |
| 状态机、就绪探针与停止顺序 | ROADMAP 07 行 | `state.rs`/`probe.rs`/`supervisor.rs` 三文件 |
| 未就绪时后续依赖不启动，停止按逆序执行且失败不级联重启 | ROADMAP 07 行验收 | 监督者按拓扑序启动、逆拓扑序停止，`Failed` unit 不重启 |

三处需要特别说清的核实结果。

**第一，`ita-server` 基线是空壳，`units` 模块由 07.1 建。** 基线 72d33c3 的 `crates/ita-server/src/` 只有 `lib.rs`（文档注释加两条 `deny`），`Cargo.toml` 只有四个依赖。07.1 建 `units/mod.rs` 与 `units/topology.rs`，07.2 在其上加 `state.rs`、`probe.rs`、`supervisor.rs`，并在 `mod.rs` 声明这三个模块。07.2 不修改 07.1 的 `topology.rs`，只消费它的 `Topology` 与 `startup_order`。

**第二，就绪探针是"功能可用"判定，不是"进程活着"判定。** ADR 0013 把就绪定义为"数据库迁移完成、IPC 套接字在监听、路由表载入完毕"，这些都是功能可用性检查。07.2 的探针是抽象（trait），真实实现留后。测试用假探针，按"就绪/未就绪/失败"三值返回，验证监督者的状态转移与停止顺序。

**第三，`lease` 不是执行器。** ADR 0014 明确"执行器是每个工作区一个独立进程，不是 server 内部的一个 unit"，0013 最小拓扑里的 `executor` 更名为**租约仲裁**，职责收窄为维护租约表与仲裁跨工作区资源。因此 07.2 的 unit 集合里 `lease` 是租约仲裁，不是执行器，测试里不得把执行器当成 unit 实例化。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **未就绪时后续依赖不启动。** 建 `store → router → ipc`（`router requires store`、`ipc requires router`），假探针对 `store` 第一次返回 `NotReady`、之后返回 `Ready`，驱动监督者，断言 `store` 处于 `Starting`（未就绪）时 `router` 保持 `NotStarted`，`store` 就绪后 `router` 才启动。守的是"未就绪时后续依赖不启动"。
2. **启动按拓扑序推进。** 建同一拓扑，所有探针返回 `Ready`，驱动监督者到完成，断言启动顺序是 `[store, router, ipc]`（拓扑序），且全部 unit 到达 `Ready`。守的是"启动按 07.1 的拓扑序推进"。
3. **停止按逆序执行。** 建同一拓扑，所有 unit 到达 `Ready`，调 `shutdown`，断言停止顺序是 `[ipc, router, store]`（逆拓扑序），且全部 unit 到达 `Stopped`。守的是"停止按逆序执行"。
4. **失败不级联重启。** 建 `store → router`（`router requires store`），假探针对 `store` 返回 `Failed`，驱动监督者，断言 `store` 是 `Failed`、`router` 保持 `NotStarted`（从未启动），再调一次 `run_until_blocked` 断言 `store` 仍是 `Failed`（未重启）。守的是"失败不级联重启"。
5. **失败不阻塞独立 unit。** 建 `store → router` 与独立 `model`（无边），假探针对 `store` 返回 `Failed`、对 `model` 返回 `Ready`，驱动监督者，断言 `store` 是 `Failed`、`router` 是 `NotStarted`、`model` 是 `Ready`（`store` 的失败不阻塞独立的 `model`）。守的是"失败只影响其依赖者，不影响独立 unit"。
6. **探针区分就绪与运行。** 一个 unit 进程活着（`Starting`）但探针返回 `NotReady`，断言 unit 保持 `Starting`（不是 `Ready`），其依赖者不启动。守的是"就绪不等于运行"。
7. **状态机拒绝非法转移。** 调 `next(Ready, Start)`，断言返回 `None`；调 `next(Stopped, Start)`，断言返回 `None`。守的是"非法转移被拒绝，不是原地不动"。
8. **失败 unit 状态机层面不可重启。** 断言 `next(Failed, Start)` 返回 `None`（状态机本身拒绝重启失败 unit）。守的是"状态机层面禁止重启失败 unit"。
9. **孤立 unit 启动与停止。** 建单个 unit 无边，驱动监督者，断言到达 `Ready`；调 `shutdown`，断言到达 `Stopped`。守的是"孤立 unit 正常工作"。
10. **七 unit 最小拓扑启动与停止。** 按 ADR 0013 最小拓扑实例化：`store → router → ipc`（`router requires store`、`ipc requires router`）、`lease requires tools`（`↔` 落单方向）、`model` 孤立、`telemetry` 孤立，所有探针返回 `Ready`，驱动监督者到完成，断言全部 unit 到达 `Ready`；调 `shutdown`，断言全部 unit 按逆拓扑序到达 `Stopped`。守的是"ADR 0013 最小拓扑是合法 DAG 且能正确启动与停止"。

第 1、6 条守的是"未就绪不启动"与"就绪不等于运行"。第 2 条守的是启动按拓扑序。第 3 条守的是停止按逆序。第 4、5、8 条守的是失败不级联重启（状态机与监督者双层保障、独立 unit 不受影响）。第 7 条守的是非法转移被拒绝。第 9 条守的是退化形状工作。第 10 条守的是 ADR 0013 最小拓扑的实例化。

## 六、实现顺序与每步验证

分三次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的先做"排，`state.rs` 的纯转移函数是最便宜的定形，`probe.rs` 的探针抽象次之，`supervisor.rs` 的监督者循环是核心算法。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `units/state.rs`（`UnitState`、`UnitEvent`、`next`）与内联测试 | `cargo nextest run -p ita-server -E 'test~state'`，覆盖第四节第 7、8 条（非法转移、失败 unit 不可重启） |
| 二 | 写 `units/probe.rs`（`ProbeResult`、`ReadinessProbe`）与内联测试（假探针） | `cargo nextest run -p ita-server -E 'test~probe'`，假探针按三值返回 |
| 三 | 写 `units/supervisor.rs`（`Supervisor`、`step`、`run_until_blocked`、`shutdown`、查询方法）与内联测试，更新 `mod.rs` 声明三模块 | `cargo nextest run -p ita-server`，此时测试覆盖第四节全部十条验收 |

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里入册，断言消息仍然用中文。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 监督者在依赖未就绪时就启动依赖者（只检查"依赖存在"，不检查"依赖就绪"） | 正常路径通过，依赖未就绪时才暴露 | 第四节第 1 条：断言依赖 `Starting` 时依赖者保持 `NotStarted` |
| 停止按启动序而不是逆序执行 | 正常路径通过，多 unit 停止时才暴露 | 第四节第 3 条：断言停止顺序是启动顺序的逆 |
| 失败 unit 被重启（监督者重新发 `Start`） | 正常路径通过，失败路径才暴露 | 第四节第 4、8 条：断言失败 unit 保持 `Failed` 且状态机拒绝重启 |
| 失败级联到独立 unit | 正常路径通过，有独立 unit 时才暴露 | 第四节第 5 条：断言独立 `model` 到达 `Ready` |
| 探针把就绪与运行混为一谈（把"进程活着"当 `Ready`） | 正常路径通过，未就绪时才暴露 | 第四节第 6 条：断言 `NotReady` 时 unit 保持 `Starting` |
| 状态机允许非法转移（返回原状态而不是 `None`） | 正常路径通过，非法输入才暴露 | 第四节第 7 条：断言返回 `None` |
| 监督者用错顺序（不是 07.1 的 `startup_order`） | 正常路径通过，非平凡拓扑才暴露 | 第四节第 2、10 条：断言精确的拓扑序 |
| unit 状态机落内核而不是 `ita-server` | 编译通过，但"两套监督语义靠类型分开"失效 | 状态机落 `ita-server` 的 `units` 模块，不进内核、不与 `ita-workflow` 混用 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：就绪探针是"功能可用"判定，不是"进程活着"判定。ADR 0013 把就绪定义为"数据库迁移完成、IPC 套接字在监听、路由表载入完毕"，都是功能可用性检查。若把探针做成"进程存活"检查，会让"就绪不等于运行"失效，且"打开就能用"的冷启动体感会被"进程起来了但功能不可用"破坏。这条职责分离是"这一批只有一个目的"的前提，不靠调用方记得"探针是功能判定不是存活判定"。

## 八、已裁决的分歧点

一处分歧点由 Explorer 直接定形（unit 状态落库与 `units` 表建表归 07.3），其余三处（状态机状态集、探针抽象形式、监督者同步还是异步）也由 Explorer 直接定形，理由充分。

| 分歧 | 两种做法 | 定形 |
|---|---|---|
| 状态机状态集 | 甲：六状态（未启动、启动中、就绪、失败、停止中、已停止），无独立 `Degraded`。乙：加独立 `Degraded` 状态区分运行期崩溃 | **直接定形选甲。** 理由见第二节第 2.1 条。`Degraded` 是 server 级能力概念（07.4 的能力集），由 unit 状态推导，不是 per-unit 状态。per-unit 的 `Failed` 已承载"不再重启"语义，运行期崩溃的 `Degraded` 是 07.3/07.4 的扩展，07.2 不引入 |
| 探针抽象形式 | 甲：trait `ReadinessProbe`。乙：闭包 `Fn(&UnitId) -> ProbeResult` | **直接定形选甲。** 理由见第二节第 2.2 条。trait 可扩展，监督者持 `Box<dyn ReadinessProbe>`，闭包无法携带额外上下文 |
| 监督者同步还是异步 | 甲：同步纯逻辑。乙：异步（tokio） | **直接定形选甲。** 理由见结论第 5 条。07.2 是纯逻辑，crate 无 tokio，真实 unit 的异步执行留到后续批次 |
| unit 状态落库与 `units` 表建表 | 甲：归 07.3（激活门需要持久化状态）。乙：归 07.2 | **直接定形选甲。** 理由见第二节第 2.6 条。07.2 是纯逻辑，状态机在内存里，落库是 07.3 的事 |

## 九、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 07.2：必需与非必需启动门与降级（07.3）；能力集快照与变更推送（07.4）；unit 状态落库与 `units` 表建表（07.3）；真实 unit 实现（`store`、`router`、`ipc` 等，后续批次）；真实的每 unit 就绪探针实现（检查迁移、套接字、路由表，留到真实 unit 存在时）；执行器进程（0014，独立进程，不是 unit）；工作流节点类型（`ita-workflow`，与 unit 类型分开）；事件日志与模型代理（08.x）；本地 socket 与连接级工作区绑定（08.2）；group commit（08.4）；异步执行（07.2 是同步纯逻辑）。

## 十、Explorer 核对与补强（基线 72d33c3）

本节的核对对象是批次基线 72d33c3 的已提交代码，不是实现者的工作树。结论是：十条验收对基线全部成立，状态机、探针与停止顺序的口径都没有被证伪，需要改写的只是"怎么做"与一处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 `ita-server` 现状核对：空壳，`units` 模块由 07.1 建

基线 72d33c3 的 `crates/ita-server/src/` 只有 `lib.rs`（文档注释加 `#![deny(unsafe_code)]` 与 `#![deny(missing_docs)]`），`Cargo.toml` 只有 `ita-store`、`ita-proto`、`ita-model`、`ita-workflow` 四个依赖，没有 tokio、没有 async。07.1 建 `units/mod.rs` 与 `units/topology.rs`，07.2 在其上加 `state.rs`、`probe.rs`、`supervisor.rs`。07.2 不修改 07.1 的 `topology.rs`，只消费它的 `Topology` 与 `startup_order`。

### 10.2 迁移文件核对：没有 `units` 表

`0001_core.sql` 建 `workspaces`、`sessions`、`nodes`、`events`、`workspace_seq`；`0002_content.sql` 建 `blobs`、`snapshots`、`snapshot_entries`、`read_set`。没有 `units` 表，也没有 unit 状态列。07.2 不建表、不新增迁移，unit 状态落库是 07.3 的事。

### 10.3 07.1 产出类型核对：`UnitId`/`DepKind`/`Topology`/`startup_order`

07.1 的执行计划（detail 28）产出 `UnitId`（标签名义类型）、`DepKind`（`Requires`/`Wants`/`After` 三变体）、`Topology`（`add_unit`、`add_requires`/`add_wants`/`add_after`、`find_cycle`、`startup_order`）、`CycleError`（带环路径）。07.2 的 `Supervisor` 消费 `Topology` 与 `startup_order`，不重新实现拓扑排序。07.2 的 `UnitState`/`UnitEvent`/`Supervisor` 与 07.1 的 `UnitId`/`DepKind`/`Topology` 是同一 `units` 模块下的不同类型，互不混用。

### 10.4 四处补强

**第一，状态机是纯转移函数，非法转移返回 `None`。** 转移函数 `next(state, event) -> Option<UnitState>` 是纯函数，非法转移返回 `None` 而不是原地不动。这保证了"状态机拒绝非法转移"是可测试的（第四节第 7 条），且"失败 unit 不可重启"在状态机层面就有保障（第四节第 8 条），不依赖监督者记得不重启。

**第二，就绪探针是"功能可用"判定，不是"进程活着"判定。** ADR 0013 把就绪定义为"数据库迁移完成、IPC 套接字在监听、路由表载入完毕"，都是功能可用性检查。07.2 的探针是抽象（trait），真实实现留后。测试用假探针，按"就绪/未就绪/失败"三值返回，验证监督者的状态转移与停止顺序。

**第三，失败不级联重启是双层保障。** 状态机层面，`next(Failed, Start)` 返回 `None`（状态机本身拒绝重启失败 unit）；监督者层面，`Failed` unit 不是 `NotStarted`，不会被重新选中启动，其依赖者因依赖未 `Ready` 而永不启动。两层保障让"失败不级联重启"不依赖单一实现点。

**第四，unit 状态落库与 `units` 表建表归 07.3。** 07.2 的状态机在内存里（纯逻辑），不建表、不新增迁移。unit 状态落库与 `units` 表建表归 07.3，因为激活门需要持久化状态（server 重启后恢复 unit 状态）。这条裁决避免了 07.2 混入 IO 与建表，保持"这一批只有一个目的"。
