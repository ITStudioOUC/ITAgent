# 批次 06.4 帧写入与 head 比较并交换的执行计划

拆分依据给 06.4 的验收是"过期期望 head 提交帧返回冲突，帧行与 head 不变，workspace_seq 计数器保持原值；帧引用的会话与祖先节点必须属于同一工作区"。核对基线 07aa370 的已提交代码之后，结论是：**验收口径成立且不需要改，但它依赖的三件事必须写进计划，否则实现者会在细节上做对数值、做错语义。** 三件事分别是：帧正文的可逆编码必须不引入新依赖、不新增迁移；head 的比较并交换必须同时匹配节点与代次，单比节点会在 ABA 情形下失效；事件追加必须排在比较并交换成功之后，冲突才不烧 seq。文件规划 `heads.rs`、`commit.rs` 与现状吻合，另需在 `db.rs` 加四个错误变体、在 `lib.rs` 声明模块。

## 结论

1. 06.4 的原始拆分成立。表结构与 ADR 都没有把这项工作推到别的批次，也没有出现让验收口径失效的变更。需要改写的是"怎么做"，不是"做什么"。
2. 帧正文的落库方式是**长度前缀文本**，写进 `nodes.inline_body`，不引入 `serde_json`、不新增迁移。理由是仓里目前没有任何 JSON 依赖，为一个非安全用途的序列化加依赖违背"不引入不必要依赖"；而 `nodes` 表没有为帧单列字段，`ALTER TABLE` 加列虽合法，却会把帧专属的列塞进通用节点表，污染所有其它正文种类。
3. head 的比较并交换是**一条 `UPDATE` 同时匹配 `(head_node, head_generation)`**，影响行数为零即冲突。只比节点会在"回退到祖先再前进"的 ABA 情形下让过期令牌通过——这正是内核 `Tree` 用代次解决的问题，落库版本不能把它丢掉。
4. 事件追加排在比较并交换成功之后。06.3 已定下的接口边界（`events::append_in` 吃事务、`AppendedEvent` 带 seq、`Store::conn_mut` 是 `pub(crate)`）直接复用，本批不再发明。
5. 06.4 不写内容寻址存储，帧正文一律内联。0018 把压缩散文上限定在 4 KiB，加上覆盖节点（每个 26 字节）与固定层指纹，帧正文是有界的，`body_hash` 与 `body_len` 对帧节点恒为 NULL。大正文走 CAS 是 06.5 的事。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、迁移文件的实际内容、以及 06.2 修复链之后剩下的代码。

| 拆分里的说法 | 现状 | 判断 |
|---|---|---|
| 验收"过期期望 head 提交帧返回冲突，帧行与 head 不变" | `sessions` 表已有 `head_node` 与 `head_generation` 两列，`nodes` 表已建 | 成立，CAS 是一条 `UPDATE` 同时匹配两列 |
| 验收"workspace_seq 计数器保持原值" | `workspace_seq` 表已由 06.1 建好，事件追加由 06.3 提供 | 成立，事件追加排在 CAS 成功之后即可保证冲突不烧号 |
| 验收"帧引用的会话与祖先节点必须属于同一工作区" | `nodes` 与 `sessions` 都有 `workspace_id` 外键，但跨工作区错配表结构拦不住 | 成立，由写入路径在事务内用 `SELECT` 断言 |
| 文件 `crates/ita-store/src/{heads,commit}.rs` | 两个文件都还不存在，`lib.rs` 只声明了 `db`、`migrate`、`scope` | 成立，另需 `db.rs` 加错误变体、`lib.rs` 声明模块 |
| 依赖"04, 06.3" | 04 提供 `CommitPlan` 与 `Frame` 类型，06.3 提供事件追加与事务入口 | 成立，另需 06.3 的 `conn_mut` 与 `append_in` |

被证伪的是拆分之外的一件事：拆分没有提到帧正文怎么落库。`nodes` 表只有 `body_kind`、`inline_body`、`body_hash`、`body_len` 四列承载正文，没有任何一列能表达"帧覆盖哪些节点"或"帧的检查点"。因此 06.4 必须自己定形帧正文的编码，这是本批唯一的跨 crate 设计决定，见第二节。

## 二、帧写入与 head CAS 的实际形状

### 2.1 帧正文的编码：长度前缀文本，不引入依赖

内核的 `Frame` 结构有四个字段，全部要落库并能在读路径还原：

| 字段 | 类型 | 落库方式 |
|---|---|---|
| `summary` | `String` | 长度前缀，正文可含换行，读方按长度精确取字节 |
| `covers` | `Vec<NodeId>` | 计数前缀，每个 id 恰好 26 字节 |
| `checkpoint` | `Option<CheckpointId>` | 一位存在标志，存在时跟 26 字节 id |
| `fixed_layer_fingerprint` | `String` | 长度前缀 |

编码是**长度前缀文本**，整体是合法 UTF-8，写进 `inline_body`（TEXT 列）。不引入 `serde_json` 的理由是仓里目前没有任何 JSON 依赖，为一个非安全用途的序列化加依赖违背"不引入不必要依赖"；用 `ALTER TABLE` 加列的理由不成立，因为帧专属的列会污染通用节点表，而 `nodes` 表还承载 `turn`、`tool_call`、`notice` 等其它正文种类。

建议的字节布局（实现者可在可逆与无依赖的前提下微调，但不得引入外部依赖）：

```
<summary_len>":"<summary 字节>"\n"
<covers 计数> "\n"
<每个 cover 的 26 字节 id> "\n"   （重复 covers 计数次）
<"0" 或 "1"> "\n"                 （checkpoint 是否存在）
<checkpoint 的 26 字节 id> "\n"    （仅当存在时）
<fingerprint_len>":"<fingerprint 字节>"
```

`summary_len` 与 `fingerprint_len` 是十进制 ASCII 数字，后跟冒号；`summary` 与 `fingerprint` 是自由文本，可含换行，但读方按长度精确取字节，换行不构成歧义。`covers` 的每个 id 固定 26 字节，`checkpoint` 用一位存在标志加可选 id 表达。整个串是合法 UTF-8，能直接进 `inline_body`。

**注意**：`CommitPlan` 还带一个 `prompt_version` 字段，但内核的 `Frame` 结构**没有**这个字段。因此 `prompt_version` 不进帧节点，它属于压缩调用事件（见第八节待裁决项）。帧节点只存 `Frame` 的四个字段。

### 2.2 head 的比较并交换：一条 UPDATE 同时匹配节点与代次

head 存在 `sessions` 表上，不是独立的 head 表。比较并交换是一条 `UPDATE`：

```sql
UPDATE sessions
SET head_node = ?新帧节点, head_generation = head_generation + 1
WHERE id = ?会话 AND head_node = ?期望节点 AND head_generation = ?期望代次
```

影响行数为零即冲突。只比节点会在 ABA 情形下失效：会话回退到祖先再前进会让节点 id 重新变成"当前值"，此时一个过期的写入会通过比较。代次是单调的，因此能区分"同一个节点，但不是同一次推进"。这条与内核 `Tree::append` 的语义一致，落库版本不能把代次丢掉。

### 2.3 事务内的顺序：节点插入 → CAS → 事件追加

一次帧提交在**一个立即事务**里做三件事，顺序是刻意的：

1. **插入帧节点**：`INSERT INTO nodes`，`body_kind` 取 `'frame'`，`inline_body` 是第二节的编码，`parent_id` 是期望节点，`session_id` 与 `workspace_id` 取作用域。
2. **比较并交换 head**：执行 2.2 的 `UPDATE`。影响行数为零即冲突，整笔回滚，帧节点行不落库，head 不动。
3. **追加事件**：经 06.3 的 `events::append_in` 追加一条压缩事件，消耗一个 seq。

事件追加排在 CAS 成功之后，是"冲突不烧 seq"这个可测性质的来源。若反过来先追加事件再 CAS，冲突时事件行已写入、seq 已消耗，回滚虽能撤销事件行，但"计数器保持原值"这条验收就守不住了——回滚把 `workspace_seq` 的读改写也撤销了，计数器确实回到原值，但"冲突不烧号"这个更强性质无法在测试里断言，因为烧号与回滚发生在同一事务内，外部观察不到。

### 2.4 跨工作区校验：会话与祖先节点同属一个工作区

`nodes` 与 `sessions` 的 `workspace_id` 外键只保证"引用的工作区存在"，不保证"引用的节点属于当前作用域的工作区"。单库多工作区下，一个节点可以引用另一个工作区的会话，外键照样通过。因此写入路径必须在事务内用 `SELECT` 断言：

- 会话的 `workspace_id` 等于作用域的工作区。
- 父节点（期望节点）的 `workspace_id` 等于作用域的工作区。
- 覆盖列表里每个节点的 `workspace_id` 等于作用域的工作区。

检查点是弱引用，允许悬空，不校验（0003 的决策）。任何一条断言失败即回滚，帧节点行不落库，head 不动，seq 不消耗。

## 三、ADR 对帧提交的硬要求

与 06.4 相关的决策分布在四份 ADR 里，逐条对照如下。

| 要求 | 出处 | 06.4 怎么落地 |
|---|---|---|
| 压缩的提交是原子的：先完成模型调用，再用一次只覆盖"写帧与比较并交换 head"的短事务提交 | 0004 决策段 | 帧节点插入、head CAS、事件追加在同一事务内，要么全成要么全撤 |
| 摘要生成失败、格式不合法、被截断时，不移动 head，保留旧上下文并重试 | 0004 决策段 | 这是内核的职责（`CommitPlan` 生成失败就不出计划），06.4 只执行已生成的计划，计划不存在时不碰库 |
| 回退与压缩是同一个操作的两个投影，共用 head 比较并交换原语 | 0003 理由段 | 06.4 的 CAS 原语是通用的，帧提交只是它的一个消费者；回退是另一个消费者，属后续批次 |
| 显式 head 是分叉的前提，head 的比较并交换更新是分叉正确性的唯一保障 | 0003 理由段 | CAS 同时匹配节点与代次，过期令牌必被拒 |
| 帧对检查点是弱引用，允许悬空 | 0003 决策段 | 检查点不校验存在性，落库时只存 id 或空 |
| 压缩调用本身要落库：固定提示版本、温度为零，完整请求与响应以内容寻址引用加预览进事件表 | 0004 决策段末条 | 06.4 追加一条压缩事件，但请求与响应的内容寻址引用要等 06.5 的 CAS 写入落地，本批事件只记种类与节点引用，正文四列全空 |
| 节点完成状态由事件推导，完成记录在事务内写入 | 0011 决策段 | 帧提交事务内追加的事件就是这条完成记录，状态由它推导 |
| 压缩散文上限 4 KiB | 0018 第九节参数表 | 帧正文有界，`inline_body` 够用，`body_hash` 与 `body_len` 对帧节点恒为 NULL |

三处需要特别说清的核实结果。

**第一，`nodes` 表的 `body_kind` 是裸 TEXT，没有取值域。** 06.2.1 给 `snapshots.kind` 与 `snapshot_entries.kind` 加了取值域 CHECK，但 `nodes.body_kind` 没有。这不是缺口，是刻意的：节点正文种类（`turn`、`tool_call`、`tool_result`、`frame`、`notice`、`todo`、`fixed_layer`）的完整词表散见于各 ADR，06.4 只引入 `'frame'` 一个值，不发明完整枚举。取值域留给后续批次统一补，本批不挤。

**第二，`prompt_version` 不进帧节点。** 内核的 `Frame` 结构没有这个字段，`CommitPlan` 有。因此 `prompt_version` 属于压缩调用事件，不属于帧正文。06.4 的事件是"压缩调用"这一种类，但请求与响应的内容寻址引用要等 06.5，所以本批事件只记种类与会话、节点引用，`payload_hash`、`payload_len`、`preview_head`、`preview_tail` 四列全空。`prompt_version` 的落库推迟到 06.5 之后能写内容寻址引用的时候，见第八节待裁决项。

**第三，`sessions.head_node` 是 `NOT NULL`，没有外键指向 `nodes`。** 这意味着 head 可以指向一个不存在的节点（数据损坏时），但正常路径下 head 永远指向一个已插入的节点。06.4 的 CAS 不校验 head 指向的节点存在，因为 CAS 的条件是"期望节点等于当前 head"，期望节点由调用方给出，调用方负责它存在。这条与内核 `Tree` 的语义一致：`append` 校验的是新节点的父，不是当前 head 的存在性。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **正确期望 head 提交帧成功。** 会话在节点 X 第 1 代，提交一个期望 (X, 1) 的帧，返回新帧节点 id 与新代次 2。断言 `nodes` 里多了一行 `body_kind = 'frame'` 的帧节点，`parent_id` 是 X，`sessions.head_node` 是帧节点，`head_generation` 是 2，`workspace_seq.next_seq` 比调用前大 1。守的是"成功提交移动 head 并消耗一个 seq"。
2. **过期期望 head（节点不符）返回冲突。** 会话在节点 X 第 1 代，提交一个期望 (Y, 1) 的帧（Y 不是当前 head）。断言返回冲突错误，`nodes` 里没有新增帧节点行，`sessions.head_node` 仍是 X，`head_generation` 仍是 1，`workspace_seq.next_seq` 与调用前相等。守的是"冲突不写帧行、不动 head、不烧 seq"。
3. **过期期望 head（代次不符，ABA 情形）返回冲突。** 会话在节点 X 第 1 代，先正常提交一个帧到 F 第 2 代，再用测试专用连接把 `sessions.head_node` 改回 X、`head_generation` 改成 3（模拟回退再前进），然后提交一个期望 (X, 1) 的帧。断言返回冲突，帧节点行不落库，`head_generation` 仍是 3。守的是"代次是 CAS 条件的一部分，单比节点会在 ABA 下失效"。
4. **帧引用的会话属于另一工作区被拒。** 在工作区 A 注册会话 S_A，在工作区 B 注册会话 S_B 与节点。用 A 的作用域提交一个帧，但帧的会话是 S_B。断言返回跨工作区错误，`nodes` 里没有新增帧节点行，A 的 `workspace_seq.next_seq` 不变。守的是"帧引用的会话必须属于同一工作区"。
5. **帧的父节点属于另一工作区被拒。** 在 A 与 B 各建节点，用 A 的作用域提交一个帧，父节点是 B 的节点。断言返回跨工作区错误，帧节点行不落库，seq 不变。守的是"父节点必须属于同一工作区"。
6. **帧的覆盖列表含另一工作区的节点被拒。** 覆盖列表里混入一个 B 工作区的节点 id，用 A 的作用域提交。断言返回跨工作区错误，帧节点行不落库，seq 不变。守的是"覆盖的祖先节点必须属于同一工作区"。
7. **帧正文可逆。** 提交一个带非空 `summary`、多个 `covers`、有 `checkpoint`、有 `fixed_layer_fingerprint` 的帧，然后用测试专用连接读出 `inline_body`，按第二节的编码解码，断言解码出的 `Frame` 与提交前的逐字段相等。守的是"帧正文落库后能还原"。
8. **重复的帧节点 id 被拒。** 用同一个节点 id 提交两次帧，第二次断言返回重复节点错误，head 不动，seq 不消耗。守的是"节点不可变，重复 id 一律拒绝而不是覆盖"。
9. **冲突时事件不追加。** 提交一个会冲突的帧（期望 head 不符），断言 `events` 表里没有新增行，`workspace_seq.next_seq` 与调用前相等。守的是"事件追加排在 CAS 成功之后，冲突不烧号"。这一条与第 2 条合起来覆盖"冲突不写帧行、不动 head、不烧 seq、不追加事件"四个可观察量。

第 2、3、9 条合起来守的是同一件事：冲突时库的四个可观察量（帧节点行、head 节点、head 代次、seq 计数器）全部不变。第 4、5、6 条合起来守的是跨工作区校验的三个位置（会话、父节点、覆盖列表）。第 7 条守的是帧正文的可逆性，是读路径（08.x 的 `resolve` 输入组装）能还原 `Frame` 的前提。

## 六、实现顺序与每步验证

分三次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的先做"排，`heads.rs` 的 CAS 原语不碰帧正文编码，最便宜也最容易把 ABA 这条细节一次做对。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `heads.rs` 的 CAS 原语与它的模块内单测，`db.rs` 加四个错误变体 | `cargo nextest run -p ita-store -E 'test~head'` |
| 二 | 写 `commit.rs` 的帧提交路径与帧正文编码解码，`lib.rs` 接线 | `cargo nextest run -p ita-store`，此时 `tests/commit.rs` 覆盖第四节第 1、2、3、7、8、9 条 |
| 三 | 补跨工作区校验与其余验收，跑完整三件套 | `cargo nextest run --workspace --locked`、`cargo build --workspace --locked`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo fmt --all --check`、`bash .w1mer/scripts/check_kernel_purity.sh` |

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里入册，断言消息仍然用中文。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| CAS 只比节点不比代次 | "过期期望 head 返回冲突"在节点不符时成立，代次不符的 ABA 情形测不出来 | 第四节第 3 条：把 `head_generation` 手动改成与期望不同的值，正确实现返回冲突，只比节点的实现会通过 |
| 事件追加排在 CAS 之前 | 正常路径的断言全部通过，冲突时"seq 不消耗"这条测不出来 | 第四节第 9 条：冲突后断言 `workspace_seq.next_seq` 与调用前相等，且 `events` 表无新增行。烧号与回滚在同一事务内，外部观察不到，只有"事件追加排在 CAS 之后"这个顺序才能守住 |
| 帧正文编码不可逆 | 写入时不报错，读路径还原时才炸，而读路径是 08.x 的事 | 第四节第 7 条：提交后立即读出 `inline_body` 解码，断言与提交前逐字段相等。把可逆性守在本批，不留给读路径 |
| 跨工作区校验漏掉覆盖列表 | 只校验会话与父节点，覆盖列表里混入另一工作区的节点测不出来 | 第四节第 6 条：覆盖列表里混入另一工作区的节点 id，断言被拒。三个位置（会话、父节点、覆盖列表）各有一条 |
| 帧节点的 `body_kind` 写错 | 写入不报错，读路径按 `body_kind` 分发时才炸 | 第四节第 7 条断言读出的 `body_kind` 是 `'frame'`，与解码出的 `Frame` 一起守 |
| `prompt_version` 被塞进帧正文 | 帧正文多一个字段，解码时多读一段，测试通过 | 第二节明确 `prompt_version` 不进帧节点，`Frame` 结构没有这个字段。解码只读四个字段，多读会失败 |
| 用 `MAX(seq) + 1` 分配事件 seq | 正常路径通过 | 这是 06.3 的风险，06.4 复用 06.3 的 `append_in`，不自己分配 seq。06.3 已守这条 |
| 空覆盖列表被当成合法帧 | `covers` 为空时编码是"计数 0"，解码也成功 | 内核 `CommitPlan` 已保证 `covers` 非空（`EmptyFold`），06.4 信任计划。但若想守，可在 `commit.rs` 加一条断言 `covers` 非空，代价是一次空检查 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：`body_kind` 的取值 `'frame'` 是 06.4 引入的第一个节点正文种类值。`nodes.body_kind` 没有取值域 CHECK，因此 `'frame'` 不会被表结构拦，只会被写入路径保证。这条与 06.3 的 `kind` 词表问题同型，不发明完整枚举，留给后续批次统一补。

## 八、已裁决的分歧点

四处分歧点已由主 Agent 裁决，全部采纳 Explorer 的建议：帧正文用长度前缀文本（选甲），`prompt_version` 推迟到 06.5 之后随内容寻址引用落库（选乙），CAS 原语通用、帧提交与回退共用（选乙），事件种类词表只引入 `'compression'` 一个值（选甲）。裁决理由见下表"建议"列。

| 分歧 | 两种做法 | 建议（已裁决采纳） |
|---|---|---|
| 帧正文的编码方式 | 甲：长度前缀文本写 `inline_body`，不引入依赖、不新增迁移。乙：加 `serde_json` 依赖，把 `Frame` 序列化成 JSON 写 `inline_body`。丙：`ALTER TABLE` 加帧专属列 | **选甲。** 理由见第二节。乙为一个非安全用途的序列化引入依赖，违背"不引入不必要依赖"；丙把帧专属的列塞进通用节点表，污染 `turn`、`tool_call` 等其它正文种类。甲的编码是纯函数，可单测，不碰数据库 |
| `prompt_version` 落库的位置 | 甲：06.4 的压缩事件带 `prompt_version`，需要事件表加列或塞进 `kind`。乙：推迟到 06.5 之后能写内容寻址引用时，`prompt_version` 随请求与响应一起进事件表 | **选乙。** 06.4 的事件是"压缩调用"这一种类，但请求与响应的内容寻址引用要等 06.5 的 CAS 写入。`prompt_version` 是请求的属性，不属于帧正文（`Frame` 结构没有这个字段），把它单独塞进事件表会留下一列没有正文的孤字段。推迟到 06.5 之后，`prompt_version` 随完整请求与响应一起落库，0004 的"完整请求与响应以内容寻址引用加预览进事件表"才真正成立 |
| 06.4 的 CAS 原语是否同时支持回退 | 甲：`heads.rs` 的 CAS 原语只服务帧提交，回退是另一个原语。乙：CAS 原语是通用的，帧提交与回退共用 | **选乙。** 0003 明确"回退与压缩是同一个操作的两个投影，共用 head 比较并交换原语"。`heads.rs` 的 CAS 吃 `(会话, 期望节点, 期望代次, 新节点)`，不关心新节点是帧还是回退目标。本批只接线帧提交，回退是后续批次的消费者，但原语形状已经是通用的 |
| 事件种类词表 | 甲：06.4 引入 `'compression'` 一个值，不发明完整枚举。乙：06.4 统一补全节点与事件的种类词表 | **选甲。** 与 06.3 的 `kind` 词表问题同型，散见于各 ADR 的词表不在本批发明。06.4 只引入 `'compression'` 一个值，完整词表留给后续批次统一补 |
