# 批次 06.3 事件追加、seq 分配与预览截断的执行计划

拆分依据里给 06.3 的验收是"连续三条事件得到连续 seq，超长正文按头 4 KiB 尾 1 KiB 预览"。
核对当前表结构与 ADR 之后的结论是：**验收口径成立且不需要改，但它依赖的三个前提必须写进
计划，否则实现者会在细节上做对数值、做错语义。** 三个前提分别是：seq 的唯一性是按工作区
而不是全局；seq 必须从 `workspace_seq` 计数器分配而不是从表里取最大值；预览是两个独立的
列（`preview_head` 与 `preview_tail`）而不是一个字符串。文件规划 `events.rs`、`seq.rs`、
`preview.rs` 与现状吻合，另需在本 crate 的 `db.rs` 加一个 crate 内部可用的可变连接入口，
供 06.4 把事件追加与 head 比较并交换放进同一个事务。

## 结论

1. 06.3 的原始拆分成立。表结构与 ADR 都没有把这项工作推到别的批次，也没有出现让验收口径
   失效的变更。需要改写的是"怎么测"，不是"测什么"。
2. seq 的分配方式由表结构已经定死：`workspace_seq` 表存在、按工作区分行、与工作区注册在
   同一事务里写入。因此实现是"在写事务内读出 `next_seq`，把它当作本条事件的 seq，再写回
   加一，然后用该值插入事件"。这里有一处硬约束：`CONVENTIONS.md` 明确禁用自增主键与
   `RETURNING`，所以不能用 `UPDATE ... SET next_seq = next_seq + 1 RETURNING next_seq`
   这类一步写法。安全性由 06.1 已经设好的 `BEGIN IMMEDIATE` 提供——事务一开始就拿写锁，
   读到的值在写回之前不会被别人改。用 `MAX(seq) + 1` 会通过"连续三条得到 1、2、3"这条
   验收，却是错的，理由见第八节。
3. "头 4 KiB 尾 1 KiB"出自 `docs/adr/0018` 第九节的参数表，不是计划文档自己拍的数字。它是
   默认值而不是不变量，同一节末段要求"全部参数都要有配置入口"，所以 06.3 不能把这两个数字
   写成调用点上的常量。
4. 表结构层面没有任何东西阻止 UPDATE 与 DELETE，事件表的"不可变"目前只是代码纪律。06.3
   不补触发器：那是另一个验收行为，且需要新增迁移。这一点作为已知缺口留在本计划，由主 Agent
   决定是否单开一个批次。
5. 06.3 不写内容寻址存储，也不算哈希。正文的哈希由调用方给出（内容写入是 06.5 的工作），
   `payload_len` 与预览由正文本身推出。这条边界决定了 `append` 的入参形状。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、迁移文件的实际内容、以及 06.2 那条修复链之后剩下的
代码。

| 拆分里的说法 | 现状 | 判断 |
|---|---|---|
| 验收"连续三条事件得到连续 seq" | `events` 主键是 `(workspace_id, seq)`，`workspace_seq` 表已建 | 成立，但测试必须按工作区隔离地断言 |
| 验收"超长正文按头 4 KiB 尾 1 KiB 预览" | 表里是 `preview_head` 与 `preview_tail` 两列 | 成立，两列分别写入，不是一个字段拼两段 |
| 文件 `crates/ita-store/src/{events,seq,preview}.rs` | 三个文件都还不存在，`lib.rs` 只声明了 `db`、`migrate`、`scope` | 成立 |
| 依赖"04, 06.2" | 04 提供 id 类型，06.2 提供表结构 | 成立，另需一个来自 06.1 的 `workspace_seq` 行 |

被证伪的是拆分之外的一件事：拆分没有提到 `Store` 目前取不到写事务的入口。`Store` 把
`Connection` 私有持有，只暴露 `conn()`（crate 内部，返回 `&Connection`）与 `conn_for_test()`。
rusqlite 的 `Connection::transaction` 要求 `&mut self`，所以现有形状下开不了普通事务。

两条出路，二选一。甲：在 `db.rs` 加 `pub(crate) fn conn_mut(&mut self) -> &mut Connection`，
写方法取 `&mut self`，与 `create_workspace` 现有的形状一致。乙：用 rusqlite 的
`unchecked_transaction(&self)`，它接受共享引用但放弃了编译期的"不嵌套事务"检查。
**建议选甲**：`create_workspace` 已经因为同样的理由取了 `&mut self`，同一个句柄上出现两种
事务获取方式会让后续批次各自挑顺手的那个。无论哪条路，"分配 seq 与插入事件在同一事务内"
都是本批不可让的。

## 二、事件表的实际形状

`0001_core.sql` 第 50 行至第 64 行定义的事件表，与 seq 分配有关的性质有四条。

| 性质 | 实际内容 | 对验收的影响 |
|---|---|---|
| 主键 | `PRIMARY KEY (workspace_id, seq)` | seq 的唯一性粒度是**每个工作区**，不是全局。两个工作区的第一条事件都是 seq 1，这在库里是合法且预期的 |
| 计数器 | 独立的 `workspace_seq(workspace_id, next_seq)`，默认 1，由 `create_workspace` 在同一事务里插入 | seq 不从事件表自身推导，分配发生在计数器上 |
| 正文的引用与预览 | `payload_hash`、`payload_len`、`preview_head`、`preview_tail` 四列，全部可空 | 大段正文只进内容寻址存储，库里留引用加预览，与"大对象外置"一致 |
| 可选引用 | `session_id` 与 `node_id` 是可空列，没有外键 | 事件可以不属于任何会话（例如工作区级的生命周期事件） |

由此得出两条对测试的硬要求。第一，"连续三条得到连续 seq"必须在同一个工作区里断言，跨工作区
比较会得到"两个 1"并误判为实现错误。第二，`events.seq` 的正确性不能靠"表里已有内容"来验证，
因为一张空表和一张只差计数器的表在插入前完全一样，测试必须显式读 `workspace_seq.next_seq`。

`created_at` 是 epoch 毫秒，由 `db::now_millis()` 提供，该函数在时钟异常时返回错误。事件顺序
由 seq 决定，不由 `created_at` 决定，因此测试不应断言时间戳单调。

### seq 与主键 id 是两件事

`CONVENTIONS.md` 与架构不变量都写着"ID 用 ULID `VARCHAR(26)`，禁自增、禁 `RETURNING`"。
这条禁令**不**适用于 seq，理由要分清，否则实现者会以为 seq 也得是 ULID。

| 项 | id | seq |
|---|---|---|
| 作用 | 标识一行是哪个对象，跨工作区全局唯一 | 该工作区内的写入顺序，也是断线续传的游标 |
| 类型 | 26 字符 Crockford base32 文本（`EventId` 走这条） | `INTEGER`，从 1 开始单调递增 |
| 生成方 | 调用方或存储层用 ULID 生成器产生，与时序无关 | 存储层从 `workspace_seq` 计数器分配，与时序强相关 |
| 谁保证唯一 | 应用层生成器加表上的约束 | 主键 `(workspace_id, seq)` 加计数器读改写 |
| 为什么这样分 | ULID 让跨库合并与离线生成都成立，不必问数据库要号 | seq 必须连续无洞，"哪条是第 N 条"是可比较的事实，随机文本承担不了 |

自增主键被禁的理由是"留住换 Postgres/MySQL 的门"，与 seq 无关：seq 本来就是一个业务字段，
它在任何数据库里都该由应用在事务内分配。反过来，如果为了"不使用自增"而把 seq 也做成
ULID，第四节第 1 条"连续三条得到连续 seq"根本无法通过。因此 06.3 要同时守住两条看似矛盾的
规则：**主键 id 是 ULID，seq 是整数计数器，两者都不自增。**

`RETURNING` 被禁这一条对本批有实际影响：不能用一条带 `RETURNING` 的 `UPDATE` 一步完成
"加一并取回"。写法只能是先 `SELECT next_seq`，再 `UPDATE`，两者都在同一个立即事务里。

## 三、ADR 对事件层的硬要求

与 06.3 相关的决策分布在四份 ADR 里，逐条对照如下。

| 要求 | 出处 | 06.3 怎么落地 |
|---|---|---|
| 事件表 append-only、不可变，写入后永不改变，因此可以缓存 | 0002 第 23 行与第 41 行 | 代码纪律：`events` 模块只提供追加与读取，不提供更新与删除。表结构层面没有触发器，见本节末段 |
| 追加事件属于权威写，确认必须代表已持久化 | 0002 第 16 行 | 追加在事务提交后才返回；返回值的类型要能让调用方拿到 seq 与事件 id |
| 完整请求与响应"以内容寻址引用加预览的形式进事件表，引用必须能还原完整报文"，事件行不内联大段正文 | 0018 第 78 行至第 79 行 | `append` 只存哈希、长度与两段预览，正文本身不写库 |
| 事件正文预览默认头 4 KiB 加尾 1 KiB，依据是"报错通常在尾部，上下文通常在头部" | 0018 第九节参数表 | `preview.rs` 的默认参数取这两个值，并允许覆盖 |
| 全部参数都要有配置入口，不得以常量散落在调用点 | 0018 第九节末段 | 引入 `PreviewLimit` 结构默认值，两个数字只出现一次，由调用方传入 |
| 事件按序号读取、可缓存、可复制、可续传 | 0002 第 23 行 | 06.3 只实现"按 seq 之后取一批"这一种读法，不做缓存与流式 |
| 工作流节点完成状态由事件推导，完成记录在事务内写入 | 0011 决策段 | 事务内写入的要求落在 06.4 的接口形状上，见第七节 |
| 压缩调用本身要落库：固定提示版本、温度为零，完整请求与响应以内容寻址引用加预览进事件表 | 0004 决策段末条 | 这是"四个可空列"的第一个真实消费者，`payload_hash` 与预览必须能承载一对请求与响应；本批只提供形状，不写压缩调用 |
| 事件表每工作区超过 200 MB 时归档，库内只留索引，范围读接口不变 | 0002 第 62 行至第 63 行 | 这条决定了 seq 不能从表里取最大值，见第八节 |

三处需要特别说清的核实结果。

**第一，append-only 在表结构层面没有约束。** `0001_core.sql` 里没有任何 `CREATE TRIGGER`，
表定义里也没有别的"禁止更新"表达方式。因此"事件不可变"目前是纯代码纪律，与 `nodes` 表
"没有 UPDATE 路径，只有 INSERT"（`0001_core.sql` 文件头注释）同类。这不构成 06.3 的阻塞，但
要知道：任何拿到连接的人都能改历史行，防线只有"业务代码拿不到连接"这一条。

**第二，"头 4 KiB 尾 1 KiB"确实是 ADR 定的。** 数字出在 0018 第九节参数表的"事件正文预览"
一行，同一行的依据写的是"报错通常在尾部，上下文通常在头部"。它与 `ita-kernel` 里
`Budget::preview_bytes`（默认五 KiB）数值相同但语义不同：后者是解析时给模型看的每节点预览
长度，前者是写进事件行的两段预览。`R_04_3` 已经把这件事说清过——`preview_bytes` 的注释原先
把出处也指向 0018 参数表，而那一行讲的是事件正文，解析预览长度在表里根本没有单独的值，所以
出处不可引用。06.3 **不要**复用 `Budget`，也不要把事件预览算进预算，否则单位与用途会混在一起。
这次真正的出处是明确的，`preview.rs` 可以直接引用那一行。

**第三，大对象外置对事件表的落地方式就是四个可空列。** 哈希与长度成组出现，预览随正文存在；
没有正文的事件（例如工作区级生命周期事件）四列全空。这条"成组"关系表结构没有 CHECK 承接，
由写入路径保证，是 06.3 必须自己守的一条不变量。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **同工作区连续追加三条事件，seq 依次为 1、2、3，且追加后 `workspace_seq.next_seq` 为 4。**
   守的是"连续且不跳号"这个字面验收。
2. **两个工作区各自从 1 开始。** 在 A 追加两条之后，B 的第一条仍是 1，且 A 的第三条是 3。
   守的是"seq 的唯一性按工作区而不是全局"。
3. **seq 取自计数器而不是表里的最大值。** 用测试专用连接把 `workspace_seq.next_seq` 直接改成
   100，再追加一条，得到 seq 100，而表里此前的最大 seq 是 3。守的是分配来源，这是本条验收里
   唯一能区分正确实现与 `MAX(seq) + 1` 的断言。
4. **追加返回的 seq 与库里那一行、以及读路径读到的 seq 三者一致。** 连做两次追加，断言
   `AppendedEvent.seq` 等于随后按顺序读出的第一条与第二条的 seq。守的是"返回值代表已持久化的
   那一行"，而不是"分配到的下一个号"。把返回值写成 `next_seq` 的旧值、新值或分配后的计数器，
   三种写法在现场都能让 `workspace_seq` 最终正确，只有这一条能把它们分开。
5. **正文长度不超过头加尾（默认 5120 字节）时不截断。** `preview_head` 等于完整正文，
   `preview_tail` 为空，`payload_len` 等于正文长度。
6. **正文超过 5120 字节时 `preview_head` 是正文前 4096 字节、`preview_tail` 是正文最后
   1024 字节。** 用 ASCII 正文构造，这样长度断言是精确值；两段在正文里不重叠，中间被省略的
   部分是 `body.len() - 5120` 字节；`payload_len` 仍是全量长度。
7. **截断不切开多字节字符。** 用全中文正文（每字三字节）在超长档构造，断言拆出的两段各自
   是合法 UTF-8、拼回正文的头部与尾部之后与原文一致，且两段长度不超过各自预算。注意此时
   长度允许小于预算：4096 不是 3 的整数倍，首段只能退到 4095。
8. **边界两侧各一条。** 恰好 5120 字节不截断（`preview_tail` 为空），5121 字节截断，且
   `preview_head` 长度为 4096、`preview_tail` 长度为 1024。两条都用 ASCII 正文，避免把
   "是否截断"与"字符边界回退"两个变量混在一条断言里。
9. **没有正文的事件四列全空。** `payload_hash`、`payload_len`、`preview_head`、`preview_tail`
   都为 NULL，而不是空串。
10. **事件 id 是 26 字符的 ULID 文本，两条事件的 id 不同。** 守的是"ID 用 ULID、长度 26"这条
    架构不变量。
11. **同一工作区内 seq 唯一，跨工作区可重复。** 这一条可以直接由数据库主键拒绝重复插入来验证，
    也可以在读出时断言。它的价值是给第八节的风险留一条回归。
12. **写事务失败时 seq 不被消耗。** 先用测试专用连接占住下一条 seq 的那一行（直接插一条
    `(workspace_id, seq)` 相同的事件），再走公开入口追加，断言返回错误，且
    `workspace_seq.next_seq` 与调用前相等。守的是"分配与插入同一事务"。
13. **取不到作用域时计数器不变。** 用一个未注册的工作区 id 调 `Store::scope`，返回
    `UnknownWorkspace`，此后读 `workspace_seq` 里已有的行，计数器保持原值。守的是写入路径
    在拿到作用域之前不碰计数器。公开入口收 `&WorkspaceScope`，而它只能由 `Store::scope` 从
    已注册工作区构造，所以"未注册工作区能不能追加"在类型层面就不可表达，这一条守的是紧挨着
    它的那一步。它与第 12 条合起来覆盖失败的两个位置：一个在开事务之前，一个在插入那一步。

第 5 至 9 条合起来守的是同一件事：库里不出现大段正文。因此断言要写"两列长度之和"，而不是
分别断言某一列"看起来不长"——实现把超额部分塞进 `preview_tail` 时，分别断言仍然会通过。
第 6 至 9 条另外守住"截断的判据是头加尾这个总预算，不是两段各自的上限"。

`PreviewLimit` 通过参数传入，不让 `Store` 持有。理由是仓里目前没有任何配置结构，为一两个数字
在 `Store` 上加字段与方法，等于提前定下一套配置形状，而 0018 要求的那套配置属于 server 侧，
等它落地时把 `PreviewLimit` 作为一个字段塞进去即可。参数化的写法同样满足"不以常量散落在调用
点"这条要求，因为数字只出现在 `PreviewLimit::defaults()` 一处。若主 Agent 认为必须由句柄持有，
改法是把默认值搬到 `Store` 的构造处，接口其余部分不变。

事件 id 类型有两种放法，各有代价。放进内核的理由是内核已经有四个同类 id 类型与一套共享的校验
（26 字符、Crockford base32、首位只能取 0 到 7），在存储层另写一份等于把这条校验复制成两份。
反对的理由同样成立：事件是存储层的概念，不属于上下文模型，`ita-kernel` 的模块文档把自己限定在
"消息树、解析、命令文法、检查点与租约类型"，加一个事件 id 会略微加宽那份词汇表。

两种放法都能满足第四节第 10 条，判断标准是"同一套文本校验出现几次"。若放存储层，应写成对
`ids.rs` 那套规则的显式复用不可能——它是私有宏——因此只能重写一份校验，那份重复才是真正的
代价。**倾向放内核**，但这条不影响验收，可以就地按实现者的判断处理，只要不同时维护两份校验。

**注意**：06.2.2 正在同一批里改内核测试函数名，`ids.rs` 会被它动到测试模块。冲突的风险存在但
很小，新加的是宏调用与一段导出，都在文件末尾附近；真撞上按"两边都保留"的常规方式解。

## 六、实现顺序与每步验证

分三次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的
先做"排，`preview.rs` 不碰数据库，最便宜也最容易把 UTF-8 边界这类细节一次做对。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `preview.rs` 与它的模块内单元测试，同时在 `ids.rs` 加 `EventId` | `cargo nextest run -p ita-store -E 'test~preview'` 与 `-p ita-kernel -E 'test~id'` |
| 二 | 写 `seq.rs` 与 `events.rs` 的追加路径，`db.rs` 补 `conn_mut`，`lib.rs` 接线 | `cargo nextest run -p ita-store`，此时 `tests/events.rs` 覆盖第四节第 1 至 6、9 至 13 条 |
| 三 | 补读路径与其余验收，跑完整三件套 | `cargo nextest run --workspace --locked`、`cargo build --workspace --locked`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo fmt --all --check`、`bash .w1mer/scripts/check_kernel_purity.sh` |

读路径的最小形状是一句话能说清的：给定作用域与一个起始 seq，按 seq 升序返回至多 N 条。
它存在的理由有两个——测试要能通过公开接口观察写入结果，而不是自己拼 SQL 去读；06.6、06.8、
08.4 都要追加或回读事件。它**不**包含游标对象、缓存、流式返回与"活到某个 seq"的阻塞等待，
那些属于 08.5 的读路径与 02 的续传语义。

这条查询不需要新索引：`events` 的主键是 `(workspace_id, seq)`，按工作区加 seq 范围天然走它。
另一条现成的索引 `events_by_session(session_id, seq)` 服务的是"某个会话的事件"这种读法，本批
不必用到，也不要顺手为它造接口。

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里
入册，但判断已经定了，06.3 不必等它落地再遵守；断言消息仍然用中文。

## 七、与 06.4 的接口边界

06.4 的验收是"过期期望 head 提交帧返回冲突，帧行与 head 都不变"。它要在**一个短事务**里做
两件事：写入帧节点，比较并交换会话 head。0011 又要求节点完成记录在事务内写入，08.4 的批量
提交也建立在"一次事务多条权威写"上。因此 06.3 必须留下一个吃事务的入口，而不是只留一个自己
开事务的 `append`。

要给 06.4 的东西只有三样：

1. `events::append_in(&Transaction, &WorkspaceScope, &NewEvent, PreviewLimit) -> Result<AppendedEvent, StoreError>`，
   由 `Store::append_event` 在自己的事务里调用它。前者是 crate 内部可见，后者是公开入口。
2. `AppendedEvent`，至少带 seq 与事件 id，让调用方在提交后能拿到权威写的确认内容。
3. `Store::conn_mut`，让 06.4 能开事务。它必须是 `pub(crate)`，不能公开，否则"业务代码拿不到
   连接"这条约束就破了。

06.3 **不**做的事，逐条写清以便复审时不必猜：不写 `nodes` 行；不动 `sessions.head_node` 与
`head_generation`；不实现 head 令牌的比较并交换（那是内核 `Tree` 已有语义的落库版本）；不定义
帧提交要用的具体事件种类；不做批量提交与 group commit；不写内容寻址存储对象。

还有一条顺序约定要写进 `append_in` 的注释：06.4 应当先做 head 的比较并交换，成功之后再追加
事件。理由是冲突时不消耗 seq。即便反过来写也不会错（同一事务会一起回滚），但"冲突不烧号"是
一个可以在测试里断言的更强性质。

## 八、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 用 `MAX(seq) + 1` 分配 | "连续三条得到 1、2、3"完全成立 | 第四节第 3 条：把计数器预置成 100，正确实现得到 100，`MAX` 实现得到 4。两条更深的影响：其一，0002 第 62 行至第 63 行要求事件表超过 200 MB 时把旧事件段搬进内容寻址存储、库里只留索引，那时表内最大 seq 会低于已发出的最大 seq，续传游标从此不发号；其二，`workspace_seq` 这张表就变成死数据，而它正是 `create_workspace` 与工作区行同事务写入的那一行，留着不用的代价是下一次有人读它时得到错误结论 |
| seq 分配与插入不在同一事务 | 正常路径的断言全部通过 | 第四节第 13 条守"开事务之前就失败"、第 12 条守"插入那一步才失败"，两侧都从可观察的计数器值兜住。第 12 条要先用测试专用连接人为占住下一行，这样才能在插入这一步制造失败，而不是在参数校验处失败 |
| 按字节数截断却没有回退到字符边界 | 用 ASCII 正文构造的用例全部通过 | 第四节第 7 条用全中文正文。实现要分别处理两头：首段向内收，次段向后移，两段都不得超过预算 |
| 头尾重叠 | "头 4096 加尾 1024"字面成立 | 正文长度落在 4096 与 5120 之间时，机械地取"前 4096 后继 1024"会重叠。判定基准必须是"头加尾"这个总预算：不超过就整段留下，超过才切两段。第四节第 5 条与第 8 条一起守这条分界 |
| `preview_tail` 被当成"总是有值" | 观察预览内容时看不出区别 | 第四节第 5 条与第 8 条断言不截断时 `preview_tail` 为空。有了这条，"是否截断"才有一个可读的判据 |
| 把全量正文塞进 `preview_head` | 只要正文不大，所有内容断言都通过 | 断言两列长度之和不超过总预算，这是"库里不出现大段正文"的唯一可测形式 |
| 事件 id 用 seq 拼出来 | 唯一性与长度都可能碰巧满足，读路径也不报错 | 第四节第 10 条要求能被 `EventId::parse` 接受，26 字符与首位只能取 0 到 7 两条都会被拦 |
| `payload_len` 从调用方传入并手抄 | 正常路径通过 | 让长度由正文本身推出，入参不带长度，从形状上消除两个真相来源 |
| 预览来源与哈希指向的内容不是同一份 | 没有任何断言能发现 | 入参把哈希与正文放在同一个结构里，注释写明二者必须对应同一份内容。真正的校验要等内容寻址存储落地（06.5）才算得出，06.3 只能靠调用约定 |
| `created_at` 被当成排序依据 | 单次测试里时间戳恰好单调 | 顺序一律按 seq 取；读路径的 `ORDER BY` 只写 seq |
| 空正文与无正文混为一谈 | 两种都能插入 | 第四节第 9 条要求"无正文"四列全 NULL，空串不是一个合法的替代 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：`kind` 与 `actor` 两列在库里是
裸 TEXT，没有取值域。仓库里目前没有任何一处定义事件种类与执行者身份的完整清单，`kind` 的取值
散见于各 ADR 的叙述（目录事件、拒绝事件、工具调用事件、节点完成事件、用量事件）。06.3 **不应
自己发明**一份枚举：那会把一份随手定的词汇表写进必须兼容的历史，而迁移又不能删列改名。入参
保持 `&str`，不走校验，把"词汇表由谁定"列为待裁决项。

| 分歧 | 两种做法 | 建议 |
|---|---|---|
| 是否在 06.3 补表结构层面的不可变性与引用完整性 | 甲：新增 0003 迁移，加 `BEFORE UPDATE` 与 `BEFORE DELETE` 触发器、给 `events.id` 加唯一索引、给 `session_id` 与 `node_id` 加外键。乙：本批不做 | 选乙，但三件事的可补性不同，要分开说。触发器能表达"禁止 UPDATE 与 DELETE"，却与"迁移只加表加列"的字面纪律不符，需要一次明确裁决。`events.id` 的唯一索引与 `sessions` 上的复合唯一索引都可以用 `CREATE UNIQUE INDEX` 后补，技术上一分钱不花，但它们与 seq 和预览都无关。真正做不到的是**在既有 `events` 表上加复合外键**：`ALTER TABLE ADD COLUMN` 只能给新列带 `REFERENCES`，没有任何语句能给既有列补外键，唯一出路是重建表，撞上 `DROP TABLE` 禁令。因此"事件引用的会话属于同一工作区"这条在本史诗内只能由写入路径断言，见下一行 |

## 十、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 06.3：内容寻址存储的写入、
去重与原子改名；帧节点与 head 的比较并交换；快照清单、回滚对齐与回收；批量提交；事件读路径
的缓存与续传；事件种类与执行者身份的词表；表结构层面的不可变性。
