# 批次 06.6 快照清单：文件、墓碑与超阈值的执行计划

拆分依据给 06.6 的验收是"删除的声明路径留下墓碑；超阈值条目带未存内容标记、尺寸与修改时间；目录行写入 mode 与 mtime，文件行写入 mode；content_stored = 1 的条目其哈希必在 blobs 里，由写入路径断言而不加外键"。核对基线 db15ffd 的已提交代码之后，结论是：**验收口径成立且不需要改，但它依赖的五件事必须写进计划，否则实现者会在细节上做对数值、做错语义。** 五件事分别是：快照 seq 从表内最大值加一分配而不是从计数器分配（无计数器表、无新迁移）；父边由存储层自动链接而不是由调用方给出（首个快照是基线，其余是增量）；快照 id 复用内核的 `CheckpointId` 而不是新增 `SnapshotId`；content_stored = 1 的条目在事务内用 `SELECT EXISTS` 断言 blobs 存在；读路径属于 06.6（06.7 与 06.8 都要读清单）。文件规划 `snapshots.rs`、`entries.rs` 与现状吻合，另需在 `db.rs` 加两个错误变体、在 `lib.rs` 声明模块。

## 结论

1. 06.6 的原始拆分成立。表结构（`snapshots` 与 `snapshot_entries`）与 ADR 0005、0006、0017 都没有把这项工作推到别的批次，也没有出现让验收口径失效的变更。需要改写的是"怎么做"，不是"做什么"。
2. 快照 seq 的分配方式是**表内最大值加一**，在立即事务内读改写。`snapshots` 表没有计数器表，也不该有：快照 seq 是工作区内的序号，不是断线续传的游标，不会被归档搬走，因此 `MAX(seq) + 1` 在单写者加 `BEGIN IMMEDIATE` 下是原子的。这与事件 seq 必须从 `workspace_seq` 计数器分配是两回事，理由见第二节。
3. 父边由存储层自动链接：取该工作区 seq 最大的快照作父，没有则父为空、kind 取 `baseline`，否则取 `incremental`。调用方只给清单，不给链结构。06.7 的重定基线是独立动词，会改写链，本批不碰。
4. 快照 id 复用内核的 `CheckpointId`，不新增类型。帧对检查点是弱引用，检查点编号就是快照行的 id（ADR 0003 与 0018 的 `CheckpointFacts.reachable` 定义的是"该检查点是否仍在快照保留窗口内"），`snapshots.id` 是 26 字符 ULID，与 `CheckpointId` 的校验完全相容。
5. content_stored = 1 的条目其哈希必在 blobs 里，这条由写入路径在事务内用 `SELECT EXISTS` 断言，而不是加外键。表结构层没有这条约束，也不该有：超阈值条目（content_stored = 0）按内容算出哈希但正文不进内容存储，加外键会把正常条目判成悬空。
6. 06.6 提供读路径：读快照元信息与读清单。06.7 的 squash 要读清单合并，06.8 的回滚对齐要读清单写回，读路径是它们的公共依赖，与 06.5 把 `get` 收进本批的裁决同型。
7. 06.6 不追加事件、不写回收、不做 squash、不做回滚对齐，不算事件 seq，不写 `events` 或 `nodes` 行。

## 二、快照清单的实际形状

### 2.1 快照 seq 的分配：表内最大值加一，不是计数器

`snapshots` 表没有计数器表，也没有 `workspace_seq` 那样的独立行。seq 的分配是**在立即事务内读出该工作区的 `MAX(seq)`，加一，作为本快照的 seq**。这与事件 seq 必须从 `workspace_seq` 计数器分配是两回事，理由要分清：

| 项 | 事件 seq | 快照 seq |
|---|---|---|
| 作用 | 断线续传的游标，必须连续无洞 | 工作区内的快照序号，只用于排序与唯一性 |
| 会不会被搬走 | 会：0002 要求事件表超过 200 MB 时把旧事件段搬进内容寻址存储，库里只留索引，那时表内最大 seq 会低于已发出的最大 seq | 不会：快照保留窗口是基线加 64 个增量，squash 只合并不归档，表内行永远在 |
| 分配来源 | `workspace_seq` 计数器 | 表内 `MAX(seq) + 1` |
| 为什么这样分 | 游标不能从表内推导，搬走旧行后推导会发错号 | 序号没有续传语义，表内推导在单写者加 `BEGIN IMMEDIATE` 下是原子的 |

`MAX(seq) + 1` 的安全性由两条保证：单写者意味着没有并发写入，`BEGIN IMMEDIATE` 意味着事务一开始就拿写锁，读到的最大值在写回之前不会被别人改。06.7 的 squash 会删父快照行，删掉最大 seq 的行后，下一个快照的 seq 会低于被删行的 seq，这不构成错误：seq 是序号不是游标，唯一索引防碰撞，没有任何读路径按 seq 排序快照（窗口查询沿父边走）。

### 2.2 父边与 kind：存储层自动链接，调用方只给清单

快照链是线性的，每个工作区一条链。存储层自动链接：取该工作区 seq 最大的快照作父，没有则父为空、kind 取 `baseline`，否则取 `incremental`。调用方只给清单（条目列表），不给链结构。

这样做的理由有三条。第一，链结构是存储层的不变量，不该由调用方决定：调用方给错父边，链就断了，而断链在表结构层没有约束拦截（`parent_id` 是可空外键，指向任何快照都过）。第二，06.7 的重定基线是独立动词，会改写链（把最老的两个增量合并进基线），本批不碰链改写，只负责按链追加。第三，首个快照是基线这条不变量由存储层保证，不靠调用方记得"第一次要传 baseline"。

### 2.3 快照 id：复用内核的 `CheckpointId`，不新增类型

`snapshots.id` 是 26 字符 ULID。内核已有 `CheckpointId`，帧对检查点是弱引用，检查点编号就是快照行的 id。ADR 0018 的 `CheckpointFacts.reachable` 定义的是"该检查点是否仍在快照保留窗口内"，即检查点等于快照。因此 `snapshots.id` 的类型就是 `CheckpointId`，存储层生成 ULID 后返回 `CheckpointId`，不新增 `SnapshotId`。

不新增类型的理由：内核已有五个 id 类型与一套共享的 `id_type!` 宏，新增一个只为"快照"单设的类型等于把同一套校验复制成两份，而 `CheckpointId` 的语义已经覆盖了"快照行的 id"这个角色。`snapshots.id` 列的格式校验由内核的 `id_type!` 宏提供（26 字符、Crockford base32、首位 0 到 7），与 ULID 生成器完全相容。

### 2.4 条目形状：三种 kind，非法形状不可表示

`snapshot_entries` 的形态 CHECK 已定形（06.2.1.1 补强），写入路径的职责是让 Rust 类型与表结构对齐，让非法形状在编译期或写入路径的第一道校验就被拦住，而不是靠 CHECK 兜底。

条目类型是三种 kind 的枚举：

| kind | 必填列 | 可空列 | 说明 |
|---|---|---|---|
| `file` | `hash`、`size`、`mode`、`content_stored` | `mtime`（仅当 `content_stored = 0` 时必填） | 正文已存的条目 `mtime` 可空；超阈值条目 `mtime` 必填 |
| `dir` | `mode`、`mtime` | `hash`、`size`、`content_stored`（三列必须为空） | 目录有权限位与修改时间，回滚要恢复目录权限时它们有用 |
| `tombstone` | 无 | `hash`、`mode`、`size`、`mtime`、`content_stored`（五列必须为空） | 当时被删除，那里什么都没有 |

写入路径的校验分两步。第一步是 Rust 类型层面的形状校验：`file` 条目必须带 `hash` 与 `size`，`content_stored = 0` 时必须带 `mtime`，`dir` 条目必须带 `mode` 与 `mtime`，`tombstone` 条目五列全空。第二步是 blobs 断言：`content_stored = 1` 的条目其 `hash` 必须在 `blobs` 表里，用 `SELECT EXISTS` 在事务内断言，不存在则返回 `MissingBlob` 错误，整笔回滚。

### 2.5 读路径：读快照元信息与读清单

读路径是 06.7 与 06.8 的公共依赖。06.7 的 squash 要读清单合并，06.8 的回滚对齐要读清单写回。读路径的最小形状是两条：

1. 读快照元信息：给定作用域与快照 id，返回 id、seq、parent、kind、created_at。跨工作区校验：快照的 `workspace_id` 必须等于作用域的工作区，不等则返回 `UnknownSnapshot`。
2. 读清单：给定作用域与快照 id，返回该快照的全部条目，按路径排序。跨工作区校验同上。

读路径不返回游标对象、不做分页、不做流式，那些属于 08.5 的读路径。

## 三、ADR 对快照清单的硬要求

与 06.6 相关的决策分布在四份 ADR 里，逐条对照如下。

| 要求 | 出处 | 06.6 怎么落地 |
|---|---|---|
| 快照是对齐的依据，不是备份：条目记录"当时这个路径是什么"，墓碑记录"当时这里没有东西"，两者缺一不可 | 0006 决策段与 `0002_content.sql` 文件头注释 | 条目类型是三种 kind 的枚举，墓碑是其中一种，不是独立表 |
| `kind` 取 `file`、`dir`、`tombstone` 三值，墓碑是必需项 | 0006 决策段 | 取值域 CHECK 已定形，写入路径只负责把 kind 填对 |
| 超过大小阈值的文件只记录尺寸、修改时间与哈希，不存内容，回滚时警告 | 0006 决策段与 0017 决策段 | 超阈值条目是 `file` 条目，`content_stored = 0`，带 `hash`、`size`、`mtime`，正文不进 blobs |
| 超阈值文件只报告，从不删除、从不覆盖 | 0017 决策段 | 这是 06.8 回滚对齐的职责，06.6 只负责把条目写对，让 06.8 能读到 `content_stored = 0` 并据此只报告 |
| 回收用全局标记-清除加宽限期，不用引用计数 | 0006 决策段 | 06.6 不写回收，但 `unreferenced_since` 列已建，留给 06.9 |
| 快照在工具进程组被回收之后才打 | 0005 决策段 | 这是 09.9 执行器的职责，06.6 只提供存储层入口，不碰进程 |
| 完整请求与响应以内容寻址引用加预览的形式进事件表 | 0018 第六节 | 06.6 不追加事件，快照清单本身是审计记录，事件日志记录工具调用（09.9 的流程） |
| 回滚即对齐：范围内、有内容记录的文件与删除墓碑，不含因超过阈值未记录内容的文件 | 0017 决策段 | 06.6 把条目写对，06.8 的对齐算法据此区分"写回"与"只报告" |

三处需要特别说清的核实结果。

**第一，`snapshots` 表带 `workspace_id` 列，`snapshot_entries` 不带。** `0001_core.sql` 的注释明确"snapshot_entries 同样不带工作区列，按快照 id join 回 snapshots 才能确定归属"。因此读路径的跨工作区校验必须 join `snapshots` 表，不能只看 `snapshot_entries`。

**第二，`parent_id` 是自引用外键，刻意不加级联也不置空。** `0002_content.sql` 的注释明确"合并必须在同一事务里先把子快照重挂到基线、再删父快照。留成无动作外键，忘记重挂会让整笔事务失败"。06.6 不删快照行，只追加，因此父边约束不会触发，但 06.7 的 squash 会触发，本批不碰。

**第三，`content_stored` 不给默认值。** `0002_content.sql` 的注释明确"默认值会让'写墓碑时忘了带标记'落成一行自洽的坏数据"。`file` 条目必须显式给出 0 或 1，`dir` 与墓碑必须留空。写入路径的 Rust 类型必须让"墓碑带 content_stored"不可表示。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **工作区的首个快照是基线，seq 为 1，父边为空。** 在一个空工作区创建快照，断言 `snapshots` 表里多了一行，`kind` 是 `baseline`，`seq` 是 1，`parent_id` 是 NULL。守的是"首个快照是基线"这条不变量。
2. **第二个快照是增量，seq 为 2，父边是第一个快照的 id。** 在已有基线的工作区再创建一个快照，断言 `kind` 是 `incremental`，`seq` 是 2，`parent_id` 是基线的 id。守的是"父边由存储层自动链接"。
3. **快照 seq 从表内最大值加一分配，不是从计数器分配。** 用测试专用连接直接插一条 `seq = 100` 的快照行，再走公开入口创建快照，断言返回的 seq 是 101，而不是 2。守的是分配来源，这是本条验收里唯一能区分正确实现与"从 1 开始数"的断言。
4. **文件条目带 content_stored = 1 时，hash、size、mode 写入，mtime 可空。** 先用 06.5 的 `put` 写一个 blob，再创建快照，断言 `snapshot_entries` 表里多了一行，`kind` 是 `file`，`hash` 等于 blob 的哈希，`size` 等于内容字节数，`mode` 非空，`content_stored` 是 1，`mtime` 是 NULL。守的是"正文已存的条目不需要修改时间"。
5. **文件条目带 content_stored = 0 时，hash、size、mtime 必填。** 创建一个超阈值条目，断言 `hash` 非空、`size` 非空、`mtime` 非空、`content_stored` 是 0。再创建一个缺 `mtime` 的超阈值条目，断言被拒。守的是"超阈值条目必须带修改时间，残留清单靠它判断"。
6. **目录条目写入 mode 与 mtime，hash、size、content_stored 为 NULL。** 创建一个目录条目，断言 `kind` 是 `dir`，`mode` 非空、`mtime` 非空，`hash`、`size`、`content_stored` 三列全 NULL。守的是"目录有权限位与修改时间，没有哈希与尺寸"。
7. **墓碑条目五列全空。** 创建一个墓碑条目，断言 `kind` 是 `tombstone`，`hash`、`mode`、`size`、`mtime`、`content_stored` 五列全 NULL。守的是"当时被删除，那里什么都没有"。
8. **删除的声明路径留下墓碑。** 在快照清单里对一条已被声明的路径写入墓碑条目，断言 `snapshot_entries` 表里该行 `kind` 是 `tombstone`。守的是拆分依据里的验收口径"删除的声明路径留下墓碑"。
9. **content_stored = 1 的条目其哈希必在 blobs 里。** 创建一个 `content_stored = 1` 的条目，但 `hash` 不在 `blobs` 表里（没有先 `put`），断言返回 `MissingBlob` 错误，`snapshots` 表里没有新增行，`snapshot_entries` 表里没有新增行。守的是"由写入路径断言而不加外键"。
10. **同一快照内同一路径不能有两条。** 在一个快照里对同一路径写两条条目，断言第二条被拒。守的是"条目主键是快照加路径"。
11. **读回清单与写入一致。** 创建快照后，用读路径读出全部条目，断言每条的 kind、hash、size、mode、mtime、content_stored 与写入时逐字段相等。守的是"清单落库后能还原"。
12. **跨工作区读快照被拒。** 在工作区 A 创建快照，用工作区 B 的作用域读，断言返回 `UnknownSnapshot`。守的是"快照的 workspace_id 必须等于作用域的工作区"。
13. **空清单允许。** 创建一个没有条目的快照，断言成功，`snapshot_entries` 表里没有新增行。守的是"工具调用没改任何文件时，快照仍然打，只是清单为空"。

第 1、2、3 条合起来守的是同一件事：快照链的 seq 与父边由存储层保证。第 4、5、6、7、8 条合起来守的是条目形状的三种 kind。第 9 条守的是 blobs 断言。第 11、12 条守的是读路径。第 13 条守的是空清单的合法性。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 用计数器分配快照 seq | "首个快照 seq 为 1、第二个为 2"完全成立，但表里没有计数器表，实现者会自己发明一个 | 第四节第 3 条：直接插一条 `seq = 100` 的行，正确实现得到 101，"从 1 开始数"的实现得到 2 |
| 父边恒为空 | 首个快照的断言通过，第二个快照的父边断言才暴露 | 第四节第 2 条：断言 `parent_id` 是基线的 id，不是 NULL |
| kind 恒为 `incremental` | 第二个快照的断言通过，首个快照的 kind 断言才暴露 | 第四节第 1 条：断言首个快照的 `kind` 是 `baseline` |
| blobs 断言在提交之后做 | 正常路径通过，坏行已写入，回滚来不及 | 第四节第 9 条：断言 `snapshots` 与 `snapshot_entries` 都没有新增行，整笔回滚 |
| 超阈值条目缺 `mtime` 不被拒 | 写入不报错，CHECK 兜底但错误消息是 CHECK 而不是友好错误 | 第四节第 5 条：断言缺 `mtime` 的超阈值条目被拒，且错误是写入路径的校验错误而不是 CHECK |
| 墓碑条目带 `mode` 或 `mtime` | 写入不报错，CHECK 兜底但形状不可表示 | 第四节第 7 条：断言墓碑五列全 NULL，Rust 类型让墓碑带 `mode` 不可表示 |
| 跨工作区读快照不校验 | 同工作区读通过，跨工作区读才暴露 | 第四节第 12 条：用 B 的作用域读 A 的快照，断言被拒 |
| 读路径不分页、不做流式 | 正常路径通过，大清单才暴露 | 读路径只返回全量，不做分页与流式，那些属于 08.5 |
| 空清单被当成非法输入 | 正常路径通过，空清单的写入被拒 | 第四节第 13 条：空清单允许，`snapshot_entries` 表里没有新增行 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：`snapshots.kind` 的取值域是 `baseline` 与 `incremental`，由 CHECK 兜底。写入路径的 kind 推导（首个是基线，其余是增量）是存储层的不变量，不靠调用方记得。这条与 06.3 的 `kind` 词表问题同型，不发明完整枚举，留给后续批次统一补。

## 八、已裁决的分歧点

五处分歧点已由主 Agent 裁决，全部采纳 Explorer 的建议（均选甲）：快照 seq 用 `MAX(seq) + 1`（是序号不是游标，不会被归档搬走，单写者加 `BEGIN IMMEDIATE` 下原子）；读路径属于 06.6（是 06.7 与 06.8 的公共依赖，与 06.5 把 `get` 收进本批同型）；快照 id 复用内核 `CheckpointId`（帧对检查点是弱引用，检查点编号就是快照行的 id，不新造 `SnapshotId`）；快照创建不追加事件（清单本身是审计记录，没有事件种类可挂）；父边由存储层自动链接（链结构是存储层不变量，不靠调用方记得"第一次要传 baseline"）。裁决理由见下表"建议"列。

| 分歧 | 两种做法 | 建议（已裁决采纳） |
|---|---|---|
| 快照 seq 的分配方式 | 甲：`MAX(seq) + 1`，无计数器表，无新迁移。乙：新增 `snapshot_seq` 计数器表（迁移 0003），与 `workspace_seq` 同型 | **选甲。** 理由见第二节。快照 seq 是序号不是游标，不会被归档搬走，`MAX(seq) + 1` 在单写者加 `BEGIN IMMEDIATE` 下是原子的。计数器表是为事件 seq 的续传语义准备的，快照没有这个语义 |
| 读路径是否属于 06.6 | 甲：06.6 提供读快照元信息与读清单。乙：06.6 只提供写入，读路径留给 06.7 或 06.8 | **选甲。** 理由见第二节。06.7 的 squash 与 06.8 的回滚对齐都要读清单，读路径是它们的公共依赖。与 06.5 把 `get` 收进本批的裁决同型：读路径是验证写入路径的前提（读回清单断言等于写入清单），也是 0018 第六节"引用必须能还原完整报文"的落地 |
| 快照 id 的类型 | 甲：复用内核的 `CheckpointId`。乙：新增 `SnapshotId` 类型 | **选甲。** 理由见第二节。帧对检查点是弱引用，检查点编号就是快照行的 id，`CheckpointId` 的语义已经覆盖了"快照行的 id"这个角色。新增 `SnapshotId` 等于把同一套校验复制成两份 |
| 快照创建是否追加事件 | 甲：06.6 不追加事件，快照清单本身是审计记录。乙：06.6 追加一条 `snapshot` 事件 | **选甲。** 理由见第三节。快照清单本身是审计记录，事件日志记录工具调用（09.9 的流程）。06.4 的压缩事件是"压缩调用"这一种类，快照创建不是工具调用，没有事件种类可挂。追加事件会让 `events` 表多一条没有正文的行，而快照的审计信息已经在 `snapshots` 与 `snapshot_entries` 表里 |
| 父边由谁给 | 甲：存储层自动链接，调用方只给清单。乙：调用方给父边与 kind | **选甲。** 理由见第二节。链结构是存储层的不变量，不该由调用方决定。调用方给错父边，链就断了，而断链在表结构层没有约束拦截。首个快照是基线这条不变量由存储层保证，不靠调用方记得"第一次要传 baseline" |

## 十、Explorer 核对与补强（基线 db15ffd）

本节的核对对象是批次基线 db15ffd 的已提交代码，不是实现者的工作树。结论是：十三条验收对基线全部成立，表结构、seq 分配与条目形状的口径都没有被证伪，需要改写的只是"怎么做"与五处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 表结构核对：全部成立

`0002_content.sql` 的 `snapshots` 与 `snapshot_entries` 表与计划第二节所写逐列一致。`snapshots` 的主键是 `id`，`workspace_id` 有外键，`seq` 与 `workspace_id` 组成唯一索引，`parent_id` 是自引用外键，`kind` 有取值域 CHECK，重定基线留痕三列有 CHECK。`snapshot_entries` 的主键是 `(snapshot_id, path)`，`kind` 有取值域 CHECK，形态 CHECK 已定形（06.2.1.1 补强），`content_stored` 不给默认值。`blobs` 表已建，`hash` 是主键，`unreferenced_since` 可空且带 CHECK。

### 10.2 句柄形状核对：`conn_mut` 已就位

`Store` 把 `Connection` 私有持有，`conn()` 与 `conn_mut()` 都是 `pub(crate)`，由 06.3 提供。`conn_mut` 取 `&mut self`，与 `create_workspace` 的形状一致。`configure` 已经设了 `set_transaction_behavior(Immediate)`，所以 `conn_mut` 拿到的事务一开就是 `BEGIN IMMEDIATE`，"seq 分配与快照插入在同一事务内"这条硬约束由现有配置直接提供，不需要额外动作。

### 10.3 内核 id 类型核对：`CheckpointId` 是唯一不重复校验的放法

`crates/ita-kernel/src/context/ids.rs` 用 `id_type!` 宏生成 `NodeId`、`SessionId`、`WorkspaceId`、`CheckpointId`、`EventId` 五个名义类型，共享同一套校验（26 字符、Crockford base32、首位只能取 0 到 7）。`CheckpointId` 的语义是"一次检查点：上下文位置与文件快照的组合标识"，帧对检查点是弱引用，检查点编号就是快照行的 id。`snapshots.id` 列的格式校验由 `id_type!` 宏提供，与 ULID 生成器完全相容。06.6 不需要新增 `SnapshotId`，`CheckpointId` 已经覆盖了"快照行的 id"这个角色。

### 10.4 四处补强

**第一，`ulid` crate 已经是 `ita-store` 的声明依赖。** `crates/ita-store/Cargo.toml` 有 `ulid.workspace = true`，工作区依赖在根 `Cargo.toml` 有 `ulid = "1"`。快照 id 的生成不需要新增依赖：`ulid::Ulid::new().to_string()` 产出 26 字符 Crockford base32，首位恰好落在 0 到 7，与内核 `id_type!` 的校验完全相容。

**第二，`snapshots` 表没有计数器表，seq 分配用 `MAX(seq) + 1`。** `0001_core.sql` 的 `workspace_seq` 计数器表只为事件 seq 服务，`snapshots` 表没有对应的计数器表。06.6 不新增迁移，seq 分配在立即事务内用 `SELECT COALESCE(MAX(seq), 0) + 1` 读出，再插入。这条与事件 seq 必须从计数器分配是两回事，理由见第二节。

**第三，`content_stored` 不给默认值，写入路径的 Rust 类型必须让"墓碑带 content_stored"不可表示。** `0002_content.sql` 的注释明确"默认值会让'写墓碑时忘了带标记'落成一行自洽的坏数据"。条目类型是三种 kind 的枚举，`tombstone` 变体没有 `content_stored` 字段，`dir` 变体也没有，只有 `file` 变体有。这样"墓碑带 content_stored"在编译期就不可表示，不靠 CHECK 兜底。

**第四，读路径的跨工作区校验必须 join `snapshots` 表。** `snapshot_entries` 不带 `workspace_id` 列，按快照 id join 回 `snapshots` 才能确定归属。读路径的跨工作区校验是"快照的 `workspace_id` 等于作用域的工作区"，不等则返回 `UnknownSnapshot`。这条不能只看 `snapshot_entries`，因为 `snapshot_entries` 没有 `workspace_id` 列。

### 10.5 一处与 ROADMAP 的计数差异

ROADMAP 的 06.6 行写"快照清单：文件、墓碑与超阈值"，拆分依据的验收口径写"删除的声明路径留下墓碑；超阈值条目带未存内容标记、尺寸与修改时间；目录行写入 mode 与 mtime，文件行写入 mode；content_stored = 1 的条目其哈希必在 blobs 里，由写入路径断言而不加外键"。两处对验收口径的描述一致，没有计数差异。这里只作记录，不改 ROADMAP 表格行。
