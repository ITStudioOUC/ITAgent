# 批次 07.4 能力集快照与变更推送的执行计划

拆分依据给 07.4 的验收是"订阅者先收完整能力集，降级后收带版本号的增量"。核对基线 817f57a 的已提交代码、07.1 的执行计划（detail 28）、07.2 的执行计划（detail 29）、07.3 的执行计划（detail 30）、ADR 0013 与 0014 之后，结论是：**验收口径成立且不需要改，但它依赖的六件事必须写进计划，否则实现者会在细节上做对状态、做错语义。** 六件事分别是：能力集是 unit 就绪状态的投影，落在 `ita-server` 的 `units` 模块，建在 07.1 的 `UnitId` 与 07.3 的 `units` 表与 `Store::read_all_unit_states` 之上（ADR 0013 明确"能力集合的变化推送给已连接的客户端"，能力集是 server 级能力概念，由 unit 状态推导，不是 per-unit 状态）；能力集快照读 `units` 表建，不读内存状态（07.3 已把 unit 状态落库，07.4 消费这个判定建快照）；版本号是单调递增计数器，首次推送是完整能力集（版本 0），每次变更递增一次；推送是进程内 watch 通道，不是 IPC（07.4 在 08.x 之前，真实 socket 推送是 08.2 的事，07.4 的"已连接客户端"是进程内订阅者）；能力集推送与工具目录追加通知是同一套机制（ADR 0013），watch 通道设计成可承载两者，但 07.4 只实现能力集，工具目录追加留到工具系统批次；就绪与降级区分，失败 unit 计入降级（客户端要能展示"模型不可用"而不是笼统错误）。文件规划 `crates/ita-server/src/units/{capability,watch}.rs` 与现状吻合，07.4 零新增依赖、不改 `ita-store`（07.3 已建 `units` 表与 store 操作）。

## 结论

1. 07.4 的原始拆分成立。基线 817f57a 的 `ita-server` 有 `lib.rs` 与 `units` 模块（`mod.rs`、`topology.rs`、`state.rs`、`probe.rs`、`supervisor.rs`），07.3 在其上加 `activation.rs` 与 `plan.rs` 并建 `units` 表，07.4 在其上加 `capability.rs` 与 `watch.rs`。需要改写的是"怎么做"，不是"做什么"。
2. **能力集是 unit 就绪状态的投影，落在 `ita-server`，不进内核。** ADR 0013 的硬边界是"unit 管进程生命周期，工作流管任务语义，两者不共享状态机"，能力集是 server 级能力概念，由 unit 状态推导（07.2 计划 detail 29 第八节明确裁决"`Degraded` 是 server 级能力概念（07.4 的能力集），由 unit 状态推导，不是 per-unit 状态"）。因此能力集类型必须独立于 `ita-workflow` 的节点类型，而内核的职责域是"上下文树的解析、命令文法的分析、租约与权限的策略判定"（`lib.rs` 文档注释），能力集不在其中。07.1 已把 `UnitId` 落在 `ita-server`，07.2 已把 `UnitState`/`Supervisor` 落在同一模块，07.3 已把 `StartupPlan`/`ActivationResult` 落在同一模块，07.4 沿用同一模块，维持不改。
3. **能力集快照读 `units` 表建，不读内存状态。** 07.3 已把 unit 状态落库（`units` 表，`state` 取值域 `ready`/`degraded`/`failed`），并在 `ita-store` 加 `Store::read_all_unit_states` 操作。07.4 的能力集快照由 `read_all_unit_states` 读出的 unit 状态投影而来：`ready` 计入就绪列表，`degraded` 与 `failed` 计入降级列表。能力集读表不读内存，让"server 重启后恢复能力集"成立（与 07.3 激活门读表恢复 unit 状态同型）。
4. **版本号是单调递增计数器，首次推送是完整能力集。** 能力集带版本号，首次推送是完整能力集（版本 0），每次变更递增一次。版本号是进程内计数器，不落库（07.4 不新增迁移），server 重启后版本归零但首次推送仍是完整能力集，不影响语义。"带版本号的增量"指变更后的推送带递增的版本号，承载完整能力集，客户端按版本号跟踪自己在哪个版本。
5. **推送是进程内 watch 通道，不是 IPC。** 07.4 在 08.x 之前，真实 socket 推送是 08.2 的事。07.4 的"已连接客户端"是进程内订阅者（回调），watch 通道是进程内的。08.x 会把这条通道接到真实 socket。因此 07.4 不引入 tokio、不建 socket、不碰网络，watch 是同步的进程内通知。
6. **能力集推送与工具目录追加通知是同一套机制。** ADR 0013 明确"能力集合的推送与工具目录的追加通知是同一套机制"。07.4 的 watch 通道设计成可承载两者（能力集变更与工具目录追加），但 07.4 只实现能力集，工具目录追加留到工具系统批次。watch 通道的抽象让"同一套机制"成立，不靠调用方记得"能力集与目录追加走同一条通道"。

## 一、拆分是否仍然成立

核对覆盖了三处：拆分依据里的文件规划、07.3 的执行计划（detail 30）产出的类型与 `units` 表、以及基线 817f57a 的 `ita-server` 现状。

| 拆分里的说法 | 现状 | 判断 |

| 依赖"07.3" | 07.3 产出 `units` 表与 `Store::read_all_unit_states`（detail 30） | 成立，07.4 消费这些 |

被证伪的是拆分之外的一件事：拆分没有提到能力集版本号落不落库、推送走 IPC 还是进程内通道。本批裁决：版本号是进程内计数器不落库（07.4 不新增迁移），推送是进程内 watch 通道（08.x 接 socket），见第二节第 2.4、2.5 条与第八节。

## 二、能力集快照与变更推送的实际形状

### 2.1 能力集是 unit 就绪状态的投影

`CapabilitySet` 是能力集快照类型，三个字段：`version: u64`（版本号，单调递增）、`ready: Vec<UnitId>`（就绪 unit 列表，按标签排序）、`degraded: Vec<UnitId>`（降级 unit 列表，按标签排序）。能力集是 unit 状态的投影：`ready` 状态的 unit 计入 `ready` 列表，`degraded` 与 `failed` 状态的 unit 计入 `degraded` 列表。`failed` 计入降级，因为客户端要能展示"模型不可用"而不是笼统错误（ADR 0013 后果段"降级状态需要整条链路理解：客户端要能展示'模型不可用'而不是报一个笼统的错误"）。

投影函数 `build_capability_set(records: &[UnitStateRecord], version: u64) -> CapabilitySet` 是纯函数：输入是 unit 状态记录（unit id 加状态字符串）与版本号，输出是能力集。记录按状态投影，`ready` 进 `ready` 列表，`degraded` 与 `failed` 进 `degraded` 列表，两个列表都按 `UnitId` 标签排序保证稳定。

### 2.2 能力集快照读 `units` 表建，不读内存状态

07.3 已把 unit 状态落库（`units` 表，`state` 取值域 `ready`/`degraded`/`failed`），并在 `ita-store` 加 `Store::read_all_unit_states` 操作。07.4 的能力集快照由 `read_all_unit_states` 读出的 unit 状态投影而来。能力集读表不读内存，让"server 重启后恢复能力集"成立（与 07.3 激活门读表恢复 unit 状态同型）。watch 通道持有 `Store` 句柄，在变更时调 `read_all_unit_states` 读表重建能力集。

### 2.3 版本号是单调递增计数器，首次推送是完整能力集

版本号是进程内计数器，首次推送是完整能力集（版本 0），每次变更递增一次。版本号不落库（07.4 不新增迁移），server 重启后版本归零但首次推送仍是完整能力集，不影响语义。"带版本号的增量"指变更后的推送带递增的版本号，承载完整能力集，客户端按版本号跟踪自己在哪个版本。版本号单调递增，不回退、不重复。

### 2.4 推送是进程内 watch 通道，不是 IPC

07.4 在 08.x 之前，真实 socket 推送是 08.2 的事。07.4 的"已连接客户端"是进程内订阅者（回调），watch 通道是进程内的。`CapabilityWatcher` 持有 `Store` 句柄、当前能力集、版本号与订阅者列表。`subscribe(callback)` 注册订阅者并立即推送当前完整能力集（版本 0）。`notify_change()` 读 `units` 表重建能力集、递增版本号、向全部订阅者推送带版本号的完整能力集。watch 是同步的进程内通知，不引入 tokio、不建 socket、不碰网络。08.x 会把这条通道接到真实 socket。

### 2.5 能力集推送与工具目录追加通知是同一套机制

ADR 0013 明确"能力集合的推送与工具目录的追加通知是同一套机制"。07.4 的 watch 通道设计成可承载两者（能力集变更与工具目录追加），但 07.4 只实现能力集，工具目录追加留到工具系统批次。watch 通道的抽象让"同一套机制"成立：通道是通用的"能力变更推送"，能力集变更是其中一种消息。07.4 不实现工具目录追加本身，只保证通道可承载。

### 2.6 就绪与降级区分，失败 unit 计入降级

能力集区分 `ready` 与 `degraded` 两个列表，不混用。`ready` 状态的 unit 在 `ready` 列表，`degraded` 与 `failed` 状态的 unit 在 `degraded` 列表。客户端按能力集展示"哪些功能可用、哪些降级"，而不是笼统错误。这是 ADR 0013 后果段"降级状态需要整条链路理解"的落地。

## 三、ADR 对能力集快照与变更推送的硬要求

与 07.4 相关的决策分布在 ADR 0013、0014 与 ROADMAP 07 行，逐条对照如下。

| 要求 | 出处 | 07.4 怎么落地 |
|---|---|---|
| 能力集合的变化推送给已连接的客户端 | 0013 决策段 | watch 通道向进程内订阅者推送能力集变更，08.x 接真实 socket |
| 能力集合的推送与工具目录的追加通知是同一套机制 | 0013 决策段 | watch 通道设计成可承载能力集变更与工具目录追加，07.4 只实现能力集 |
| 降级状态需要整条链路理解，客户端要能展示"模型不可用" | 0013 后果段 | 能力集区分 `ready` 与 `degraded` 列表，`failed` 计入降级 |
| 非必需 unit 失败只标记降级 | 0013 决策段 | 07.3 激活门把非必需失败标记 `degraded` 落库，07.4 读表投影进 `degraded` 列表 |
| unit 管进程生命周期，工作流管任务语义，两者不共享状态机 | 0013 决策段 | 能力集类型独立于 `ita-workflow` 节点类型，落 `ita-server` 的 `units` 模块 |
| 两套监督语义靠文档与类型分开 | 0013 后果段 | `CapabilitySet`/`CapabilityWatcher` 独立类型，不与工作流节点类型复用 |
| 执行器是独立进程，不是 server 内的 unit | 0014 决策段 | 07.4 的 unit 是 server 内部子系统，不含执行器；能力集只投影 server 内部 unit |
| 能力集快照与变更推送 | ROADMAP 07 行 | `capability.rs`/`watch.rs` 两文件 |
| 订阅者先收完整能力集，降级后收带版本号的增量 | ROADMAP 07 行验收 | watch 首次推送完整能力集（版本 0），变更后推送带递增版本号的完整能力集 |

三处需要特别说清的核实结果。

**第一，`ita-server` 基线有 `units` 模块，07.4 在其上加 `capability.rs` 与 `watch.rs`。** 基线 817f57a 的 `crates/ita-server/src/units/` 有 `mod.rs`（`UnitId`、`DepKind`）、`topology.rs`（`Topology`、`find_cycle`、`startup_order`、`CycleError`）、`state.rs`（`UnitState`、`UnitEvent`、`next`）、`probe.rs`（`ProbeResult`、`ReadinessProbe`）、`supervisor.rs`（`Supervisor`），07.3 加 `activation.rs` 与 `plan.rs`，07.4 在其上加 `capability.rs` 与 `watch.rs`。07.4 不修改 07.1 的 `topology.rs`、07.2 的 `state.rs`/`probe.rs`/`supervisor.rs`、07.3 的 `activation.rs`/`plan.rs`，只消费 `UnitId` 与 `Store::read_all_unit_states`。

**第二，能力集快照读 `units` 表建，不读内存状态。** 07.3 已把 unit 状态落库（`units` 表，`state` 取值域 `ready`/`degraded`/`failed`），并在 `ita-store` 加 `Store::read_all_unit_states` 操作。07.4 的能力集快照由 `read_all_unit_states` 读出的 unit 状态投影而来。能力集读表不读内存，让"server 重启后恢复能力集"成立。

**第三，推送是进程内 watch 通道，不是 IPC。** 07.4 在 08.x 之前，真实 socket 推送是 08.2 的事。07.4 的"已连接客户端"是进程内订阅者（回调），watch 通道是进程内的。08.x 会把这条通道接到真实 socket。因此 07.4 不引入 tokio、不建 socket、不碰网络，watch 是同步的进程内通知。

## 四、改写后的验收标准

每条都能写成一个测试，括号里写明它守的是什么。

1. **能力集是 unit 就绪状态的投影。** 建 `units` 表（07.3 迁移），写入 `store` 为 `ready`、`model` 为 `degraded`、`telemetry` 为 `failed`，调 `read_all_unit_states` 读出全部 unit 状态，调 `build_capability_set` 建能力集，断言 `ready` 列表是 `[store]`、`degraded` 列表是 `[model, telemetry]`（`failed` 计入降级）。守的是"能力集是 unit 就绪状态的投影"。
2. **订阅者先收完整能力集。** 建 `units` 表，写入 `store` 为 `ready`、`model` 为 `degraded`，建 watch 持有 `Store`，调 `subscribe` 注册订阅者，断言订阅者收到的第一条消息是完整能力集（`ready` 是 `[store]`、`degraded` 是 `[model]`、版本 0）。守的是"订阅者先收完整能力集"。
3. **降级后收带版本号的增量。** 接第 2 条，把 `model` 状态从 `degraded` 改成 `ready`（或把 `store` 改成 `degraded`），调 `notify_change`，断言订阅者收到第二条消息，版本号是 1（递增），能力集反映新状态。守的是"降级后收带版本号的增量"。
4. **版本号单调递增。** 接第 2 条，连续调两次 `notify_change`（每次改一个 unit 状态），断言版本号从 0 增到 1 再增到 2，严格递增不回退不重复。守的是"版本号单调递增"。
5. **就绪与降级区分。** 建 `units` 表，写入 `store` 为 `ready`、`model` 为 `degraded`，建能力集，断言 `store` 在 `ready` 列表、`model` 在 `degraded` 列表，不混用（`store` 不在 `degraded` 列表、`model` 不在 `ready` 列表）。守的是"客户端能展示'模型不可用'而不是笼统错误"。
6. **失败 unit 计入降级。** 建 `units` 表，写入 `model` 为 `failed`，建能力集，断言 `model` 在 `degraded` 列表（`failed` 计入降级，不是丢弃）。守的是"失败 unit 计入降级"。
7. **能力集变更推送给已连接客户端。** 建 `units` 表，建 watch，注册两个订阅者，改一个 unit 状态，调 `notify_change`，断言两个订阅者都收到推送。守的是"能力集变更推送给已连接客户端"。
8. **推送与工具目录追加是同一套机制。** 建 watch，断言 watch 通道的抽象可承载能力集变更与工具目录追加两种消息（通道是通用的"能力变更推送"，能力集变更是其中一种消息）。07.4 只实现能力集，工具目录追加留到工具系统批次，但通道设计让"同一套机制"成立。守的是"能力集推送与工具目录追加是同一套机制"。
9. **七 unit 最小拓扑能力集。** 按 ADR 0013 最小拓扑实例化：`store → router → ipc`（必需）、`lease requires tools`（必需）、`model` 孤立（非必需）、`telemetry` 孤立（非必需），写入 `units` 表：必需 unit 为 `ready`、`model` 为 `degraded`、`telemetry` 为 `failed`，建能力集，断言 `ready` 列表是全部必需 unit（`[ipc, lease, router, store, tools]` 按标签排序）、`degraded` 列表是 `[model, telemetry]`。守的是"ADR 0013 最小拓扑的能力集"。
10. **能力集读 `units` 表。** 建 `units` 表，写入 unit 状态，建 watch 持有 `Store`，调 `notify_change`，断言能力集由 `read_all_unit_states` 读表投影而来（不是读内存状态）。改 `units` 表后再次 `notify_change`，断言能力集反映表的新状态。守的是"能力集读 `units` 表建快照"。

第 1、6 条守的是"能力集是 unit 就绪状态的投影"与"失败 unit 计入降级"。第 2 条守的是"订阅者先收完整能力集"。第 3、4 条守的是"降级后收带版本号的增量"与"版本号单调递增"。第 5 条守的是"就绪与降级区分"。第 7 条守的是"能力集变更推送给已连接客户端"。第 8 条守的是"推送与工具目录追加是同一套机制"。第 9 条守的是"ADR 0013 最小拓扑的能力集"。第 10 条守的是"能力集读 `units` 表"。

## 六、实现顺序与每步验证

分三次提交，同一批次共用同一个版本号，版本只在最后一次提交前推进一次。顺序按"能独立验证的先做"排，`capability.rs` 的投影纯函数是最便宜的定形，`watch.rs` 的 watch 通道是核心算法。

| 步骤 | 做什么 | 验证方式 |
|---|---|---|
| 一 | 写 `units/capability.rs`（`CapabilitySet`、`build_capability_set`）与内联测试 | `cargo nextest run -p ita-server -E 'test~capability'`，覆盖第四节第 1、5、6 条（投影、就绪与降级区分、失败计入降级） |
| 二 | 写 `units/watch.rs`（`CapabilityWatcher`、`subscribe`、`notify_change`）与内联测试，更新 `mod.rs` 声明两模块 | `cargo nextest run -p ita-server`，此时测试覆盖第四节全部十条验收 |
| 三 | 补全仓验证与文档 | `bash .w1mer/scripts/verify.sh all`，全仓验证通过 |

测试函数名用英文 snake_case，上方一行 `///` 用中文写这个用例守的行为。这条规则在 06.2.2 里入册，断言消息仍然用中文。

## 七、风险：容易做成测试通过但语义错的地方

| 风险 | 为什么测试会照样通过 | 对策 |
|---|---|---|
| 能力集读内存状态而不是 `units` 表 | 正常路径通过，server 重启或表被外部改后才暴露 | 第四节第 10 条：断言能力集由 `read_all_unit_states` 读表投影而来，改表后 `notify_change` 反映新状态 |
| 首次推送不是完整能力集（只推送变更） | 正常路径通过，订阅者首次连接时才暴露 | 第四节第 2 条：断言 `subscribe` 后立即推送完整能力集（版本 0） |
| 版本号不递增（每次都推版本 0） | 正常路径通过，多次变更时才暴露 | 第四节第 4 条：断言版本号严格递增不回退不重复 |
| 失败 unit 被丢弃而不是计入降级 | 正常路径通过，有 `failed` unit 时才暴露 | 第四节第 6 条：断言 `failed` unit 在 `degraded` 列表 |
| 就绪与降级混用（一个 unit 同时在两个列表） | 正常路径通过，多 unit 时才暴露 | 第四节第 5 条：断言 `ready` 与 `degraded` 列表不相交 |
| 推送走 IPC 而不是进程内通道 | 编译通过，但 07.4 在 08.x 之前没有 socket，引入 tokio 会破坏"零新增依赖" | watch 是进程内同步通知，不引入 tokio、不建 socket、不碰网络 |
| 能力集落内核而不是 `ita-server` | 编译通过，但"两套监督语义靠类型分开"失效 | 能力集落 `ita-server` 的 `units` 模块，不进内核、不与 `ita-workflow` 混用 |
| 版本号落库（新增迁移） | 编译通过，但 07.4 不新增迁移的纪律被破坏 | 版本号是进程内计数器不落库，07.4 不新增迁移 |
| 工具目录追加混进 07.4 | 编译通过，但"这一批只有一个目的"失效 | 07.4 只实现能力集，工具目录追加留到工具系统批次，watch 通道只保证可承载 |

还有一条不属于"测试通过但语义错"，但会直接影响可复审性的：能力集快照读 `units` 表建，不读内存状态。07.3 已把 unit 状态落库，07.4 消费这个判定建快照。若把能力集做成读内存状态，会让"server 重启后恢复能力集"失效，且"能力集是 unit 就绪状态的投影"这条验收会被"能力集是内存状态的投影"偷换。这条职责分离是"这一批只有一个目的"的前提，不靠调用方记得"能力集读表不读内存"。

## 八、已裁决的分歧点

四处分歧点由 Explorer 直接定形，理由充分。

| 分歧 | 两种做法 | 定形 |
|---|---|---|
| 能力集版本号落不落库 | 甲：进程内计数器不落库（07.4 不新增迁移）。乙：落库（新增迁移加版本列） | **直接定形选甲。** 理由见第二节第 2.3 条。版本号是推送协议的递增标识，不是持久化状态；server 重启后首次推送仍是完整能力集，版本归零不影响语义。落库会让 07.4 新增迁移，破坏"07.4 零新增依赖、不改 `ita-store`"的纪律 |
| 推送走 IPC 还是进程内通道 | 甲：进程内 watch 通道（08.x 接 socket）。乙：直接走 IPC | **直接定形选甲。** 理由见第二节第 2.4 条。07.4 在 08.x 之前，没有 socket，引入 tokio 会破坏"零新增依赖"。进程内 watch 通道让 07.4 是纯逻辑加一次读表，08.x 再把通道接到真实 socket |
| "带版本号的增量"是完整能力集还是真 delta | 甲：推送承载完整能力集加递增版本号。乙：推送只承载变更的 unit（真 delta） | **直接定形选甲。** 理由见第二节第 2.3 条。完整能力集加版本号让客户端按版本号跟踪自己在哪个版本，不需要本地应用 delta；真 delta 让客户端要维护本地状态并应用变更，复杂度高且 07.4 是进程内通知，完整能力集足够。"增量"指版本号递增，不是只推变更 |
| 工具目录追加是否混进 07.4 | 甲：07.4 只实现能力集，工具目录追加留到工具系统批次。乙：07.4 同时实现能力集与工具目录追加 | **直接定形选甲。** 理由见第二节第 2.5 条。ADR 0013 说"同一套机制"是指 watch 通道可承载两者，不是 07.4 要同时实现两者。07.4 只实现能力集，watch 通道设计成可承载工具目录追加，但工具目录追加本身留到工具系统批次 |

## 九、本批不做的事

为了让复审能用"这一批只有一个目的"来判断，以下几项明确不属于 07.4：真实 unit 实现（`store`、`router`、`ipc` 等，后续批次）；真实的每 unit 就绪探针实现（检查迁移、套接字、路由表，留到真实 unit 存在时）；工具目录追加本身（工具系统批次，07.4 只保证 watch 通道可承载）；本地 socket 与连接级工作区绑定（08.2）；权威与遥测分流（08.3）；group commit（08.4）；批量读（08.5）；执行器进程（0014，独立进程，不是 unit）；工作流节点类型（`ita-workflow`，与 unit 类型分开）；事件日志与模型代理（08.x）；异步执行（07.4 是同步进程内通知，不引入 tokio）；版本号落库（进程内计数器，不新增迁移）。

## 十、Explorer 核对与补强（基线 817f57a）

本节的核对对象是批次基线 817f57a 的已提交代码，不是实现者的工作树。结论是：十条验收对基线全部成立，能力集快照与变更推送的口径都没有被证伪，需要改写的只是"怎么做"与三处待裁决项的定形。下面逐条记录核对结果与四处补强。

### 10.1 `ita-server` 现状核对：`units` 模块有五个文件，07.4 加两个

基线 817f57a 的 `crates/ita-server/src/units/` 有 `mod.rs`（`UnitId`、`DepKind`）、`topology.rs`（`Topology`、`find_cycle`、`startup_order`、`CycleError`）、`state.rs`（`UnitState`、`UnitEvent`、`next`）、`probe.rs`（`ProbeResult`、`ReadinessProbe`）、`supervisor.rs`（`Supervisor`），07.3 加 `activation.rs` 与 `plan.rs`，07.4 在其上加 `capability.rs` 与 `watch.rs`。07.4 不修改 07.1 的 `topology.rs`、07.2 的 `state.rs`/`probe.rs`/`supervisor.rs`、07.3 的 `activation.rs`/`plan.rs`，只消费 `UnitId` 与 `Store::read_all_unit_states`。

### 10.2 `units` 表核对：07.3 建表，07.4 读表

基线 817f57a 的迁移文件（`0001_core.sql`、`0002_content.sql`）没有 `units` 表。07.3 新增 `0003_units.sql` 迁移建 `units` 表（`id TEXT PRIMARY KEY`、`state TEXT NOT NULL`、`updated_at INTEGER NOT NULL`），并在 `ita-store` 加 `set_unit_state`/`read_unit_state`/`read_all_unit_states` 操作。07.4 读 `units` 表建能力集快照，消费 `Store::read_all_unit_states`，不新增迁移、不改 `ita-store`。

### 10.3 07.3 产出类型核对：`StartupPlan`/`ActivationResult`/`units` 表

07.3 的执行计划（detail 30）产出 `StartupPlan`（`required`/`optional` 两集合）、`ActivationResult`（`Ready` 带降级列表、`NotReady` 带未就绪列表）、`activate` 纯函数，并建 `units` 表与 `Store::read_all_unit_states` 操作。07.4 的 `CapabilitySet`/`CapabilityWatcher` 与 07.3 的 `StartupPlan`/`ActivationResult` 是同一 `units` 模块下的不同类型，互不混用。07.4 消费 07.3 落库的 unit 状态（`units` 表的 `state` 列），不重新实现激活门。

### 10.4 四处补强

**第一，能力集快照读 `units` 表建，不读内存状态。** 07.3 已把 unit 状态落库，07.4 消费这个判定建快照。能力集读表不读内存，让"server 重启后恢复能力集"成立。这条职责分离是"能力集是 unit 就绪状态的投影"的前提，不靠调用方记得"能力集读表不读内存"。

**第二，版本号是进程内计数器不落库。** 版本号是推送协议的递增标识，不是持久化状态。server 重启后首次推送仍是完整能力集，版本归零不影响语义。落库会让 07.4 新增迁移，破坏"07.4 零新增依赖、不改 `ita-store`"的纪律。

**第三，推送是进程内 watch 通道，不是 IPC。** 07.4 在 08.x 之前，没有 socket。进程内 watch 通道让 07.4 是纯逻辑加一次读表，08.x 再把通道接到真实 socket。引入 tokio 会破坏"零新增依赖"。

**第四，能力集推送与工具目录追加是同一套机制。** ADR 0013 明确"能力集合的推送与工具目录的追加通知是同一套机制"。07.4 的 watch 通道设计成可承载两者，但只实现能力集，工具目录追加留到工具系统批次。通道抽象让"同一套机制"成立，不靠调用方记得"能力集与目录追加走同一条通道"。
